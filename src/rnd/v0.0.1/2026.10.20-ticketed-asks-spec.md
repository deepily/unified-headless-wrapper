# Ticketed asks: cosa-voice asks that outlive one MCP call

**As of:** 2026-10-20 · follows C14/C14b (Jetski cuts every MCP call off at 180 s, and the limit is not configurable), D27 (escalation) and the role table

## Problem

Today `converse`, `ask_yes_no`, `ask_multiple_choice`, `ask_open_ended_batch` and `commons_ask_sync` hold the MCP call open until an answer arrives or `timeout_seconds` expires. Jetski cancels the call at 180 s, and the model sees `context deadline exceeded`. A human who answers at minute four is answering a question nobody is waiting for any more.

## Contract

Every blocking ask keeps its current signature and gains one behavior: **it waits at most `ASK_HOLD_SECONDS` (150), then returns a ticket.**

```python
ASK_HOLD_SECONDS = 150                                          # below Jetski's 180 s cut-off, with margin

def ask_yes_no( question, ..., timeout_seconds=600 ):
    ticket = asks.open( caller, "yes_no", question, deadline=now() + timeout_seconds )
    return asks.wait( ticket, hold=min( ASK_HOLD_SECONDS, timeout_seconds ) )

def ask_wait( ticket ):                                         # new tool, listed wherever an ask is listed
    return asks.wait( ticket, hold=ASK_HOLD_SECONDS )
```

`asks.wait` returns exactly one of:

```json
{ "status": "answered", "ticket": "ask-3f2a9c1e", "answer": "yes", "answered_by": "human" }
{ "status": "answered", "ticket": "ask-3f2a9c1e", "answer": "yes", "answered_by": "surrogate", "confidence": 0.86 }
{ "status": "pending",  "ticket": "ask-3f2a9c1e", "waited_seconds": 150, "deadline_in_seconds": 450 }
{ "status": "expired",  "ticket": "ask-3f2a9c1e", "default": "no" }
```

The tool description tells the model what to do with `pending`: call `ask_wait( ticket )`, or do other work and call it later. An answer that arrives while no `ask_wait` is open is not lost. The ticket holds it, and the supervisor may also deliver it as the persona's next inbound message (framework §6), so a persona that ended its turn still gets it.

## Session state

`awaiting_human` (framework §5.2) now spans polls. It begins at the first ask call and ends when the ticket is answered or expires, regardless of how many `ask_wait` calls happen in between. The supervisor tracks this per ticket, not per tool call.

## Escalation (D27)

| Asker | Route |
|---|---|
| Crew member | Doesn't call ask tools (role table). It DMs its manager, which asks on its behalf |
| Manager | Asks you directly. If the ticket reaches its fallback point unanswered and the manager still needs an answer, the ticket escalates to the chief of staff |
| Chief of staff | Asks you directly. On escalation or its own fallback, it consults the preference learner and may answer as **surrogate** |

**Fallback point:** a per-ask `fallback_after_seconds`, defaulting to the ask's `timeout_seconds`. It's set by the asker, so an urgent ask can fall back sooner.

**Surrogate answers** are always marked: `answered_by: "surrogate"`, with the learner's confidence. They're logged with the ticket, so you can review them later. The surrogate policy is a separate design: which ask types are eligible, the confidence floor below which it keeps waiting for you, and review. In shadow mode today the learner predicts but never answers. This spec only provides the hook where its answer would enter.

## Engine-neutral by construction

Claude Code has no 180 s cut-off, but it gets the same contract. One behavior for all engines means one set of workflow instructions, consistent with D29 and D30.

## Changes

| Where | Change |
|---|---|
| `cosa_voice_mcp.py` | Asks open a ticket and wait at most `ASK_HOLD_SECONDS`; add `ask_wait( ticket )`; `commons_ask_sync` gets the same treatment |
| Lupin API | Ticket store (`/api/asks/{ticket}`): open, answer, wait (long poll), escalate, expire; answers from voice, console and web all land on the ticket |
| Supervisor | `awaiting_human` per ticket; late answers delivered as an inbound message; escalation to the chief of staff at the fallback point |
| Role table | `ask_wait` listed wherever an ask tool is |
| planning-is-prompting | Workflows that rely on a blocking ask learn the `pending` → `ask_wait` loop (cosa-voice-integration, session-start) |

## Open

1. **`ASK_HOLD_SECONDS`:** 150 is a margin under 180, and nothing else forces it. A shorter hold (60 s) makes turns more responsive but means more polls.
2. **Late answers:** should an answer that arrives after the persona ended its turn always become its next inbound message, or only when the persona is idle?
