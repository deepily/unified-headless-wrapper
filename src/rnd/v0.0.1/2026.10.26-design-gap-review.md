## 4. Never discussed (new)

1. **Engine authentication and quota.**
   - How does a headless AGY fleet authenticate (one Google login shared by N processes?) and what are the rate limits per model?
   - The cost baseline (Max 200 plan) has no AGY counterpart.
   - The deferred capture on cross-turn prompt caching still stands.
2. **Context exhaustion on AGY/Jetski.**
   - Does the engine auto-compact, error, or truncate when the window fills?
   - Context pressure from `usage` is designed, but not what happens at the limit, nor the respin trigger.
3. **Engine self-update in a live fleet.**
   - AGY updates itself, and a new version can rename tools (it already did, 1.3 → 1.4).
   - Proposal: at spawn, the kernel compares `--version` with the last vetted version. On change it runs the C2 tool-name smoke check before admitting the persona; on failure it refuses and narrates why.
4. **Host capacity.** How many engine processes fit per VM (memory per AGY process), and the `cc_memory_watch` equivalent keyed on registry pids.
5. **Permission prompts.**
   - With `--dangerously-skip-permissions`, nothing prompts; the gate is the only check.
   - AH4L's voice-forwarded permission flow (`permission_request.py`) has no UHW disposition beyond "Jetski `allow_tool`".
   - Decide whether voice-approved permissions survive at all.
6. **Client changes.**
   - Late-answer rejection ("answered too late") and ticket state shown in web and mobile.
   - The engine/model label on cards.
   - `sender_id` parsing (2.5).
   - None of these is in a spec.
7. **System broadcasts and the DM tutor.**
   - Both deliver by tmux today. They become inbox writes, but the broadcast slicing (`@persona:` directives, `<system-reminder>` wrapper, acks) needs a per-engine wrapper, because `<system-reminder>` is a Claude convention.
8. **The preference learner as surrogate.**
   - D26/D27 and the ticket spec leave a hook. The surrogate policy (eligible ask types, confidence floor, review) is a separate design not yet scheduled.
   - So is the Bayesian-learner improvement.
9. **Claude-coupled components outside the harness** (inventory §17: `swe_team` orchestrator, the expediters, `dispatcher.py`). They need their own migration path or an explicit "stays on the Claude Agent SDK" ruling.
10. **Switch-over data migration.**
    - Bridge files → registry; live tasks and their `accountable_manager`; open DMs and asks in flight; mementos under `~/.claude`.
11. **Credential exposure.**
    - The X-API-Key file is readable by any persona with shell access.
    - Within D25, but worth one gate rule in observe mode (shell commands reaching `:7999`, or reading `src/conf/keys/`).
12. **Claude's MCP timeout** is still unmeasured. The ticket design makes it moot, but the framework flags it as open.
