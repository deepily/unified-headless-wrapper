**Claude:**
Good question, and the answer is: direction is deducible from the envelope, but the study you describe should not depend on the envelope at all. It should come from the per-persona log, which sees both ends of every message. Here is the encoding I'd add:

**In the envelope (what the model reads):** direction is implied by `kind` plus one attribute. `voice` is human→AI. `dm` is AI→AI. `answer` carries `by human` / `by <persona id>` / `by learner`, so it is human→AI, AI→AI, or learner→AI. `kernel` is kernel→AI. Nothing else is needed by the model.

**In the log (what you analyze):** the `inbox.received` event keeps the **raw notification dict verbatim**, so Lupin's own `direction` field (`human_to_ai` / `ai_to_ai`), `sender_id`, `sender_persona`, `thread_id`, `reply_to`, `priority`, timestamps and the notification id all survive, plus the kernel's `kind`, `channel`, and later `inbox.written` with the turn id. The outbound side is already covered by two other events: AI→human speech is the kernel's own notification at the result (spoken characters, abstract, `needs_repair`), and AI→AI outbound is the persona's `dm_send` call, which the gate shim sees with its full arguments and logs.

**For the DM-compression study specifically:** the sender's gate log holds the text as the model wrote it (`dm_send` arguments); the recipient's inbox log holds the text as delivered after Lupin's rewriter. Both carry the same message id, so the before/after pair per message is a join across two persona logs. The one thing that is *not* deducible today is which treatment Lupin applied; the rewriter runs on the Lupin side (D12 as amended), so the notification record needs a treatment stamp (`rewrite: {applied, rule_version, chars_before, chars_after}`), which is a Lupin application change (T27 row), and the kernel copies it through untouched because it keeps the raw dict.
