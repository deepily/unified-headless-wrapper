## 2026-11-05 evening to 2026-11-06 midday · T32, credential exposure → D50

The session opened on the status page's next item, T32, which the register had as one line: add an observe-mode rule for shell commands that reach the Lupin server or read the key directory. Reading lupin's credential code on the laptop clone (`outbound_api_key.py`, `api_key_auth.py`, `task_approval_settings.py`, `hook_credentials.py`, the cosa-voice call sites) changed the item's shape. There were four credentials on a fleet host, not one: the fleet key, which authenticates the account and is shared by every seat ("policy control, not a security boundary", in lupin's own comments); the per-project service login in `~/.lupin/config`; the human owner's login, which the retired notification listener can read from an optional `[owner]` section of the same file to learn the owner's user id; and the engines' vendor credentials. The one that mattered was the third: Lupin checks a human approval by the email on a signed login token, so a persona able to read the owner's password could approve its own destructive-act ticket. Since every persona runs as one operating-system user, the honest framing became: there is no credential boundary between personas; the user account is the boundary, and the threat-model decision accepts that. T32 became four controls: see the bypass, contain secrets at the kernel's writers, keep approvals unforgeable, keep the one credential that would forge them off the host.

The first write-up was a dense, acronym-heavy walkthrough with six numbered questions. Rick rejected it: too much indirection, decisions referred to by register number, no narrative a cold reader could follow. The rewrite became a document for his manager: principles named in words, a credential inventory, seven problem statements, six solutions each with pros, cons and a recommendation, a decisions table, a glossary. Rick liked the form and made it the standing rule for every item, with a markdown copy kept under `narratives/`.

Two of the document's assumptions were wrong, and Rick caught both. "The service account" was underspecified (it is the per-project hook login, `claude.code@lupin.deepily.ai`), and the `[owner]` section, which the document treated as present, is optional: the listener skips silently without it. A small read-only script, `t32_credential_inventory.py`, was written into `src/captures/` and run on the development server: no `[owner]` section, sixteen per-project service logins, none on the approver map. The first run failed on an import path, because a script run by path puts its own directory first on `sys.path`; the script now resolves lupin's `src` from `LUPIN_ROOT` or the working directory. The narrative was corrected to say the forgery path is latent, not live, and the recommendation stood: a startup check is what keeps an empty slot empty.

The rulings were first presented as a six-item list, and Rick rejected that too: a walk-through means one clickable choice at a time, because the whole point of the wrapper is to save operator attention. From then on every decision has gone through the multiple-choice dialog, one per question. All six were adopted as recommended and recorded as D50: the owner's user id in kernel config with a refuse-to-start invariant; human approvals only through the signed-login door and persona approvals only when the kernel witnessed the answer at the gate; the secrets rule split into credential read (block), credential print (log), direct call (log, per instance and role); pattern rules now plus an identifying header on cosa-voice's outbound calls, access-log reconciliation deferred; redaction at the session-log writer and the narration path; T36 opened for per-persona keys, with the bcrypt sweep as its first task.

## 2026-11-06 afternoon · progress estimate, then T37, convention parity → D51, D40 amended

Rick asked how far along the design was, to allocate time to a full spec. Two numbers were given: about 35% of the full register by weighted effort (twelve of twenty-nine design items ruled, the large ones still open), and about 80% of what the first-phase bootstrap candidate needs (two or three sessions: T12, T13, and the C17 capture).

He then raised a doubt about the handoff: when an Antigravity persona takes over implementation, would it follow all of planning-is-prompting, so he could manage the build like any Claude Code project? The baseline said no. The dogfooding decision triggers on the eight kernel tests, which prove plumbing only; the conventions an implementer needs were the second phase's deliverable, so the handoff was scheduled before the thing it depends on. Reading the planning-is-prompting checkout confirmed the October inventory's dependency counts and turned up one telling detail: `workflow/decision-walkthrough.md` already prescribes exactly the one-click ruling format Rick had demanded that morning, the clearest example of what an Antigravity persona would lack.

The T37 narrative laid out four placements for the handoff, a solo-implementer convention kit of about twenty-five workflows, a nine-item acceptance set proving each convention end to end, who builds the port, and whether to keep one workflow set or two. Five rulings, one click each, all as recommended: port the kit first, then a conventions gate between the kernel tests and the handoff; the kit's scope with the rule that a missed convention is added, never improvised around; the nine-item set as the gate; the Phase 1 Claude Code session ports the kit after its last kernel test; one workflow set with engine plumbing behind kernel verbs. Recorded as D51, amending D40.

Closing the day, Rick asked for two process changes. Acceptance labels like "A1 to A8 and B1 to B9" are mile markers without a map; they became `Kernel-1` to `Kernel-8` and `Convention-1` to `Convention-9` across the live documents (the archive keeps the old labels), with the rule that any register key travels with its name. And he asked whether the whole design conversation could be reconstructed for publication; the answer was that a fresh chat sees only the repository and search snippets of past chats, so this chronicle was started, written at session close while the context is still in hand, with the chat transcripts as the lossless record.

## 2026-11-06 evening · T12, the inbox envelope and ledger → D52

The session opened on the status page's first item, T12, which the register had as three fragments: the merged-turn envelope, ledger persistence, and the Claude mid-turn write policy. The narrative was drafted before anything was asked, as the standing rule now requires, and reading lupin's inbox code first changed the item's shape in two ways. First, the current harness frames inbound text four different ways (a `<voice-message>` envelope with a speaking rider, `[Voice]:` lines from the buffer, a `<system-reminder>` block per peer DM with a full `dm_send` reply line, and a bracketed late-answer block), and three of the four repeat standing instructions on every turn; under the kernel, which speaks at the result and renders six instruction layers per spawn, those riders are either obsolete or belong in the contract once. Second, the Phase 1 spec's claim that the server replays missed notifications on reconnect turned out to be false for the kernel's sockets: Lupin's sequence-numbered replay runs only for sessions holding a device slot, and `resolve_device_slot` grants one only to a mobile session with a device id. A `cc-listener-*` session gets nothing. Catch-up has to be a pull, and for human voice there is no pull that works while a browser is open, a gap the current harness already has and nobody had named.

The narrative laid out ten problems and six solutions: a headed-block grammar on every engine (`[kind time attrs]`, four kinds including a `kernel` kind that also closes the question of a per-engine reminder wrapper for later pokes and broadcasts); identifiers in the header and the how-to-answer paragraph in the contract; six merge rules, including a count line at two rather than today's five and a forgery rule that indents a header-like body line instead of truncating the human's words; a small per-persona index file beside the session log, rebuildable from it, in place of today's three hook-side files; the acknowledgement order (write, then ledger, then receipt, so a crash repeats rather than loses); the voice gap closed by a small Lupin change after Phase 1; and the mid-turn rule written as one line reading the capability flag.

Before the first ruling Rick stopped on a question the narrative had not answered: how is direction (human to AI, AI to human, AI to AI) encoded or deducible, because he intends to study treatments such as DM compression by rewriting and must know the effect is captured. The answer was that the envelope implies direction from kind plus one attribute, but analysis should never read the envelope; it reads the per-persona log, where `inbox.received` keeps the raw notification dict verbatim, the kernel's own result notification records what was spoken, and the gate's record of `dm_send` holds the text as the model wrote it. The sender's gate record and the recipient's inbox record share a message id, so before-and-after pairs are a join across two logs. The one thing not deducible today is which treatment Lupin's rewriter applied, so a treatment stamp on the notification record went onto the Lupin application changes item. That subsection was added to the narrative and the first ruling re-asked.

Seven rulings, one click each, all as recommended. On the second, Rick adopted the contract-once design with a caveat he wanted on record: he doubts current models, not trained for a voice-in, voice-out environment, will hold a contract faithfully over a long run of turns, suspects per-turn reinforcement will be needed, and guesses that only a fine-tuned adapter would truly fix it. The design therefore keeps an optional per-persona rider, off by default and logged on every envelope it touches, so that if the contract alone fails the reinforcement can be turned on and measured as a treatment rather than assumed. Recorded as D52. The inbound type, defined differently in the framework and the Phase 1 spec, was unified; the Phase 1 spec's replay claim was struck; the kernel contract in the launch spec gained its inbox paragraph; acceptance Inbox-1 to Inbox-6 were folded into Kernel-1, Kernel-5 and Kernel-7, with Inbox-6 held for the Claude phase.
