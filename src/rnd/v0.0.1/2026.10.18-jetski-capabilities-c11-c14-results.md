Consequences for planning-is-prompting on Jetski (inventory §19.5):
1. **Global mandates** (`global/CLAUDE.md`) deploy to `~/.gemini/AGENTS.md` (or `GEMINI.md`): shared by every Jetski persona.
2. **Per-persona instructions** go in the persona workspace's `AGENTS.md`/`GEMINI.md`. That is Jetski's missing system-prompt flag (framework §5.1).
3. **Skills** install as `.agents/skills/<name>/SKILL.md`, the same `name`/`description` frontmatter Claude uses. Per-project today; global pending C11b.
4. **Roles** (cascade seats, SWE-crew charters) can be agent definitions launched with `--agent`, once the tools field is known.
5. **Slash commands** have no native file route. The engine-neutral option stands: the harness expands `/plan-…` from the command file and sends the text as the turn.

## C12: subagents and plan mode

| Question | Result |
|---|---|
| Subagent tool | **`invoke_subagent`**, arguments `Prompt`, `Role`, `TypeName` |
| Do project hooks fire inside the subagent? | **Yes**: `run_command` and `send_message`, with `parentConversationId` set and `agentName: self` |
| Veto by name | **Works**: one deny, zero child calls, no fallback; the model reported the `deny_reason` verbatim |
| Subagent in the stream | only as a `step_update/subagent` frame; the parent's stream keeps one conversation id. Subagent tool calls are visible through hooks, not the stream |
| `--mode plan` | Turn 1 wrote **only** `implementation_plan.md` to the engine's artifact directory (`~/.gemini/jetski/brain/<conversation>/`) and asked for approval. Turn 2, "approved", created the workspace file and a `walkthrough.md`. Approval works in-band over stream-json |

Consequences:
1. **SWE-crew cardinal rule:** the tool gate denies `invoke_subagent` for crew personas (common-shape rule `subagent{…}`). Subagents that are allowed are still governed, because hooks fire inside them and lineage is in the payload.
2. **`send_message`** is a native subagent-to-parent channel. Crew traffic should stay on cosa-voice DMs, so the gate may want to log it.
3. **Plan mode maps onto the workflows' plan steps:** the plan is a file the harness can read, and approval is a normal user turn. The gate must allow writes to `artifactDirectoryPath` (the brain directory).

## C14: how long one MCP call may block

| Requested | Result |
|---|---|
| 45 s | answered |
| 200 s | `MCP tool call to server "uhw-probe" timed out after 3m0s: context deadline exceeded`; `notifications/cancelled` sent at 180.0 s |
| 620 s | same, 180.0 s |

- **The limit is 180 s per call.** The turn still ends `SUCCESS`, and the model sees the timeout as a tool error.
- **Before the first call to a tool, the model reads its schema file** (`~/.gemini/jetski/mcp/<server>/<tool>.json`). That explains the `read_file` calls seen before the first MCP call in C3.

Consequence for voice asks (framework §5.2, §6), unless C14b shows the limit is configurable:
- A cosa-voice ask long-polls for at most about 150 s, then returns `{status: pending, ticket}`.
- The model calls `ask_wait( ticket )` again, or ends its turn and the harness delivers the answer as the next turn.
- The session stays `awaiting_human` across the polls. This shape is engine-neutral and costs Claude nothing.
