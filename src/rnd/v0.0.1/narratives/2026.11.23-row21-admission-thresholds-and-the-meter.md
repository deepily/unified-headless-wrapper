# What the kernel refuses when an allowance runs low, against the usage meter as it really is (row 21 of "Outstanding actions")

**As of:** 2026-11-23 · written on the test VM under Antigravity, before any ruling · this repository at `aaceb60`, lupin at `e8f253162d` (not read: lupin holds no code that reads the meter) · no register item and no new decision row; what is ruled here is recorded under the decision on engine sign-in and quota (D68 in the glossary).

## In brief

Every engine keeps a usage meter: how much of each allowance the signed-in account has left. The kernel is designed to read that meter every five minutes and to act on it in three ways. It refuses to start a new persona when the allowance is low. It keeps a reserve so that managers can still take turns when workers have used most of it. And it names the allowance in the sentences you read when a persona has to wait.

All three were ruled on 2026-11-11 from the public record of an older engine version. That record described three allowances, each with a five-hour clock and a weekly clock. The meter on the test VM today looks nothing like that: **six allowances, each with a single twenty-hour clock, under names the design does not know.** A script run for this page shows the consequence: the design's reader, given today's meter, understands none of it. Since the design also says "what is unknown never refuses", the kernel as specified would never refuse a spawn for a low allowance and never hold a reserve. It would fail silently, and its tests would still pass, because they are fed the old shape.

Nothing is built yet, so nothing is broken. Seven decisions were asked; after Rick's first reading the seventh was rewritten and two were added (decisions 7 to 9, and "What the public record says about Claude Code's clocks"). The first three make the kernel read whatever the meter reports instead of a shape written into code, so that the next change of shape does not repeat this. The next two set the numbers. The last two settle the words you read, including the "token buffet" names owed since 2026-11-22.

## Where the record stands

### What was ruled on 2026-11-11

From the sign-in and quota spec (`specs/2026.11.11-t22-engine-sign-in-and-quota-spec.md`, Sections 5, 6, 11 and 14) and its decision row:

- The kernel reads the engine's own meter every 300 seconds (`agy -p "/usage" --output-format json`, zero tokens). A reading that is missing, unreadable or older than 900 seconds is "unknown", and unknown admits.
- A group of models that shares one allowance is a **pool**. The spec names three: `gemini`, `third_party` ("Claude and GPT models") and `argon`. It finds a model's pool from the start of the model's identifier: anything that does not begin with `gemini` is `third_party`.
- Each pool has two clocks, five-hour and weekly. **A spawn is refused when the pool has under 15% of its five-hour allowance or under 5% of its weekly allowance.** A wake of a sleeping persona is never refused for a low meter.
- **The reserve:** under 25% of the five-hour allowance, only the chief of staff and managers start new turns. It runs in observe mode first (it logs what it would have done and does nothing).
- Separately, a pool is **blocked** when a turn receives an error that states its own reset time. That rule does not read the meter and is not touched by this page.
- The spec said its reader was "written to the field names of the public record" and that the hosts would show the real names. That host run (row 9) has not been made.

**What this means for the design.** The kernel will meet at least three shapes: one twenty-hour clock (Antigravity on this host today), one weekly clock (Claude Code on a verified Ultra account), and a five-hour clock beside one or two weekly clocks (Claude Code on Max). Three things follow, taken up as decisions 7, 8 and 9: a sentence that names no clock leaves the reader unable to tell a wait of hours from a wait of days; a time written as a weekday and an hour is ambiguous once the refill is six or more days away; and one floor for every clock, accepted as decision 3, refuses spawns for days when a weekly clock runs low.

## Problems and options

### 1. How the kernel learns which allowances exist

The spec holds a table of three group names in code. None matches. The names have changed at least once between engine versions and may differ between hosts.

- **A. Every group the meter reports is a pool.** No table of names in code. The pool's key in records is the meter's group name in lower case with underscores (`third_party_models`, `gemini_pro_next`). *For:* nothing to update when the engine renames or adds a group; identical code on every host; the key is the name you see when you run `/usage` yourself. *Against:* a renamed group becomes a new pool in the records, so a history that spans the rename has two keys; the records' `pool: third_party` of earlier rulings becomes `third_party_models`.
- **B. Correct the table to today's six names.** *For:* the smallest edit; stable keys of our choosing. *Against:* it is the same design that just failed, and it fails the same way (silently, as "unknown") at the next rename, or on a host whose plan shows other groups.
- **C. A configuration key per group** mapping the meter's name to a pool key. *For:* stable keys without a code change. *Against:* a renamed group still reads as unknown until someone edits the file, and the kernel would be silent meanwhile.

**Recommendation: A.**

### 2. How the kernel learns which allowance a model draws on

The spec guesses from the identifier's first letters, which is already wrong for one family.

- **A. Join the engine's two lists.** `agy models` gives identifier and display name; the meter lists display names under each group. The kernel reads both at start and again whenever it meets a model it has not placed. A model found in no group is "unknown": it admits, and the kernel says so once in its log at warning level. *For:* exact for every model today; zero tokens; no list to maintain. *Against:* it depends on the meter's descriptive sentence ("Models within this group: …") keeping its form; if that changes, every model becomes unknown at once, which is why the warning matters.
- **B. Keep the prefix rule, corrected.** *For:* no dependence on a sentence. *Against:* a guess, to be corrected by hand for each new family.
- **C. A configuration key for each role model** naming its pool. *For:* explicit. *Against:* one more thing to edit when a model changes, and wrong silently when forgotten.
- **D. A, with C as an override** for a model the join cannot place. *For:* a way out if the sentence changes. *Against:* a second mechanism built before the first has ever failed.

**Recommendation: A.**

### 3. Which clocks the floor is checked against

The spec names two clocks and gives each its own floor. The meter has one, with another name.

- **A. Every clock the meter reports for the pool, one floor.** A spawn is refused when any clock of its pool is under the floor. One key, `kernel engine quota spawn floor`, replaces the two. *For:* correct today (one clock), correct where a host still shows two, and correct after the next change; one number to tune. *Against:* where a host does show a short and a long clock, both get the same fraction, which the original ruling chose not to do (15% and 5%).
- **B. One key for each clock name** (`kernel engine quota spawn floor 20h`); a clock with no key has no floor. *For:* keeps a number for each clock. *Against:* a clock the file does not name is silently unguarded, which is today's failure again.
- **C. Rewrite the spec for the twenty-hour clock only.** *For:* simplest to read. *Against:* it writes a shape into the design a second time.
- **D. A, plus an optional key for a named clock** that overrides the one floor. *For:* A's safety with B's precision where wanted. *Against:* more surface than any reading yet justifies.

**Recommendation: A.**

### 4. The floor's number

Under 15% of a five-hour allowance, the spec refuses spawns. The clock is now twenty hours, so a refusal can last much longer, and the same fraction is a larger absolute amount.

- **A. Keep 15%, and re-set it from the first week of the kernel's own meter records,** as the original ruling already provides. *For:* no new number invented without data; one working persona draws about 3 points in a session, so 15% leaves room for the personas already running to finish their turns. *Against:* near the end of a heavy day, new spawns may be refused for hours while one sixth of the allowance sits unused.
- **B. 10%.** *For:* less allowance stranded. *Against:* a number with no more evidence than 15%, and less margin for a fleet whose draw is unmeasured.
- **C. 5%,** the old weekly figure. *For:* the long clock's number for a long clock. *Against:* a handful of personas mid-turn could exhaust it, which blocks every Claude persona on the host until the reset.

**Recommendation: A.**

### 5. The reserve for the chief of staff and managers

The spec keeps 25% of the five-hour allowance for them, in observe mode.

- **A. The same rule on whichever clock of the pool is lowest, 25%, still in observe mode.** The key becomes `kernel engine quota reserve`. *For:* consistent with decision 3; it does nothing but log until you switch it on, so the number costs nothing while the first week's records come in. *Against:* when enforced, a quarter of a twenty-hour allowance is a long time for workers to wait.
- **B. The same, at 15%,** and the spawn floor (decision 4) lowered to match or sit under it. *For:* less waiting once enforced. *Against:* chosen without data; managers get less margin.
- **C. Withdraw the reserve** until a fleet has been measured. *For:* less to build for Kernel-5. *Against:* observe mode is how the fleet gets measured; withdrawing it loses the records that would set the number.

**Recommendation: A.**

### 6. What each allowance is called in a sentence you read

Ruled on 2026-11-22: a pool is "the \<vendor-or-family-name\> token buffet" wherever a person reads it, and this page owes the table of names. The one name on record, "Claude and GPT", described the old group; today's group lists Claude models only.

- **A. A short table, with the meter's own name as the fallback.** The table is configuration (`kernel engine pool name third party models = Claude`). A pool with no entry is called by the meter's group name with a trailing "Models" dropped. Today that gives:

  | The meter's group | Said as |
  |---|---|
  | Third-Party Models | the Claude token buffet |
  | Gemini Pro Next | the Gemini Pro Next token buffet |
  | Gemini Flash Next | the Gemini Flash Next token buffet |
  | Gemini Teamfood Models | the Gemini Teamfood token buffet |
  | Gemini Flash | the Gemini Flash token buffet |
  | Gemini Flash Lite | the Gemini Flash Lite token buffet |

  *For:* the one allowance every default role uses gets a vendor's name, as you asked; a group that appears tomorrow already has a sayable name with no edit; a name is changed in a file, not in code. *Against:* "Claude" is wrong the day the group carries another vendor's model, until the key is edited.
- **B. The meter's name always:** "the Third-Party Models token buffet". *For:* no table at all; it is what `/usage` shows. *Against:* not a vendor or family name, which is what you asked for.
- **C. Keep "Claude and GPT"** for the third-party group. *For:* no change to the sentences ruled on 2026-11-22. *Against:* it names a vendor whose models the group does not list.

**Recommendation: A.**

### 7. The sentence that refuses a spawn (rewritten after Rick's first reading)

Ruled wording, as amended on 2026-11-22: `the Claude and GPT token buffet has 10% of its five-hour allowance left, under the 15% floor; it refills at 15:04`. "Five-hour" is true of no clock on this host, and the time is in a form the later rulings dropped (`3:42 PM Thursday` was ruled for the deferred wake).

As first written, this page recommended naming no clock when a pool has only one. The record on Claude Code changes that. "10% left" on a five-hour clock is a short wait; on a weekly clock it can be most of a week. One fleet will hold personas on engines of both kinds, and a manager who is handed the sentence should not have to work out which from the refill time.

- **A. Always name the clock, in words.** `the Claude token buffet has 10% of its twenty-hour allowance left, under the 15% floor; it refills at 9:08 AM Tuesday`; on a weekly clock, `… has 10% of its weekly allowance left …`. The words come from the meter's own label by a small rule: a label of hours (`5h`, `20h`) is spelled out ("five-hour", "twenty-hour"), `weekly` is said as it is, and a label the rule does not know is said as printed (`its 36h allowance`). When a pool has several clocks, the sentence names the one that is under the floor. *For:* the reader knows at once whether the wait is hours or days, on every engine and plan; nothing breaks on an unknown label. *Against:* a small rule tied to the meter's vocabulary, which decisions 1 to 3 otherwise avoid.
- **B. Never name the clock.** `the Claude token buffet has 10% of its allowance left, under the 15% floor; it refills at 9:08 AM Tuesday`. *For:* true everywhere with no rule at all; the refill time already says how long. *Against:* with two clocks the reader cannot tell which one ran low, and has to do arithmetic on the time.
- **C. Name the clock only when the pool has several** (this page's first recommendation), by the meter's short label. *For:* shortest sentence on this host. *Against:* the sentence changes form from engine to engine; `5h` and `weekly` side by side is the one case it covers, and it covers it tersely.

**Recommendation: A.**

### 8. A refill time that is six or more days away (raised by the research)

Ruled on 2026-11-22 (row 106): a reset time is written `3:42 PM Thursday`. That form assumed resets within a day or two. A weekly clock can refill up to seven days out, and the older engine's exhaustion error on record already stated a reset 148 hours ahead, which is six days and four hours. On a Thursday afternoon, "3:42 PM Thursday" could then mean today or next week.

- **A. Add the date when the time is six or more days away:** `3:42 PM Thursday, December 3`. Nearer than that, the form stands as ruled. It applies to every sentence that states a refill or reset: the refusal of a spawn, the deferred wake, the blocked pool's card. *For:* never ambiguous; the ruled form is unchanged in every case it was ruled for. *Against:* two forms of one time.
- **B. Always add the date.** *For:* one form. *Against:* longer in the common case, and it changes sentences ruled yesterday.
- **C. Leave the form as ruled.** *For:* nothing changes. *Against:* ambiguous in exactly the case where the wait is longest.

**Recommendation: A.**

### 9. Whether one floor for every clock needs an exception now (decision 3, put again because the research touches it)

Decision 3 was accepted as recommended: every clock the meter reports is checked against one floor of 15%. Its stated cost was that a short and a long clock get the same fraction. The research makes that concrete: on a Claude Code account with a weekly clock, spawns would be refused from 15% of the week's allowance until the weekly reset, which can be days.

- **A. Leave decision 3 as ruled, and take the question up when the Claude engine's meter is designed** (row 38, Phase 3). Row 38 gains a line saying so. *For:* no engine with a weekly clock is built before Phase 3; by then the kernel's own records will show what a fleet draws; nothing is added to Kernel-1 on a guess. *Against:* the question is carried, not answered.
- **B. Add the optional key now** (decision 3's option D): `kernel engine quota spawn floor <clock>` overrides the one floor for a clock of that name, and a weekly clock is given 5%, the figure ruled on 2026-11-11. *For:* answered once. *Against:* a key and a number for a clock no engine in Phase 1 reports.

**Recommendation: A.**

Four details of the refusing sentence.** Ruled as recommended: whole hours from 1 to 24 are spelled out and any other label is said as the meter prints it; the percentage left is rounded down, so it never reads as the floor; where several clocks are low the one with the least left is named; where the meter gave no reset time the sentence ends at the floor.

## Glossary

- **Row 21, row 9, row 106, row 121:** rows of the "Outstanding actions" table in `00-status.md`. Row 21 is this page. Row 9 is the engine-account inventory you run on both hosts. Row 106, ruled 2026-11-22, set the wording of a deferred wake and the words "token buffet". Row 121 is the older kernel lines of the sign-in and quota spec, still to be reworded. Row 38 is the Claude engine's own usage meter and error table, deferred to Phase 3.
- **D68:** the decision on engine sign-in and quota for a headless fleet, ruled 2026-11-11 from register item T22; its spec is `specs/2026.11.11-t22-engine-sign-in-and-quota-spec.md`. Parts 4, 5 and 10 are the meter, the admission check and the reserve.
- **D44:** the decision that gives each role a default model.
- **Pool:** a group of models that draws on one allowance in the engine's usage meter. In a sentence a person reads it is a "token buffet"; records, keys and code keep `pool`.
- **Clock (window):** the period over which an allowance is counted and after which it refills.
- **Floor:** the fraction of an allowance under which the kernel refuses to start a new persona.
- **Reserve:** the fraction under which only the chief of staff and managers start new turns.
- **Observe mode:** the rule logs what it would have done and does nothing.
- **Kernel-1, Kernel-2, Kernel-5:** acceptance gates of the Phase 1 build. **Quota-1, Quota-4, Quota-9:** acceptance tests of the sign-in and quota spec.
- **AGY:** Antigravity, the engine on the test VM.
