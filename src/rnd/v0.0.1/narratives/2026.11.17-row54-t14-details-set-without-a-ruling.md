## Problems and options

### 1. The two new log records

The spec names two records. One is written the first time a persona calls a built-in tool the gate does not know, once per tool and engine version: the engine, its version, the tool, the persona. The other is written by the check on a new version: the engine, its version, what was granted, what the model reported, what did not arrive, what arrived unasked, and the verdict.

Two things are unstated. The first record carries the persona's identifier in its own fields, which the envelope already carries, unless the record is written to the kernel's log, where the envelope's field is empty. And "once per tool and version" needs a memory that outlasts a kernel restart, or every restart tells you again.

- **A. Confirm the names and fields, and state both: each record is written to the kernel's log, and the first is remembered on the version's entry in the vetted-versions file** (recommended). For: the fact is about an engine version, not about one persona; the persona's own log still gets the gate's ordinary refusal record; the persona field then names who met the tool first and duplicates nothing; the file is already the kernel's memory per version and is read at every spawn. Against: one more field on that file's entry.
- **B. Confirm as written and leave both to the builder.** For: nothing to amend. Against: the builder decides which log by guessing, and the memory is likely to be the kernel's process, so a restart repeats the notice.
- **C. Write the first record to the persona's log and drop the persona field.** For: no duplicated field. Against: a fleet-wide fact is found only by reading every persona's log; "once per version" no longer matches where it is written.

### 2. How those records name the engine and its version

The check on a new version now writes two records. The one you confirmed on 2026-11-16 says `binary` and `version`. The one in this spec says `engine` and `engine_version`, as the session records, the registry row and the control interface do. A reader joining the two records of one check must know both spellings.

- **A. `engine` and `engine_version` in all three records; the confirmed record is amended to match** (recommended). For: one spelling across the log; it is the older and wider usage (three specifications); "engine" is the word the naming rule prefers; no code is written against either. Against: it changes a detail you confirmed two days ago, by an amendment to that spec.
- **B. `binary` and `version` in the two new records.** For: the two records of the check agree, and the confirmed one is untouched. Against: the gate's record then disagrees with the session records it is read beside; `version` alone is ambiguous in a log that also carries kit and schema versions.
- **C. Leave the mismatch.** For: nothing to amend. Against: it is found again by whoever writes the first query across the two.

### 3. The name of the rule that refuses an unknown tool

`unknown_builtin_tool`, in force from the first day.

- **A. Confirm** (recommended). For: it has the form of every other rule name and says what it matches; it already stands in the framework, the tool-approvals spec and the reference code. Against: none found.
- **B. `unshaped_builtin_tool`.** For: closer to the reason (the gate has no shape for it). Against: "shape" is the kernel's word, not one a reader of a refusal knows; three documents to change.

### 4. The names of the three new shapes

`task{action, task_id}` for every call to the background-task tool; `task_kill{task_id}` beside it when the action is a kill; `shell_input{task_id, command}` beside it when text is sent.

- **A. Confirm** (recommended). For: `shell_input` sits beside `shell` and carries the same field name, `command`, so every command-line rule reads it without a second case; the names stand in the framework's port rules and the tool-approvals spec. Against: `task` is also the crew layer's word for a unit of work in the task store, though no gate shape has that name.
- **B. `background_task`, `background_task_kill`, `shell_input`.** For: cannot be mistaken for a task-store task. Against: longer; three documents and the reference code to change; the task store's calls reach the gate as tool-server calls, never as this shape.

The reference code also emits a placeholder, `builtin`, for every other tool. It stands in for the adapter's existing shapes and is not a name to confirm; it is dropped when the module is built into the kernel.

### 5. An action of the background-task tool the gate does not know

The tool has four actions today. The spec refuses a fifth "under ruling 5's reasoning". It does not say which rule the refusal is logged under, nor whether the first one is recorded and told to you as an unknown tool is. A new action is the same event as a new tool: the engine has grown something the gate cannot judge.

- **A. Refused under the same rule; the first per engine version is recorded and told to you once, the record gaining an `action` field that is empty for a whole tool** (recommended). For: you learn that a version added an action, rather than a persona failing quietly; one rule, one record, one memory. Against: one more field on the record of detail 1.
- **B. Refused under the same rule, the gate's ordinary record only** (the nearest reading of the spec). For: nothing added. Against: nobody is told; the cause is found only by reading a persona's log.
- **C. Refused under a rule of its own.** For: a query can separate the two. Against: a second rule for one event; the `action` field separates them as well.

### 6. The wording of the question put to the model

The ruling is that the check asks the model to name its tools. The spec's wording, "name every tool you have, each in backticks, and nothing else in backticks", exists once, in a comment. The kernel has no value to send, and the comparison depends on the wording: a tool the model mentions as absent, or an argument name in backticks, is read as a tool it has.

- **A. Fix the wording as a constant in the module, as written with one clause added: name only tools you can call, and do not mention any you cannot** (recommended). For: the builder sends exactly what the comparison was written for; the added clause closes the one failure the script showed with a realistic reply; a change of wording becomes a visible change to a constant with a test. Against: whether the model obeys is unmeasured until the first real check at the second kernel gate; a constant is changed with the adapter, not by configuration.
- **B. Fix the wording as a constant exactly as the comment has it.** For: nothing invented. Against: leaves the "I do not have" reply to be read as a tool.
- **C. Leave the wording to the builder.** For: nothing to write. Against: the comparison's behavior then depends on a sentence no document holds.
- **D. Ask for a structured reply (a list in a fixed form).** For: nothing to mistake. Against: a second parser; the thirteen captured replies show backticks are what the models already write; a malformed list is a new way to fail.

### 7. A tool the model reports that nobody granted

The spec admits the version, records the name, tells you once, and relies on the gate to refuse the tool when a persona first calls it.

- **A. Confirm, with one repair: a name the gate already knows (the tool-server call) is not reported as unasked** (recommended). For: the gate's refusal is the real protection and holds whether or not the model mentioned the tool; refusing the version would stop every persona on it for a tool none may use anyway; the repair removes a false notice at every check, since the check itself uses the tool server. Against: a stray word in backticks still produces one low-priority notice per version (detail 6 reduces it); the repair changes one line of the reference code and adds a test.
- **B. Confirm exactly as written.** For: nothing to change. Against: the acceptance test that expects nothing unasked on the real engine fails whenever the model names the tool-server call.
- **C. Refuse the version.** For: the strictest reading; nothing unknown is ever present. Against: an engine update that adds any tool stops the fleet until the adapter is changed, for a tool the gate already refuses.

### 8. A reply that names no tool at all

The spec refuses the version: an empty or unreadable reply proves nothing about what arrived.

- **A. Confirm** (recommended). For: the alternative is to admit a version of which nothing is known; it is treated as every other failed check is (the spawn is refused, the reason is narrated). Against: one bad reply blocks a version; the script shows a reply in capital letters is also read as empty.
- **B. Ask once more within the same check, then refuse.** For: forgives one bad reply. Against: a second model turn; a rule for this failure alone, when the check has no retry for any other.
- **C. Admit, with every tool recorded as not arrived.** For: the fleet keeps running. Against: personas are then told they have no tools, which is worse than a refusal that names its cause.

### 9. The background-task tool written in a tool list

The engine attaches the tool to every persona whether or not it is listed. The spec refuses it in a list before launch, with the reason "never listed; it arrives with run_command".

- **A. Confirm** (recommended). For: what the kernel wrote stays the list of what it granted; listing it was never measured on either engine, and a refusal before launch needs no measurement. Against: a persona definition written by hand with the tool in it is refused where the engine might have accepted it.
- **B. Tolerate it: accept the name and drop it before writing.** For: forgiving. Against: the kernel silently rewrites a list; it is the one name treated so.
- **C. Tolerate it and write it.** For: the list shows everything the persona has. Against: unmeasured on both engines; a grant column would hold a tool that is not a grant.

### 10. The notebook tool

The tool is gone from both measured engines; the name loads and delivers nothing. The first narrative said its row leaves the role table and offered to put that as a decision. The amendment withdrew the row whole, and the row also carried Claude's notebook tool, which the spec says elsewhere is not decided until the Claude adapter is built.

- **A. Confirm for the two engines measured, and say that Claude's notebook tool is decided with the Claude adapter's table** (recommended). For: matches what was measured; a notebook is a file, edited by the write and edit tools or a command; it keeps the spec's own statement that Claude's table is later work. Against: one sentence added to the role table's amendment.
- **B. Confirm the withdrawal whole, Claude included.** For: one list across three engines. Against: decides a Claude tool no capture examined, against the spec's own "not decided here".
- **C. Adopt Jetski's notebook skill in its place.** For: notebook edits by cell. Against: unexamined; Jetski only; whether a kernel-launched persona would have it is unknown.

### 11. The image tool

It exists on both engines and works when granted. No role has it.

- **A. Confirm: granted to no role; the check before launch refuses it in a list, and the gate refuses a call to it** (recommended). For: no role's work needs it; on AGY it wrote outside the workspace, which no gate rule covers. Against: a persona asked for an image must say it cannot.
- **B. Grant it to the author.** For: documents with figures. Against: writes outside the workspace on AGY; the gate has no shape for it; no stated need.
- **C. Open it as a register item.** For: decided on its merits later. Against: a design item for a need nobody has stated.
