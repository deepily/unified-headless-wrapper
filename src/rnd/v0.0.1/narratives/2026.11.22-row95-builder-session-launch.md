# How the builder's session is launched (row 95 of "Outstanding actions")

**As of:** 2026-11-22 · Not a register item; no decision row. Ruled 2026-11-22: six decisions (four as recommended, the launch line against the recommendation, the persona's name changed by Rick) and one finding while recording. The body below is as written before the rulings; the table and the section after it say what was ruled. Recorded under the decision on where Phase 1 is built (D45 in the glossary), as an amendment to the exit-criteria and switch-over spec, where the earlier rulings about the builder are recorded.

## In brief

The Phase 1 builder is a Claude Code session that will write the first phase of the Lupin kernel on the test VM, in its own copy of this repository. It runs under the harness Lupin uses today (the ad hoc harness for Lupin, AH4L): Claude Code inside a tmux session, with eight hooks and one tool server that give it a voice, an inbox and the task store. Everything else about the builder is ruled: its folder, its instructions, its list of work, how it reports. What nobody has written down is how the session is started, and three questions were added to this row since: do the task store's tools reach it, under which persona name does it file and claim its work, and who is its manager.

A zero-token script read the host. It found that the launch itself is one line with lupin's own launcher, and that the voice and the task store's tools arrive together with no further setup. It also found four things that will stop or spoil the first launch if nothing is done:

1. **The builder's folder has no Lupin account.** Lupin names a session's project after its folder. The builder's folder was given a different name from planning's on purpose (ruled 2026-11-17), so its project is `unified-headless-wrapper-builder`, and no account or credentials exist under that name. Without them the voice server starts degraded and sends an urgent error on every connection.
2. **The persona name is drawn at random at every launch** from a pool of fourteen, unless a name is declared. The task store ties every row to a persona's name, so a name that changes between sessions orphans the builder's rows.
3. **The launcher does not carry one variable the hooks need.** The hooks run under an interpreter named by `LUPIN_CC_VENV`; without it they fall back to an interpreter that cannot import them on this host. The variable reaches the session only if the shell that starts tmux has it.
4. **The launcher's own dry run is not free of effects**: it starts a throwaway tmux session, and with it a tmux server if none is running. None is running now.

Six decisions are requested. The first two settle the launch line and the account; the next three the persona, its manager and the project named on its rows; the last, the model and permissions.

## Problems and options

### 1. The launch line

The session must start in the builder's clone's root, inside tmux (the harness wakes an idle session by sending keystrokes to its tmux pane, which is how a spoken message reaches it), with the hooks' interpreter in reach.

- **A. Lupin's launcher, a fixed session name, the folder by flag (recommended).** From an interactive shell on the test VM: `cctmx uhw-builder --work-dir /mnt/lupin-data/unified-headless-wrapper-builder`; a later session resumes with the same line plus `--continue`, or reattaches if the tmux session is still alive. *For:* the path every other session on this host takes; a name that says what the session is, in tmux and in the memory slice; the folder cannot be got wrong by standing in the wrong place. *Against:* depends on the shell carrying `LUPIN_CC_VENV` (the runbook's line checks it first).
- **B. The same, without a name or a flag:** `cd` into the clone, then `cctmx`. *For:* what was done for the two past sessions. *Against:* a hashed session name; started from the wrong folder it becomes a planning session with the builder's job.
- **C. Bare `claude` in the clone, no tmux.** *For:* nothing to learn. *Against:* the hooks still run, but an idle session cannot be woken, so the build is not "driven by voice"; no memory ceiling.
- **D. Headless, with the brief as a prompt.** *For:* nobody need attach. *Against:* the builder stops for Rick's word nine times; a session he cannot see is the wrong shape for that.

### 2. The account for the builder's folder

The folder's name is its project, and that project has no account on the instance that carries the voice.

- **A. Give the project its own account (recommended).** Rick creates the user `claude.code@unified-headless-wrapper-builder.deepily.ai` in the admin page of the instance on port 7999 and adds a section of that name to `~/.lupin/config`: the two steps the voice server's own error message asks for. *For:* completes what row 87 chose, the builder apart from planning in every list Lupin keeps; nothing in lupin changes. *Against:* a chore of Rick's, on a credentials file planning does not touch.
- **B. A section of the new name that holds planning's account.** *For:* no admin step. *Against:* two folders speak as one user while naming two projects; whether the server's check accepts an email that does not match the project was not tried.
- **C. Make the folder resolve to planning's project** (a git worktree in place of the clone, or an alias in lupin). *For:* no new account. *Against:* reopens two rulings of row 87 and their fourteen checks, or needs a change to lupin, which is written only on the development server; planning's and the builder's sessions share one project again.

### 3. The builder's persona name

The store's rows carry a persona's name as owner. A name drawn afresh at each launch leaves yesterday's rows with someone who is no longer there.

- **A. One fixed name, declared in the roster for the builder's project (recommended).** One line in `~/.claude/fleet-roster.env`. *For:* the same name at every launch, by the harness's own mechanism; the declaration also makes that name the project's manager, so the builder may write the store at real priorities (decision 4 says whether that is wanted). *Against:* the two effects cannot be separated; a chore of Rick's.
- **B. One fixed name, asked for by the builder in its first act** (the voice server's `request_persona` tool). *For:* fixes the name without making it a manager. *Against:* rests on the builder remembering; a random name is held, and may be spoken, before the request; needs a sentence in the loader.
- **C. Whatever the pool gives.** *For:* nothing to do. *Against:* the orphaned rows above; the importer's manifest must name its owner before the session exists.

Which name is Rick's to say. The recommendation is **Rachel**: the first name in the pool's order that owns no row in this host's store and manages nothing here (Maria owns a row; Mr. Radio is the persona that administers this host from the development server).

### 4. The builder's manager

Lupin's baseline gives every worker a manager who files its rows and chases them. The record names none for the builder, and the import of row 117 needs one name as owner and manager of every seeded row.

- **A. No second session: the builder is its project's declared name, runs the import itself, and Rick is the manager in fact (recommended).** The builder's persona owns the seeded rows; Rick approves the batch and gives his word at each of the nine stops; planning reads the build log at every opening. Whether the rows then name the builder, `rick` or nobody as accountable manager is settled at the import, by what the store accepts. *For:* one session in the clone, as the loader already says; no seat that exists only to chase one worker; the chasing the baseline wants from a manager is what the nine stops already are. *Against:* departs from the baseline's two roles; the store's automatic chase has no separate manager to call.
- **B. A standing manager from this host, Cheech, in a session of its own.** *For:* the baseline as built. *Against:* a second session that no ruling describes, in a folder not yet chosen (the loader makes the builder the only session in its clone); Cheech already manages two other projects here.
- **C. `rick` as owner and manager of every row.** *For:* known today. *Against:* some forty rows to carry; the importer wants an actor with a session.

### 5. The project named on the builder's rows

The manifest's header names a project, and the builder's own queries are scoped by one. The store on this host holds no row for this repository under any name.

- **A. The project the session carries, `unified-headless-wrapper-builder` (recommended).** *For:* the rows are found by the builder's default scope; they stay apart from anything planning ever files; the titles carry `[UHW]` either way. *Against:* a longer name than the repository's.
- **B. `unified-headless-wrapper`.** *For:* the repository's name. *Against:* the builder must override its own project on every call, or it files into one project and reads another.

### 6. Model and permissions

The account-wide settings give every Claude Code session on this host Opus 5.5 with the long context, billed through Vertex, in permission mode `auto`.

- **A. As the host's settings give them; the launch line names neither (recommended).** *For:* one fewer thing to keep in step; the loader's stops and its "asked first" list bind the builder regardless of mode. *Against:* a later change to the host's settings changes the builder silently.
- **B. Name the model and the mode on the launch line.** *For:* the build is pinned. *Against:* a second place that states them, to be corrected whenever the host's default moves.

## Ruled after the walk-through

**The builder is Maria, and decision 3's Rachel is withdrawn.** When decision 4 was put, Rick had already written the roster's line, with another name: `COSA_VOICE_MANAGERS__UNIFIED_HEADLESS_WRAPPER_BUILDER="Maria"`. That line offers Maria first to every session in the builder's folder and makes her the project's manager, so decisions 3 and 4 were put again and ruled as the table shows. Maria owns one row in another project on this host's store; rows are scoped by project.

**Rick did two chores during the session.** The account for `unified-headless-wrapper-builder` and its section in `~/.lupin/config` (decision 2), and the roster's line. The script was run again at 21:07 US Eastern: the section and the roster's key now read `yes`. Its output file holds that second run; the body above describes the first, of 19:04.

**The loader (one click, 2026-11-22).** The loader said the list of work "is seeded there before your first turn"; decision 4 has the builder run that import herself. Ruled as recommended: the sentence now says the list is seeded from the manifest of the cascaded review and "you run that import yourself, on Rick's word, and he approves the batch", and one sentence is added: "Your persona is Maria, the declared manager of the project `unified-headless-wrapper-builder`, which is the project your rows carry; no second session works in this clone until multi-player mode."

**What decision 1 as ruled brings with it.** The launcher takes its first argument as the tmux session's name, so the bare `cctmx` Rick ruled has no place for `--continue`: every launch is a new conversation under a hashed session name, which is what the loader already assumes (it reads the build log "at the start of every session"). A session whose tmux is still alive is rejoined with `tmux attach`.
