# How long Claude lets one tool call run (T33)

**As of:** 2026-11-16 · drafted on the test VM under Antigravity, this repo at `9018577`, lupin at `aabadd221` · ruled 2026-11-16, two for two as recommended; recorded as D72, `specs/2026.11.16-t33-claude-tool-call-timeout-spec.md`

## In brief

The register asks for one measurement: how long Claude Code lets a single call to a tool server run before it cuts the call off. The same question was measured for the other two engines in October (both cut at 180 seconds, and the limit cannot be changed), and that result is why every question a persona asks now waits at most 150 seconds and then hands back a ticket.

The record already answers the question for Claude, so **no capture is needed and the "moot" label is confirmed**:

- The vendor documents the limit. It is a setting, not a fixed cut: about 28 hours when unset.
- Lupin measured, in July, that Claude obeys the setting to the second.
- The kernel's longest held call is 150 seconds, far inside any of this.

One thing remains, and it is a choice, not a measurement: **what value the kernel's Claude adapter gives that setting.** The framework says only "keep it above 150 seconds". Today's harness sets 660 seconds for a reason that the ticketed design has since removed. Two decisions are requested.

The tool-approval spec says the same of approvals: the only held call is the ticket wait, at most 150 seconds (`specs/2026.11.05-t26-tool-approvals-spec.md` line 199).

**What the vendor documents** (read directly on 2026-11-16, `code.claude.com/docs/en/env-vars.md` line 507 and `mcp.md` line 462; zero tokens):

| Limit | Default | Applies to the kernel's tool server? |
|---|---|---|
| `MCP_TOOL_TIMEOUT`, the wall-clock limit on one tool call | 100,000,000 ms, about 28 hours | yes |
| Per-server `timeout` in the server's configuration entry | none; overrides the variable for that server | yes, if set |
| Idle limit (`CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT`): no response and no progress notice | 30 minutes for a server on standard input and output; 5 minutes for a network server; never longer than the wall-clock limit | yes, at 30 minutes |
| Per-request timer | 60 seconds, raised by either setting above | **no**: only network servers have it |

The kernel's tool server is one process per persona on standard input and output (`01-framework.md` lines 151 and 225), so the 60-second timer does not reach it.

**What lupin measured and does today** (lupin at `aabadd221`):

- `src/scripts/start-cc-with-tmux.sh` line 427 sets `MCP_TOOL_TIMEOUT=660000` on every seat the harness starts.
- The comment above it (lines 411 to 426) gives the reason and the proof. A tool call that never returned once held a turn open for 54 minutes 47 seconds. On Claude Code 2.1.199, a tool made to hang for 120 seconds under a 15-second setting was cut "at exactly 15s and the turn recovered".
- 660 seconds was chosen to sit above the old 600-second ceiling on a blocking ask (`src/tests/unit/test_mcp_tool_timeout_spawn_env.py` lines 40, 41 and 105). Ticketed asks retire that ceiling: no call waits past 150 seconds.
- The design note those comments cite (`src/rnd/v0.1.9/2026.07.03-notify-turn-hold-fix-design.md`) is not in the test VM's checkout, so the receipt is read from the script and the test, not from the note.

**What the kernel already has for a stuck call.** The held-turn watch (`specs/2026.11.08-t17-log-schema-and-rotation-spec.md` Section 7) notices a call that has run too long and raises one advisory. It detects; it does not end the call.

**What this session did not verify.** The honor check is from Claude Code 2.1.199; the test VM has 2.1.325 (`claude --version`, read this session). Nothing in the record or the vendor's pages suggests the behavior changed, but it has not been rerun on the newer version.

## Problems and options

### 1. Whether the measurement is still owed

The register says "measure". The vendor states the limit and its default, lupin has shown the setting is obeyed, and the design never holds a call past 150 seconds.

| Option | For | Against |
|---|---|---|
| **A. Close on the record; no capture now.** Replace the capability table's "not yet measured" with the documented figures. One acceptance test runs with the Claude adapter's phase, as every other Claude check does | Costs nothing; the answer is the vendor's own and is backed by a measurement; Claude captures are deferred to the adapter's phase in any case | The check on the current version waits for that phase |
| B. Run a capture now on the test VM | Confirms 2.1.325 today | Spends Claude tokens on a documented figure; the capture script would first have to learn a third engine; the version will have moved again before the adapter is built |
| C. Leave the item open until the Claude adapter's phase | Nothing to write today | The register keeps an item with no question left in it |

**Recommendation: A.**

### 2. What value the Claude adapter sets

Unset, a call that never returns holds a Claude turn until the 30-minute idle limit. The other engines would have cut the same call at 180 seconds. The framework's "above 150 seconds" is a floor with no figure.

| Option | For | Against |
|---|---|---|
| **A. 180 seconds, set by the Claude adapter in the engine's environment at every start.** The same cut as the other engines | One behavior on every engine, which is what the ticketed-asks ruling asks for; a tool too slow for the other engines fails the same way on Claude, so the adapter's acceptance run tests what production will see; a stuck call costs three minutes, then the turn recovers; 30 seconds of margin over the 150-second hold, the same margin the other engines have | Tighter than the harness's 660; any future tool that needs longer must use a ticket, as it already must on the other engines |
| B. 660 seconds, as the harness sets today | Unchanged from what the fleet runs on now | Its reason (a 600-second blocking ask) is gone; a call that works on Claude at 400 seconds would be cut on the other engines, a difference nobody would see until a persona changed engine |
| C. Leave it unset | Nothing to configure | A stuck call holds the turn for 30 minutes; the held-turn watch only advises; this is the incident the harness's setting was written to prevent |

**Recommendation: A.**

## What follows without a decision

- The harness's `MCP_TOOL_TIMEOUT=660000` line dies with `start-cc-with-tmux.sh`, which the switch-over list already deletes; no new row is needed.
