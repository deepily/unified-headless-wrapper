# The builder's clone and the builder's own loader (row 87 of "Outstanding actions")

**As of:** 2026-11-17, written on the test VM under Antigravity, before any ruling · UHW at `32672e0`, lupin at `27e646d0ed` · host facts from `src/captures/t19_builder_clone_check.sh` (zero tokens; output in `src/captures/out/t19-builder-clone-check-lupin-host-test-20261117.txt`)

## In brief

Earlier today two things were ruled in principle (row 85, rulings 5 and 6): on the test VM the planning sessions and the session that builds the Phase 1 kernel work in **separate clones of one branch**, and the builder's clone carries **its own loader** instead of the ruling protocol. A loader is the file an engine reads by itself when a session opens in a folder; today the repo has two, the root `CLAUDE.md` (Claude Code) and the root `AGENTS.md` (Antigravity), and both say that every session follows the ruling protocol.

The mechanism was left open, and it is not trivial: two clones of one branch hold the same tracked files, so the builder's clone receives planning's loaders with every pull. This narrative asks seven decisions: where the clone lives; how planning's loaders are kept out of it; where the builder's loader lives; what it says; how the builder reports what it finished without writing planning's documents; which session conventions it follows; and when it commits and pushes.

Two findings change what was ruled this morning, and both are put as decisions rather than assumed:

- **The ruling's words cannot be met literally in Phase 1.** Ruling 6 gives the builder "the kernel-rendered layers and the convention kit". No kernel exists to render anything until the builder has written it, and the kit is ported only after Kernel-8, by this same builder. What the builder can be given today is a hand-written stand-in for both (decision 4).
- **The builder cannot report through the status page.** The status page says nothing owed is recorded anywhere else, and at least three of its open rows (27, 34, 35) are the builder's to finish; but the status page is under `src/rnd/`, which the builder does not write (D45, Phase 1 code location and write locations). Nothing says how a row the builder finishes gets struck (decision 5).

**What Claude Code offers** (public documentation; the names are present in the 2.1.326 binary, 5, 32 and 14 mentions, but **no behaviour below was tested on this host, because a test spends a turn**). ## Problems and options

### 1. Where the builder's clone lives

The clone must be on the data disk, and the folder's name is not cosmetic: AH4L takes the project's name from it.

- **A. `/mnt/lupin-data/unified-headless-wrapper-builder` (recommended).** Beside the planning checkout and lupin. *For:* `../lupin`, which the runbook's commands use, resolves; the name says what the clone is for; AH4L sees a project distinct from planning's, so the builder's mementos and session entries never mix with a planning session's. *Against:* a long name; D45's words "`unified-headless-wrapper/src/uhw_kernel/`" must be read as the repository, not the folder.
- **B. `/mnt/lupin-data/builder/unified-headless-wrapper`.** *For:* the folder keeps the repository's name, so D45 reads literally. *Against:* AH4L names both clones' sessions `unified-headless-wrapper` and they share one memento mirror; `../lupin` no longer resolves.
- **C. Under the home directory.** *Against:* off the data disk; `../lupin` no longer resolves; nothing gained.

### 2. How planning's loaders are kept out of the builder's clone

Both root files arrive with every pull and both say "every session in this repo follows the ruling protocol".

- **A. Sparse checkout: the builder's clone leaves the two root files out of its tree (recommended).** Two lines of git configuration in that clone. *For:* it does not depend on any engine, so it holds for Claude Code and for Antigravity alike; the trial shows a clean tree, pulls that succeed when planning changes a loader, and builder commits that never touch them. *Against:* the setting lives in the clone's `.git/` and is invisible in a listing unless one looks; a fresh clone made by hand without it gets planning's loaders back. A setup script with a `--check` mode covers both.
- **B. An engine setting: `claudeMdExcludes` in the clone's `.claude/settings.local.json`.** The files stay in the tree. *For:* nothing unusual in git. *Against:* Claude Code only, so an Antigravity session opened there still reads `AGENTS.md`; untested on this host; the builder can read the files it was told to ignore.
- **C. Overwrite the two files in the clone and mark them skip-worktree.** *Against:* the trial's pull fails the first time planning amends a loader, which it has done once since they were written (commits of 11-14 and 11-15 touch them).
- **D. Leave them, and let the builder's loader say it overrides.** Rejected in row 85's narrative: the root loader says "every session", and both texts would stand in the same context.

### 3. Where the builder's loader lives

With the root files absent, something else must be read at launch, by itself. Two questions in one: where the text is kept, and what makes the engine read it.

- **A. The text is a tracked document under `src/rnd/v0.0.1/`, named `03-builder-loader.md`; the clone's root holds an untracked `CLAUDE.local.md` of one line that imports it (recommended).** `CLAUDE.local.md` is already ignored by git and is read at launch. *For:* the text is versioned and reviewed like the protocol beside it; it is under the path the builder does not write, so **the builder cannot edit its own instructions**, and a change to them is a planning ruling; the planning clone has no `CLAUDE.local.md`, so planning never loads it; the import form is the one the root `CLAUDE.md` already uses on this host. *Against:* the one-line file exists only in the clone and must be written by the setup script; that an import works from `CLAUDE.local.md` is documented, not tested here.
- **B. The whole text as an untracked `.claude/CLAUDE.md` in the clone.** *For:* no import. *Against:* unversioned, unreviewed, lost with the clone, and the builder can rewrite it.
- **C. A tracked `src/uhw_kernel/CLAUDE.md`.** *For:* beside the code. *Against:* a subfolder's file is read only once the session touches a file there, so the opening turn runs without it; a planning session that reads kernel code would load it; it sits in a package that later moves to lupin.
- **D. A launch flag, `--append-system-prompt-file`.** *Against:* it rests on every launch line being typed right, and how AH4L launches on this host is not established.

### 4. What the builder's loader says

The ruled words, "the kernel-rendered layers and the convention kit", describe a persona under the kernel. Before the kernel exists they need a stand-in.

- **A. A short hand-written stand-in for the layers, about forty lines, drafted below (recommended).** It states the job, the documents to read and their order, where the builder writes and where it never does, D45's constraints, the gates at which it stops, how it reports, and which conventions apply. It restates no design: every rule points at the spec or decision that holds it. It ends at the relocation, after which the session works in lupin under lupin's own `CLAUDE.md`. *For:* the builder is told its job and its limits in one screen; nothing is duplicated that could drift. *Against:* it is written by hand, so it is one more document to keep true; it is what the kernel will later render, done once by a planning session.
- **B. One line: "read the Phase 1 spec, Section 14, item 5, and follow it".** *For:* nothing to maintain. *Against:* the write boundaries, the reporting rule and the commit rule are in four other places or nowhere; the opening turn in the spec predates today's rulings.
- **C. The rules inlined in full (house style, naming, configuration, every constraint).** *Against:* a second copy of rules the protocol and the specs hold; it drifts.

### 5. How the builder reports what it finished and what it owes

The status page is the one list of what is owed, and the builder does not write it.

- **A. The builder keeps a log it owns, `src/uhw_kernel/BUILD.md`; each planning session reads it at its opening and carries it into the status page (recommended).** The ruling protocol's Section 2 gains the step. *For:* disjoint paths hold, so the two writers never meet in one file; the status page stays planning's and stays the one list; the builder's state survives its own context. *Against:* a row the builder finishes stays open on the status page until the next planning session; one more step at every opening.
- **B. The builder strikes its own rows in the status page.** *For:* the page is always current. *Against:* two writers in one file whose rows are single lines of up to several thousand characters, so any two edits to the table collide on rebase; it breaks the disjoint-paths rule ruled twice.
- **C. By voice only.** *Against:* nothing is written, and the record depends on Rick's memory.

### 6. Which session conventions the builder follows before the kit is ported

AH4L's conventions are the planning-is-prompting workflows (session start and end, history file, to-do file, mementos, voice). On this host the global mandates that demand them are a copy from July, and the commands that carry them out are not installed for this repository.

- **A. The global mandates as the host has them, voice included; the build log is the builder's history and to-do; no kit installed in this repository; the project prefix is `[UHW]` (recommended).** *For:* nothing to install; one file instead of three; the full kit arrives through the port, which is this builder's own later job and is proven by its own gate (Convention-1 to Convention-9). *Against:* the July mandates name workflows this repository has no commands for, so the loader must say that the build log stands in for them; the builder works under a stale global file unless Rick refreshes it (a new row, owed to Rick, either way).
- **B. Install the kit's commands into the builder's clone first, and refresh the host's global mandates from the kit.** *For:* the builder follows the same ritual as any lupin session. *Against:* an installation into a repository that tracks `.claude/commands/`, done before the port that exists to do exactly this properly; it adds a history file and a to-do file to the root, outside the builder's write paths.
- **C. Exclude the global mandates as well; the builder's loader is everything.** *Against:* the voice rules are in the global file, and D45 has the build driven by voice.

### 7. When the builder commits and when it pushes

Planning commits and pushes together, on Rick's word. The builder's work is many small steps, and planning needs it only at the build log.

- **A. The builder commits by itself at every green step; it pushes on Rick's word, at each gate and at the end of each session, after `git pull --rebase` (recommended).** *For:* small commits make the history readable and a bad step cheap to drop; nothing leaves the host without Rick's word, as for planning. *Against:* between pushes the work exists on one disk only; planning sees the build log only after a push.
- **B. It commits and pushes by itself.** *For:* planning always sees the current log; nothing is ever only on one disk. *Against:* a push without Rick's word, on the branch planning records on.
- **C. Both on Rick's word.** *Against:* a word per commit, by voice, many times a session; in practice commits would become large.

## What follows without a decision

It is run by this session once the decisions are ruled, and stays as the runbook's top block for the next host.
- **Planning commits, then pulls with rebase, then pushes.** The trial shows a pull refusing while an edit is uncommitted. With a second writer on the branch the ruling protocol's Section 7, step 5 says so, and its Section 2, step 4 pulls at the opening.
- **The ruling protocol's Section 1** gains the clone's line, and the status page's "Code location" row its path.
- **The Phase 1 spec's opening turn** (Section 14, item 5) is amended to the loader's reading order; "read `00-status.md`" stays a reading, never a writing.
