# The rest of the sign-in and quota settings: ten keys with no ruling, and the details set without a click (rows 124 and 125 of "Outstanding actions")

**As of:** 2026-11-23 (fourth session) · written on the test VM under Antigravity, before any ruling; the rulings were entered the same evening · this repository at `f0e4609`, lupin at `89d6a56115` (read for one fact: its settings file holds no kernel key yet) · no register item and no new decision row; what is ruled here is recorded under the decisions on engine sign-in and quota and on host capacity (D68 and D60 in the glossary).

## In brief

The kernel's rules for the engine's sign-in and its usage allowance are driven by a family of settings in lupin's settings file. Four of them (the floor, the reserve, the reserve's mode and its roles) were ruled earlier today: required, bounded, read again when the file changes. **Ten others have never had a ruling** on whether they must be present, what values are legal, or when they are read. The second kernel gate (Kernel-2) is the first to read a real host's settings file, so the gap closes before it.

Reading for this page turned the question from "what bounds" into "which of the ten should exist at all". Four findings:

1. **Two of the ten keys time the same command.** The sign-in check (every 600 seconds) and the meter read (every 300 seconds) both run `agy -p "/usage"`. A meter read that answers has already proved the sign-in.
2. **The file-storage setting governs a variable the engine on this host does not contain.** A script run for this page found the name `GEMINI_FORCE_FILE_STORAGE` absent from the `agy` 1.5.15 binary, and found the sign-in already kept in a file, mode 600, rewritten within the hour by sessions that never set the variable. This is the same kind of finding as the heap setting earlier today.
3. **The warning ahead of a lapse cannot run.** Its key is 0 ("off until the renewal interval is known"), and the interval was to be read from the sign-in file's age. The file is rewritten in ordinary use, so its age says nothing about when the sign-in ends.
4. **The price setting is written as one key holding a table,** a form ruled out on 2026-11-16, when configuration tables were given one key for each number.

So the recommendations below keep five of the ten as required, bounded keys, turn one into a table of optional keys, and withdraw four. Ten decisions are asked on the ten keys (row 124). Eight more confirm, or change, details the amendments of earlier today set without being asked (row 125); seven are recommended as written and one, a refusal's wording that is untrue of Claude Code, is recommended changed. Nothing is built yet, so each is a change to text and reference code only.

## Problems and options

### 1. The sign-in check and the meter read are one command on two clocks (row 124)

Both run `agy -p "/usage"` (zero tokens, about two seconds). A reply with usage figures proves the sign-in; a refused read is how a lapse is seen.

- **A. One read, one key (recommended).** `kernel engine login check seconds` leaves. Every meter read is the sign-in check: a read that fails is retried once after 5 seconds, as now, before the sign-in is declared lapsed. The sign-in is then checked every 300 seconds, not every 600. *For:* one timer, one key, one code path; a lapse is seen sooner; nothing is lost, since the meter read already ran twice as often. *Against:* it changes the words of the decision's part 3 ("the meter is read every ten minutes"); while lapsed, the check that looks for the restored sign-in runs at the meter's pace, which is what one wants.
- **B. Two keys, as written.** *For:* no change to the decision's text. *Against:* two timers for one command; with the values as they stand the slower one never learns anything the faster has not.

### 2. Whether the timing keys must be present (row 124)

`meter seconds`, `meter max age seconds`, `login remind hours` and `quota reopen card min minutes` (and `login check seconds`, if problem 1 keeps it).

- **A. Required (recommended).** A file without one is refused by the missing key's name, at the kernel's start; the values live in the baseline block of lupin's settings file with the nineteen. *For:* the rule every comparable key has; a misspelled key is caught, not run on a default; `sample_max_age` loses its default in code. *Against:* four more lines every settings file must carry.
- **B. Optional, defaults in code.** *For:* nothing to write. *Against:* the silent failure the earlier rulings removed; the worst case is a misspelled `meter max age seconds`, where a wrong default makes the meter "unknown", and unknown admits.

### 3. Their legal values (row 124)

- **A. Whole numbers, each with the one bound its use gives (recommended).** `meter seconds`: at least 60, the read's own time limit, so a read cannot be due while the last is still running. `meter max age seconds`: greater than `meter seconds`; otherwise every reading is stale before the next arrives, the meter is always "unknown", and the floor and the reserve never act, with nothing said. `login remind hours`: at least 1 (the reminder is urgent and spoken; 0 would mean either "never" or "every pass", and neither is wanted). `quota reopen card min minutes`: 0 or more, where 0 is a plain value (every reopening gets its card), not an off switch. No upper bounds. *For:* each bound stops one named failure. *Against:* two keys are checked against each other, as the fleet's size is against its maximum; a very long meter interval is legal.
- **B. Positive whole numbers, no relation between keys.** *For:* simplest to state. *Against:* `meter max age seconds = 60` beside `meter seconds = 300` is accepted and disables every allowance rule silently.
- **C. As A, with upper bounds** (for example the meter read at most hourly). *For:* stops an absurd interval. *Against:* numbers with no measurement behind them; the first week of records is meant to set these.

### 4. The warning ahead of a lapse (row 124)

`kernel engine login warn hours = 0`. The card it would send is still unworded and has a priority but no type (row 121 of the list).

- **A. Withdrawn: the key and the card (recommended).** Both leave the design until a renewal interval has been observed, which this page shows cannot be read from the file's age. The lapse itself is still noticed within one meter read and announced at once. *For:* nothing is built for a feature that cannot run; no 0-means-off key, the form rejected this afternoon; row 121 loses one of its questions. *Against:* if sign-ins prove to lapse on a regular interval, the warning is ruled again then, with the interval in hand.
- **B. Kept, required, a whole number of 0 or more, 0 meaning off.** *For:* ready the day the interval is known. *Against:* a required key whose only legal use today is 0; an unlabelled off switch.
- **C. Kept, optional; absent means off.** *For:* no line needed in the file. *Against:* the one optional single-valued key among twenty-odd required ones; a misspelled key is silently off.

### 5. The overage switch: presence and legal values (row 124)

- **A. Required; `never` or `allow`, read without regard to case or surrounding spaces, as the reserve's mode is (recommended).** Any other word is refused by the key's name. *For:* this key decides whether money can be spent beyond the subscription; a file must say which, in a word the kernel recognizes. *Against:* one more required line.
- **B. Optional; absent means `never`.** *For:* the safe side by default; a misspelled key fails safe. *Against:* a person who typed `allow` under a misspelled key is not told it did not take; the one exception to "required".

### 6. The file-storage setting (row 124)

The key `kernel engine force file storage = true` switches a variable that the decision's part 2 says is set "always", and whose name the engine's binary on this host does not hold.

- **A. The key leaves; the variable is still sent to every engine, unconditionally (recommended).** Nothing in the settings file can turn it off. The start's own proof stands: the kernel reads the meter from inside its unit, with no terminal, and fixes the file's and the directory's modes. The runbook's sign-in command keeps the variable. *For:* the ruling said "always", and a key that can say `false` contradicts it; a variable an engine does not read costs nothing, and one that does read it (another build, another host, Jetski) is covered; what proves the sign-in is readable is the start's meter read, not the variable. *Against:* the launch environment carries a variable that, on this host's `agy`, is known to do nothing.
- **B. Kept, required, `true` or `false`.** *For:* a host can be told to use its keyring. *Against:* no ruling wants that; `false` on a headless host is the failure the variable exists to prevent.
- **C. The variable and the key withdrawn for `agy`, kept for Jetski until Jetski is read,** as the heap setting was ruled this afternoon. *For:* the launch environment claims nothing untrue. *Against:* unlike the heap, this variable is documented for this tool family and harmless when unread; if a later `agy` build reads it again the fleet's sign-in could move to a keyring the service cannot open.

### 7. The price setting's form (row 124)

`kernel engine prices` is written as one key holding a table. It is first read in the Phase 4 shadow week.

- **A. One key for each number, as every other table (recommended):** `kernel engine prices <model> input`, `… output`, `… cache read`, each in dollars for a million tokens, the model's name normalized as in the context-window table. No row is required: a model with no keys is unpriced and shows blank, as ruled. A model with one or two of the three is refused by the missing key's name; a value that is not a number of 0 or more is refused. *For:* the form already ruled for tables; one loader; a half-entered price cannot print a wrong cost. *Against:* three lines for each priced model; ruled now for a reader built in Phase 4.
- **B. One key, parsed,** as the spec has it. *For:* compact. *Against:* a second table grammar beside the one ruled; the form is not even fully stated in the spec.
- **C. Left unruled, with a row on the list for Phase 4.** *For:* nothing reads it before then. *Against:* the spec goes on showing a form that is already ruled out.

### 8. The daily usage job's time (row 124)

- **A. The key leaves; 00:10 in the app's time zone is the job table's default, as for the other four jobs (recommended).** *For:* no job has a settings key for its time; if job times are ever made settings, one ruling covers all five. *Against:* moving the job means a code change.
- **B. Kept, required, `HH:MM` on the 24-hour clock.** *For:* a host can move it. *Against:* the one job with a key; a required line for a job that first runs in Phase 4.

### 9. Which of these are read again while the kernel runs (row 124)

- **A. The overage switch joins the admission's reading; the timing keys keep their start values (recommended).** The spec already has the overage fields written "before every spawn"; so the switch is read where the floor is, at the start and at an admission when the file has changed, and a bad word then refuses a spawn and defers a wake, naming the key, as the other ten keys of that reading do. Rick's change of `never` to `allow` for a deadline then needs no restart. The four timing keys are read at the start only: a change means a restart, and a bad value on disk is met at the next start. *For:* the one key a person changes under time pressure is the one that takes effect live; no timer is re-armed in mid-run, which nothing yet built does. *Against:* two lifetimes inside one family.
- **B. All of them join the admission's reading.** *For:* one lifetime. *Against:* a typing error in a reminder interval would refuse spawns; the meter's timer would have to be re-armed when its interval changes.
- **C. All start-only.** *For:* least to build. *Against:* switching overage on for a deadline means restarting the kernel under the fleet.

### 10. A pool-name key with no value (row 124; raised while reading)

- **A. Refused by the key's name (recommended).** A name key is optional, but one that is present says something: a name of at least one character. Read where the keys of problem 9's start-only group are. *For:* a line left half-typed is caught; no silent fallback. *Against:* a key naming a pool the meter never reports is still accepted, since pools are learned from the meter and may come and go; the sentence then uses the meter's own name, which is at least visible.
- **B. As written: a blank value is passed over.** *For:* no change. *Against:* the only blank value in the family that is accepted in silence.

### 11. The reserve's mode read without regard to case or surrounding spaces (row 125)

- **A. Confirmed as written (recommended).** `Enforce` and ` enforce ` are `enforce`. *For:* the switch to `enforce` is the one edit the spec schedules, and a capital letter should not refuse spawns. *Against:* a second spelling is legal.
- **B. Exact lower case only.** *For:* one spelling. *Against:* refuses an edit whose meaning is plain.

### 12. A role's name read as written; a repeated role not refused (row 125)

- **A. Confirmed as written (recommended).** Role names are identifiers (`chief_of_staff`), compared exactly with the kernel's own list; `manager, manager` is the same list as `manager`. *For:* identifiers are not prose; a repeat changes nothing. *Against:* `Manager` is refused as an unknown role, where the mode beside it forgives case.
- **B. Case forgiven, and a repeat refused.** *For:* the same latitude as the mode; a repeat is likely a typing error. *Against:* role names are compared exactly everywhere else.

### 13. A change on disk in force from the first admission after it (row 125)

- **A. Confirmed as written (recommended).** The file is read again only at an admission (a spawn or a wake), so a fleet that admits nothing keeps the values it has. *For:* it is what ruling 3 of this afternoon says, stated out; no file watcher. *Against:* after switching the mode to `enforce`, nothing changes until something is spawned or woken.
- **B. Also read before each turn's reserve check.** *For:* the switch acts at the next turn. *Against:* a file check on every turn, and a bad key could then stop turns, which ruling 3 forbids.

### 14. `QuotaPolicy` loses its four defaults (row 125)

### 15. Jetski is sent the relaunch variable only when its row carries a heap (row 125)

- **A. Confirmed as written (recommended).** The two variables travel as a pair, as the code of 2026-11-10 had them, until Jetski is read (row 123 of the list). *For:* ruling 8 of this afternoon said "the same treatment"; nothing is decided about Jetski on a guess. *Against:* a Jetski row with no heap gets no relaunch switch either.
- **B. The relaunch variable always sent to Jetski; the heap only when the row carries one.** *For:* the two do different jobs. *Against:* a second ruling about an engine nobody has read.
