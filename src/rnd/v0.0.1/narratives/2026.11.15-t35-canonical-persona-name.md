# One canonical persona name (T35)

**As of:** 2026-11-15 · Read at this repo `e651769` and lupin `aabadd221` (test VM, `/mnt/lupin-data/lupin`); planning-is-prompting is a deployed copy with no HEAD to cite.

## In brief

A persona has a machine identity (eight hex characters, settled earlier) and a name people use: `María`, `Mr. Radio`. The name is written several ways across Lupin, and each mismatch has been a bug: a query for `maría` finding nothing stored under `maria`, a memento filed under `mar-a`.

Lupin has since built one shared normalization rule and moved most callers onto it. What is still open is everything around that rule:

- which form is *the* stored form;
- what happens to a name the rule cannot represent;
- where the display spelling comes from;
- whether the configuration file is itself in the stored form;
- how a person may type a name when addressing a persona;
- who enforces the form at the stores;
- how the kernel takes part without a copy of the rule.

Seven decisions are requested; an eighth was raised after the walk-through by the inventory script and is recorded in the table. None blocks the first four kernel gates; the kernel handles no names until voice allocation arrives.

## Where the record stands

**The rule that exists.** `lupin_mcp/persona_normalization.py` declares itself the single source of truth (lines 1 to 32). Its root, `canonical_persona_key` (lines 37 to 90), decomposes accents, drops the accent marks, lowercases, turns every run of characters outside `a-z0-9` into one space and trims the ends. Four forms derive from it:

| Form | `María` | `Mr. Radio` | Used for |
|---|---|---|---|
| Key (`canonical_persona_key`, line 37) | `maria` | `mr radio` | store writes and queries, comparisons, dictionary keys |
| Match (`normalize_for_match`, line 91) | `maria` | `mrradio` | resolving a typed or spoken reference |
| Slug (`persona_slug`, line 125) | `maria` | `mr-radio` | file names, session names |
| DM topic (`dm_topic_for`, line 200) | `dm-maria` | `dm-mr_radio` | the direct-message topic |

The key is used in 27 non-test files, the DM topic in 7, the slug in 7, the match form in 3.

- `doc_lint/train_builder.py:91` is still a local copy, producing a space-free form for actor names in document lint.

Two additions were made to the shared module: `dm_topic_for`, replacing four identical copies, and `memento_slugs` (lupin commits `d91b4f33c`, `db15dd06c`). One further local comparison exists that the record did not list: `self_respin_core.py:1408` matches roster keys by case only, keeping accents.

**The configuration file is not in key form.** The pool line (`src/conf/lupin-app.ini:2120`) reads `maria, mr radio, Rachel, Tiberius, Rio, Tiffany, Krishna, sam, Clayton, Cheech, maya, pocholo, chloe, john`. **The task store normalizes at the router, not at the store.** The tasks router normalizes a persona value before use (`routers/tasks.py:99`, eight uses). The repository compares the raw value (`task_repository.py:1001` and `1005`, for the owner and the accountable manager), so a caller that reaches the repository another way must remember to normalize.

**What this record already holds.**

- Only the machine identity crosses a kernel interface; the registry holds one name field in key form and the display form is derived at the edge (framework Section 4.1; stable-identity spec Section 7).
- The broadcast door resolves `@name` mentions with an interim function, `normalize_name` (broadcasts spec, Section 9). It is not the same rule: it keeps apostrophes and other punctuation that the key turns into spaces, so `O'Brien` is `o'brien` there and `o brien` in lupin.
- The pool table and the sweep table at the switch-over are keyed on the canonical key (migration spec, Section 4).
- The task store's sweep refusal uses `canonical_persona_key` until this item rules (manager-checks spec, open items).

## Problems and options

### 1. Which form is the stored form

Four derived forms circulate. One must be the form that is stored and compared; the others are computed from it and never stored as identity.

- **A. The key (`mr radio`), as lupin's module already says. (Recommended)**
  - Pros: already the form in 27 files, in the task store and in the configuration keys; readable; every other form derives from it and none derives back from the others (the match form cannot recover the space).
  - Cons: contains a space, so it can never be used directly as a file name or topic; a derivation is always needed there.
- **B. The slug (`mr-radio`).**
  - Pros: safe everywhere without a second form.
  - Cons: two separators are already in use (hyphen in files, underscore in DM topics); every stored row and configuration key would be rewritten.
- **C. The display name, normalized at each comparison.**
  - Pros: nothing is lost.
  - Cons: this is the arrangement that produced the bugs.

### 2. A name the rule cannot represent

`Søren`, `Straße` and `李` normalize to a damaged or empty key, and two different names can normalize to one key.

- **A. Refuse at the door. (Recommended)** A pool entry must be in key form already, must be unique, and must be non-empty; the pool loader refuses the configuration otherwise and names the entry. A persona whose spelling the key cannot carry gets a hand-chosen key (`soren`) and its spelling from the display setting of problem 3.
  - Pros: no silent damage; the rule stays the fourteen lines it is; the human chooses the key once.
  - Cons: one more step when adding such a persona.
- **B. Add a transliteration table** (`ø` to `o`, `ß` to `ss`, `ł` to `l`).
  - Pros: more names normalize cleanly without help.
  - Cons: the table is never complete; changing the rule changes existing keys' meaning; non-Latin scripts still fail.
- **C. Allow Unicode keys.**
  - Pros: every name representable.
  - Cons: topics, file names and the server's topic pattern are ASCII; every derived form would need its own answer.

### 3. Where the display spelling comes from

Today it is a rule plus a two-entry table in code.

- **A. An optional per-persona configuration key, defaulting to the present rule. (Recommended)** `cc session voice persona maria display name = María`; absent, the capitalize-and-honorific rule applies. The code table goes. The loader checks that the display name normalizes to the persona's key, or, where it cannot (problem 2's hand-chosen keys), accepts it as given.
  - Pros: a new accented name is a configuration line, not a release; the overflow persona already has such a key (`voice_persona_helpers.py:214`).
  - Cons: one more key per unusual persona.
- **B. Keep the table in code.**
  - Pros: nothing to change.
  - Cons: a code change per name; invisible to whoever edits the pool.
- **C. Store the display name in the kernel registry beside the key.**
  - Pros: no derivation at the edge.
  - Cons: contradicts the earlier rule of one name field; two fields can disagree.

### 4. The configuration file

Seven pool entries and eight sets of per-persona keys are capitalized, so the pool is not in the stored form.

- **A. Rewrite the file into key form and make the loader refuse anything else. (Recommended)** One edit in lupin (`Rachel` to `rachel` on the pool line and the key names), then the check from problem 2. The loader returns the pool already in key form, so no caller normalizes again.
  - Pros: the file, the loader's contract and the stores agree; the refusal catches the next drift at start, not in production.
  - Cons: an edit to a shared file on the development server; a typo is a refused start (by design).
- **B. Leave the file; normalize on read.**
  - Pros: no edit.
  - Cons: the per-persona key lookup must be normalized too; the file keeps teaching the wrong form.
- **C. Leave both.**
  - Pros: none beyond no work.
  - Cons: the loader's contract stays false.

### 5. How a person may write a name when addressing a persona

Broadcast mentions and typed references arrive as `@Mr. Radio:`, `@mr radio:`, `@mrradio`, `@mr-radio`.

- **A. Key first, then the space-free match form if it names exactly one live persona; otherwise refuse with the roster. (Recommended)** The door's interim function is replaced by lupin's two functions.
  - Pros: forgiving of how people type; never guesses between two personas; one rule shared with the DM router.
  - Cons: `@mrradio` works, which some would call loose.
- **B. Key only.**
  - Pros: strictest.
  - Cons: `@mrradio` and a spoken "mister radio" transcribed without a space are refused.
- **C. Keep the interim function.**
  - Pros: already written and tested.
  - Cons: a second rule, differing on punctuation, which is the problem this item exists to end.

### 6. Who enforces the form at the stores

The task store is correct only because its router normalizes first.

- **A. Normalize at the store's own door, check at the database, and normalize existing rows once at the switch-over. (Recommended)** The repository normalizes the owner, the accountable manager and the sweep's persona key on write and on query; the tables carry a check that the value equals its own key form; one migration normalizes what is already stored.
  - Pros: no caller can forget; a bad row cannot be written; the two new switch-over tables start clean.
  - Cons: a migration and a constraint to write; a constraint failure surfaces as an error where today there is silence.
- **B. Leave it to callers, as now.**
  - Pros: nothing to change.
  - Cons: each new caller is a new chance for the June bug.
- **C. The database check only.**
  - Pros: smallest change that cannot be bypassed.
  - Cons: callers that pass a display name now fail instead of working.

### 7. How the kernel takes part

The kernel registry holds the name in key form, and the kernel build may not import lupin before it moves there.

- **A. The kernel checks and never normalizes. (Recommended)** It accepts a name only if it is already in key form (lowercase letters and digits in words separated by single spaces) and refuses anything else with the control interface's error body. Normalizing stays in lupin, in one module.
  - Pros: no copy of the rule in the kernel, before or after the move; a caller that sends a display name is told at once.
  - Cons: every caller must normalize before calling (they are all lupin code, which has the module).
- **B. Copy the module into the kernel with a parity test.**
  - Pros: the kernel can accept any spelling.
  - Cons: a second copy, which is how the local copies began.
- **C. Wait and import it after the move.**
  - Pros: no copy.
  - Cons: the registry has no rule at all until then.

## What follows without a decision

- The earlier rule stands: only the machine identity crosses a kernel interface, and a name is never a routing argument.
- The two separators stay as they are: hyphen in file and session names, underscore in DM topics. Changing either would split existing mementos or topics.
- `memento_slugs` keeps its second, unnormalized spelling until the files written before the memento fix have aged out.
- `board_sweep.persona_slug` is deleted with its file when the sweep becomes a store query (already ruled under the turn-end policy); `self_respin_core`'s case-only match goes with the re-spin observer. Only `train_builder.py:91` survives the switch-over and is repointed at the match form.
- The stale comment in `respin_wake_check.py` is a lupin correction, routed to the Lupin application changes list.
- A zero-token inventory script, `src/captures/t35_name_seam_inventory.sh`, lists every normalization outside the module and every raw name comparison, so the audit can be rerun on both hosts.
