To learn whether the VM's credential may write to GitHub, the script's first version ran `git push --dry-run` from the deployed tree, twice. The next deploy resets ownership of `.git` and purges compiled files (line 501); the empty folder would remain. The mistake is how the push gate's failure on the VM was found.

## Problems and options

### 1. Where the writable clone pushes

Two hosts will write one branch. They need one place both can push to and pull from.

- **A. GitHub, `github.com/deepily/lupin` (recommended).** *For:* it is how both UHW clones on this host already work; the VM reads it today; no new machinery; it matches "each pulling and rebasing". *Against:* write access is unproved until the first push; the development server pushes to GitHub about daily, so it must push before the VM can see its work, which is a change of habit for this one branch.
- **B. The bundle file, as deploys do.** *For:* already in place. *Against:* it runs one way, development server to VM; the VM's work would have no way back.
- **C. The development server itself as the remote, over ssh.** *For:* always current. *Against:* a new credential from the VM into the development server, which the record has avoided (D50, credential exposure).

### 2. The branch's name

Lupin's working branches are named `wip-v<version>-<date>-<subject>` and are replaced every week or two (v0.2.3 on 11-04, v0.2.4 on 11-17). The dedicated branch outlives several of them: it is cut at the relocation and lives until the switch-over branch is cut.

- **A. `lupin-kernel` (recommended).** *For:* names the package it exists for (`src/lupin_kernel/`); undated, as befits a branch that crosses versions; short enough to say aloud. *Against:* departs from lupin's naming pattern.
- **B. `wip-kernel-<date of the relocation>-single-persona-kernel`.** *For:* looks like lupin's other branches. *Against:* the date is not known today, so the name cannot be written into the loader yet; a tool that picks "the newest `wip-` branch" by name could pick it by accident.
- **C. No separate branch: write on lupin's working branch.** *For:* nothing to keep current. *Against:* contradicts D3; the working branch is deployed to port 7999 daily, so half-built kernel wiring would ship with it.

### 3. What the branch is cut from, and how it is kept current

Lupin's working branch moves by about 58 commits a day. A kernel branch that never takes them in drifts until it cannot be merged.

- **A. Cut from the working branch as GitHub holds it on the day of the relocation; merge the current working branch into it at the start of each working session (recommended).** *For:* drift is paid for a day at a time; a merge keeps the history both hosts share intact. *Against:* merge commits in the history; when lupin's working branch is renamed for a new version, the session must notice and merge the new one.
- **B. Rebase onto the working branch instead of merging.** *For:* a straight history. *Against:* rewrites a branch two hosts share, which forces the other host to repair its copy every time.
- **C. Do not update it; reconcile once, when the switch-over branch is cut.** *For:* no daily work. *Against:* weeks of drift met at the worst moment.

"Each pulling and rebasing before it starts" (row 85) is about a host catching up with the other host's commits on the same branch; it stands under any of these.

### 4. Where the clone sits

- **A. `/mnt/lupin-data/lupin-kernel`, owned by this account (recommended).** *For:* beside the deployed tree and the two UHW clones, on the disk with room; the folder carries the branch's name; owned as the UHW clones are, so no `sudo` to write it. The server's container runs as user 1001 with this account's group added, so it can write its output folder there if the clone is group-writable. *Against:* a folder beginning `lupin` could be picked up by something that globs `lupin*`; none was found.
- **B. `/mnt/lupin-data/lupin-writable`.** *For:* says what it is beside "the deployed tree". *Against:* the name says nothing about the kernel.
- **C. Under the home directory.** *For:* plainly personal. *Against:* the boot disk, not the data disk; the container's mounts all live under `/mnt/lupin-data`.

It is a full clone, not a git worktree of the deployed tree: the server mounts the tree's `.git` folder, which a worktree does not have, and a deploy resets the repository a worktree would share.

### 5. Lupin's gates in the clone

A fresh clone has no hooks, so nothing would check the kernel's commits; with hooks installed, the push gate fails on the VM today for a reason that has nothing to do with the kernel (the interpreter is too old to read three of lupin's files).

- **A. Install lupin's hooks in the clone and give them an interpreter that reads the tree, Python 3.12 or newer (recommended).** *For:* the kernel's commits meet the same gates as everything else in lupin, before they reach GitHub; it is found and fixed now, not at the first push after Kernel-8. *Against:* work for lupin's implementer (a virtual environment on the VM, or the hook taught to find one); until it is done the relocation cannot push.
- **B. No hooks in the clone; the gates run when the branch is merged on the development server.** *For:* nothing to build. *Against:* findings arrive weeks late and in bulk; lupin's own text says a push that was not checked is not a pass.
- **C. Push with the gate skipped (`--no-verify`).** *For:* works today. *Against:* a standing bypass of a gate lupin relies on.

### 6. How port 8000 is re-pointed at the clone, and when (row 100)

The ruling of 2026-11-18 stands: port 8000 serves the clone. Open is how. The three ways the row lists:

- **A. One variable in the overlay file (recommended).** Each of the server's 20 relative mounts (the overlay's 21 less the database container's one; corrected while recording) becomes `${LUPIN_TEST_TREE:-.}/…`; the variable is set in the VM's environment file to the clone's path at the relocation. Unset, everything is as today. The database container keeps its one mount on the deployed tree. *For:* one small change in lupin, harmless until the variable is set, reversible by unsetting it; `lupin-vm.sh`, the shared compose project and the network are untouched; it also ends today's side effect, a deploy changing the code port 8000 serves. *Against:* the overlay file itself is still read from the deployed tree, so a change to the overlay made on the kernel branch does not act until it is deployed.
- **B. A second compose project run from the clone's folder.** *For:* complete separation. *Against:* the container names, the network and the secrets are defined for one project; each would need a second definition, and `lupin-vm.sh test-server` would need to know two projects.
- **C. `lupin-vm.sh test-server` changes into the clone.** *For:* one line. *Against:* it names the base file too, so compose would see port 7999's service defined from a second folder inside the same project, and an `up` could recreate the wrong container.

**When, under any of them:** the change is written now by lupin's implementer on the development server and deployed; the variable is set by Rick at the relocation, when the clone first holds the kernel. Until then port 8000 keeps serving the deployed tree, which is what Kernel-2 to Kernel-8 are built against: the Phase 1 kernel lives in this repository and reaches the server only over HTTP.
