## Problems and options

### Row 133: the sign-in and quota settings

### 1. The words of each refusal

Eight sentences, each led by the setting's name, built the same way as the refusals you have already confirmed for the earlier settings (`missing: the key is required`; `not one of observe, enforce, off: …`). One differs in a small way: the overage switch reports the word after normalizing it, so what the operator reads is not what the operator typed.

- **A. Confirm, and the overage refusal repeats the value as typed (recommended).** *For:* one rule for every refusal; a stray space or capital is visible in the message. *Against:* one line of code changes.
- **B. Confirm as written.** *For:* nothing changes. *Against:* one refusal of eight shows a value the file does not hold.

### 2. The constants' names

`METER_SECONDS`, `METER_MAX_AGE_SECONDS`, `LOGIN_REMIND_HOURS`, `REOPEN_CARD_MIN_MINUTES` and `OVERAGE` name settings by their own words; `TIMING_KEYS` lists the four timing settings; `METER_READ_LIMIT_SECONDS` is the 60 seconds a meter read may take; `OVERAGE_WORDS` and `PRICE_QUANTITIES` list the legal words; `POOL_NAME_PREFIX` and `PRICES_PREFIX` begin the two optional families. (`FILE_STORAGE_ENVIRONMENT` was confirmed yesterday.) Each is a noun, none abbreviated, and they follow the earlier module's pattern (`QUOTA_KEYS`, `RESERVE_MODES`).

- **A. Confirm (recommended).**
- **B. Rename.** I have no candidate that reads better.

### 3. What counts as a price

The amendment refuses `nan` and `inf`, which Python reads as numbers and which would poison every cost computed from them. The same reader also takes forms nobody would call a price: `3_0` is 30 dollars, `3e0` is 3. The four timing settings are already stricter (digits only).

- **A. Confirm the refusal, and a price is digits with at most one decimal point (recommended):** `3`, `3.00`, `0.30`; nothing else. *For:* `nan`, `inf`, a sign, an exponent and an underscore all fall out of one rule, with no list of bad words; it matches the whole-number settings. *Against:* `.5` and `1e-3` are refused, which someone may type; the two ratio settings ruled earlier (the spawn floor, the reserve) still use Python's reader, so the kernel has two readings of a decimal until those are next touched.
- **B. Confirm as written.** *For:* one number reader everywhere a decimal is read. *Against:* `3_0` is 30. A wrong price harms nothing but the cost table, which is not printed until Phase 4.

### 4. A price setting whose model is several words

`kernel engine prices claude fable 5.2 input` is refused; the model's name in a setting is its normalized form, one word (`claude-fable-5.2`), as in the context-window table you ruled earlier. The refusal says so.

- **A. Confirm (recommended).** *For:* the same rule as the other per-model table; without it the reader cannot tell where the model ends and `cache read` begins.
- **B. Join the words with hyphens.** *For:* forgiving. *Against:* two spellings for one setting.

### 5. The seconds since the last sign-in

The figure exists for one purpose: after two lapses, to show whether sign-ins end on a regular interval (row 132). Whole seconds are ample. But the two times come from the host's clock, one kept across a kernel restart, and a clock corrected backward in between gives a negative figure.

- **A. Confirm whole seconds, rounded down; a figure below zero is recorded as "none" (recommended).** The record already allows "none" (the first lapse the kernel sees has no figure). *For:* a reader of two records never mistakes a clock correction for an interval. *Against:* the lapse is recorded without its figure, and why is not said in the record.
- **B. A figure below zero is recorded as 0.** *For:* always a number. *Against:* 0 reads as "lapsed the moment it was restored", which is a false interval.
- **C. As written.** *Against:* −600 in a field named for elapsed time; and "rounded down" is not what the code does below zero.

### 6. `kernel engine pool name` with nothing after it

Passed over, like any setting the kernel does not know. You ruled yesterday that a withdrawn setting left in a file is ignored and that no list is kept; a setting the kernel has never known is treated no worse.

- **A. Confirm (recommended).** *For:* it follows that ruling. *Against:* a typing error (`pool names`) is not reported; the pool then shows the meter's own name, which is visible.
- **B. Refuse it by name.** *Against:* the first step toward the list you declined.

### 7. Two settings that name one pool (on no list)

A pool's key is written with spaces for its underscores. `third party models` and `third_party models` are therefore one pool under two settings; today the second silently wins.

- **A. Refused at the start, naming the second setting (recommended).** *For:* the same treatment as a blank name, which you ruled is refused; two lines of code and one test. *Against:* a refusal for a case that takes two near-identical lines to produce.
- **B. As written.** *For:* nothing changes. *Against:* which name is spoken depends on alphabetical order.

### Row 136: where Lupin is, and the key file

### 8. The names

`LupinConnection` (the pair), `load_lupin_connection`, `read_lupin_key` and `URL_SCHEMES` follow the naming rule: a noun, two verbs with their objects, a noun. `URL_KEY` and `KEY_FILE_KEY` are the only two of the record's seventeen setting names to end in `_KEY`, and "key file key" uses one word for two things, the setting and the secret.

- **A. `LUPIN_URL` and `LUPIN_KEY_FILE`; confirm the other four (recommended).** *For:* one pattern across the kernel's settings; the builder, copying modules side by side, sees one. *Against:* `LUPIN_KEY_FILE` holds the setting's name, not a path, which a reader must learn once (as with `OVERAGE`).
- **B. All six as written.** *For:* `_KEY` says outright that the constant is a setting's name. *Against:* the odd pair out.

### 9. The form of the address

The list says "limited to `http` or `https`, a host and a port". The code requires the scheme and a host and does not look at the port. What that lets through is under "What the probe read". Two separate questions: whether a port must be written, and what is done with a malformed one.

- **A. The port is optional; when written it is a whole number from 1 to 65535; a host holds no space; an empty `user@` part, an empty `?` or `#` and an unfinished bracket address are refused; every refusal names the setting, and none repeats an address that carries a credential (recommended).** The host is lowered in case, as the scheme already is. *For:* `https://lupin.example` is a legitimate address; an omitted port means 80 or 443, neither of which is a Lupin on this host (7999 and 8000), so "no kernel reaches a server by omission" holds; every malformed address is caught at the start and by name. *Against:* the list's words said "a host and a port", and this reads them as "a host, and a port if one is given".
- **B. The port is required, with the same checks.** *For:* the list's words as written; nothing about the address is left to a default. *Against:* an address behind an ordinary web front must carry `:443`.
- **C. As written.** *Against:* `http://localhost:port` passes the start and fails at the first request, away from the settings file; one malformed address ends the start in a Python error.

Not proposed, and said so that it is not silence: an `http` address on another machine is accepted, and the fleet key would cross the network unencrypted. I did not read how the kernel reaches Lupin on the development server, and D50 (credential exposure) keeps the fleet key as it is for Phase 1; a rule here would be new policy in a session about details. If you want one (`http` for this machine only), say so and it is a sixteenth question.

### 10. The key file's path

`~` is the host's convention for the key file (`~/.lupin/notification-api.key`) and is expanded. Anything else that is not a full path is kept as typed and resolved against the folder the kernel was started in, which for a host service is an accident of its unit file.

- **A. Confirm `~`; once expanded, the path must be absolute, or it is refused by the setting's name (recommended).** *For:* one rule closes three cases (a relative path, `$HOME/…`, an unknown `~user`); the path printed in a later refusal is the file actually tried. *Against:* a relative path that would have worked is refused.
- **B. As written.** *For:* nothing changes. *Against:* the same settings file names a different key file from a different folder.
- **C. Also expand `$HOME` and other variables.** *For:* forgiving. *Against:* the settings file's meaning then depends on the kernel's environment, which D50 keeps small.

**Corrected during the walk-through (2026-11-24), before this decision was put.** Lupin's settings reader already expands `$NAME` and `${NAME}` in every value it returns (`os.path.expandvars`, lupin `src/cosa/config/configuration_manager.py`, line 801), and the kernel is handed its settings through that reader. So `$HOME/key` reaches the module already expanded when the variable is set, and as typed only when it is not; option C describes what the reader does today, and its "against" is a property of every Lupin setting, not a choice here. The probe handed the module its values directly and did not show this. Option A is unchanged, and under it a variable that is not set leaves a path that is not absolute, which is refused.

### 11. What the key file holds (on no list)

The module removes the white space around the key and returns the rest. A file with two keys, one to a line, returns both with the line break between them; the request header cannot carry that, so the failure arrives at the first request, as an error from the network library and not from the settings.

- **A. The key is one unbroken word: a byte-order mark and surrounding white space are removed, and white space or a control character inside is refused, by the file's path and never by its content (recommended).** *For:* the start proves the key is sendable; the refusal names the file. *Against:* none found; Lupin's keys hold no white space.
- **B. The first line is the key.** *For:* tolerates a comment line below. *Against:* silently ignores what may be the newer key.
- **C. As written.**

Not proposed: refusing a key file that every account on the host may read. The record sets the mode (640, credential exposure spec, 2026-11-09) and under D50 the operating-system user is the boundary; a check of the mode at the kernel's start would be a new rule.

### 12. The words of each refusal

Seven sentences: `missing: the key is required`; `not an http or https address with a host: …`; `the address carries a credential; the key goes in the key file`; `the address carries more than scheme, host and port: …`; `blank: the key is required` (for a blank path); `cannot read <path>: FileNotFoundError` and `<path> is empty`. One is unclear: for a blank path, "the key is required" could mean the secret.

- **A. Confirm, with the blank path's sentence reading `blank: the key file's path is required` (recommended);** the sentences for whatever decisions 9 to 11 add are written to the same pattern and put to you as one click while recording. *For:* each sentence says which thing is wrong.
- **B. Confirm as written.**

### 13. Both settings read once, at the start

Neither is read again when a persona is admitted, unlike the overage switch and the quota settings. A change of server or key file takes a kernel restart; so does a key replaced inside the same file.

- **A. Confirm (recommended).** *For:* a kernel that changed servers while personas ran would split one fleet's records across two Lupins; it matches your ruling 9 of yesterday (settings that are not admission decisions are read at the start only). *Against:* a replaced key means a restart.
- **B. Read the key file again when Lupin refuses the key.** *For:* a replaced key needs no restart. *Against:* behavior on a refused key is not designed anywhere yet; this would design it by the way.

### 14. No acceptance test of their own

The builder builds to the gates, and the phase table in the framework is what says which tests run at which gate. Twelve unit tests named by no gate depend on the builder's care alone; and nothing on the host proves the two refusals that matter (a kernel started without either setting does not start). The sign-in and quota settings have both: Quota-14 (the unit tests, Kernel-1) and Quota-15 (each required setting removed in turn on the test VM, Kernel-2).

- **A. One test, `Connection-1`, with Kernel-2 (recommended):** the module's unit tests green; on the test VM, the kernel refuses to start with either setting removed and names it; with both set, its first request to port 8000 is admitted. *For:* the two settings that keep a kernel under test off the wrong server are proven on the host; the phase check script then guards the gate. *Against:* a new one-test family in the phase table. Note for the builder: the settings are required from the first start that loads this module, which is step 3 of the build order (Kernel-2), not Kernel-1.
- **B. As written: no test.** *For:* Kernel-2 cannot pass without a working pair; the branch-naming module is a precedent. *Against:* Kernel-2 proves the pair works, not that its absence is refused.
- **C. A clause added to Quota-15.** *For:* no new family. *Against:* these are not quota settings.

### 15. "The Move clock" as the gate of the other hosts' inventories

### 16. How the kernel's refusals use the splainer (raised by Rick during the walk-through)

Rick, at decision 8: "when it comes to key naming, we always have the configuration file splainer, which is basically used to describe the values or the purpose that a key value pair serves. It's a part of the runtime behavior, such that when a key is requested and not found the error thrown provides human intelligible feedback as to what's going on."

What the code shows (lupin at `89d6a56115`, `src/cosa/config/configuration_manager.py`). `get_required` (lines 827 to 870) prints a banner and the key's splainer line, then raises `MissingConfigKeyError`, for a key that is absent and for one whose value is blank; `get` (lines 795 to 825) splains a missing key and returns the default or nothing; `splain_me` is at lines 919 to 945. `get` also passes every value through `os.path.expandvars` (line 801), which bears on decision 10. The kernel's reference modules do not go through either: they are handed every setting at once (`{ key: manager.get( key ) for key in manager.get_keys() }`, turn-end policy spec, line 444) and raise their own `ConfigurationError`, so the splainer never speaks for a kernel setting. The record says every kernel setting is "explained in `lupin-app-splainer.ini`" (D62, turn-end policy, part 10); the two amendments of 2026-11-23 wrote no splainer line for their eleven settings, and neither of lupin's two files holds a `kernel` setting yet.

- **A. Every refusal carries the setting's splainer line after the kernel's own sentence, and every amendment that adds a setting writes its line (recommended).** *For:* the operator reads what the setting is for at the moment it is refused, as elsewhere in Lupin. *Against:* one more parameter into the modules; eleven lines to word.
- **B. The lines are written; the refusal does not quote them.** *Against:* documentation only.
- **C. The kernel reads each required setting through `get_required`.** *Against:* undoes the refusal wording ruled on 2026-11-23 and in decision 1; a bad value would still need the kernel's sentence.
