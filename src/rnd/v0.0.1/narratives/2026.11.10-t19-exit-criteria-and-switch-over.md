# Exit criteria and the switch-over: how AH4L ends (T19)

2026-11-10 · Rick Ruiz · Claude doc `https://claude.ai/artifact/FodPQXGrs4ivCTKbGJNWMM` · resolved as D63

## In one paragraph

This item decides three things the design register has postponed since October: what "done" means for each build phase and gate, what the week that retires the current harness (AH4L) looks like step by step, and the list of everything in lupin that is deleted, kept, renamed, flipped or moved when the kernel takes over. Today the framework draws eight stages but defines an exit for only two of them (the Phase 1 tests Kernel-1 to Kernel-8 and the convention gate Convention-1 to Convention-9); "Claude parity" has no operational meaning; and the deletion list is one long sentence in the framework plus six "handed to T19" sections in the specs, about 110 rows written under four different clocks with one verb, "delete", for six different kinds of change. The recommendation: exit criteria as a table of acceptance families and one proof workload per phase; a measured soak before the switch, with its numbers set from a shadow period rather than invented now; a bounded mixed-fleet period instead of a big bang; the deletion as one commit on a branch, merged only after the soak passes, with a tagged way back; and the list itself moved into a T19 spec as a table with dispositions and clocks, checked by an inventory script against the lupin checkout so it is tracked, not remembered.

Four timing phrases are used and never reconciled: "at switch-over", "after the move" (the kernel's move into lupin, which precedes switch-over by two phases), "after the last Claude transcript seat is gone", and "once no AH4L session remains". Everything is written as a deletion, including rows that are renames, flag flips, configuration-key moves, operational steps (stop a deploy, create an account) and modules the kernel will import. ## The problems

1. **Exit is defined for two stages of eight.** Phases 2, 3 and 4, gate G2 and the switch-over week have descriptions, not criteria. Nobody can say today when the kernel is allowed to carry real work.
2. **Seventy-six acceptance tests have no phase.** About forty ride inside Kernel-1 to Kernel-8; the rest are "Phase 2 or later". A test with no phase is proved when someone remembers it.
3. **Phase 2 proves a fleet on the Jetski family, but the fleet that does the daily work runs on Claude** on the development server. Nothing says what the first real job under the kernel is, or where.
4. **G2 is a test gate with no operating evidence behind it.** Tests prove the kernel can do each thing once; they do not prove it carries a day's load for a week without a human attaching a terminal. No duration and no numbers are stated.
5. **A mixed fleet is undesigned.** Any shadow run or soak puts AH4L seats and kernel personas on one Lupin instance at the same time. The roster, DMs, broadcasts, the task store and the voice path must see both; the fleet ruling says one kernel per host and one fleet per Lupin instance and never mentions a transition.
6. **The list has four clocks and one verb.** "At switch-over", "after the move", "after the last Claude transcript seat" and "once no AH4L session remains" are different days, weeks apart. "Delete" covers deletions, renames, flag flips, key moves, imports and operational steps alike.
7. **Half of the hooks tree, by lines, has no disposition.** Deleting the tree whole takes the five git guards (the ancestors of the gate's rule table) and the task-store client (which the owed-work query needs) with it; keeping the tree keeps the bridge files and tmux alive.
8. **There is no way back.** Once the bridge files are migrated and the harness deleted, a failure in week two has no rollback. The record says "dedicated branch" and stops.
9. **The switch-over has no operator.** Lupin is written on the development server by Claude Code sessions under AH4L. A session that deletes the harness it runs under ends its own listener mid-commit.
10. **The list is prose and nobody can check it.** T38 got an inventory script on the day it opened; this list, five times larger, has none. A row naming a file that was already renamed is a silent miss.

## Options and recommendations

### 1. What an exit criterion is

**Option A (recommended): tests plus one proof workload per phase.** A phase exits when its named acceptance families are green on the real engine for that phase and one end-to-end workload has run under the kernel with no human intervention. The workload is the thing the phase exists for; the tests are the things that must not regress. Pros: a workload catches what no test row anticipated (the T28 finding that a grade never reached a seat is the kind of thing only a run reveals); the record already has the workloads (the cascade review and the adversarial SWE team in planning-is-prompting). Cons: a workload is slower to run and needs a judgment call on "worked".

**Option B: tests only.** Pros: mechanical. Cons: Kernel-1 to Kernel-8 prove plumbing; the convention gate exists precisely because plumbing green did not mean the persona could work.

**Option C: workloads only, tests as hygiene.** Cons: regressions found late, by a persona at 2 a.m.

### 2. Which tests belong to which phase

**Option A (recommended): the assignment below, written into Section 15 as a table and into each spec's acceptance section as a phase column.**

| Stage | Exit: tests | Exit: proof workload | Platform |
| --- | --- | --- | --- |
| Phase 1 | Kernel-1 to Kernel-8 with everything folded into them (Inbox 1 to 5, Voice 1 to 5, Console 1 to 3, Pressure 1 to 6, Log 1 to 3, Fleet 1, 2, 10, Capacity 1 to 7, Broadcast 1, 2, TurnEnd 1 to 8, Bootstrap 1); C17 before, C18 before Kernel-5 | one AGY persona by voice, a day of use | test VM |
| Gate G1.5 | Convention-1 to Convention-9 | an AGY implementer follows the kit on one kernel task | test VM |
| Phase 2 | the move into lupin; then Fleet 3 to 9, Bootstrap 2 to 7, Broadcast 3 to 6, Console 4 to 7, Log 4 to 6, Inbox 6, Lupin 1 to 8, the ticket store and the grant (T36) | the cascade review run by an AGY manager with AGY workers on a scratch repository: no tmux, no bridge file touched (checked by the inventory script) | test VM |
| Phase 3 | Kernel-1 to Kernel-8 repeated with the `claude` adapter; C15b; Fleet-10's positive case (`billing: vertex` accepted) | the same single persona by voice, on Claude | test VM |
| Phase 4 | every family green on Claude; the Section 12 matrix retired in favour of this table | the development server's roles spawned under the kernel in shadow beside AH4L (Problem 5), for the baseline period | development server |
| Gate G2 | the full table green on both engine families, same fixtures | the soak (Problem 4) passed | development server |

Pros: every test has an owner phase; Phase 2 absorbs the move, which is where the record already puts the server rows. Cons: Phase 2 is heavy. **Option B: everything that is not Kernel-1 to Kernel-8 waits for Phase 4.** Pros: fewer gates. Cons: the fleet and the Lupin changes would be proved first on Claude, the last engine to be adapted, inverting the build order (Jetski family first) that D1 to D20 chose.

### 3. When the kernel first does real work

**Option A (recommended): not before Phase 4.** Phases 1 to 3 run on the test VM against the destructive-test server; the planning-is-prompting workloads run on scratch repositories. The development server sees the kernel first in the Phase 4 shadow, on real roles. Pros: matches the stated goal (a minimum bootstrappable candidate on the test VM first); keeps D45's "lupin written on the dev server only" intact until the kernel is in lupin. Cons: the first real feedback arrives late.

**Option B: one AGY persona under the kernel joins the development fleet in Phase 2**, in a role with no write access (a reader or librarian role). Pros: real traffic a phase earlier. Cons: a mixed fleet two phases early, before the Lupin rows that make it safe (the grant, the voice pull) exist.

### 4. The soak: how long and what numbers

**Option A (recommended): ten working days, numbers set from the Phase 4 shadow baseline, pass or fail stated in advance.** The kernel fleet carries the whole daily load; AH4L seats are stopped but startable. The measures are the ones the kernel already logs: `session.oom_killed` (zero), personas marked `stalled` and left unattended past one tick (zero), gate denies that were not expected rules (reviewed, none unexplained), memento verify (green every day), voice round-trip from spoken word to spoken reply (its 95th percentile no worse than the shadow baseline), turn-end pokes per persona per day (no worse than the baseline), and no tmux attach by a human for any reason. A failed measure stops the clock; the clock restarts from zero after the fix. Pros: the numbers come from the kernel's own records, so measuring costs nothing; a baseline from the shadow avoids inventing thresholds tonight. Cons: two weeks is a long time to hold two harnesses.

**Option B: five working days.** Cons: one bad day is a fifth of the evidence. **Option C: no soak; G2's tests are the gate.** Cons: Problem 4 in full.

### 5. The mixed fleet

**Option A (recommended): a mixed fleet is permitted only in the Phase 4 shadow and the soak, bounded by a date, and Lupin reads both rosters for that period.** The mechanism already exists in pieces: the fleet-state and context-pressure routes are projected from the kernel roster (D57, D59); the T31 row says the broadcast door and `active-sessions` read the kernel roster instead of bridge files. For the mixed period they read the union of the two, with the source on each row. DMs route by sender id on either side (the local parts differ by engine, D42). The task store is engine-blind already. The voice path is two listeners per human until the switch (one bridge, one kernel pull), which is what the shadow is for. Pros: the shadow and the soak become possible; the union read is small. Cons: one more Lupin row, removed again at the deletion commit.

**Option B: no mixed fleet; a big-bang weekend.** AH4L stopped Friday night, the kernel fleet Monday. Pros: no union code. Cons: no baseline, no shadow, no soak; the first real load is the live one.

**Option C: per-persona migration over weeks.** Cons: the union read for weeks, two harnesses to operate, and a manager on one side with workers on the other.

### 6. Clocks and verbs for the list

**Option A (recommended): three clocks, six dispositions, every row carries one of each.** Clocks: **Move** (the kernel's move into lupin, end of Phase 2: repoints, key moves, imports; nothing deleted); **Switch** (the switch-over week: flips, stops, the data migration, wire renames that AH4L never sees again); **Delete** (one commit after the soak passes: file deletions, route removals, the transcript-era renames). Dispositions: Delete, Keep and import, Rename, Flip, Move key, Operate. The four existing phrases map onto the clocks: "after the move" is Move; "at switch-over" and "once no AH4L session remains" are Switch; "after the last Claude transcript seat" is Delete. Pros: each row becomes checkable on a known day. Cons: three passes over lupin instead of one.

**Option B: everything in the switch-over week.** Cons: a week that deletes 45,000 lines, migrates data and flips flags at once has no small failures.

### 7. The hooks tree, module by module

**Option A (recommended): the whole of `src/lupin_cli/claude_code/` is Delete by default; the exceptions are named now and the rest is closed by the inventory script.** The exceptions: the five git guards become gate rule evaluators (the D49 rule table names their acts; they are ported as functions the gate calls, never as hooks, and `branch_guard`'s approved-bypass allowance is checked at the port); `task_store_client.py` and `task_store_map.py` are imported for the owed-rows query of D62 and the sweep; `transcript_reader.py` stays until the last Claude transcript seat is gone. Everything else is replaced by a ruling already made: `session_bridge` by the registry (T31), `hook_common` and the listener by the inbox (D52), `subagent_governance` by the D39 deny rule, `hook_credentials` by D50, the catch-up and janitor modules by D52's ledger, the heartbeat and idle modules by D62, the entry points by the kernel's own events. A module with no disposition on the day of the Delete commit blocks the commit. Pros: one default, few exceptions, every exception tied to a decision. Cons: the guards' port is real work (4,145 lines) and lands on the Move clock.

**Option B: port nothing; rewrite the guards and the client inside the kernel.** Pros: no lupin import in the gate. Cons: 4,000 lines of tested guard logic rewritten for no design reason; the gate already imports lupin after the move (D38).

**Option C: keep the tree as a library.** Cons: Problem 7's second half.

### 8. The way back

**Option A (recommended): a tag, an archive and a rehearsed runbook.** The last commit of main before the switch-over week is tagged `ah4l-final`. T31 archives the bridge files, the pool store and `~/.claude` mementos to a dated tarball on the host instead of deleting them, kept 30 days. The Delete commit is one commit on the switch-over branch, merged to main only when the soak has passed. Rollback is: stop the kernel, check out the tag, restore the archive, start the listeners; it is written as a runbook and rehearsed once on the test VM before the switch-over week. Pros: a failure in the soak costs an hour, not a weekend. Cons: 30 days of a tarball nobody wants to use.

**Option B: fix forward.** Cons: Problem 8.

### 9. Who runs the switch-over

**Option A (recommended): Rick at the laptop console; a kernel-run Claude persona on the development server makes the lupin edits and the Delete commit from its own worktree.** AH4L seats are stopped before the Delete commit, never during it. This is D40's dogfooding rule applied to the last job the harness has. Pros: the persona that deletes AH4L is proof that AH4L is not needed; the edits are in the kernel's log. Cons: the Phase 4 Claude adapter must be solid before the week begins, which it must anyway.

**Option B: Rick alone, by hand.** Pros: no dependency. Cons: 45,000 lines and a data migration by hand, and nothing learned about the kernel.

**Option C: an AH4L session does it.** Cons: Problem 9.

### 10. The list as a tracked thing

**Option A (recommended): the consolidated table lives in the T19 spec, keyed by path, with disposition, clock, replacement and the deciding ruling; `src/captures/t19_switch_over_inventory.sh` checks every row against the lupin checkout.** The script reads the table, resolves each path, INI key, route and unit name, and prints present, gone or unknown with the line count; it runs before each clock and in the Delete commit's review; a row it cannot resolve is an error. Section 15 of the framework keeps the phase table and one pointer to the spec; the sixty-row sentence goes. Pros: the T38 pattern, already accepted; the list stops drifting from the code. Cons: a table of about 110 rows to maintain, which the script makes cheap.

**Option B: keep appending to the Section 15 paragraph.** Cons: Problem 10.
