# The console (T20): what the operator sees and types once there is no terminal pane

**As of:** 2026-11-09 · **Author:** Rick (with Claude) · **Claude doc:** https://claude.ai/artifact/71NgnRoV4AW5pUUJxE8xD1 · **Ruled as D58,** amending D15; design of record `specs/2026.11.09-t20-console-spec.md`

## Why this matters

The terminal pane that every seat runs in today does five jobs for the operator, and the kernel removes the pane. Engines under the kernel run headless, as child processes that speak newline-delimited JSON; there is nothing to attach to.

| What the pane does today | Who owns it under the kernel |
| --- | --- |
| Shows the work live | the web console, reading the session log (ruled with the log) |
| Takes a typed line | the kernel's message route (first kernel specification) |
| Takes Escape to cut a turn | an urgent message (same route) |
| Shows permission prompts | approval tickets, answered through Lupin (tool-approval ruling) |
| Takes `/clear` | the re-spin handshake (bootstrap ruling) |

Four of the five have owners. What no ruling has settled is the place where an operator does them together, and what that place looks like. The record holds two descriptions of the terminal console that contradict each other, the harness's own lines have no style and no filter on either console, and context pressure has a field on the roster and no face.

There is also a gap in time. The web console's kernel side lands when the kernel moves into lupin, after the eighth kernel test. Through the whole of the first build phase, the only way to watch a kernel persona is `tail -f` on a JSON file.

## The principles this item rests on

1. **Operator attention is the scarce resource.** The wrapper exists to save it. The default view shows what a person would act on; everything else is one choice away and never gone.
2. **One log, one mapper, many readers.** The log ruling made the session log the only record and named one mapping from records to display blocks. No reader parses raw records on its own.
3. **Readers derive nothing.** The context-exhaustion ruling has the sensor publish a status and forbids readers from computing one. Level and colour follow the same rule.
4. **Nothing is dropped, only folded.** Lupin's console already shows a block of a kind it does not recognise instead of hiding it. A filter folds; it does not delete.
5. **Nothing that speaks as the human sits within a persona's reach.** The credential ruling forbids one thing: the owner's password in a plaintext file on a host that runs personas. The first draft of this document widened that to "the fleet host holds no human credential", and Rick corrected it. The test that matters is who can read the credential at the moment it is used.
6. **No new protocol where a file and a socket will do.** A tail served by the kernel was set aside until the fleet item rules on more than one host.
7. **Engine-neutral names.** Nothing introduced here carries `cc` or `claude_code`.

## The problems, stated one at a time

**Problem 1: The record defines the terminal console twice.** The decision of 10-13 calls it a notification client: it would log in to Lupin and see what notifications carry, which is spoken lines and asks. The log ruling of 11-08 calls it a reader of the session log, which sees every tool call and needs the host's files. One program cannot be both.

**Problem 2: An act done as the human needs the human's login, and the console's home decides whether holding one is safe.** Posting a typed line to Lupin's notifications API, or answering a ticket, needs a token that speaks as Rick. The first draft assumed a console could never hold one. That assumption was wrong; Solution 10 replaces it.

**Problem 3: Through the first build phase nothing can watch a kernel persona.** The web console's kernel side lands after the move into lupin. The terminal console is out of first-phase scope. The mapper is specified to be born in lupin, which first-phase code may not import.

**Problem 4: Every kernel line is the same kind.** A gate denial and a stderr progress line are both role `kernel`, kind `kernel`, plain text. A reader cannot style or filter them apart without parsing the text.

**Problem 5: Kernel lines have no style.** On the web they render at body weight between tool chips, indistinguishable from a block the client failed to recognise.

**Problem 6: There is no filter.** Three people read a console: one following the conversation, one following the work, one debugging the harness. Stderr at up to 600 lines a minute buries the first two.

**Problem 7: Pressure has a field and no face.** The status is published on the roster; neither console shows it.

**Problem 8: The input grammar has collisions.** A leading `/` now belongs to skills. A leading `!` cuts a turn, and on the Google engines that costs a process restart. The console needs commands of its own (switch seat, change view, re-spin, quit) and has no character left for them.

**Problem 9: A ticket appears where it cannot be answered.** The pane used to take the permission keypress. A human approval must now come through Lupin's login door, which the terminal console does not hold.

## Proposed solutions

### Solution 1: What the terminal console is (Problems 1 and 2)

*First-pass text. Its premise about credentials was corrected; the options were re-put under Solution 10.*

**Option A (recommended): a reader of the session log on the kernel's host, with typed input over the kernel socket.** The operator reaches it by SSH, as the pane is reached today. It amends the 10-13 decision in one phrase: "notification client" is struck; the scrollback, the input box, the mirror line and the `!` prefix stand. A typed line goes to `POST /personas/{id}/messages` and is logged with `channel: console`.

- Pros: it sees everything the log holds; no credential sits on the host; it works when Lupin is down, which is when a console is needed most; the route already exists in the first phase.
- Cons: a typed line is not a Lupin notification, so it is absent from the phone's history (the web console still shows it, as the user block); it is reachable only by SSH; any process of the same user can post to the same socket, a risk the credential ruling already accepted and observes.

**Option B: a notification client, as ruled on 10-13.** It logs in to Lupin over a WebSocket.

- Pros: runs from any machine; typed lines appear in Lupin's history; the ruling stands as written.
- Cons: it sees spoken lines and asks, not the work, so it is a poorer copy of the web client; it needs the human's login typed each session or stored on the host; it is dead when Lupin is down; it repeats the reconnect and catch-up logic the kernel already has.

**Option C: no terminal console; the web console only.**

- Pros: nothing to build.
- Cons: nothing to watch with through the first phase, and nothing when Lupin is down.

### Solution 2: Where the mapper is born (Problem 3)

**Option A (recommended): one pure module in the kernel package, written in the first phase; Lupin's tailer imports it after the move.** A record goes in; a block or nothing comes out; standard library only. This changes the file's location in the log specification and nothing in its table.

- Pros: one mapper by construction; it is tested on the fakes in the first kernel test; a terminal reader can exist before the move.
- Cons: Lupin's web layer imports from the kernel package, a one-way dependency inside one repository; the first phase grows by roughly 120 lines.

**Option B: two mappers,** Lupin's as specified and a simpler one inside the terminal console.

- Cons: the two drift. The web console's own source warns against exactly this between its pane and its page.

**Option C: as specified, in lupin after the move.**

- Cons: Problem 3 stands.

### Solution 3: What ships in the first phase (Problem 3)

**Option A (recommended): a read-only `lupin persona watch <id>` with the third kernel test; the interactive console after the eighth.** The watch command asks the kernel socket for the persona's log directory, follows the newest segment, hops to the next when a segment-opening record names it, and prints blocks through the mapper. About 80 lines, no terminal library.

- Pros: the builder and Rick can see what a persona is doing from the first real turn; the mapper is proven before Lupin depends on it.
- Cons: first-phase scope grows, against the line that excluded the console client.

**Option B: the whole interactive console in the first phase.**

- Cons: prompt handling, a status line and commands, several hundred lines ahead of the bootstrap candidate, none of them needed by the eight tests.

**Option C: nothing until after the move.**

- Cons: `tail -f` and `jq` for the length of the build.

### Solution 4: The mapper publishes a name and a level for every kernel line (Problem 4)

**Option A (recommended).** A kernel block carries `name`, the record's kind (the block shape already has an optional `name`), and a new field `level`, one of `info`, `notice`, `alert`, from one closed table in the mapper.

| Level | Meaning | Records |
| --- | --- | --- |
| `alert` | someone must act, or something was refused | `gate.deny`, `gate.ask`, `gate.unreachable`, `watch.held_turn`, `watch.pressure` at the re-spin line, `session.resume_mismatch`, an unexpected `session.exited`, `respin.without_memento`, `ask.escalated`, `ask.expired` |
| `notice` | worth knowing, nothing to do | `watch.pressure` at the notice line, `watch.compacted`, `session.interrupt`, `session.respawn`, `respin.requested`, `respin.rehydrated`, a `voice.result` that needed repair, `inbox.duplicate`, `inbox.rebuilt`, `log.truncated`, `ask.opened`, `ask.answered` |
| `info` | the harness narrating itself | the engine's start line, `session.spawned`, `session.state`, `session.stopped`, an expected `session.exited`, `gate.would_deny`, `engine.stderr` |

This adds ten kinds the log specification's table skipped: the four `ask.*` records, the three `respin.*` records, `gate.unreachable`, `gate.would_deny` and `log.truncated`.

- Pros: readers branch on a field; the change to the wire is additive, since the client ignores a field it does not know and the Claude mapper's blocks are untouched; the test that closes the record catalogue can also require a level for every mapped kind.
- Cons: one more closed table to keep; a level is a judgement and some rows will move.

**Option B: a table in each client, keyed on `name`.**

- Cons: two tables, one in TypeScript and one in Python; readers derive.

**Option C: leave kernel lines as one kind.**

- Cons: Problem 6 cannot be solved.

### Solution 5: The style of a kernel line (Problem 5)

**Option A (recommended): one dim monospace row with a coloured rule at its left edge; the level picks the colour.** `info` is grey and dim, `notice` amber, `alert` red with full-contrast text. The row reads time, name, one line of text. Consecutive stderr lines fold into a single row, "stderr × 14", that opens on demand. The terminal uses the same three levels as dim, yellow and bold red behind a `│` gutter, and no colour when its output is not a terminal. On the web it is three rules in the stylesheet on `data-kind` and a new `data-level`.

- Pros: it reads at a glance as the harness speaking, not the persona; an alert stands out without a banner; the gutter and the name carry the meaning, so it survives a monochrome terminal.
- Cons: a fourth visual treatment in the console, after prose, tool chips and thinking.

**Option B: a separate lane,** kernel lines in a side column or a second pane.

- Pros: the conversation stays clean.
- Cons: it loses the order of kernel lines against tool calls, which is their diagnostic value; it is layout work on the web and impossible in scrollback.

**Option C: plain text, as today.**

- Cons: Problem 5 stands.

### Solution 6: Three named views, applied by the reader (Problem 6)

**Option A (recommended).** The filter is a choice among three views. An alert passes every view.

| View | Shows |
| --- | --- |
| `conversation` | what was said to the persona and what it answered, plus alerts |
| `work` (default) | adds tool calls, tool results and notices |
| `everything` | adds info lines, stderr and streaming text where it is switched on |

The reader applies the view after the mapper; the tailer and the wire are untouched, so switching re-renders what is already loaded without a request. On the web it is a three-way control in the console's bottom bar, remembered per browser. In the terminal it is `--view` at launch and a command while running.

- Pros: three choices, not fourteen checkboxes; the default is quiet and hides nothing that needs action; no server change.
- Cons: no control per kind; someone will want the work view without tool results.

**Option B: a checkbox per kind,** as Lupin's notification filter panel does.

- Pros: full control.
- Cons: it spends the attention the filter is meant to save; the panel must grow with the record catalogue.

**Option C: filter in the tailer, on the server.**

- Cons: it changes the wire and its byte-offset contract; every switch of view becomes a refetch.

### Solution 7: Pressure as a colour, and the two fixed lines above the prompt (Problem 7)

**Option A (recommended): the published status picks the colour; the ratio is printed beside it as a number.** `ok` has no colour, `notice` is amber, `over_budget` is red, `unknown` is grey with a question mark. These are the same amber and red as kernel lines, so one legend covers both. It shows in three places: the terminal's status line, the web console's header beside the seat's name, and the fleet table, which already has the column.

The terminal keeps two fixed lines above the prompt. The mirror line is the 10-13 decision given a source: the newest of the persona's last spoken line and the last line heard from the human on any channel.

```
12:04:07 │ gate.ask   git push origin main  (rule branch_lock, ticket 7f3a)
12:04:07 ▸ ask_wait( 7f3a )

said: "Nothing is pushed yet. I need your go-ahead for main."
María · a1b2c3d4 · agy fable-5.1-high · awaiting human · pressure 0.61 notice · queue 0 · 1 ticket
> _
```

- Pros: it answers "is this seat about to re-spin" without opening anything; one colour vocabulary; no arithmetic in any reader.
- Cons: amber and red mean two things, a line's level and a seat's pressure. Both mean "look" and "act", so this is judged acceptable.

**Option B: a gradient bar the client computes from the ratio.**

- Cons: the reader re-derives lines the sensor owns, and is wrong the day a persona's manifest overrides a ratio.

**Option C: the fleet table only.**

- Cons: the person watching one seat has to leave it to learn its pressure.

### Solution 8: The input grammar (Problem 8)

**Option A (recommended): the first character decides, four cases.**

| The line begins | What happens |
| --- | --- |
| anything else | a message to the persona, queued or absorbed as its engine allows |
| `!` | an urgent message; the console first prints what it is about to cut ("interrupting read_file, open 41 s") |
| `/name` | passed through untouched: it is a skill for the persona |
| `:` | a command for the console itself, never sent: `:view`, `:seat`, `:respin`, `:stop`, `:quit`, `:help` |

A lone `!` or `:` is refused with the help line.

- Pros: no collision with skills; `!` stays as ruled; the two destructive acts are words, not keys; the colon is familiar from `vi` and `less`.
- Cons: a message that must begin with a colon or an exclamation mark needs a leading space; one more convention to learn.

**Option B: `/` for console commands,** as Claude Code's own pane does.

- Cons: it collides with skill invocation as the inbox ruling defined it; `/respin` typed into the wrong window becomes a prompt.

**Option C: keys only,** Escape to interrupt, as in the pane.

- Pros: muscle memory.
- Cons: over SSH, Escape is ambiguous with arrow-key sequences; a stray key cuts a turn, which on the Google engines restarts a process.

### Solution 9: Tickets in the terminal (Problem 9)

*First-pass text. Its premise about credentials was corrected; the options were re-put under Solution 10.*

**Option A (recommended): show, do not answer.** An open ticket is an alert line and a count in the status line, with the hint "answer on the web or the phone". A line typed while a ticket is open goes to the persona as a message, never to the ticket. Revisit when the ticket store lands in lupin.

- Pros: the login door stays the only path for a human approval; nothing a persona's shell could imitate through the socket; no code.
- Cons: the operator, at the keyboard with the question on screen, must switch window or pick up the phone. That is a real cost to the person the wrapper is meant to spare.

**Option B: `:login`.** The console asks for the human's password once, holds the token in memory only, and answers tickets through Lupin's doors.

- Pros: the answer is given where the question is read.
- Cons: a human token lives inside a process on the fleet host, where a same-user process could read it; it depends on a ticket store that does not exist yet.

**Option C: answer over the kernel socket.**

- Cons: this is the forgery path the credential ruling closed. Rejected.

### Solution 10: Where the console runs and what holds its credential (added after the first pass)

**Why this was added.** The first draft said the fleet host may hold no human credential, and built Solutions 1 and 9 on that. Rick pushed back: a credential need not sit in a file anyone with read rights can see. He is right about the ruling, which forbids only the plaintext password. Two points sharpen the question. Hashing is what the verifier does, and Lupin already stores passwords that way; a console is a client and must present something usable, so the client-side question is encryption plus who can reach the key. And the credential ruling's premise is that personas share one operating-system account, so anything that account can read, a persona can read.

Rick put the question to the persona that manages the test VM. It checked the host, read-only, on 2026-11-10 at 00:42 UTC.

| Checked on the test VM | Finding |
| --- | --- |
| The persona account | has passwordless `sudo` and is in the `docker` group, so a persona with a shell is effectively root |
| Other accounts | none in use; the kernel would run under the same account (inferred) |
| The SSH server | allows Unix-socket forwarding; passage through the work laptop's tunnel is inferred, not checked |
| A secret store | none installed |
| The plaintext owner section | absent |
| Lupin's tokens | 30-minute access token, 7-day refresh token |
| Reading another process's memory | blocked for the same account, but `sudo` gets around it |

**Option A (recommended): the console runs on Rick's laptop.** It reaches the kernel socket through an SSH Unix-socket forward and reads the log over the same session. Rick's Lupin login stays in the laptop's keychain. Acts done as Rick go straight to Lupin, never through the kernel, because the kernel runs as the persona account. The read-only watch command stays on the host and needs no credential.

- Pros: nothing that speaks as Rick exists on the VM; no change to the VM.
- Cons: socket forwarding from the work laptop is unverified; the console needs Python on the laptop; two connections to keep up.

**Option B: a separate operator account on the VM.**

- Pros: the console lives beside the kernel, one SSH session.
- Cons: the boundary is real only if the persona account loses `sudo` and `docker`, which breaks deploy, the arbiter, the preflight checks and access to the checkout; no secret store is installed.

**Option C: the same account, with the token held in memory only.**

- Cons: passwordless `sudo` lets any persona read the console's memory. On this VM it protects almost nothing.

**What this does to Solutions 1 and 9.** With the console on the laptop, holding both a forwarded kernel socket and a Lupin login, both were re-put.

- *Solution 1, the route of a typed line.* Option A (recommended): the kernel socket for watching, typing and interrupting; Lupin's login only for acts that must be Rick's. Option B: every typed line through Lupin as Rick, the socket as a fallback; it leaves the same history on every channel but is two code paths for one act and makes an interrupt wait on Lupin. Option C: a notification client only.
- *Solution 9, tickets.* Option A (recommended): `:answer <ticket> <reply>` posts straight to Lupin with Rick's token; a plain line never answers a ticket; shown only until the ticket store lands. Option B: show only. Option C: a plain line answers the open ticket, which risks approving a destructive act by accident.
