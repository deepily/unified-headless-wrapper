## In brief

The kernel reads its settings from lupin's settings file. This morning every kernel setting was given the one line of explanation that lupin's second file, the splainer, holds for it. For 55 of the 104 settings, that line could not say what happens when the setting is missing or holds a value that makes no sense, because nobody had ever ruled it: 41 of them have only a value written in a specification's configuration block, and 14 have a default stated in their specification's words.

Five times a family of settings has been put to you with this question, and five times you ruled the same way: the setting is required, its value lives in the baseline block of lupin's settings file, the code holds no second copy, and a value outside stated bounds stops the kernel with the setting named. This narrative asks whether that rule holds for the remaining 55, what to do with the 14 stated defaults, and puts a bound on each setting, family by family, for you to confirm or correct.

Ten decisions. The two that are not routine: whether a host's class (test or production) may be left out of the file, since leaving it out today means "test", the permissive answer; and whether the five settings for grants are ruled now or with the grant's other unconfirmed details at the Move clock.

## Problems and options

### 1. The 41 settings that have only a value in a configuration block

A line such as `kernel stop drain seconds = 180` says what the value is. It does not say what the kernel does when the line is absent from the file, or misspelled.

- **A. Required, like the five families before them. (Recommended.)** The kernel refuses to start when one is absent or blank, naming it and printing its splainer line. The values in the specifications' blocks become the starting values in lupin's baseline block; the code holds none. *For:* the rule you have given five times; a misspelled name shows as its right name missing; one place holds each value. *Against:* the first real settings file must hold every one, including settings whose feature is not built until Phase 2; the baseline block gains about fifty lines.
- **B. Optional, with the block's value as a default in code.** *For:* a short settings file; the kernel starts on an empty one. *Against:* each value lives in two places, the file and the code; a misspelled name becomes the default and the kernel starts; lupin's reader prints a notice and refuses nothing, and whether anyone reads a kernel's standard output at its start is not established. That is the fault the five rulings closed.
- **C. Required only for those Phase 1 reads; the rest ruled when their feature is built.** *For:* nothing is demanded of the file before something reads it. *Against:* the question comes back at every later gate, and the lines of those settings keep saying nothing until then.

### 2. The 13 settings whose specification states a default (the host's class is problem 3)

Four of the session and the voice, five of the log, the fleet's folder for working trees, the archive's retention, two of the inbox. Their specifications say "default 64", and their lines repeat it.

- **A. Required too; the stated default becomes the baseline block's value and the word "Default" leaves the line. (Recommended.)** *For:* one rule for every kernel setting, with one exception already ruled (Jetski's heap) and one optional family (a pool's name); the default is not lost, it moves into the file. *Against:* it reverses the words "default N" in four specifications; each is amended.
- **B. They stay optional, with the default in code, and are bounded when present.** *For:* the specifications stand as written. *Against:* two kinds of kernel setting, and nothing but history separating them: `kernel log retain minutes` would be optional because its specification of 2026-11-08 said "default", and `kernel stop drain seconds` required because its specification of 2026-11-10 did not.

### 3. The host's class: may it be left out?

Today an absent `kernel host class` means `test`: a tool call is allowed when the kernel cannot be reached. On a production host whose file lacks the line, or misspells it, the host fails open, and nothing says so.

- **A. Required: `test` or `production`, written on every host. (Recommended.)** The baseline block does not carry it; each host's own block does, so a host with no line of its own is refused. *For:* the reason you gave for Lupin's address, "so that no kernel reaches a server by omission", applies with more force here: no host is permissive by omission. *Against:* it changes the wording of your ruling of 2026-11-16 ("so no key is written"): the development server's block gets the line `kernel host class = test`. The ruling's substance, that host classed `test`, stands.
- **B. Required, and written once in the baseline block as `test`.** Every host inherits `test` unless its block says otherwise. *For:* the same rule as the other settings; one line. *Against:* a production host that forgets its own line still inherits `test`; only the misspelling is caught.
- **C. As it stands: optional, default `test`.** *For:* your ruling of 2026-11-16 to the letter. *Against:* the permissive answer by omission.

## What follows without a decision

- **When they are read.** Each of the 55 is read at the kernel's start and held until a restart: your ruling of 2026-11-16 (row 60, ruling 3) has nothing but the admission's own records read again while the kernel runs, and none of the 55 is among them. A bad value on disk is met at the next start.
- **What a bad one does.** It stops the start, naming the setting, with the reason and the setting's splainer line (rows 59, 133 and 136). The first bad setting met is the one named.
- **Every word is read without regard to case or surrounding spaces,** as the overage switch is (row 124, ruling 5).
- **The kernel checks every kernel setting at its start, whichever process uses it.** The gate's hook uses `kernel gate retry seconds` and `kernel host class`; a persona's tool server uses `kernel client retry seconds`. How those processes receive the values is as the record has it and is not asked here.
- **Each line ruled is amended:** it gains "Required", loses "Default …" where decision 2 says so, and gains its bound, in the turn-end policy spec by a new amendment; the specifications that stated a default are amended to say where the value now lives. The counting script written today then reports what remains, and its `--check` can join the checks of every recording once it reports none.
- **The reference implementation** is one table (a row for each setting: its kind, its bounds, its words) and one function that reads a settings file against it, with tests, as the protocol requires; the builder builds from it.

## Glossary

- **Splainer:** lupin's second settings file, `lupin-app-splainer.ini`, one line of explanation for each setting.
- **Baseline block:** `[Lupin: Baseline]` in `lupin-app.ini`, which every host's block inherits.
- **Row 142, and rows 7, 39, 50, 59, 60, 122, 124, 129, 133, 136, 138, 143, 144:** rows of "Outstanding actions" in `00-status.md`; none is a register item.
- **Kernel-1 to Kernel-8:** the acceptance gates of the Single persona kernel MVP (Phase 1). Kernel-1 runs on the fake engine; Kernel-2 is the first on the test VM's real engine.
- **The Move clock:** the first of the switch-over's three clocks, the lupin wiring done in Phase 2.
- **D62 (turn-end policy), part 10:** the ruling that every kernel setting lives in lupin's settings file; the rulings of this narrative are recorded under it.
