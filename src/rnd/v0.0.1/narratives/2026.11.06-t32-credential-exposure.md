# Credential exposure in the Lupin kernel: problems, options, recommendations

**As of:** 2026-11-06 · **Author:** Rick Ruiz (drafted with Claude) · **Work item:** T32, framework Section 8.1 · **Audience:** a reader coming to the project cold · **Rulings:** all six adopted as recommended on 2026-11-06, decision D50; spec `specs/2026.11.06-t32-credential-exposure-spec.md` · **Live copy:** https://claude.ai/artifact/JVXQPHuLZeYUoco4RndrPw

## Why this matters

Every AI worker in the fleet can read the credentials that are meant to prove who is calling the Lupin server and who approved a dangerous action. This work item decides what to do about that before the approval step goes live.

Some context for the reader who has not followed the design. The **Lupin kernel** is one service on the host machine. It starts each AI worker (a **persona**: one AI engine process with a role such as implementer, reviewer or manager), gives it a voice channel to the human, and checks every tool call the persona makes before the call runs. That check is the **tool gate**. Each persona also has its own small **voice tool server**, which is how the persona sends messages, asks questions and reports to the human; that server talks to the **Lupin application server** over the network.

The design just added an approval step: before a persona does something destructive (force-pushing a branch, deleting files outside its own folder, dismissing a peer), the gate stops the call, opens a ticket, and waits for a yes from a human or a manager persona. An approval is worth exactly what it costs to forge. The design as it stands has a slot that, once filled, would bring that cost down to reading a single configuration file. The slot is empty on the development server as of 6 November 2026; nothing in the design keeps it empty. The rest of this document explains why, and what to do.

The short version of the recommendation: remove the one credential that should never have been on the host, make approvals depend on things a persona cannot fake, log the cases we choose to allow, and scrub secrets out of anything the kernel writes down or speaks aloud. None of it is large. One item is urgent.

## The principles this design rests on

Five earlier decisions shape every option below. Each is named here in plain words; the glossary at the end maps the names to the design register.

**The confusion-not-malice threat model.** The kernel guards against an AI worker that is confused, misled by text it read, or over-eager. It does not guard against a deliberately hostile one, and it does not isolate workers from each other at the operating-system level. Every gate rule therefore has a mode: *enforce* (block the call and tell the persona why), *observe* (allow it, but log that the rule would have blocked it), or *off*. Turning a rule from observe to enforce is a configuration change, not a code change.

**The kernel authorizes but does not relay.** The kernel decides whether a call may happen, as which persona, and with which tools visible. It does not sit in the middle of the traffic. Each persona's voice tool server calls the Lupin application server directly, with its own copy of the credential. This keeps the kernel small and out of the data path, and it is the reason the credential has to be reachable from inside each persona's process tree.

**Approval is a gate concern, never an engine prompt.** The three AI engines (Claude Code, Antigravity, Jetski) each have their own permission prompts. The design turns all of them off and does approval in one place, the gate, the same way on every engine. The gate denies the destructive call, opens an approval ticket, and tells the persona to wait on the ticket and then repeat the exact call. The repeat is allowed once, when the ticket says yes.

**Tickets live in Lupin, not in the kernel.** A ticket is a row in the Lupin application server's database, answered through Lupin's web interface or phone client by a human, or by a manager persona through its voice tools. The kernel opens tickets and reads answers; it does not store them. This is the single most important fact for this document: *an approval is a database row that anyone holding the right credential can write.*

**Exposure is not enforcement.** Hiding a tool from a role's tool list is a courtesy to the model, not a control. A call to a hidden tool is still served, and the gate logs that it would have denied it. The design has been honest about this from the start; this document extends the same honesty to credentials.

## What is on a fleet host today

The work item was opened over one credential. Reading the Lupin source on 5 November 2026 found four, and they are not equal. All four sit in files or environment variables that belong to the same operating-system user account the personas run as, so every persona with a shell can read every one of them.

| Credential | Where it lives | What it proves to Lupin | What it buys a persona that goes around the gate |
| --- | --- | --- | --- |
| The fleet key (one long-lived application key) | A file under `src/conf/keys/`, read by each voice tool server when it makes a call | The **account**: the whole fleet is one user as far as Lupin can tell. The same key also serves the notification system and the embedding service | Any Lupin endpoint while claiming to be any persona: send a direct message as a peer, edit tasks, dismiss a session, write to a ticket. Lupin's own source comments say it: every seat carries the same fleet credential, so the "who is acting" field is policy, not a security boundary |
| The service login (email and password of the fleet's service account) | `~/.lupin/config`, used by the voice tool server for two toggle features | A signed login token naming the **service account** | The "logged-in user" door, but as a non-approver, as long as that service email is never put on the approver list |
| **The owner's login (the human's own email and password)** | **An optional `[owner]` section of `~/.lupin/config`, read by one listener process that the new design retires. Checked 6 November 2026: absent on the development server** | A signed login token naming **the human** | **The approver door.** Lupin checks a human approval by the email on the signed token. If the section were present, a persona that reads this file could log in as the human and approve its own ticket with one web request |
| The AI engines' own vendor credentials (Claude and Google sign-in tokens, cloud default credentials) | The engine's home directory and environment | The vendor account that pays for the model | Spending on the vendor account and leaking the tokens; nothing inside Lupin |

The third row is the finding that changes the work item. The approval design quietly relies on a second door that is supposed to be stronger than the fleet key: a human's yes is a signed login token carrying an allow-listed email, which, in Lupin's words, is not something a caller can type. It is not something a caller can type. It becomes something a caller can mint the day that password is written into the home directory, and the code that reads it from there already ships. On the development server the section is absent; the same file holds sixteen per-project service logins, which shows how routinely sections get added to it.

## The problems, stated one at a time

One principle sits under all of them: **when every persona runs as the same operating-system user, there is no credential boundary between them; the user account is the boundary.** The confusion-not-malice decision accepts that. So this work item cannot be "stop personas from reading keys". It has to be a set of smaller, honest controls, each matched to a real failure.

**Problem 1: A human approval can be forged.** Lupin's listener code reads the owner's email and password from an optional `[owner]` section of `~/.lupin/config` on the host, to learn the owner's user identifier. The section is absent on the development server (checked 6 November 2026), so the problem is latent rather than live. It is still a problem: the design provides the slot, nothing forbids filling it, and the listener degrades silently either way, so nobody would notice when it appeared. Once it is there, a persona that reads the file, logs in, and posts a yes to its own approval ticket has defeated the entire approval step, in three ordinary commands.

**Problem 2: A manager's approval cannot be told apart from a forgery.** Some tickets are meant to be answered by a manager persona rather than the human. Lupin cannot tell one persona from another, because they all carry the fleet key and declare their own name. If the ticket store is the authority on who answered, a persona can answer a ticket as its own manager.

**Problem 3: The kernel cannot see a persona going around the gate.** The gate sees tool calls. A persona that reads the fleet key and calls the Lupin server directly from a shell command (or from a small script, or by importing Lupin's own key-loading helper) never passes the gate for that action. Today nothing records that this happened. The threat model accepts the act; it does not accept being blind to it.

**Problem 4: Secrets leak into places that persist and places that speak.** Everything a persona's engine prints goes into the kernel's per-persona session log, which the console and the web view read. Anything the persona says to the human goes to the notification system and may be read aloud on a phone. A confused persona that pastes its environment into a message has just logged and possibly spoken a vendor token. No gate rule can see this, because the secret is already inside the text.

**Problem 5: The current rule lumps three different acts together.** The destructive-act table from the approval design has one row, "secrets and credentials", set to block. It covers reading a key file, printing environment variables, and calling Lupin directly. Those have different legitimacy. Reading a key file is never a persona's job. Printing the environment is ordinary debugging. Calling Lupin directly is the daily work of the persona that is building the kernel on the test machine and of the tester role running smoke tests. One mode cannot fit all three, and a block that the tester trips ten times a day will get turned off.

**Problem 6: The kernel's own control socket has no authentication at all.** The kernel listens on a local socket for commands: spawn a persona, send it a message, dismiss it. File permissions are the only guard, and the personas share the file owner. A persona can dismiss a peer or inject a message into a peer's inbox over that socket, bypassing the ask rule that is supposed to cover dismissals.

**Problem 7: Persona identity is asserted, not proven, anywhere in Lupin.** This is the root of Problems 2 and 3 and of an older open item (server-side role checks). It is the one problem on this list that cannot be fixed cheaply, because the fix is a change to how Lupin issues and checks keys.

## Proposed solutions

Each solution names the problem it addresses, the alternatives considered, and a recommendation. They are independent; any subset can be adopted, though Solutions 1 and 2 only make sense together.

### Solution 1: Take the owner's password off the fleet host

*Addresses Problem 1.*

The listener that needs the owner's login only wants the owner's **user identifier**, so it can filter broadcasts to the right person. It logs in as the owner to learn a number. The kernel can be given that number directly: a `owner_user_id` line in the kernel's configuration, looked up once by the human from their own machine. The `[owner]` section of `~/.lupin/config`, with the password, is then never written on a host that runs personas. The kernel checks this at startup: if an `[owner]` section exists, or if the service account's email appears on Lupin's approver list, the kernel refuses to start and says why.

- **Alternative considered:** keep the password but restrict the file. Useless, because the personas run as the same user that must read it.
- **Alternative considered:** run the kernel as a different operating-system user from the personas. The real fix for the whole class, but it reopens the threat-model decision and touches how worktrees, sockets and logs are owned. Too large for this item; noted for a later revisit.
- **Pros:** closes the forgery path before it opens; one configuration line and one startup check; the old listener keeps working on machines that do not run personas, so nothing breaks during the transition.
- **Cons:** one manual step per host when setting up; a human has to find their own user identifier once.
- **Recommendation:** adopt. This is the urgent item. Without it, every other approval control in this document is decoration.

### Solution 2: Make approvals depend on things a persona cannot fake

*Addresses Problems 1 and 2.*

Two rules, one per kind of approver.

For a **human** approver: the ticket store accepts a yes only from a caller whose signed login token carries an allow-listed email. A yes posted with the fleet key is stored (Lupin already records how each answer was authenticated) but does not count as approval. Lupin already works this way for task approvals; the ticket store adopts the same two-door pattern. With Solution 1 in place, the only way to present an allow-listed email is to be that human.

For a **manager or chief-of-staff persona** approver: the kernel, not Lupin, decides who answered. A manager answers a ticket by calling a voice tool, and every voice tool call passes the gate with its arguments before the voice tool server sends it. So the kernel witnesses the manager's answer at the gate and records (ticket, persona, gate call). The approval check requires that record. A yes that appears in Lupin's ticket store with no kernel witness is ignored and logged as a direct call (Solution 4).

- **Alternative considered:** trust Lupin's "answered by" field for persona approvers. Lupin cannot distinguish personas (Problem 7), so this field is whatever the caller typed.
- **Pros:** no new Lupin code for the human case (the seam exists); the kernel already caches the tickets it opened, so the witness record is a field on something it holds; this is the "kernel authorizes" principle applied to answers as well as calls.
- **Cons:** the human rule is only as strong as Solution 1; the manager rule adds one more thing the gate records per approval.
- **Recommendation:** adopt both rules, written into the ticket store's contract and the gate's approval check.

### Solution 3: Split the one "secrets" rule into three, each with the mode its legitimacy deserves

*Addresses Problem 5.*

| New rule | What it matches | Mode | Why this mode |
| --- | --- | --- | --- |
| Credential read | A file read, or a shell command naming, any credential path: the key directory, `~/.lupin/config`, secure-shell keys, the engines' token files, cloud default credentials, private key files | **Block** | A persona never legitimately reads a key; its voice tool server does. Same class as "never touch the database" |
| Credential print | Shell commands that dump the environment or echo variables whose names look like keys or tokens | **Log only** | Ordinary debugging. Blocking it buys little; the real risk is the output landing in the log, which Solution 5 handles |
| Direct call | A shell command or web fetch aimed at a Lupin instance (the voice server, the destructive-test server, or the kernel's own socket), or carrying the key header or a key-shaped string | **Log only, per instance, per role** | Legitimate for the builder persona and the tester against the test server. The log line names which instance was hit and by which role, so the mode can be tightened per instance after a few weeks of evidence |

The third row also covers the kernel's own socket, which addresses Problem 6 as far as this item can: a log line, not a lock, because the socket has no authentication to lock with.

- **Alternative considered:** keep one row set to block. The tester and the builder trip it daily; a rule that is tripped daily by legitimate work gets switched off, and then it protects nothing.
- **Alternative considered:** block direct calls to the voice server only. Plausible end state, but the table of destructive acts was adopted with modes as a starting point to be revisited from evidence, and this should follow the same discipline.
- **Pros:** each rule's mode matches what the act actually is; the instance-and-role detail in the log is exactly the evidence needed to tighten later.
- **Cons:** three rules to maintain instead of one; the "direct call" rule is text matching, which is Problem 3's limit (next solution).
- **Recommendation:** adopt the split with these modes.

### Solution 4: Detect direct calls two ways, one now and one later

*Addresses Problem 3.*

**Now, at the gate:** pattern rules on the shell command, the fetch address and the file path, as in Solution 3. Catches the obvious case: `curl` with a key header, a port number, a key file name.

**Later, by reconciliation:** the voice tool server adds one identifying header to every call it makes (its own name, the persona, and the gate call that authorized it). Lupin's access log keeps that header. The kernel, which saw every gated call, can then compare: a request authenticated with the fleet key but carrying no gate reference came from somewhere else, whatever command produced it. This catches the script, the one-line program and the imported helper that pattern matching misses.

- **Alternative considered:** reconciliation only. It is the stronger detector but needs a Lupin change plus a kernel job that reads a server log, and it is not what the first build needs.
- **Pros of doing the pattern rules now:** no Lupin change; engine-neutral; same place as every other rule.
- **Cons:** pattern matching is visibility of the obvious case, not a detector; it must not be described as more than that.
- **Recommendation:** pattern rules now. Add the identifying header to the voice tool server now as well, since it is one line at four call sites, so that reconciliation can be built later without a second round of Lupin changes. Record reconciliation as a deferred part of this item rather than a new one.

### Solution 5: Scrub secrets at the two places the kernel writes

*Addresses Problem 4.*

The gate cannot stop a token from being read. The kernel can stop it from being copied. One redaction function, applied at exactly two choke points: the session log writer and the narration path that sends text to the human. It recognizes the fleet key format, Google and Claude token formats, signed login tokens, and private key headers, and replaces each with a marker that includes a short fingerprint, so two sightings of the same token are still linkable in an investigation without the token itself being present.

- **Alternative considered:** block the commands that print secrets. Does nothing for a persona quoting a secret it read in a file, or an engine error that echoes a header.
- **Pros:** about twenty lines; covers every path into the log and into speech, including the ones no rule sees; the console and web view inherit it because they read the log.
- **Cons:** a legitimate token inside an engine error message is redacted too. That is the intent.
- **Recommendation:** adopt. Under a confusion-not-malice threat model this is the control that matches the actual threat: a model pasting its environment into a direct message is exactly the confusion case.

### Solution 6: Give each persona its own key, as a new work item

*Addresses Problem 7.*

If the kernel minted one Lupin key per persona at spawn and revoked it when the persona is dismissed, Lupin could tell personas apart by credential rather than by what they claim. That would make the "who is acting" field truthful, close the older open item on server-side role checks properly, and let the fleet-state rules (reassigning another persona's task, dismissing a peer) be checked on the server.

Two honest caveats. First, Lupin checks a presented key by comparing it against every active key with a slow, deliberately expensive hash; today that is one key, and the comment in the source already calls it hundreds of milliseconds. Seventeen personas would mean seconds per call. Lupin needs a key-identifier prefix for a direct lookup first, which is a schema change. Second, per-persona keys do not stop a persona from reading a sibling's key off the same user account. They make the server's record truthful; they do not add isolation.

- **Pros:** the only route to proven persona identity; unlocks server-side checks that are currently policy only.
- **Cons:** a Lupin schema and middleware change; not needed for the first build; could be mistaken for isolation it does not provide.
- **Recommendation:** open it as a separate work item with the lookup-cost fix as its first task, and keep the single fleet key for the first build.

## Decisions requested

Six rulings, in the order they matter. Two facts were checked on the development server on 6 November 2026 with `src/captures/t32_credential_inventory.py` in the wrapper repository: `~/.lupin/config` has no `[owner]` section, and none of its sixteen per-project service logins is on Lupin's approver map (only the human's own account is). The same check is to be run on the test machine.

| # | Decision | Recommendation | If deferred |
| --- | --- | --- | --- |
| 1 | Remove the owner's password from fleet hosts; kernel configuration carries the owner's user identifier; startup check refuses to run otherwise (Solution 1) | Adopt now | The day an `[owner]` section is added to a fleet host, every approval in the system can be forged by reading one file, and nothing would notice. Cheapest item here, and the one the others depend on |
| 2 | Human approvals count only from a signed human login; persona approvals count only when the kernel witnessed them at the gate (Solution 2) | Adopt both | The approval step accepts a yes that anyone with the fleet key can write |

One dated specification carries the rule definitions, the redaction patterns and the startup checks.
