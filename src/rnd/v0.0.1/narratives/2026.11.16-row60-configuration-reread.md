# How the kernel reads `lupin-app.ini` again at each admission (row 60 of "Outstanding actions")

**As of:** 2026-11-16 (app timezone) · not a register item; it needs rulings, and is recorded under the turn-end policy decision (D62), part 10, as rows 26 and 57 were. This repo at `1973fa6`, lupin at `27e646d0ed` (its `lupin-app.ini` modified in the test VM's working tree, row 32). Every count, timing and behavior below was produced by a zero-token script, `src/captures/t15_configuration_reread.sh`, run on the test VM before this page was written; its output is `src/captures/out/t15-configuration-reread-lupin-host-test-20261116.txt`.

## In brief

The kernel decides whether a new persona may start (an *admission*) from a few numbers in lupin's settings file: the fleet's size limit, the per-call limit, the "skeleton crew" switch, the share of memory held back for the host, and each engine's memory reservation. Two ruled specs say those numbers are **read from disk again at every admission**, so that an operator moves a dial by editing the file and nothing has to be restarted. A third ruled spec says the kernel reads settings through lupin's ConfigurationManager, copied unchanged.

Those two requirements do not meet. The ConfigurationManager reads the file once, when it is first built, and hands the same object to every later caller; it has no way to notice that the file changed. Lupin itself works around this in three different ways, and the script shows that two of them break the manager when the file is caught in a bad state, and the third reads a different file from the one the manager means.

**Ruled 2026-11-16, and not all as recommended:** the kernel calls `init()` on the one kept manager, quietly and with its launch overrides, only when the file has changed; the loader's records are built again for the admission; the six admission keys are required and bounded; no design for a file that cannot be parsed. The table at the foot and the two sections before the glossary hold the rulings; the text between is as it stood when they were asked.

Five choices settle it. The recommendation, in one sentence: **at every admission the kernel builds a second, private ConfigurationManager from the file, checks it, uses it for that one decision and the persona it admits, and throws it away; the long-lived one is never touched, and a file that cannot be read refuses the admission, a wake included, without disturbing anyone already running.**

## Where the record stands

**What is required.** The fleet spec, Section 5: "The `kernel fleet …` keys are re-read from disk at each admission; no restart to move the dial." The host-capacity spec, Section 2: "The `kernel host …` and `kernel memory …` keys are re-read from disk at each admission, like the `kernel fleet …` keys." The turn-end policy spec's amendment of 2026-11-16 (rows 57 and 59): on that re-read a row that is incomplete or unreadable "refuses that admission with the key named and leaves running personas as they are", and the three single-valued `kernel memory …` keys "are re-read with the memory table at each admission and are checked there by the same rule". Its test Tables-4 (a memory key made unreadable on disk; the spawn refused; the key repaired; the next spawn admitted with no restart) runs with Kernel-1 and waits on this row. No other spec asks for a re-read: the kernel-lifecycle spec, Section 5, reads its own keys "once", and the engine sign-in spec says nothing either way.

**What an admission reads.** The check list (fleet spec Section 5, framework Section 10): the skeleton-crew switch, the per-call limit, the fleet limit, host memory, engine sign-in and quota. A *wake* of a hibernated persona runs the memory check alone, with a count of one (host-capacity spec, Section 2); refused, its message stays queued and the wake is retried on every pass of the memory sampler, every 15 seconds. A re-spin passes no admission.

**Who writes the file.** An operator with an editor today. In Phase 2 the kernel itself: `PUT /fleet/config` changes the fleet limit and the skeleton-crew switch (fleet spec, Section 3). Lupin's own writer replaces the file whole and atomically (`lupin_mcp/fleet_cap_ini_io.py:247–254`); an editor may not.

**What the ConfigurationManager does** (`cosa/config/configuration_manager.py`):

- The name `ConfigurationManager` is a wrapper that keeps one instance and returns it to every caller (lines 10–66, 105). The class behind it is reachable as `type( instance )`.
- Building an instance reads the file, resolves which block inherits which, applies defaults and the launch overrides, and loads the explanations file (`init`, lines 211–262).
- `init()` can be called again on the same instance. It throws the parsed settings away **first** (line 246) and reads afterwards (line 250).
- A caller may pass `_reset_singleton=True`, which deletes the kept instance and builds another (lines 43–53); its own documentation calls this a "special testing hook, not normal API" (line 31).

**How lupin reads fresh today: three ways.**

| Where | How | What the script found |
|---|---|---|
| `cosa/rest/routers/system.py:331, 336` (the administrator's reload route) | `init()` on the kept instance | not safe against a bad file; loses overrides; prints |
| `cosa/rest/notify_rate_limiter.py:104`, `lupin_mcp/cosa_voice_mcp.py:1213` | `_reset_singleton=True`, only when the file's modification time changed; on failure, the last good values | a bad file leaves the process with no kept instance |
| `lupin_mcp/fleet_cap_ini_io.py:156` (today's fleet limit; its header says the manager has "no mtime check and no reload path") | bypasses the manager: finds the one line that defines the key | ignores blocks and inheritance |

**How the manager behaves when read again** (the script's part (c), on a small fixture in a temporary folder):

| Probe | Result |
|---|---|

| `_reset_singleton=True` on the same file | raises; the old instance, if someone still holds it, reads `14`; **the next ordinary call raises too**, because no instance is kept |
| A second instance on the same file | raises; nothing else is touched |

| One key written twice in one block | raises `DuplicateOptionError` |
| One key in a child block and its parent | builds; the child's value wins |
| The file replaced atomically with identical bytes | a new inode and a new modification time |

## Problems and options

### 1. How a fresh read is taken

The kernel needs the file's present contents without endangering the object the rest of the kernel reads from.

**A. A second, private instance for each read (recommended).** The kernel builds `type( manager )( … )` with the same arguments the first was built with, checks it, takes what the admission needs, and drops it.
- For: safe by construction. The script shows a bad file raises and "nothing else is touched"; nothing is replaced until the read has succeeded, because nothing is replaced at all. The same blocks, inheritance, defaults and launch overrides apply as at the start, since the same code runs with the same arguments. The copied file stays unchanged, as D62 requires.
- Against: it reaches the class through `type( manager )`, because the module's name is the wrapper; one line that needs a comment. A launch override keeps winning over an edit on disk for the key it names (the same as at the start).

**B. `init()` on the kept instance,** as lupin's reload route does.
- For: one object; already in lupin.
- Against: a bad file empties the kept instance, so every later read anywhere in the kernel returns `None` until the file is repaired and read again. That is the opposite of "leaves running personas as they are". It also drops launch overrides and prints unless told not to.

**C. `_reset_singleton=True`,** as lupin's rate limiter and voice server do.
- For: a failed build cannot corrupt an instance somebody already holds.
- Against: after a bad file there is no kept instance, so the next ordinary call raises; code that held the old object and code that asks afresh then see different settings in one process. The manager's own text reserves the flag for tests.

**D. Bypass the manager and find the key's line,** as lupin's fleet-limit reader does.
- For: the cheapest read.
- Against: it does not know blocks or inheritance; 51 keys are already defined in more than one block, and a host's block overriding one kernel number is exactly what the row 57 ruling provided for. The memory table is many keys under a prefix, not one line. It is a second reading of the file's meaning, where D62 says the manager is the only one.

**E. Add a reload method to the manager in lupin.**
- For: the right long-term home.
- Against: lupin is written on the development server only, and the Phase 1 kernel copies the file unchanged; it would be a lupin ticket that Kernel-1 then waits on.

**Recommendation: A.**

### 2. When the fresh read happens

**A. At every admission, unconditionally, inside the registry lock, before the first check (recommended).**
- For: it is what the two specs say, read literally. One read serves the whole check list and the creation of the admitted rows, so two batches cannot decide on different settings. Nothing is cached, so nothing can be stale: not a same-size replacement, not a changed environment variable that a value expands, not a clock with coarse resolution.
- Against: about 23 ms of the kernel's single thread per admission on the test VM. Spawns come a few per hour. A deferred wake retries every 15 seconds, so each waiting persona costs about 0.15 percent of the thread while it waits.

**B. Only when the file has changed** (compare inode, size and modification time first; 0.003 ms), as two of lupin's readers do.
- For: an admission that changes nothing costs nothing.
- Against: a second thing to get right for a saving nobody will feel. A failed read must be remembered and retried even though the file looks unchanged; the comparison must use all three fields; a value that expands an environment variable can change with the file untouched.

**C. A file watcher that reads on change.**
- For: the read leaves the admission path.
- Against: an atomic replacement gives the file a new inode, which drops a watch on the old one; a dependency or platform call for no gain over B.

**Recommendation: A.** If the admission path ever becomes hot, B is the fallback and changes no other ruling.

### 3. What the fresh read governs

The prefixes the specs name hold more than admission dials. `kernel fleet …` also holds the worktree root and the hibernation clock; `kernel host …` holds the host's class and the sampler's interval; `kernel memory …` holds the ratios at which a running persona is warned and re-spun.

**A. The admission and the persona it admits, and nothing else (recommended).** The fresh read yields one frozen record: the fleet limit, its maximum, the per-call limit, the skeleton-crew switch, the host's reserve ratio and floor, and the memory table (each engine's reservation, cap and heap). The check list reads it; the admitted persona is launched under its cap and heap. The three single-valued memory keys are checked in the same read, as ruled, and a bad one refuses the admission. Every other consumer (the sampler, the timers, the host class, the context-window table) keeps the values read at the start until the kernel restarts.
- For: one sentence states the rule: *the admission's dials move without a restart; everything else is read once.* Running personas are untouched in the plainest sense. No setting changes at a moment decided by whoever happens to spawn.
- Against: the three memory ratios are checked at each admission but take effect only at a restart; an operator who edits one sees a typing error caught at once and the new value applied later. An engine's reservation is charged from the fresh table to personas already running (host-capacity spec, Section 10: the sum reads the table, not the row), which is intended: it is how the dial moves.

**B. A good read replaces every setting the kernel holds.**
- For: one set of settings in force.
- Against: a reload as the side effect of a spawn. Intervals already handed to running tasks do not change, so the kernel would run on a mixture. The host class changing under a running kernel changes how it fails.

**C. A named list of live keys, applied kernel-wide on a good read:** the admission dials plus the two memory ratios and the re-spin window.
- For: the memory ratios move without a restart too.
- Against: a list to maintain and argue over; the sampler changes behavior when somebody spawns, not when the operator edits.

**Recommendation: A.**

### 4. A file that cannot be read at all, or lacks an admission key

The ruled refusal names a key. Three cases have none to name, and one has a key that is merely absent: the parser rejects the file (`ParsingError`, `DuplicateOptionError`); the block is missing because the file was caught half written (`AssertionError`); the file is gone; or the file was cut short in a way that still parses, which the script shows building "without error" with keys silently missing.

**A. The same refusal, extended (recommended).** Any failure to build the private instance becomes the ruled `ConfigurationError`, its `key` the file's name and its `reason` the parser's own message, which carries the line number. The six admission keys are required and bounded, like the nine ruled under row 59, with no default in code, so a file cut short shows as a named missing key: the fleet limit a whole number from 1 to its maximum; the maximum and the per-call limit whole numbers of at least 1; the skeleton-crew switch `true` or `false`; the reserve ratio at least 0 and below 1; the reserve floor a whole number of bytes, 0 or more. The same check runs at the start, where a failure stops the kernel (exit 78, as ruled).
- For: one rule for every way the file can be wrong. A dial that cannot be read never silently keeps its old value. A half-written file refuses one admission and the next read finds it whole.
- Against: the file is lupin's whole application configuration, 2,750 lines edited for many reasons; a stray line anywhere in it stops every spawn until it is repaired. (Lupin itself cannot start on such a file either.)

**B. Fall back to the last good read,** as lupin's rate limiter does, and log it.
- For: spawning continues through a bad edit.
- Against: it contradicts the ruled refusal for a bad row, or else splits it (refuse a bad row, forgive a bad file). The operator who just lowered the fleet limit and broke a line sees spawns admitted under the old limit.

**C. Refuse when the file cannot be read, but give a missing key its default from code.**
- For: fewer required lines in the file.
- Against: a file cut short would then admit under code defaults, and a misspelled key would be ignored; row 59 ruled against both for the other nine keys.

**Recommendation: A.**

### 5. A wake while the file cannot be read

A hibernated persona wakes when a message arrives for it, and a wake is an admission. If the file is unreadable at that moment, the rule of problem 4 refuses it.

**A. Deferred, exactly as a wake refused for memory (recommended).** The message stays queued; one `session.resume_deferred { reason: configuration }`; one line to the manager and one spoken line to the human, once and not on every retry; the sampler retries each pass and the wake goes through on the first pass that finds the file whole. Nothing is dropped.
- For: no new machinery: the host-capacity spec already defers, announces once and retries. One rule for spawns and wakes. The human hears at once that the settings file is broken, which also blocks a kernel restart and lupin's own start.
- Against: a persona with mail waiting stays asleep because of a typing error in a file that may have nothing to do with it.

**B. A wake that cannot read the file uses the last good record.**
- For: a persona already admitted once is not held up by a bad edit.
- Against: the last good record may predate the edit that lowered an engine's reservation or raised the host's reserve, so the wake is checked against numbers the operator has replaced; and it is the fallback problem 4 argues against, admitted through a side door.

**C. A wake never reads the file; it always uses the record of the last successful admission.**
- For: the wake path costs nothing and cannot be blocked by the file.
- Against: the host-capacity spec says the keys are re-read "at each admission" and that a wake "runs the same check"; a memory dial moved to relieve a full host would not reach the wakes that fill it.

**Recommendation: A.**

## What follows without a decision

- The private instance is built with `silent=True` and the kernel reads it through `get_keys()`, so a re-read prints nothing (the script: 26 lines otherwise).
- The kernel keeps the arguments its first ConfigurationManager was built with, and uses them for every later build. The file's path and the block cannot change while the kernel runs.
- The read is synchronous and inside the registry lock; the kernel is one asyncio process (Phase 1 spec, Sections 6 and 9), so no other task can see a read half done.
- The refusal reaches the caller as the existing `admission_refused`, its `detail.check` a new value, `configuration`, and its message `<key>: <reason>`; `fleet.refused` carries it. The control API's list of checks (control API spec, Section 4) gains the one word.
- `fleet.admitted` and `fleet.refused` already carry the numbers the decision saw; they are taken from the fresh record.
- Tables-4 no longer waits. Its reference implementation is a function of about twenty lines and its tests; the fixture is the script's.

Not settled here, and not needed by Kernel-1: how `PUT /fleet/config` writes the file in Phase 2 (which block it writes when a key is defined in two; whether it borrows lupin's line editor, which refuses such a key). It becomes a row of "Outstanding actions".

## After the first ruling

Rick ruled the first decision against the recommendation: the kernel calls `init()` on the one kept ConfigurationManager, unguarded. A second look at lupin, made at his word, confirmed that `init()` is the manager's refresh method and needs no flag (`configuration_manager.py:211`; the administrator's reload route calls it, `system.py:331, 336`). A probe on a fixture confirmed the three properties already in the table above, and one more: launch overrides survive when the caller passes them to `init()` again.

The ruling changes what the remaining decisions choose between:

- **What the call passes** becomes a decision of its own (1b): `init()` with no arguments prints 26 lines and drops launch overrides.
- **Decision 3** is no longer whether a good read replaces the kept settings; it does, for every reader, by construction. The choice is which kernel code reads the kept manager while the kernel runs.
- **Decision 4:** after a file that cannot be read, the kept manager holds nothing until an `init()` on a repaired file succeeds. Whether that harms anything already running depends wholly on decision 3.
- **Decision 5** stands as written, with the same dependence.

## After the third question

Put decision 3 in terms of a file that cannot be read, Rick answered: "I've been using this code for years and have never once had file corruption being an issue … Your effort far outweighs the importance, and even more the possibility of anything like this happening … let Lupin load and reload this file as often as it wants; it's not going to fail, unless the server itself is going up in flames." Taken as a ruling on scope:

- **No design for a file the parser cannot read, in this iteration.** An exception from `init()` is an ordinary kernel error. The "For" and "Against" lines above that rest on that case no longer weigh.
- **Decision 5 is withdrawn;** it existed only for that case.
- **Decision 4 is reduced** to its other half, a typing error rather than a broken file: whether the six admission keys are required and bounded.
- **Decision 3 is put again** on its remaining ground: how much of the kernel reads the manager while it runs.
