# Host capacity (T25): how many engine processes one machine holds, how the kernel knows, and what it does when memory runs short

**As of:** 2026-11-10 · **Author:** Rick (with Claude) · **Claude doc:** (link added at publication) · **Ruled as D60;** design of record `specs/2026.11.10-t25-host-capacity-spec.md`

## Why this matters

The fleet ruling (D59, 2026-11-09) made the kernel the one process that admits a spawn, and left one check in its admission list empty: *does this host have room for another engine process?* It also asked a second question it could not answer alone: an idle persona is hibernated after thirty minutes; should memory pressure hibernate a persona too?

The question is not academic. On 2026-08-22 the development server's kernel killed two Claude Code processes at 229 GB and 124 GB resident on a 251 GiB machine, taking about two dozen seats with them; the next day systemd's own killer struck twice more. Lupin's answer was a per-launch memory cap and a read-only watcher. Both are AH4L-shaped: the cap is composed inside a tmux launcher, the watcher finds its processes by scanning `/proc` for a command named `claude` and names the session by reading a sibling listener's command line. Under the kernel the engines are AGY and Jetski (`node`, not `claude`), there is no listener and no pane, and the kernel already knows every pid it started. The watcher's two hardest parts, finding the processes and naming them, disappear; what remains is the policy.

This item answers five questions: what "capacity" is counted in; where a persona's memory is measured; what the kernel does when one persona or the whole host runs short; what numbers to start with; and whether one machine holds the fleet, which was D59's revisit trigger.

## The principles this item rests on

1. **The kernel kills nothing by hand.** Where memory must be bounded, the operating system's cgroup does it; the kernel sets the bound, records the event and restarts. Lupin's watcher "kills nothing and notifies nobody" for a reason, and that reason survives.
2. **Admission is a reservation, not a measurement.** A healthy engine sits far below a gigabyte; a leaking one reaches the cap. Admitting on free memory would admit until the first leak, then refuse everything. The kernel charges each running persona a fixed reservation and refuses when the budget is committed.
3. **A per-persona bound and a fleet-wide bound are both needed.** One keeps a single runaway from taking its neighbours; the other keeps the fleet from taking Lupin, its database and the kernel. Neither alone does both. (Lupin's own finding: a slice-level cap *alone* kills the whole fleet at once.)
4. **A soft limit is not a kindness.** `MemoryHigh` throttles and reclaims instead of killing, which manufactures the sustained pressure systemd's killer selects victims on. Lupin removed it and pinned the removal in a test. It is not reintroduced here.
5. **The same remedy for the same disease.** A process whose memory grows without bound is cured the way a context window that fills is cured (D57): a re-spin through the memento handshake. One mechanism, two triggers.
6. **Measure once, in records, then set the numbers.** The 24 GB ceiling of August was a judgement; the 8 GB that replaced it was a ruling. Lupin's own advice, to run the watcher for a day and read the distribution, was never acted on. The kernel's records make that a query instead of a project.
7. **Engine-neutral names.** Nothing here carries `cc`, `claude_code` or `tmux`.

Consequences for the design: the pid the kernel holds for an AGY persona may be a thin parent whose memory lives in a child; a persona's memory is spread over the engine, its tool server and any MCP server it starts; summing per-process resident sizes double-counts shared pages; and a stop signal sent to the parent may never reach the child. All four argue for measuring and bounding the persona's **cgroup**, not its pid. "Keyed on registry pids", the phrase the TODO carried since October, is the wrong key.

## The problems, stated one at a time

**Problem 1: "capacity" has no unit.** The slot says "host capacity"; the TODO says "engine processes per VM, memory per AGY process". A process count is a proxy for memory; a memory figure needs a reservation rule and a host budget. Nothing says which, or how a 251 GiB server and a small test VM are described by one rule.

**Problem 2: the memory of a persona is not the memory of its pid.** The relaunch child, the tool server and MCP servers are separate processes; resident sizes double-count; `memory.peak` is missing on the development server. Lupin learned to group on the scope's anonymous memory and never sum RSS. The kernel has no equivalent yet.

**Problem 3: nothing says what happens to a persona whose memory grows.** The cap kills at 8 GB with no warning the kernel sees; the transcript's last turn is lost; the row's process is gone and the crash rule restarts it cold on the next message. The context-pressure ruling has a gentler path for the analogous disease and it is not wired to this one.

**Problem 4: nothing says what happens to the host.** Admission refuses new spawns when the budget is committed, but a host can still run short through growth. The only idle rule is thirty minutes. D59 asked whether pressure should hibernate.

**Problem 5: the numbers are a judgement.** 8 GB is Rick's ruling for Claude on the development server. AGY and Jetski have no figure; the test VM has no budget; no reservation figure exists at all. The public record gives ranges, not a distribution, and the kernel's records will.

**Problem 6: the Node engines bound their own heap at a size that defeats the cap.** With `autoConfigureMemory` on, the engine chooses its heap limit from host memory, not from the cgroup it runs in; a heap runaway therefore dies by SIGKILL at the cap instead of by a legible V8 error on stderr. And the relaunch leaves a stop signal unforwarded.

**Problem 7: a hibernated persona wakes without asking.** D59 says a hibernated persona does not count against host capacity. Then its wake must re-acquire room, and the record does not say what happens when there is none.

**Problem 8: an uncappable host.** `systemd-run --user` needs a user manager (`XDG_RUNTIME_DIR`, lingering) and cgroup v2 delegation; a container or a minimal VM may lack them. Lupin launches uncapped with a reason. The credential ruling drew a line between `production` and `test` hosts that this item can reuse.

**Problem 9: the facts about the test VM are not in the record**, and D59's revisit trigger ("one machine cannot hold the fleet") cannot be evaluated without them.

## Proposed solutions

### Solution 1: Capacity is a memory budget, charged by reservation (Problem 1)

Three options:

| Option | For | Against |
| --- | --- | --- |
| **A. A memory budget and a per-persona reservation.** `budget = MemTotal − host_reserve`; each *running* (not hibernated) persona is charged `reserve_bytes` for its engine; a batch is admitted when `committed + count × reserve ≤ budget`. | One rule describes every host; the budget is read from the machine, the reserve from the engine table. The refusal says how many fit. Matches Principle 2. | Two new numbers (reserve, host reserve) that must be set and later re-set from records. |
| B. A process count, `max_processes` per host. | One number; nothing to measure. | A proxy with no relation to the machine. The number would be re-derived by hand from memory anyway. |
| C. Admit on `MemAvailable` now. | Reflects reality at the instant. | Admits until the first leak, then refuses everything while healthy personas hold 600 MB each; two batches a second apart both see the same free figure. |

**Recommended: A.** The fleet cap (14, ceiling 18) stays as the staffing bound; capacity is the second, machine-derived bound, and on a large host it never binds.

```python
# capacity.py — pure; the fourth admission check (framework Section 10.2)
def capacity_refusal( requested, engine, rows, host, table ):
    running   = [ row for row in rows if row.state not in ( "closed", "hibernated" ) ]
    committed = sum( table[ row.engine ].reserve_bytes for row in running )
    budget    = host.budget_bytes
    reserve   = table[ engine ].reserve_bytes
    fit       = max( 0, ( budget - committed ) // reserve )
    if requested > fit:
        return ( f"host capacity: budget {gib( budget )} GiB, committed {gib( committed )} GiB by "
                 f"{len( running )} running, {fit} more {engine} fit at {gib( reserve )} GiB each, {requested} requested" )
    return None
```

Rows in `provisioning` count as running (the admitted rows are created under the same lock, so a second batch sees them). The refusal names budget, committed, running, fit and requested, as D59's refusals name their census.

### Solution 2: One cgroup per persona; the kernel reads the cgroup, not the pid (Problem 2)

| Option | For | Against |
| --- | --- | --- |
| **A. One transient scope per persona** under one slice: `lupin-personas.slice/lupin-persona-<id>.scope`, started by `systemd-run --user --scope --collect -p MemoryAccounting=yes -p MemoryMax=<cap> -p MemorySwapMax=0 --slice=lupin-personas.slice -- <engine>`; the tool server and every MCP child inherit the scope. The kernel samples `memory.current`, `memory.stat anon`, `memory.events oom_kill` and, where present, `memory.peak`; otherwise it keeps the peak itself from samples. | The scope *is* the persona: no `/proc` scan, no command-name match, no resolvers; the relaunch child, the tool server and MCP servers are inside it; shared pages are counted once; the kill is attributable from `memory.events` before the process is reaped. The slice is the fleet-wide bound of Solution 7. This is the composition lupin already runs, minus tmux. | Needs a user manager on the host (Solution 8 covers the lack). |
| B. Sum resident size over the pid's descendants. | Works anywhere. | Double-counts shared pages (lupin's reducer refused to do this); misses nothing but measures wrong; no bound at all. |
| C. `/proc/<pid>/smaps_rollup` proportional set size over descendants. | Correct accounting without cgroups. | Slow per pass; still no bound; still has to walk a tree whose parent may be a shim. |

**Recommended: A**, with C as the measurement fallback where A is unavailable (Solution 8).

The watcher's three session resolvers, the listener argv map, the scope-name parser and the tmux pane lookup, are not ported. `parse_cgroup_path`, `read_scope_anon_kb` and the alert policy (`AlertTracker`: first crossing, then after a step of growth, re-arm below) are the parts worth keeping, as about sixty lines in the kernel.

### Solution 3: A persona under its own pressure is re-spun, as under context pressure (Problem 3)

Lines are ratios of the persona's **cap**, evaluated on every sample:

| Option | For | Against |
| --- | --- | --- |
| **A. Notice at 0.60 of cap, re-spin at 0.80.** `watch.memory line=notice` then `line=respin`; the respin line opens the D54 handshake with `trigger: memory` and tells the manager; manifest `memory.action: respin \| advise`, default `respin`; the cap itself (1.0) is the operating system's kill, recorded by the kernel as `session.oom_killed` from `memory.events` with the last sample, then the crash rule. | The memento is written while the process still answers; the new process starts at baseline; the cure the public record agrees on (a fresh process) is applied before the kill, not after. Same code path as D57. | A leak fast enough to go from 0.80 to 1.0 inside one sample interval is still a kill; the interval (15 s) bounds that. |
| B. Advise only (lupin's watcher philosophy). | Nothing automatic. | The kill still comes, uninvited, with the last turn lost. The watcher's "line before the kill" never worked (threshold above cap). |
| C. Interrupt the turn at 0.90 and kill ourselves. | Earlier than the cap. | D57 refused an emergency interrupt for context; the same reasoning applies; the operating system already does this better at 1.0. |

**Recommended: A.** A persona that has been re-spun for memory twice within `memory_respin_window_hours` (6) gets `action: advise` for the third crossing and an `alert`-level record: a leak that survives a fresh process is in the work, not the process.

### Solution 4: Host pressure shortens idleness; it never hibernates a busy persona (Problem 4)

This is D59's open question. Three options:

| Option | For | Against |
| --- | --- | --- |
| **A. Under host pressure, the idle-hibernation timer shortens** from `idle_hibernate_minutes` (30) to `idle_hibernate_minutes_under_pressure` (5); host pressure is `Σ memory.current over the slice ≥ host_pressure_ratio (0.80) × budget`, or PSI `some avg60 ≥ 25` on the slice; one `host.pressure` record per crossing, re-armed below 0.70; a busy persona is never stopped for memory, only re-spun by Solution 3. | Frees what can be freed without losing a turn; the human's idle personas go quiet sooner, which is what a human would do. New spawns are already refused by Solution 1. Hibernation is a state D59 already has. | Five minutes idle is still five minutes; a host that is short because every persona is busy gets no relief except Solution 3 and the slice bound. |
| B. Hibernate the longest-idle persona immediately on crossing. | Fastest. | Stops a persona that may be mid-thought between turns; a thirty-second gap is "idle" to a timer. |
| C. Nothing: the slice bound and admission are enough. | No new rule. | The slice bound is a kill; relief before it is cheap. |

**Recommended: A.** So the answer to the D59 question is: *memory pressure hibernates idle personas sooner; it does not hibernate a busy one.*

### Solution 5: Starting numbers, identical per engine, re-set from records (Problem 5)

| Quantity | Default | Why |
| --- | --- | --- |
| `cap_bytes` | 8 GiB for every engine | Rick's live ruling for Claude; the public record puts healthy AGY and Claude sessions under 2 GB and runaways at 8 GB and beyond; no evidence that the engines differ. Manifest override `memory.cap`. |
| `reserve_bytes` | 2 GiB for every engine | Idle 0.1 to 0.7 GB, working under 2 GB in both records; the tool server and MCP children are inside the scope and share the figure. Overcommit against the cap is deliberate: the slice bound holds the line. |
| `host_reserve` | `max( 4 GiB, 0.25 × MemTotal )` | Lupin, Postgres, the kernel, the operating system. On the development server: budget ≈ 188 GiB, 94 personas fit, the fleet cap binds first. On a 16 GiB VM: budget 12 GiB, 6 fit. |
| `heap_mib` | 0.75 × cap (6,144) for the Node engines; none for Claude | Solution 6. |
| notice, respin | 0.60, 0.80 of cap | Solution 3. |
| sample, log | 15 s; one `memory.sample` per persona per 10 min | Solution 9. |

```ini

host_reserve_floor_bytes = 4294967296
```

**After one week of `memory.sample` records** the reducer (lupin's `derive_cc_memory_peak`, ported to read kernel records, Phase 2) prints the per-engine distribution and the table is re-set; that is the "run `--report` for a day" that August recommended and nobody ran. Alternatives considered: reserve = cap (strict, no overcommit: 3 personas on a 32 GiB VM while using 3 GB) and no reservation at all (Solution 1 option C). **Recommended: the table above.**

### Solution 6: The Node engines are launched with the relaunch off and a heap below the cap (Problem 6)

| Option | For | Against |
| --- | --- | --- |
| **A. `GEMINI_CLI_NO_RELAUNCH=true` and `NODE_OPTIONS=--max-old-space-size=<heap_mib>`** in the engine's environment, heap at 0.75 of cap. | The pid the kernel holds is the engine; stop signals arrive (issue 25590 avoided); a heap runaway dies at 6 GiB with a V8 error on `engine.stderr` instead of a silent SIGKILL at 8; the cgroup remains the bound on everything the heap flag does not cover. | If a future version reads memory settings elsewhere, the environment is ignored; the C20 inventory (Solution 10) checks the process tree once. |
| B. Leave `autoConfigureMemory` on. | Nothing to set. | The heap limit is sized from the host, not the scope; the kill is always SIGKILL; the parent swallows signals. |

**Recommended: A.** On Claude the cap alone applies, as today; lupin found no heap flag in the bundle and the leaks are external. Whether the `claude` binary is a Node script or a compiled executable is one `file` call in the inventory.

### Solution 7: Two bounds, one above the other (Problem 4, Principle 3)

- **Per persona:** the scope's `MemoryMax=<cap>`, `MemorySwapMax=0`, no `MemoryHigh` (Principle 4), `oom_score_adj` 500 written by the kernel before exec so the operating system prefers an engine over the kernel, Lupin or Postgres.
- **Per fleet:** `lupin-personas.slice` with `MemoryMax=<budget>`, `MemorySwapMax=0`, set by the kernel at start (`systemctl --user set-property`). A fleet-wide shortfall is then a kill *inside the slice*, of the largest engine by the operating system's own choice, recorded as `session.oom_killed`; never a global OOM, never Lupin.
- **Never:** a cap on the user slice or on any unit the kernel does not own; lupin's test that the launcher never names them is ported.
- systemd-oomd, where active, acts on the slice's pressure as it sees fit; the inventory records whether it is present; no `ManagedOOM*` property is set in Phase 1.

No alternative is offered: this is lupin's live composition, lifted out of tmux, plus the slice bound lupin designed for ("which a single drop-in can later cap fleet-wide") and never applied.

### Solution 8: An uncappable host (Problem 8)

| Option | For | Against |
| --- | --- | --- |
| **A. Reuse `[host] class`.** On `test`: the persona starts without a scope, measured by proportional set size over its process tree (Solution 2 option C), with one `memory.uncapped { reason }` record and `capped: false` on the roster; admission still charges the reservation. On `production`: the kernel refuses to start a persona it cannot cap, as it refuses to start under a privileged account (D50). | Same shape as the credential ruling; lupin's "launch uncapped with a named reason" survives where it is harmless. | A test host under load behaves differently from production; the roster says so. |
| B. Always launch uncapped with a reason. | Lupin's rule as is. | A production host with a human's credentials and no bound is the August incident again. |
| C. Always refuse. | Simple. | Phase 1 on a container-shaped test host would be blocked by plumbing. |

**Recommended: A.**

### Solution 10: A hibernated persona's wake re-acquires room; the inventory before Kernel-2 (Problems 7, 9)

**Wake.** A wake runs the capacity check with `requested = 1`. Refused: the inbound message stays in the queue, one `session.resume_deferred`, one advisory to the manager, one spoken line to the human ("<name> is waiting for room on the host"), and the sampler retries the wake on every pass. Nothing is lost; nothing is overcommitted past the budget. Alternative, a wake always proceeds: simpler, but makes "does not count against host capacity" a lie on a full host. **Recommended: defer and retry.**

**Inventory.** `src/captures/t25_host_inventory.sh`, run read-only on the test VM and the development server, no model call: `MemTotal`, swap, kernel version, cgroup v2 controllers, `memory.peak` presence, whether `systemd-run --user --scope` works for the persona account (`XDG_RUNTIME_DIR`, `loginctl show-user … Linger`), `systemd-oomd` state, PSI availability, the `claude` binary type, the Node version behind `agy` and its default heap limit, and the engine's `advanced.autoConfigureMemory`. **C20**, one trivial headless AGY turn with `pstree -p`, confirms whether the relaunch child exists under the kernel's launch line, with and without `GEMINI_CLI_NO_RELAUNCH`; cost: two one-line prompts. Both go at the top of the RUNBOOK, before the destructive-test server, since the budget and the cap composition for the test VM come out of them.

**D59's revisit trigger.** On the development server 18 × 8 GiB = 144 GiB of caps fits a 188 GiB budget with room; one machine holds the fleet by any measure. On the test VM the fleet is the smaller of the fleet cap and `budget ÷ reserve`, known after the inventory. No second host; Section 10.6 stands.
