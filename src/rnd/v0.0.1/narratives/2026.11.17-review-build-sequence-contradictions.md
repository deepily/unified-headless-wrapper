# Five places the record disagrees with itself about the build sequence (an internal review, 2026-11-17)

**As of:** 2026-11-17 · written on the test VM under Antigravity, before any ruling · this repository at `b169357`, lupin at `27e646d0ed` (read-only) · the markdown file is the only copy.

## In brief

An internal reviewer drew a flow chart of the build phases from the status page and the framework, and in drawing it found five places where the record contradicts itself or no longer matches practice. Rick passed the review on with the instruction to check each against the latest commit first. This narrative is that check, and the decisions that follow from it.

**All five stand at `b169357`.** Three stand as the reviewer wrote them. Two are sharper or narrower than the review says, and the difference changes the options:

- The two meanings of "the move" are not in two documents but in one: the switch-over spec's own ruling says Phase 2 *begins* with it, and the same spec's checklist heading says it is the *end* of Phase 2. The checklist's first step is the code move itself, so the spec treats it as one event with two times, not two events with one name.
- The rule that lupin is written only on the development server is scoped, in the decision that states it, to the time before the move. The record does not forbid writing lupin on the test VM afterwards; it is silent. The ruling protocol and four open rows, two of them written today, repeat the rule without the scope.
- The split of the last gate into a half before the switch-over week and a half after it is already the spec's wording. Only the framework's chart and table flatten it.

The check also found a sixth thing the review did not: the two loader files at this repository's root tell *every* session opened in it to run the ruling protocol, and the Phase 1 builder will be a session opened in it.

Seven decisions are asked for (the review's second splits into where and who). None touches the kernel's design; all are about sequence, place and who.

## Problems and options

### 1. The move has two times

Recorded times: the start of Phase 2 and the end of Phase 2. The checklist makes it one event; the tests make that impossible, because the event's own steps are what Phase 2 builds.

- **Two names: the relocation, and the Move clock (the reviewer's recommendation, and mine).** The relocation is step 1 alone: the package goes into lupin and `lupin_compat.py` is replaced by imports. The Move clock is steps 2 to 6: the lupin wiring, closed by the inventory run at the end of Phase 2. Step 1 leaves the Move's checklist. *For:* both texts become true; no ruling is reversed; "needed by the Move" keeps the meaning most rows already intend (before the inventory run). *Against:* sixteen rows, ten specs and the table's "Naming-3 at the move" must each be read for which one is meant; a few (the configuration manager's copy left behind, anything the kernel must import on its first day in lupin) belong to the relocation.
- **One event at the start of Phase 2.** Strike "end of Phase 2" twice. *For:* one event, and it matches ruling 2. *Against:* steps 2 to 5 are weeks of work, so "the Move" would name a day on which most of its checklist is not done, and the inventory run would have no date.
- **One event at the end of Phase 2: Phase 2 is built in this repository.** *For:* one event. *Against:* contradicts ruling 2 and both code-location decisions; Phase 2's tests need the ticket store and the grant in lupin before the kernel is.
- **Leave it.** *Against:* sixteen deadlines stay ambiguous.

### 2. After the relocation the implementer must write lupin on the test VM, and nothing says it may

Two questions, asked separately in the walk-through: where, and who relocates.

*Where lupin is written in Phases 2 and 3.*

- **A writable lupin checkout on the test VM, on the dedicated branch (the reviewer's recommendation, and mine).** *For:* the implementer, the kernel and the destructive-test server stay on one host; the Phase 1 rule lapses by its own words, so nothing is reversed. *Against:* two hosts write one lupin branch, so the pull-and-rebase rule extends to lupin; the branch has to be named, since the VM's checkout is on lupin's working branch today; the protocol's unscoped sentence and rows 67, 75 and 80 need re-wording.
- **The implementer runs on the development server.** *For:* one writer host. *Against:* a kernel carrying a working persona on the development server before the Phase 4 shadow, against the switch-over spec's ruling 3.
- **The implementer writes patches on the test VM and a development-server session applies them.** *For:* the rule survives. *Against:* a human-paced relay inside every task; the implementer cannot run what it wrote against the lupin it changed.

*Who relocates.*

- **The outgoing Claude Code session, after the kit port and before the conventions gate (the reviewer's recommendation, and mine).** *For:* the gate's observed task runs in the code's final home; the session that built the package moves it. *Against:* the relocation then belongs to the end of Phase 1, so "Phase 2 begins with the move" and the convention-parity decision's "last job before the handoff" are both re-worded; that session needs lupin write access on the test VM a phase earlier.
- **The AGY implementer, as its first task after the gate.** *For:* the order on record stands. *Against:* the gate is passed in a tree that is abandoned the next day; a new implementer's first act is the riskiest mechanical change.

### 3. The chart puts the last gate before a week that its own proof follows

- **Name the two halves the spec already has, and redraw the chart from the table (the reviewer's recommendation, and mine).** "Gate G2, parity": every family green on both engine families and Switch-5, before the week. "Gate G2, soak": the soak passed, before the Delete. The table's one row becomes two with the switch-over week between them; the chart and the stale prose under it are redrawn. *For:* stopping AH4L gets a named go or no-go; it is the spec's own order. *Against:* one more gate name.
- **Redraw only.** Phase 4, the week, the soak, the Delete, with one gate. *For:* the smallest change. *Against:* the gate's tests and its proof stay under one name on either side of the week.

### 4. Nobody is named to build the Claude adapter

- **The AGY implementer builds; a Claude persona under the kernel tests or reviews once the adapter starts (the reviewer's recommendation, and mine).** *For:* one builder throughout; the Claude persona the switch-over week relies on is exercised a phase earlier. *Against:* one more persona to staff; its verdicts come through an adapter that has not yet passed its own acceptance, so Phase 3's exit cannot rest on them.
- **The AGY implementer builds, and nothing more is said.** *For:* what dogfooding implies. *Against:* Claude-specific behaviour is learned second-hand until Phase 4.
- **A Claude persona builds its own adapter once Kernel-1 to Kernel-4 pass on it.** *For:* the earliest real use. *Against:* the adapter must run before its builder can; two implementers.

### 5. Three decisions still describe planning on the laptop

- **Amend the three to match practice, and give planning and the builder separate clones on the test VM (the reviewer's recommendation, and mine).** `src/rnd/` is written wherever planning runs; "Planning stays in Claude" reads "planning runs on Claude models, under Claude Code or Antigravity"; two clones of one branch, each pulling before it starts. *For:* a planning session's uncommitted edits never block the builder's pull, nor the reverse. *Against:* two clones to keep level; the paths in the protocol's Section 1 change.
- **Amend the three; one checkout, disjoint paths.** The Phase 1 rule as written, on one host. *For:* nothing new to maintain. *Against:* one tree has one index: either side's uncommitted work stops the other's pull.
- **Planning returns to the laptop when the build starts.** *For:* the decisions stand as written. *Against:* gives up the native shell and the checkout beside lupin that moved it.

### 6. The loaders give every session the ruling protocol, the builder included

- **The root loaders stay for planning; the builder's clone carries its own (recommended, and it needs decision 5's separate clones).** The builder's instructions are the kernel-rendered layers and the convention kit, not this protocol. *For:* each session is told its own job. *Against:* the root files differ between two clones of one branch, so the builder's loader must live at a path the planning loader does not occupy, or be written by the kernel.
- **One loader that branches on the session's first message.** *For:* one file. *Against:* a builder's behaviour would hang on a sentence in a planning document.
- **Leave it; the builder's brief overrides.** *Against:* the loader's first line says "every session", and the user rules outrank a brief.
