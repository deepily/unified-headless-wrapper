# The control API contract (T09)

2026-11-11 · narrative for Rick's rulings. Claude doc: `https://claude.ai/artifact/Y6UxEs6dvCaMbydLgRh2gB`. Specification: `specs/2026.11.11-t09-control-api-contract-spec.md`. **All ten decisions were ruled as recommended on 2026-11-11.**

## In brief

The Lupin kernel has a list of routes but no contract: nothing yet says how it refuses, how its callers learn what it speaks, how a turn is stopped without a message, or what "status" returns. This item writes that contract. Ten decisions are requested, each with a recommendation.

The control API is the kernel's one door on the host: HTTP and JSON over a Unix socket at `~/.lupin/kernel/kernel.sock`, readable only by the persona account. Everything that tells the kernel to do something, or asks it what is going on, comes through it.

What is already settled and not reopened here:

- **The transport.** FastAPI on a Unix socket, no network port.
- **The staffing routes.** Spawn, list, dismiss, re-spin, reassign, harvest and the fleet dial were fixed with the fleet design.
- **The gate.** Every tool call an engine makes is checked at `POST /gate` before it runs.
- **No event stream.** Watchers read the log files; the API carries commands and snapshots only.
- **The kernel's own life.** Start, stop, restart and upgrade were fixed with the kernel lifecycle.

What is left is the part every route shares, plus two routes nobody has designed: the bare interrupt and the status reads.

## Where the record stands

Six kinds of program call the kernel, and the record treats them as one. Read in the design repository at commit `4dd8a67` and in Lupin at `82fdc0182`.

| Caller | Where it runs | What it calls | How long its code lives |
| --- | --- | --- | --- |
| The `lupin` command line | the fleet host, Rick's shell | everything | replaced at every upgrade |
| The hook shim | inside each persona, once per tool call | the gate only | a file in the persona's worktree, written at spawn |
| The persona's tool server | inside each persona, one long-lived process | spawn, dismiss, harvest, re-spin request, hold, topic, its own row | started at spawn, survives a kernel restart |
| Lupin's server | Lupin's container, the socket mounted in | the roster, one persona's row, the fleet dial | deployed on Lupin's schedule |
| The terminal console | Rick's laptop, over a forwarded socket | roster, send, interrupt, re-spin, stop | whatever the laptop checkout holds |
| Host scripts | the fleet host | status, the roster | the repository |

What the reading found:

1. **Refusals come in four shapes.** A full fleet answers 200 with `admitted: false`. A persona that cannot prove who it is gets a 403. A manager with live reports gets 200 with a status word. A missing voice becomes a state on the row. No caller can treat them uniformly.
2. **Nothing carries a version.** The health route returns the kernel's build version and nothing about the contract. Three of the six callers are not replaced when the kernel is.
3. **A restarted kernel inherits old callers.** Engines survive a restart by design, so their tool servers and shim files are the previous version's until the persona is next re-spun. The lifecycle design handed this question here.
4. **"The operator" is whoever leaves two fields out.** A request with no persona identifier is logged as the operator. Lupin, the console, a script and a confused persona all look the same.
5. **Interrupt exists only as a side effect.** The one way to stop a turn is to send an urgent message. The held-turn watch and the compaction rule both call an interrupt that no route exposes.
6. **An interrupted persona with owed work is poked back into it.** The turn-end rule sees an idle persona that owes something and sends a poke within 600 seconds. A stop that restarts itself is not a stop.
7. **The persona's row is defined in seven places.** Each design item added fields. No document lists the row a reader gets back.
8. **Slow calls sit under a 180-second ceiling.** Engines cut a tool call at 180 seconds (measured on AGY and Jetski). A batch spawn with engine vetting, or a dismissal waiting for a memento, can pass that. The model sees a failure and tries again.
9. **Per-persona switches have no door.** Six behaviours are ruled as per-persona settings (grades, the rider, pokes, the pressure action, the memory action, the held-turn action). One ruling says "through the control API"; the rest sit in the manifest, which is read only at spawn. One route exists, for the topic alone.
10. **A message to a persona that cannot run it has four answers.** Hibernated, waiting for room, crash-looping and closed are each handled in a different document, and the send route returns only a queue position.

## Problems and options, part one: what every route shares

### 1. How the kernel says no

**Problem.** Four refusal shapes mean four handlers in each of six callers. The tool server has the hardest job: it must turn a refusal into words a model can act on, and today it would be matching on English.

- **Option A, one error body and one rule (recommended).** Every refusal is `{ error: { code, message, retryable, detail } }` with an HTTP status by class. The rule: *refused before anything changed* is an error; *done, with an outcome worth reading* is a 200 with a status word. `code` comes from a closed catalogue of about twenty, and a unit test fails on a code that is not in it. `message` is one full sentence the tool server hands to the model unchanged. The command line maps classes to exit codes (0 done, 1 refused, 2 usage, 3 kernel unreachable).
    - For: one handler per caller; the model reads a sentence written once, by the kernel; `curl -f` and `raise_for_status` work.
    - Against: the fleet design's spawn reply changes (a full fleet becomes a 409 instead of `admitted: false`); a catalogue to keep.
- **Option B, always 200 with an `ok` flag.**
    - For: one parse path, no status-code debates.
    - Against: every HTTP tool reports success on a refusal; unlike Lupin's own routes.
- **Option C, FastAPI's default `{ detail: "…" }`, as Lupin does.**
    - For: no code; familiar.
    - Against: no machine-readable code, so callers branch on prose.

### 2. What a caller does while the kernel is starting or stopping

**Problem.** The socket exists before the kernel has taken its engines back, and a plain stop drains busy turns for up to 180 seconds. Engines in those turns are still making tool calls. Only the hook shim has a rule for an absent kernel.

- **Option A, three states and a budget per caller (recommended).** The health route reports `starting`, `ready` or `stopping`. While starting, everything else answers 503 `kernel_starting`. While stopping, reads, the gate and hold keep answering until the last engine has ended; routes that change the fleet answer 503 `kernel_stopping`. Each caller has a stated budget: the shim 30 seconds (already ruled) and it treats a 503 like a refused connection; the tool server 30 seconds, then a sentence to the model; the command line none, it prints the state; Lupin shows its last roster marked stale.
    - For: a draining turn can finish its work; no caller improvises.
    - Against: four small retry loops to write and test.
- **Option B, everything refuses during a stop, the gate included.**
    - For: simplest kernel.
    - Against: on a production host the shim denies after 30 seconds, so the turns being drained fail at their next tool call.
- **Option C, leave it to each caller.**
    - Against: this is how the shim's fail-open got written and then withdrawn.

### 3. How a caller learns what the kernel speaks

**Problem.** Three callers are not replaced when the kernel is: the persona's tool server, the shim file in its worktree, and Lupin. The laptop console is a fourth. None can tell whether the kernel in front of it still understands them.

- **Option A, one contract number, announced both ways (recommended).** An integer, starting at 1. Adding a route, a field, an enum value or an error code leaves it alone; removing, renaming or retyping raises it. The kernel reports `api_version` and `api_minimum` on the health route. Every caller sends `Lupin-Client: <name>/<build> api=<n>`. A request outside the supported range is refused with 426 `api_version_unsupported`, naming both numbers. Callers ignore fields they do not know. A contract test compares the generated schema with the last release and fails if something disappeared without the number rising.
    - For: one number; the kernel also learns who is out of date; additions cost nothing.
    - Against: "additive" is a discipline, held only by that test.
- **Option B, the version in the path (`/v1/…`), as Lupin's `/api/v2/…`.**
    - For: visible in every log line; two versions mount side by side.
    - Against: a bump edits every route string in six callers; says nothing about who is calling.
- **Option C, no version; everything ships together.**
    - For: nothing to build.
    - Against: it is not true; see the next problem.

### 4. Old callers in front of a new kernel

**Problem.** A restart leaves the engines running, on purpose. After an upgrade, every persona's tool server and shim file are the previous version's until that persona is re-spun. The lifecycle design left the rule to this item.

- **Option A, serve the previous version, then re-spin at leisure (recommended).** The kernel answers the current contract and the one before it. Each row records the contract its shim and tool server were rendered with. After a start, a persona on the older contract is marked `upgrade_pending` and re-spun through the memento handshake at its next idle moment, one persona at a time. A persona two versions behind is refused at the gate with a sentence saying so and re-spun at once. A re-spin always re-renders the shim and restarts the tool server.
    - For: the restart stays invisible, as promised; nobody runs old code for more than a working day.
    - Against: two sets of handlers for the length of one release; a memento turn per persona per contract change (about fourteen).
- **Option B, re-spin the whole fleet at any upgrade that raises the number.**
    - For: one version alive at a time.
    - Against: such an upgrade interrupts everyone at once and waits on every busy turn.
- **Option C, freeze the gate and tool-server routes for good.**
    - For: no machinery.
    - Against: the first mistake in the gate's contract can never be corrected.

### 5. Who is calling

**Problem.** A request with no persona identifier is "the operator". That covers Rick, Lupin, the console, a script, and any persona whose tool server left the fields out. Records cannot tell them apart and operator-only routes cannot be kept operator-only.

- **Option A, ask the operating system (recommended).** A Unix socket reports the calling process. The kernel reads that process's control group: a caller inside `lupin-persona-<id>.scope` *is* that persona, whatever its request says. Any other caller is logged under the name it declares (`cli`, `lupin`, `console`, `script`). Operator-only routes refuse a caller that sits in a persona's scope. The existing gate claims stay: they prove which call was approved, which this does not. On a test host that cannot make scopes the kernel falls back to the declared identifier and records `identity: asserted`.
    - For: identity is witnessed at no cost to the caller; omission no longer promotes a persona to operator. Tried today: about twenty lines, working against the current server library.
    - Against: not a security boundary (a process on the same account can move itself between control groups on purpose); it relies on one subclass of the server's connection handler, so the library version is pinned and tested.
- **Option B, a declared name only.**
    - For: one header.
    - Against: still an assertion; a persona is whoever it says.
- **Option C, leave it.**
    - Against: finding 4 stands.

## Problems and options, part two: the routes still missing

### 6. Stopping a turn without saying anything

**Problem.** The only interrupt is an urgent message, which costs a model turn and invites a reply. And a persona stopped mid-task still owes its work, so the turn-end rule pokes it back into the task within 600 seconds.

- **Option A, a bare interrupt that holds (recommended).** `POST /personas/{id}/interrupt { reason, hold_seconds = 900 }`. A busy persona's turn is cut by the engine's own mechanism, and the call returns at once with the tool call that was open; `?wait=30` waits for the persona to settle. A persona that is not busy answers `interrupted: false`, which is not an error. The interrupt places an operator hold over everything the persona owes, so no poke restarts it; the next message from a human lifts the hold. The next turn opens with the kernel's interrupt line, naming the cut call and the operator. The held-turn watch and the compaction rule use the same path. Callers: the operator and the console (a lone `!`); a manager's tool for its own reports comes with the crew layer.
    - For: a stop costs no tokens and stays stopped; one path for three users.
    - Against: one route and one more kind of hold; a held persona sits idle until someone speaks, by design, and the roster must show it.
- **Option B, no bare interrupt; send `!stop`.**
    - For: nothing to build.
    - Against: a turn spent to stop a turn; the model may argue; the poke still comes.
- **Option C, a `paused` state that needs an explicit resume.**
    - For: unambiguous.
    - Against: a new state through hibernation, wake and turn-end; a forgotten pause is a dead persona.

### 7. What "status" returns

**Problem.** The health route has three fields, `lupin kernel status` is five words in a runbook, and a persona's row gained fields in seven design items with no single list. Yesterday's oomd ruling added one more.

- **Option A, three reads for three audiences (recommended).**
    - `GET /health` answers without touching the registry: state, contract version and minimum, build version, process, start time. For probes, the shim and the one-kernel check.
    - `GET /status` is the operator's page: the previous run and how it ended, reattached and pending personas, crash loops; the host (class, capped, slice bound, oomd, budget, committed, pressure); the fleet by state against its cap; inbound sockets connected; jobs with last and next run; configuration hash; invariants. `lupin kernel status` prints it.
    - `GET /personas/{id}` returns the row of record: one table in the specification listing every field, its type, the design item that owns it, and whether callers may depend on it or it is diagnostic.
    - For: a probe stays cheap; one place defines the row; the laptop console and Lupin read the same thing.
    - Against: consolidating the row is an editing pass over seven specifications.
- **Option B, one health route carrying everything.**
    - For: one route.
    - Against: every probe takes the registry lock; the shim parses a page to learn one word.
- **Option C, no status route; the command line reads the registry file and the logs.**
    - For: no code.
    - Against: the laptop console has no files to read.

### 8. Calls that take longer than a tool call may

**Problem.** Engines cut a tool call at 180 seconds. A batch spawn that has to vet a new engine version, or a dismissal waiting for a memento, can pass that. The model sees a failed call, repeats it, and the fleet gets a second batch.

- **Option A, the row is the receipt (recommended).** Spawn, dismiss and re-spin answer within two seconds of the decision, with status 202 and the rows in `provisioning`, `dismissing` or `respinning`. The tool tells the model what was admitted and that it will be told the outcome; the kernel then sends the manager one kernel line per child as it becomes ready or fails. Callers that want to wait use `GET /personas/{id}?wait_for=idle&timeout=60`. The command line, Lupin and scripts may send an `Idempotency-Key`; a repeat within ten minutes returns the first answer.
    - For: nothing can reach the ceiling; no double spawn; no polling by a model.
    - Against: a manager learns outcomes one turn later; the first-cut spawn reply ("the idle row") changes.
- **Option B, stay synchronous and raise timeouts.**
    - Against: the 180 seconds belongs to the engines, not to us.
- **Option C, a separate operations resource (`/operations/{id}`).**
    - For: general.
    - Against: a second identifier for something the row already is.

### 9. Changing one persona's switches

**Problem.** Six behaviours are per-persona settings: spoken grades, the inbox rider, pokes, the action at the context line, the action at the memory line, the held-turn action. Only the grades ruling names the control API; the other five live in the manifest, so changing one today means a re-spin. The only route written is for the topic.

- **Option A, one patch route with a closed list (recommended).** `PATCH /personas/{id}` accepts `manager_id`, `topic` and a `settings` object holding exactly those six keys; any other key is refused by name. Each change is one `persona.setting` record with the old value, the new value and the caller. It takes effect at the next turn and is stored on the row over the manifest, so it survives a re-spin; null clears it. A persona may set only its own topic. The separate topic route written into yesterday's migration ruling is withdrawn before anyone builds it.
    - For: one route, one record, one rule; measurement switches flip without a re-spin.
    - Against: reverses a line that is one day old.
- **Option B, a route per switch.**
    - For: each is trivial and separately gated.
    - Against: seven routes and seven records for one idea.
- **Option C, no runtime door; edit the manifest and re-spin.**
    - For: the manifest stays the only truth.
    - Against: a memento turn to flip a switch; contradicts the grades ruling.

### 10. A message for a persona that cannot run it now

**Problem.** The send route returns a queue position. It does not say whether the persona is asleep, waiting for memory, stopped for crash-looping, or gone, and each of those is specified in a different place.

- **Option A, always take it unless the persona is closed, and say what happened (recommended).** The reply is `{ message_id, disposition, queued_position }`, with `disposition` one of `running`, `queued`, `waking`, `deferred_capacity`, `held_crash_looping`. A closed persona is a 409 `persona_closed`; an unknown one a 404; a body over 1 MiB a 413. `message_id` is the inbox ledger's identifier, so the sender can find the message in the log. An urgent message to a persona that is not busy is an ordinary message.
    - For: nothing is dropped, and the sender knows where it went; the console can print it.
    - Against: a message can wait behind a crash loop unless the caller reads the disposition.
- **Option B, refuse whatever cannot run now.**
    - For: the sender finds out at once.
    - Against: the sender must retry; breaks "nothing is dropped", ruled for deferred wakes.
- **Option C, leave the reply as it is.**
    - Against: finding 10 stands.
