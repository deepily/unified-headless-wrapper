# Lupin application changes (T27): problems, options, recommendations

2026-11-08 · Rick Ruiz · Claude doc: https://claude.ai/artifact/BeLcZsbGswrv6Kpu6eAMsR

## Why this matters

The wrapper is built so that agents keep calling Lupin's existing endpoints and Lupin stays the system of record (the control-path-not-data-path decision). That only holds if Lupin itself needs few changes, and this item is the complete list of them. Everything a persona does reaches a human through Lupin: a spoken line, a card, a document link, an ask waiting for an answer. If any of those paths silently misbehaves for a kernel persona, the operator loses attention or loses a message, and the whole point of the wrapper is to save operator attention.

Five earlier rulings each left one or two rows here instead of settling them in place, because each row is a change to the running Lupin application rather than to the kernel. This item gathers those rows, adds what reading the code turned up, and asks for one ruling per row so the Lupin side can be built in order after the kernel's first phase.

The work splits cleanly into three places: the Lupin server (four rows), the web client (three rows, all in the TypeScript multiplexer), and the mobile app (a sibling repository, mirrored later). One row turned out not to be a Lupin change at all and is proposed for re-homing.

## The principles this item rests on

1. **Lupin stays the system of record; the kernel gates and configures, it does not proxy.** Each persona's own voice server calls Lupin's REST endpoints directly. So a Lupin change is a change for every persona at once, and a kernel change reaches only kernel personas.
2. **Delivery is marked on receipt, never on a send attempt.** Lupin's late-answer handback already lives by this rule: its "delivered" mark is set only when the asking session confirms it has the answer. Any new delivery mark here follows the same rule, or it recreates the defect it is meant to fix.
3. **The kernel cuts nothing and rewrites nothing.** It measures the spoken line, logs the measure, and leaves length and rewriting to Lupin. Whatever Lupin does to a message must therefore be visible on the message, so the persona's log can tell what was said from what was delivered.
4. **A name never crosses a kernel interface; the eight-hex persona id does.** The sender id carries the engine as its local part (`agy@`, `jetski@`, `claude.code@`) and the persona id after the `#`. Client code that matches `claude.code` literally breaks the day the first `agy@` persona speaks.
5. **One client.** The TypeScript multiplexer replaces the legacy `notifications.js`; the cut-over is a one-line configuration flag that already exists. The legacy file gets no new work.
6. **Nothing here blocks the kernel's first phase.** Every row lands after it; the kernel ships with the documented workarounds (documents off on remote hosts, over-cap lines logged not cut, the voice gap as it stands under the current harness).

## The problems, stated one at a time

**Problem 1 — The voice gap is wider than the row said.** A human message typed while the kernel is down and a browser is open is lost: the row is marked by the browser's receipt, the listener's result is thrown away, and the only pull endpoint is keyed on the human, not the persona. The inbox ruling closed every other hole (answers and DMs are pulled on every connect) and left this one to a Lupin change.

**Problem 2 — Rewriter treatments are invisible to the recipient.** The DM rewriter can replace a sender's text with a distilled version. The sender's gate record holds the original and the recipient's inbox log holds what arrived, but nothing on the delivered message says a rewrite happened, which version of the rules did it, or by how much it shortened. Fifteen fields describing exactly that already exist and go only to a training corpus.

**Problem 3 — The spoken cap has a side door.** Lupin's 500-character spoken cap is enforced in the voice MCP server, which every persona uses for its own speaking tools. The kernel posts its own notifications over REST, and that door has no cap. The voice-out ruling made the kernel log length and cut nothing, deliberately, and left the enforcement point here. Without a decision the kernel is the one sender class that can speak past the cap.

**Problem 4 — A kernel host that does not share the Lupin filesystem cannot place a document.** The pyramid's third layer is a file under Lupin's `io/tmp/` or `io/write-ups/`. On the dev server and the test VM the kernel writes it directly. On any other host it would have to upload, and the upload route demands an admin JWT, which fleet hosts do not hold by design (the credential ruling). Today such a host runs with documents off.

**Problem 5 — The web client has one literal left and nowhere to show the engine.** The multiplexer treats any `#`-suffixed sender as a session, so the card renders. But the project label is derived by a regex anchored on `claude.code@`, so an `agy@` persona shows `UNKNOWN`. Nothing on a card says which engine or model a persona runs on, and the sender id carries the engine but not the model.

**Problem 6 — The client has no idea of a ticket.** The ticketed-asks ruling makes every ask a ticket that outlives one call: pending, answered, expired, escalated, and an answer that arrives after the deadline is refused with a notice naming the question. The tool-approval ruling adds a ticket kind with a rule, an approval key, and a greyed learner prediction. The client renders response cards with a countdown and knows `responded` and `expired`; it knows nothing of ticket ids, escalation, late answers, or approvals. The ticket store itself is a server row that is not yet built either.

**Problem 7 — The mobile app is a separate repository that nobody has read for this item.** It shares the notification shapes and must mirror the client rows, but it is not on this laptop.

**Problem 8 — One row is in the wrong register.** "Stop deploying `~/.claude/CLAUDE.md` to fleet hosts" is a change to planning-is-prompting's sync, not to the Lupin application. The persona-bootstrap spec already files it under the switch-over checklist; the status page filed it here.

**Problem 9 — Order.** Eight rows, three codebases, none blocking the kernel's first phase, two of them wanted for daily use the day the first AGY persona speaks. The item needs an order, not just a list.

## Proposed solutions

### Solution 1: Close the voice gap the way the late-answer handback was closed (Problem 1)

The late-answer handback is the model: a persona-keyed pull, a delivery mark set only on receipt, a separate acknowledgement. The voice gap gets the same three parts.

**Option A — Receipt-gated pull, mirroring `answers-owed` (recommended).** One new nullable column `listener_delivered_at` on the notification row (one migration; precedent `answer_delivered_at`). `GET /api/notifications/undelivered` gains an optional `job_id`: with it, the endpoint returns the human-to-persona rows for that job whose `listener_delivered_at` is null, oldest first, cursored on `created_at`, under the existing age cap, each as the same raw dict the live frame carries. The fleet key resolves to the human owner exactly as it does for `answers-owed`, so the recipient check passes. A new `POST /api/notifications/undelivered/ack` with a list of ids sets the mark. The kernel's order per message becomes stdin write → ledger → ack, which is the receipt the inbox ruling already named, and the kernel adds a `voice_cursor` as the third pull row on every connect. The six emit sites are not touched; the helper's `listener_delivered` result stays a log line.
- Pros: the mark is honest by construction; a kernel that took the frame and died before writing stdin still gets the message back; one contract for answers, DMs and voice; the ledger already de-duplicates the one possible replay.
- Cons: one extra POST per human message; a migration; the kernel gains a third cursor.

**Option B — Emit-based mark.** The six dispatch sites set `listener_delivered_at` when the helper reports `listener_delivered`; no acknowledgement.
- Pros: no kernel change beyond the pull.
- Cons: a send signal is not a receipt, which is the exact rule the handback code warns against; six sites to touch and keep in step; a frame accepted by a socket whose kernel dies a moment later is marked delivered and lost.

**Option C — Server replay on listener reconnect.** Extend the resume replay to `cc-listener-*` sessions.
- Pros: no pull at all.
- Cons: the inbox ruling already struck replay for listeners; the replay buffer is device-slot scoped and in memory; the kernel pulls answers and DMs anyway, so this would be a second mechanism for one job.

### Solution 2: Stamp the treatment on the message (Problem 2)

**Option A — `payload.rewrite`, five fields, written at delivery (recommended).** The DM router copies from the tutor's meta into the row's `payload` and onto the live frame: `rewrite: { applied, rule_version, chars_before, chars_after, outcome }`. `rule_version` is the tutor's own version string (`dm-tutor-1` today). `outcome` is the tutor's outcome word, so a reader can tell "did not fire" from "fired and refused" from "fired and rewrote"; `applied` alone cannot. The key is absent when no rewriter ran on that path. Any later rewriter on any path (Solution 3's cap included) writes the same key. The corpus row keeps its fifteen fields; nothing moves. No migration: `payload` exists.
- Pros: four fields the voice-out ruling asked for plus the one that makes them readable; reaches the recipient's log untouched because the kernel keeps `raw` verbatim; one key for every treatment.
- Cons: the stamp grows by one field over the ruling's text.

**Option B — Copy all fifteen `tutor_*` keys into `payload`.**
- Pros: nothing lost.
- Cons: fabrication-guard internals land in every recipient's log; the ruling asked for a stamp, not a corpus.

**Option C — A dedicated `rewrite` column.**
- Cons: a migration for one small object when a JSONB slot made for exactly this already exists.

### Solution 3: Lupin enforces the spoken cap for REST senders by routing, not rewriting (Problem 3)

The voice-out ruling's own phrase decides this: routing, not rewriting. At the MCP layer there is a model in the loop, so a rejection is a correction it can act on. At the REST layer the turn has ended; there is no one to correct, only a line to place.

**Option A — Lupin cuts at a sentence boundary, keeps the overflow, stamps it (recommended).** `/api/notify` measures the spoken text with the same function the MCP layer uses (a link counts as its label) under the same two configuration keys (value and kill-switch), for every caller whose `job_id` is a persona. Over the cap: the spoken text becomes its leading sentences up to the cap; the full original text is placed verbatim at the top of the abstract (creating one if absent) above a rule; `payload.rewrite = { applied: true, rule_version: "spoken-cap-1", chars_before, chars_after, outcome: "routed_to_abstract" }`. No word is changed, none is lost, the card shows the whole line one tap away, and the persona log can count it.
- Pros: one cap, one measure, one owner (Lupin owns length); no model on the path; the stamp from Solution 2 makes it attributable; every present and future REST sender is covered, not only the kernel.
- Cons: Lupin now alters the shape of a message it was asked to deliver; the first sentence may be an odd thing to hear alone (the per-turn `spoken_chars` log tells how often).

**Option B — Reject with 422 naming the measured length, and let the kernel repair.** The kernel re-posts with the first sentence spoken and the full line moved to the abstract.
- Pros: Lupin stays a pure deliverer.
- Cons: two round trips per over-cap line; the identical repair written a second time in the kernel; the kernel, which was ruled to cut nothing, now cuts.

**Option C — Tutor-style distillation on the notify path.**
- Cons: a model on the hot path of every spoken line; the DM tutor needed ten guards to be trusted; the voice-out ruling deleted a rewrite model for exactly this reason.

**Option D — Nothing; log only (status quo).**
- Cons: kernel personas remain the one sender class that can speak past the cap, indefinitely, by design.

### Solution 4: Open the upload door to the fleet key, for two folders (Problem 4)

**Option A — Same route, narrowed for key callers (recommended).** `POST /api/docs/upload` takes `require_api_key_or_jwt`. A JWT caller keeps today's admin behaviour unchanged. An API-key caller is confined: `dir` must be exactly `io/tmp` or `io/write-ups` (no subfolders, no project scope), the filename must match `yyyy.mm.dd-<8 hex>-<slug>.md`, `on_conflict` may be `refuse` or `rename` but never `replace`, and the existing size cap, credential check, atomic write and `view_url` apply as they stand. Every success logs the persona id from the filename beside the account. The kernel's `voice_out.documents` becomes `write | upload | off`, chosen at start: `write` when `lupin.root` is a writable path on this host, otherwise `upload`.
- Pros: one door, one set of guards; the narrowing is a few lines in the existing handler; Lupin's sweep keeps owning deletion.
- Cons: the route's role changes from admin-only to admin-or-fleet, which the route's own docstring and the auth requirements file must say.

**Option B — A new fleet-only route.**
- Cons: duplicates the atomic write and guard code; two doors to keep in parity.

**Option C — Keep documents off on remote hosts.**
- Cons: the pyramid's third layer vanishes on any host that is not the Lupin host, and an abstract over the spill threshold has nowhere to go.

### Solution 5: One regex, and the engine label travels on the message (Problem 5)

Two parts. The first has no real alternative; the second does.

**Part 1 — generalize `projectFromSenderId`.** The regex becomes `^[a-z][a-z0-9.-]*@([a-z][a-z0-9]*(?:-[a-z0-9]+)*)\.deepily\.ai`: any local part, same project capture. One line, one test with an `agy@` and a `jetski@` sender. The legacy `isCCSession` literal in `notifications.js` is left alone; that file gets no new work.

**Part 2, Option A — the kernel stamps `payload.engine` on every notification it posts (recommended).** `engine: { name: "agy", version: "1.4.7", model: "gemini-3.8-flash-high" }`, from the values the kernel already records at every spawn. The sender card shows a small label from the newest message's `payload.engine` when present; when absent it derives the engine name from the sender id's local part and shows no model.
- Pros: no server change; the data already exists on the kernel side; a persona that respawns on a new engine version shows the change on its next message.
- Cons: a few bytes on every post; the label is per message, so the card shows the latest, not a registry truth.

**Part 2, Option B — a server-side sender registry.** The kernel registers each persona at spawn; the clients fetch `/api/senders/{sender_id}`.
- Pros: one truth per persona; could later carry the voice-persona pool state that the switch-over migration item owes.
- Cons: a new table, endpoint and client fetch for a label; the pool store belongs to its own item and should be designed there.

**Part 2, Option C — encode the model in the sender id.**
- Cons: breaks the rule that the local part is the engine and the suffix is the whole identity.

### Solution 6: Tickets as a kind of action-required card, specified now, built after the store (Problem 6)

The ticket store itself (`/api/asks/{ticket}`: open, answer, wait, escalate, expire) is a server row of the ticketed-asks ruling and is not yet built. It must exist before the kernel's waiting-for-a-human state does anything, so it is a kernel-phase dependency, not a client one. What this item decides is the client's half and the wire shape the two halves share.

**Option A — Extend the existing response card (recommended).** Every ticket event arrives as a notification carrying `payload.ticket = { id, kind, state, deadline, approver, asked_by, question }` (kind `yes_no | choice | free_text | tool_approval`; state `pending | answered | expired | escalated`). The action-required widget keys its cards by ticket id when present and gains three things: the `escalated` state (the card moves to whoever the ticket now names, with the original question and who passed it on); the late-answer notice, shown when the answer call is refused because the deadline passed, naming the question as the ruling requires; and the approval card for kind `tool_approval` from the tool-approvals ruling (rule, persona, the normalized act, yes/no, an optional message, the learner's prediction greyed when present). Countdown, "answered in another session" and the mic row are reused as they stand.
- Pros: one place to answer, as today; the countdown and expiry logic exist; the wire shape is settled before the store is written, so the store emits what its consumer reads.
- Cons: the widget grows a kind switch; the approval card is a new template.

**Option B — A separate tickets pane.**
- Pros: a list view over every open ticket by persona.
- Cons: a second place to answer; can be added later as a view over the same payload if wanted.

**Option C — Defer the client entirely until the store exists.**
- Cons: the store's shape would be designed without its reader; the two would then be reconciled twice.

### Solution 7: The mobile app mirrors the client rows from the same payload (Problem 7)

**Option A — Mirror after the web rows land, same keys (recommended).** `payload.engine`, `payload.ticket` and `payload.rewrite` are the contract; the mobile app reads the same keys. A follow-up in the `lupin-mobile` repository, opened when the web rows are merged, read in its own session. No server shape may be web-only.
- Cons: the mobile app lags the web by one step.

**Option B — Defer mobile indefinitely.**
- Cons: asks and approvals are answered from the phone more often than from a desk; a ticket the phone cannot show is a ticket that expires.

### Solution 8: Re-home the mandates row (Problem 8)

**Option A — Move it to the switch-over checklist, where the bootstrap spec already put it (recommended).** It is a planning-is-prompting deploy change; Section 18 and this item drop it; the status page's wording is corrected.

**Option B — Keep it here with a note.**
- Cons: a Lupin-changes item carrying a non-Lupin change is the kind of drift the register exists to prevent.

### Solution 9: Build in the order the first AGY persona will feel it (Problem 9)

**Option A — By daily-use impact (recommended).**
1. `projectFromSenderId` regex (minutes; the first `agy@` card is wrong without it).
2. Voice gap: migration, `job_id` on the pull, the ack; kernel `voice_cursor`.
3. Spoken cap and the treatment stamp together (they share `payload.rewrite`).
4. Engine label: kernel stamps `payload.engine`; card reads it.
5. Upload door (needed only when a kernel host is not the Lupin host; none planned yet).
6. Ticket cards, after the ticket store.
7. Mobile mirror.
8. Flip `legacy notifications redirect enabled` at switch-over (a switch-over checklist step, not a build step).

**Option B — By codebase (all server rows, then all client rows).**
- Cons: the one-line regex waits behind a migration.

**Option C — By the date of the ruling that created the row.**
- Cons: ruling order is not use order.
