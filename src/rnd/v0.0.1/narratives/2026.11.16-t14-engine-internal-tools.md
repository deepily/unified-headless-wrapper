# The engines' built-in tools beyond the ones we grant (T14)

**As of:** 2026-11-16, revised the same afternoon after the Jetski results came in · written on the test VM under Antigravity, before any ruling · this repo at `dffad7d`, lupin at `aabadd221` (not read: the item concerns the engines, not lupin's code) · measured on AGY 1.5.9 (test VM) and Jetski 2026.11.13 (cloud workstation), one run on each.

## In brief

Every persona is launched with a short list of the engine's built-in tools that its role may use (run a command, read a file, write, edit, search the web). The question left open since 3 November was whether the Jetski family carries other built-in tools, in particular read-only ones for searching and listing, that ought to be added to that list. A capture was run on both engines today, and the vendor's own record (release notes, and on AGY the engine binary and a skill shipped beside it) was then read at no cost.

The answer to the question as asked is **no**. On neither engine can a further search or listing tool be given to a persona: the names are still accepted at launch, and the model never receives the tools. Jetski's release notes say why: the vendor retires a tool and keeps its name "accepted as a no-op" so that old persona definitions still load.

The captures raised four things nobody had asked, and all four hold on both engines:

1. **A launch that accepts a tool name proves nothing.** AGY accepted ten names and the model could use two by name; Jetski accepted twelve and the model could use three.
2. **One tool arrives without being granted.** `manage_task` reached the model in every launch on both engines. Our role table lists it among the tools a persona must never have, on the belief that it duplicates a Lupin service. It does not: it lists, inspects, feeds and kills the commands a persona has left running in the background.
3. **Through that tool a persona can type into a running shell** without the text passing any of the checks we apply to commands.
4. **Old tool names still work, and collide.** A list that carries both an old name and its current name stops the launch, on both engines.

One tool we grant today, the notebook editor, no longer exists on either engine. One tool exists on Jetski only (a search over skills).

Six decisions are requested. None blocks the Phase 1 build; the earliest any of them bites is the tool gate (Kernel-5).

## Where the record stands

Sources: the two capture runs (`src/captures/out/c17-agy-20261116T192214/` and `c17-jetski-20261116T193513/`; the raw frames of the second stay on the workstation), and a script that spends no tokens, `src/captures/t14_internal_tools_inventory.sh`, run on each host. Its outputs are `src/captures/out/t14-internal-tools-lupin-host-test-20261116.txt` and `t14-internal-tools-jetski-20261116.txt`. Every count below was produced by that script from the recorded frames, not taken from the capture's own verdict line, which overstates.

**What the capture did.** For each of 15 candidate names it launched the engine with a persona definition that allowed only that name. Where the launch was accepted, it launched again allowing that name and `read_file`, and asked the model to use the tool. A hook recorded every call the model made. Two controls (a tool known to exist, and a made-up name) behaved on both engines.

**What it found.**

| Outcome | AGY 1.5.9 | Jetski 2026.11.13 |
|---|---|---|
| Refused at launch | 5: `code_search`, `view_code_item`, `view_file_outline`, `skill_search`, `browser_subagent` | 3: `view_code_item`, `view_file_outline`, `browser_subagent` |
| Accepted at launch | 10 | 12 (the same ten, with `code_search` and `skill_search`) |
| … called by the model under its own name | 2: `generate_image` (`AspectRatio`, `ImageName`, `Prompt`; 76 seconds), `search_web` (`query`) | 3: the same two, and `skill_search` (`query`) |
| … an old name, for which the model was given the current tool | 2: `write_to_file` → it called `write_file`; `replace_file_content` → it called `edit_file` | 2: the same two names; the model reported having `write_file` and `edit_file` and, told to use only the old name, called nothing |
| … the second launch failed | 1: `view_file` beside `read_file`: `tool name conflict: multiple tools resolved with name "read_file"` | 1: the same name, the same error |
| … accepted, and the model said it had no such tool | 5: `grep_search`, `find_by_name`, `list_dir`, `read_url_content`, `notebook_edit` | 6: the same five, and `code_search` |

**`manage_task` arrives ungranted on both.** In every reply where the model stated what it had (5 on AGY, 8 on Jetski) it named `manage_task`, which no definition had allowed, beside the tools that had been allowed and nothing else. None of the other seven never-granted tools appeared.

**The list in the engine's first frame is not the persona's tool list.** Every launch, the refused ones included (27 on AGY, 29 on Jetski), printed one fixed list of tool names in its opening frame, whatever had been allowed: 60 names on AGY, 63 on Jetski (the three extra are `code_search`, `skill_search` and `moma_search`). On both engines the list contains `browser_subagent`, which a launch refuses, and lacks `read_file`, `write_file` and `edit_file`, which the model demonstrably has. It is neither the set of names a launch accepts nor the set the model receives. The kernel must not read it as either.

**What the vendor's record says.**

- *Retired names are kept as accepted names.* Jetski's release notes: the built-in `notebook_edit` tool "has been removed while remaining accepted as a no-op in custom agent tool lists so existing custom agents continue to load"; notebooks are now edited through a skill named `nbedit`. And: custom agents that list "the retired `view_file`, `write_to_file`, or `replace_file_content` tool names" are given `read_file`, `write_file` and `edit_file`. So both behaviours the captures found (a name accepted and nothing delivered; an old name delivering the current tool) are the vendor's stated policy, not accidents.
- *The search and listing tools.* Both engines' release notes say `find_by_name`, `grep_search` and `list_dir` were retired from the default set "while keeping them available to custom agents that explicitly list them" (AGY 1.2.7). **Both captures contradict the second half:** listed explicitly, they did not reach the model, on either engine. The likeliest reading, given the policy above, is that they have since become accepted no-ops; no release note says so.
- *What `manage_task` is.* AGY's binary carries the description the model is given: "Manage the background tasks of this conversation: 'list' the running tasks, check a task's 'status' and recent log output, 'send_input' to a running task, or 'kill' one." Both engines' release notes say it was given to "declarative agents" that have "not opted out of fundamental components, so a custom agent can list and kill its own background tasks" (AGY 1.1.13). That is why it arrives ungranted: the engine attaches it to every persona definition.
- *The opt-out.* Both engines' release notes describe a persona-definition field, `excludeDefaultComponents`, that, in Jetski's words, lets a definition "opt out of all default system prompt sections and built-in tools while selectively adding back desired tools" (AGY 1.2.1 says the same more briefly). Whether it removes `manage_task` has not been tried.
- *The vendor's own list of built-in names.* A skill shipped with AGY (`migrate-agent-settings`, lines 154 to 160), which converts another vendor's persona definitions, names six: `read_file`, `edit_file`, `write_file`, `run_command`, `manage_task`, `search_web`. It maps the other vendor's file search and file-name search to `read_file`, and its shell tool to `run_command` **and** `manage_task` together. Jetski does not ship that skill.

**What our own record says today.**

- The role table (`specs/2026.10.18-uhw-role-table.md`, Section 1) grants seven built-in tools across the seven roles, `notebook_edit` among them (to two roles), and names eight that are never granted because each duplicates a Lupin service. `manage_task` is among the eight. Its last line leaves one question open: which read-only tools join the reading row after this capture.
- A rule in the same table ("native duplicates") logs a would-deny whenever a never-granted tool is reached anyway. As things stand it would fire on every use of `manage_task` by every persona.
- The framework's tool-gate section already records that a command may outlive the tool call that started it, and that listing, searching and file-name matching all arrived through `run_command`, so the checks on command lines cover them.
- The launch validator (launch-per-persona spec) already refuses a tool name absent from a per-engine table. The engine-vetting rule already runs one short turn on an unseen engine version and compares the tools used with the adapter's table.

**Not established.**

- The argument names of `manage_task` as a hook sees them. (The session writing this was itself given the tool with `Action`, `TaskId` and `Input`; that is an observation on AGY, not a capture.)
- Whether `excludeDefaultComponents` removes `manage_task`, and what else it removes.
- Anything from Jetski's binary: the script found no readable text in it (the path is a launcher image), so the tool's description there was not read.
- What `skill_search` returns, and whether it writes anything. What `moma_search` is; it was not among the candidates.
- Whether a persona launched by the kernel would have Jetski's `nbedit` skill.
- Which model the Jetski run used is not in its pushed files.

## Problems and options

### 1. Whether any further tool joins a role's list

This is the question the item was opened for. The search and listing tools cannot be delivered on either engine. One candidate remains: `skill_search`, on Jetski only.

- **A. None joins, `skill_search` included. Searching, listing and file-name matching stay with `run_command`; fetching a page stays with `run_command` or `search_web`. (Recommended.)** *For:* it is what both engines deliver; the vendor's own mapping sends file search to `read_file` and nothing else; the checks on command lines already cover the route; the two engines keep one list. A persona's skills are supplied by the kernel, and a tool that searches the vendor's catalog would bring in skills the kernel never placed. *Against:* a reviewer searches through a shell rather than through a tool that cannot write.
- **B. Grant `skill_search` on Jetski to the roles that have web search.** *For:* it exists and works. *Against:* what it returns is unexamined; AGY refuses the name, so the role lists would differ by engine; it opens a second source of skills.
- **C. List `grep_search`, `find_by_name` and `list_dir` anyway, in case a version delivers them again.** *For:* costs nothing at launch today. *Against:* tools the gate has no shape for could appear without notice after an engine update; the persona's instructions would name tools it lacks.

### 2. What `manage_task` is to the kernel

It arrives ungranted on both engines, and the role table forbids it on a mistaken reading of what it does.

- **A. Accept it as the second half of `run_command`: move it out of the never-granted row, treat it as present wherever `run_command` is (every role), and give the gate a shape for it so its `kill` is seen by the same rule that sees `kill` in a command line. (Recommended.)** *For:* matches both engines and the vendor's mapping; a persona that leaves a command running can inspect and stop it, which the turn-end and watchdog logic assume is possible; the would-deny rule stops firing on normal work. *Against:* one more shape in the gate; its argument names must be captured first.
- **B. Remove it with the opt-out field in the persona definition.** *For:* the list of granted tools would again be the whole truth. *Against:* untested; the field also drops every default prompt section and built-in tool, to be added back one by one, effect unknown; a persona could start a background command and never stop it.
- **C. Leave it in place and deny every call in the gate.** *For:* no new shape. *Against:* the model is shown a tool that always fails; background commands become orphans.

### 3. Text sent to a command that is still running

`manage_task` can send input to a running task. A persona that has left a shell running can therefore type a command into it, and the text is not a command line, so none of the command checks (history rewrite, branch lock, kill, destruction outside the worktree) sees it. This is a route around the gate by accident, which is exactly what the threat model guards against.

- **A. The gate reads the text of `send_input` as a command line and applies the same rules. (Recommended.)** *For:* closes the route with rules that already exist; keeps the legitimate use (answering a prompt from an installer). *Against:* input meant for a program that is not a shell may occasionally match a rule and be held for approval.
- **B. Deny `send_input` for every role.** *For:* simplest; headless work should not depend on interactive programs. *Against:* a persona cannot answer a yes-or-no prompt and must kill and rerun; a new refusal with no AH4L precedent.
- **C. Allow it and log it.** *For:* no behavior change; data before a rule. *Against:* the destructive-act rules, which are the ones in force, would have a known gap.

### 4. Which tool names the kernel writes into a persona definition

The vendor calls the old names retired, still accepts them, and maps them to current tools; an old name beside its current name stops the launch on both engines.

- **A. The per-engine table holds current names only (`run_command`, `read_file`, `write_file`, `edit_file`, `search_web`, and `invoke_subagent` where the role table allows it); the validator refuses a retired name before launch, naming the current one. The gate's adapter keeps the old names as aliases for calls it sees. (Recommended.)** *For:* one vocabulary; the collision cannot occur; the error is ours and legible rather than the engine's. *Against:* a manifest written from older notes is refused until corrected.
- **B. Accept old names and translate them.** *For:* forgiving. *Against:* two spellings in manifests and logs for one tool; the translation table needs upkeep.
- **C. Pass names through and let the engine decide.** *For:* no table. *Against:* the launch failure arrives as an engine error at spawn, and a retired name that is now a no-op passes unnoticed.

### 5. A built-in tool that reaches a persona without a grant

`manage_task` shows the engines attach a tool the definition never listed, and a release can add another. The gate sees every call, and today lets through any call no rule matches.

- **A. The gate refuses a call to a built-in tool that is not in the adapter's table for that engine, with a reason naming the tool; the event is logged and narrated once per tool and engine version. (Recommended.)** *For:* a tool with no shape passes none of the shaped checks, so letting it run is the unsafe default; costs no tokens; the first use reveals it. *Against:* after an engine update a persona may be stopped on a harmless new tool until the table is amended; a refusal in force from the first day, where new rules normally begin by observing.
- **B. Log a would-deny and let it run.** *For:* consistent with how new rules start; no work is blocked. *Against:* the unknown tool runs unchecked until someone reads the log.
- **C. Nothing; rely on the vetting run.** *For:* no rule. *Against:* the vetting run sees only the tools one short turn happens to use.

### 6. A granted tool that does not reach the persona

The vendor retires tools and keeps their names loading as no-ops. `notebook_edit`, granted to two roles, went that way, and nothing in the kernel would have noticed: the launch succeeds and the persona's instructions promise a tool it lacks. It will happen again.

- **A. The vetting run for an unseen engine version asks the model, in the turn it already spends, to name its tools; the reply is compared with the names granted plus those known to arrive ungranted. One of the four core tools missing refuses the version; any other missing name is recorded as "not delivered on this version", narrated once, and left out of what the persona is told it has. (Recommended.)** *For:* no added launch; turns the surprise into a recorded fact per version; thirteen replies across the two engines stated the tool set consistently. *Against:* it rests on a model's account of itself; a longer vetting prompt.
- **B. A separate launch per granted tool, each asked to use it, as the capture did.** *For:* proof by use rather than by report. *Against:* six or more turns per engine version per host; `generate_image` alone took 76 seconds.
- **C. No check.** *For:* nothing to build. *Against:* found only when a persona fails at the task.

## What follows without a decision

- The role table's open line is closed and its note on the never-granted row corrected: seven tools, each duplicating a Lupin service; `manage_task` is not one of them (subject to decision 2).
- **The `notebook_edit` row leaves the role table.** The tool no longer exists on either engine; a notebook is a file, edited with the write and edit tools or through a command. Jetski's `nbedit` skill is noted and not adopted; whether a kernel-launched persona would even have it is unexamined. Say so if you want this put as a decision instead.
- `generate_image` exists on both engines and works when granted. No role is granted it today and none gains it: under the launch ruling a tool not listed is not given. On AGY it wrote its file to the engine's own data directory, outside the workspace. Say so if you want this put as a decision instead.
- `read_url_content` and `code_search` stay unlisted: accepted, not delivered.
- The kernel never treats the first frame's tool list as a persona's tools, and never treats an accepted launch as proof of a tool.
- The kernel always writes a tool list into a persona definition (it already does).
- The framework's tool map keeps the old-name column as aliases, now confirmed on current versions of both engines and in the vendor's notes, rather than carried from AGY 1.3.
- The capture script is repaired (row 53 of "Outstanding actions"): a name counts only when the hook saw it called; a substitute call and a second-launch error are reported; the first frame's list is recorded. It also captures `manage_task`'s arguments, which decisions 2 and 3 need before the gate is built.
- The release-note sentence about the three listing tools is recorded as contradicted by measurement on both engines, unexplained.
