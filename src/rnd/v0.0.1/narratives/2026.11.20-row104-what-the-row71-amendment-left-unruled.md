## Problems and options

### 1. The limits in the record of a spawn refused for a bad file

The record exists so that anyone can later see what a decision was made on. This decision was made on nothing from the file: the file was refused before the first check ran.

- **A. The three limits are empty (`null`); the four counts are written as usual; `refusal` names the key and the reason.** For: it is what the decision saw. A reader cannot mistake it for a refusal under a limit of 14. The last good limits are not lost; they are in the previous `fleet.admitted` or `fleet.refused` record. Against: a consumer of the record must accept an empty value in three fields that are otherwise always filled.
- **B. The last good limits, as the code holds them.** For: every record has the same shape; nothing to special-case. Against: the record shows limits the decision did not use and that the file on disk may contradict (the probe's 14 against 13), in the record whose stated purpose is to be trusted after the fact.
- **C. The last good limits and a marker saying they are stale.** For: the shape is kept and the reader is warned. Against: a ninth field that exists for one case, and a reader who misses the marker is misled exactly as in B.

**Recommendation: A.**

### 2. The words of the line to the manager

The manager is usually the one whose message caused the wake. It is waiting for a reply that will not come until something outside its reach changes. The line should say whose wake, why, that the message is safe, and what ends the wait; it should ask for nothing.

The form proposed, with a first clause shared by every reason:

```
<name>'s wake is deferred: the kernel's settings file has a bad key, <key>. Its message is kept, and it wakes when the file is corrected.
<name>'s wake is deferred: the host has no room for it. Its message is kept, and it wakes when room is freed.
```

The probe rendered the first for each of the eleven keys the reference fixture's loader reads: every one is two sentences, the longest 163 characters. It carries the key and not the loader's reason, as the line you hear does; the reason is in the log record of the refusal.

- **A. That form, worded now for the two reasons Kernel-1 builds:** a bad settings key, and no room on the host (Capacity-5 runs with Kernel-1). The two sign-in and quota reasons take the same form when Kernel-2 is near, as a new row. For: the builder has words for everything it builds first; the two later lines need a time in your time zone and a pool's name, which deserve their own look. Against: one more row.
- **B. The settings line only.** For: the narrowest reading of row 104. Against: the builder reaches Capacity-5 in the same gate and has no words for it.
- **C. All four now.** For: closed once. Against: the two engine lines would be worded here without the sign-in and quota spec having been read for them.

**Recommendation: A.**

### 3. How the line reaches the manager

- **A. A `kernel` block in the manager's inbox, not urgent, headed `[kernel HH:MM:SS report deferred <id8>]`, the sentence of decision 2 as its body; a persona with no manager tells you by one `priority: low` card.** This is the stalled report's form. For: a manager is a model, and a model learns things only from its inbox; a card on your screen tells the manager nothing, and it is the manager that is waiting. One defined precedent, no new machinery. Against: the manager spends a turn on a line that asks nothing of it. And a hibernated manager's line is itself an inbound message: under a bad file its wake is deferred too, and its own manager is told, up to the chief of staff, which by its default template never hibernates. That chain is at most as long as the fleet is deep and each persona is reported once.
- **B. A notification card to you (`type: info`, `priority: low`), nothing in any inbox.** For: no model turn is spent; it matches the vocabulary the specs use. Against: "the manager is advised" then means that you are; for a bad settings file you already hear one spoken line, so the cards add one per deferred persona and tell you nothing new.
- **C. Leave the channel as a row of its own, and rule only the words here.** For: the same question stands behind four other such lines (context pressure, a compaction, a persona idle for a day, the branch probe at dismissal) and could be ruled once for all. Against: Kernel-1 then waits on another ruling; Pressure-2, which runs with Kernel-1, tests for "one `type: info` line".

**Recommendation: A,** for the deferred wake. Whichever is ruled, the four other lines get a row asking whether they follow it.

### 4. The reader's field names

Eight to settle: `manager`, `engines`, `reads`, `identity`, `configuration`, `refused_identity`, `refused_error`, `announced`.

- **A. Confirm all eight as written.** For: six are plain nouns; `announced` is the ordinary way to name a yes-or-no state (`if self.announced`); the twenty-four tests read `reads` and `refused_error` and stand untouched. Against: `announced` is not a noun, and your rule's words are that fields are nouns.
- **B. Confirm six; rename the two that are not plainly nouns: `reads` to `read_count`, `announced` to `announcement_made`.** For: the rule holds to the letter; `read_count` cannot be taken for a verb. Against: `announcement_made` is longer and no clearer; the module and its tests are changed by script and rerun.

**Recommendation: A.** If the rule is meant to the letter, B.

### 5. Your naming rule and reference code written before it

- **A. The builder applies the rule as it copies:** a verb-less function in any spec's reference code is given a verb when it enters the kernel, a private helper that another module imports loses its underscore, and each renamed name is listed, old beside new, in `BUILD.md`. The specs stand as written. One sentence is added to the builder's loader. For: one instruction covers every spec, not only this module; nothing ruled is rewritten; you see the names at the stop that ends each step. Against: the builder chooses the names, and the kernel's names then differ from the specs', so the list in `BUILD.md` is the only map between them.
- **B. Planning renames the tables module's twelve now,** by script, in an appended section, the tests rerun: `build_context_key`, `build_memory_key`, `get_context_window`, `get_engine_memory`, `build_context_lines`, `build_memory_lines`, `get_required_value` and `parse_whole_number` (both made public), `_select_under`, `_parse_fraction`, `_check_notice_below_respin`, `_align_lines`. For: you choose the names; spec and kernel agree for this module. Against: it settles one module of many, and the same contradiction meets the builder at the next spec.
- **C. The rule binds code first written after 2026-11-18; reference code is copied as ruled.** For: spec and kernel always agree; no renaming at all. Against: most of the kernel's first code would then be in the style you said you do not prefer, for good.

**Recommendation: A.**
