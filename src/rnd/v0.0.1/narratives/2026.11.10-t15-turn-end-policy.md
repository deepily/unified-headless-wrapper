# Turn-end policy: what a persona does when its turn ends (T15)

2026-11-10 · Rick Ruiz · Claude doc `https://claude.ai/artifact/2SKnEC5FbmbzpwZdzJkesV` · resolved as D62

## In one paragraph

When a persona's turn ends, something has to decide whether it is done, whether it still owes work, and whether anyone should hear about it. Under the current harness that decision is made by a hook that runs after every turn: it reads a task board, a hold file, the fleet roster and the session transcript, and either silently re-prompts the model ("do not stop yet") or lets it go idle. This item moves that decision into the kernel, which already owns the turn loop, the roster, the queue and the clock. **The recommendation:** the turn-end step becomes one small, pure rule in the kernel, run when a turn ends and again on a timer while the persona is idle. Its only inputs are things the kernel already holds or can ask the task store for: queued messages, owed rows in the store, live reports, open tickets, and a hold the persona declared through a kernel verb. Its only outputs are: start the next queued turn; send one poke as the next turn; or go idle and start the hibernation clock. Everything that repeats a standing instruction (goal lines, sweep orders, memento ticks), every file read, and the detached timer processes are deleted or moved to where they belong.

## What happens today when a turn ends

Read from lupin at `82fdc0182`: `stop.py` (2,446 lines) and sixteen leaf modules under `hooks/lib/` (about 9,000 lines together). Claude Code runs the Stop hook after every turn; the hook may let the model stop or block the stop with a reason, which the model then reads as its next prompt. The hook runs these steps in order, and the first that acts wins.

1. **Auto-narrate safety net** (speakerphone sessions only). If the turn ended without a `notify` call, the hook synthesizes one from the last assistant message so the console is never silent.
2. **Loop guard.** If this Stop is the re-fire after a block, allow it; never block twice.
3. **Voice wins.** If the voice buffer holds a human message, block the stop with that message as the reason, up to `MAX_STOP_BLOCKS`. Buffered peer DMs are delivered through the terminal and the stop is allowed.
4. **The owed-work oracle, then the poke.** Nine signals are gathered (table below), a hold file is read, and a pure five-step rule decides: a fresh, reasoned hold is honored; nothing owed means done; owed work under the poke cap blocks the stop with a reason that opens `Do not stop yet` and names what is owed; owed work at the cap allows the stop and posts one "max nudges reached" line. The poke cap defaults to **1** per idle episode and is reset by any human prompt. A runtime mute switch silences the poke without disabling the rest.
5. **The idle behaviour**, when nothing poked: `idle_announce` (the default in the fleet since 06-06) posts one low-priority card, "I'm <persona>. Idle, nothing owed."; `ask` arms a detached waiter process that sleeps 5, 10, 20, 40, 60 minutes and then asks "Anything else?" with a yes or no card; `none` does nothing. The waiter is killed by the next tool call, prompt, or session end.

Outside the hook, three more things touch the same question. The Notification hook's `idle_prompt` branch posts the same idle line and an "alive by idle" event the arbiter counts. The arbiter sends a directed poke to a session stuck mid-turn for 720 s (at most three per episode) and to a manager whose bridge file has not moved for 2,700 s. A server-side `HeartbeatPokerJob` wakes a list of recipients on a fixed cadence through the commons; it is a job, not the hook, and is out of scope here.

| Signal gathered at every Stop | Source read | Default | Finding |
| --- | --- | --- | --- |
| Own owed task rows | the session transcript, replaying `Task*` tool calls; the task store behind a flag | transcript replay (flag off) | D21 ruled the store is the only source; the flag was never flipped in the code read |
| Live un-reaped reports | bridge files on disk | on | a manager with workers out never idles |
| Unanswered inbound DMs | the DM topic, minus an acked-ids ledger | **off since 06-16** | the arbiter's own pokes counted as owed inbound and re-poked themselves |
| Manager look-in debt | a timestamp in the hold file, 600 s debounce | on | overrides a hold |
| Open user gates | rows in the hold file, with store deferral and a re-ask budget | on | overrides a hold; the ticket store (D37) now owns asks |
| Spin-up nudge (proactive manager, face A) | store backlog count, idle crew capacity, a hold timestamp | on | crew layer, Phase 2 under D51 |
| Gate re-surface (face B) | open gates and a hold timestamp | on | same mechanism as the look-in debt |
| Board-sweep gate | a per-persona JSON ledger with a frozen row set and a TTL | silent unless a ledger exists | a countdown the poke text carries |
| Memento verify tick | a daily ledger | once a day | a scheduled job riding on the poke |

**The hold** is `.heartbeat-hold-<session_id>.json`: `held_at`, `ttl_seconds` (default 900), a required `reason`, `work_owed`, `awaiting`, the gate rows and three debounce stamps. It is honored while fresh and reasoned. 1,512 lines exist to write, find (repo root, worktree, fleet data root, via the bridge) and prune it; a hold with an unusable TTL is poked forever and warns once.

**The poke text** is the owed specifics, a hold clause, then the role's goal line from `lupin-app.ini` (three sentences per role, repeated on every poke), then the sweep line, then the memento line. The event exhaust goes to `~/.claude/heartbeat-events/*.jsonl`.

## What the kernel already has

Most of what the Stop hook reconstructs from files, the kernel holds in memory or has already ruled on. Each row below is a reason this design is smaller than its ancestor.

| Already decided | What it gives the turn-end step |
| --- | --- |
| Inbound routing (D8) and one envelope per turn (D13) | The queue is the kernel's. "Voice wins" is no longer a buffer peek: when a turn ends, queued messages simply start the next turn. Nothing to block. |
| Owed-work source (D21) | The global task store is the only source of owed work; transcript replay and the mirror are retired. |
| Ticketed asks (D37, D49) | An open question to the human is a ticket in a store with a deadline, an approver and the escalation chain. The hold file's gate rows and re-ask budget are this, done once. |
| Inbox envelope (D52) | A `kernel` block already exists; the kernel contract is stated once, with no per-turn rider. A poke is a `kernel` block body; a goal line repeated per poke is the rider D52 ruled out. |
| Voice out (D28, D53) | Every turn's result is parsed and posted. The auto-narrate safety net has nothing left to catch. |
| Re-spin handshake (D54) | The kernel can ask the persona for a memento and respawn it with a trigger. |
| Log schema (D56) | A held turn (busy, open call past 600 s, no frame) is detected by the session and advised once. This is the arbiter's 720 s stuck poke. The kernel log replaces the heartbeat event exhaust. |
| Context pressure (D57) and host capacity (D60) | Re-spins on a line crossing, through the handshake. |
| The fleet (D59) | The registry knows every persona's manager (`manager_id`), state and `last_event_at`. "Live reports" is a roster query, not a bridge walk. Idle personas hibernate after 30 minutes; the kernel never retires one. |
| Broadcasts (D61) | A runtime switch with a per-persona override and per-delivery logging is the pattern for anything that can be muted. |

What the kernel does **not** have yet, and this item supplies: the rule that runs at turn end; a way for a persona to declare "I am waiting, do not poke me"; the poke's body, cap and reset; the re-check while idle that replaces the arbiter's manager-stale poke; and what the roster and the human see when a persona goes idle with work still owed.

## The problems

**Problem 1: the poke is a hook trick.** "Block the stop with a reason" exists because a hook cannot send a message; it can only refuse to let the model stop. The kernel writes the model's stdin. The question is what shape the poke takes, and when it is sent relative to messages already queued.

**Problem 2: nine signals, built over five months, each with its own source.** Three read files the kernel will not have (transcript, bridge files, hold rows). Two are off or never flipped. Two are a manager heuristic with a debounce stamp. One is a countdown ledger and one a daily job. Which signals mean "this persona owes work" in a kernel that already knows the store, the roster and the tickets?

**Problem 3: the hold is a file.** A persona that is legitimately waiting (on a review, on a human, on a long external job) declares a hold so it is not poked. Today that is a JSON file whose location took 1,512 lines to agree on, whose freshness depends on file mtime because agents have no clock, and whose rows became the place manager debounce stamps and gate rows accumulated. Under the kernel every persona has a worktree the kernel made and a registry row the kernel owns.

**Problem 4: the cap, the reset and the mute.** The poke cap is 1 by default, so in practice a persona is poked once per idle episode. The count resets on any human prompt, which the arbiter's escalations also triggered (the comment in `heartbeat_work_owed.py` records the loop). The mute is a settings file re-read per Stop. Who may mute, at what scope, and what resets the count?

**Problem 5: what idle looks like.** The "anything else?" ask and its detached waiter are dormant in the fleet; the idle announce posts a low-priority card every time any persona finishes a turn with nothing owed. The kernel has a roster, a console (D58) and hibernation (D59). What, if anything, should the human still hear when a persona goes idle?

**Problem 6: the poke carries standing instructions.** Every poke appends the role's three-sentence goal line, the sweep order and the memento line. D52 ruled that the kernel contract is stated once and the inbox carries identifiers; a reminder repeated per poke is the rider pattern. The sweep gate is a real need (a seat holding the board must iterate every row) expressed as a file the poke reads.

**Problem 7: pokes come from two places on two clocks.** The self-poke fires only at turn end. A persona that went idle with owed work and was poked once (the cap) is then silent until the arbiter, on its own 2,700 s clock and from its own reading of bridge mtimes, pokes it again through tmux or a DM. Two authors, two envelopes, two liveness clocks. D56 already took the stuck-mid-turn case.

**Problem 8: owed work and hibernation.** D59 hibernates an idle persona after 30 minutes. It did not say what happens when the persona is idle because it hit the poke cap with work still owed, or holding on a long wait. Does it hibernate? What does the manager see?

**Problem 9: the auto-narrate safety net and the liveness clock.** Two Stop-hook duties that are not policy: synthesizing a `notify` when the model forgot, and touching the bridge mtime so the arbiter counts the session alive. Both have kernel-native replacements (D53's result parsing; the registry's `last_event_at`) and need only to be confirmed gone.

**Problem 10: what the operator can tune at runtime.** Today: a settings file, three INI goal lines, an INI idle behaviour, arbiter thresholds in a deploy config. Which of these survive as kernel config, which as per-persona manifest fields, and which are gone?

## Options and recommendations

### 1. The poke's shape and timing

**Option A (recommended): the poke is a `kernel` block, sent as the next turn, only when the queue is empty.** When a turn ends the kernel first starts the next queued turn if there is one (D8). Only when nothing is queued does it run the owed-work rule, and a poke is then one envelope holding one `kernel` block: `[kernel HH:MM:SS poke owed N]` with a body naming the owed items by store id, ticket id and persona. If a message arrives while the poke is being composed, the message wins and the poke is dropped, not merged: queued human or peer traffic will itself end a turn and the rule runs again.
- Pros: one mechanism for every inbound thing (D52); no block semantics; the poke never delays a real message; the poke never stacks with one.
- Cons: a poke is a model turn, which costs tokens; the cap bounds this.

**Option B: the poke merges into the next envelope as an extra block.** Every envelope that starts a turn carries a poke block when work is owed.
- Pros: never a turn spent on the poke alone.
- Cons: every voice reply would carry a reminder; that is the rider D52 rejected, and it would poke a persona that is plainly busy answering.

**Option C: no poke; the manager or human asks.** The roster shows owed work; whoever cares sends a DM.
- Pros: zero kernel policy; zero token cost.
- Cons: this is the state the fleet was in before 06-04, and the reason the heartbeat was built: idle personas with owed rows went unnoticed for hours.

### 2. Which signals mean "work is owed"

**Option A (recommended): four signals, all from stores the kernel already reads, and nothing from files.**
1. *Owed rows*: the persona's own task rows in the store in an owed status (D21), one query.
2. *Live reports*: registry rows whose `manager_id` is this persona and whose state is not `closed`. A manager with reports out is not done.
3. *Tickets owed by this persona*: open tickets this persona raised (D37) whose re-ask is due, and open `tool_approval` tickets waiting on it as approver (D49, Phase 2 learner aside). This replaces the hold file's gate rows, the gate re-surface face and the per-user chase, because the ticket store already carries deadline, chase and escalation.
4. *Verification debt*: a manager with live reports and no look-in for `verify_after_seconds` (600). Kept, but the stamp is a kernel record (`turn_end.looked_in`, written when the manager reads a report's status through the control API or a kernel tool) rather than a timestamp the persona writes into a file.

Dropped: transcript replay (D21); unanswered inbound DMs (off since 06-16 and D52's ledger records delivery, not answers; a reply obligation is the DM protocol's business, T19 if ever); the spin-up nudge (crew layer, Phase 2 under D51; when it returns it is a fifth signal, not a second mechanism); the sweep gate and memento tick (problem 6).
- Pros: every input is a query against a store with an owner; nothing is reconstructed; a store outage reads as `unknown`, never as "nothing owed" (the O1 lesson stands).
- Cons: the verification debt keeps one heuristic; it is the only one with a receipt rule behind it.

**Option B: the owed rows alone.** One signal, one query.
- Pros: smallest.
- Cons: a manager whose rows are all delegated owns nothing in the store yet owes the fleet its attention; this is the v3 finding of 06-09 ("a supervising manager must never idle-announce while workers are out").

**Option C: port all nine as they are.**
- Pros: parity by construction.
- Cons: three read files the kernel has no reason to create; two are off; the gate rows duplicate the ticket store.

### 3. The hold

**Option A (recommended): a kernel verb, stored on the registry row, with a kernel clock.** The persona calls `hold( reason, ttl_seconds, awaiting )` (a kernel tool through the gate, like `ask`; default TTL 900 s, maximum 4 hours, a required reason) and `release()`. The kernel stamps `hold_until` from its own clock and records `turn_end.hold` with the reason. The rule honors a live hold except for an obligation override: a ticket of this persona's that is due, or verification debt, pokes through a hold exactly as today. The hold shows on the roster (`hold: { until, reason, awaiting }`) and in the console. No file, no search path, no mtime.
- Pros: the clock is the kernel's, so "agents have no reliable wall-clock" stops being a bug class; the hold is visible to the manager and the human; the three debounce stamps leave the hold because they were never the persona's to write.
- Cons: a persona under the current harness writes the file through a `write_hold` verb already, so the port is a rename for the persona; the arbiter's hold janitor (prune, misplaced-zone report) is deleted with the files.

**Option B: keep the file, read it from the worktree only.** Under D59 every persona has exactly one worktree the kernel knows, so the 1,512-line resolver collapses to one path.
- Pros: a persona can hold without a kernel tool.
- Cons: the file still carries an agent-supplied time or an mtime; it is invisible to the roster; the inventory's "keep the artifact; read at turn end" was written before D59 gave the kernel the row.

**Option C: no hold; a persona that is waiting is expected to say so in a ticket or a DM.**
- Pros: nothing to design.
- Cons: a persona waiting on an external job has no ticket to raise, and a poke mid-wait costs a turn and often a confused reply.

### 4. Cap, reset and mute

**Option A (recommended): a cap per idle episode of 1 by default, reset by a real inbound, a mute as a runtime switch with a per-persona override.** `turn_end.poke_cap` (default 1, manifest-overridable); the count resets when any `voice`, `dm`, `answer` or `broadcast` block starts a turn, never on a poke, and never on a kernel notice. The mute is `[turn_end] pokes: on | off` with a per-persona override through the control API (the D61 pattern), logged on every suppressed poke (`turn_end.poke_suppressed`). A cap reached is one log record and a roster field, not a notification.
- Pros: today's working numbers; the arbiter-escalation reset loop cannot recur because a kernel notice is not a reset; the mute is one switch in one place.
- Cons: a persona that genuinely stalls after its one poke stays idle with owed work; problem 7's re-check and problem 8's advisory cover that.

**Option B: no cap; poke on every idle re-check until the work is done or held.**
- Pros: never silent while owed.
- Cons: a persona that cannot finish burns a turn per tick; this is the loop the cap was added to stop.

**Option C: cap 3, as the arbiter's per-episode limit.**
- Pros: three chances.
- Cons: no evidence the second and third pokes do what the first did not; measurable later from `turn_end.poke` records, so start at 1.

### 5. What idle looks like

**Option A (recommended): no "anything else?" ask, no waiter; one idle line per episode, low priority, only when the persona was spoken to.** The ask and `idle_waiter` are deleted (dormant in the fleet already; the roster owns liveness). When a persona goes idle with nothing owed, the kernel posts one card at `priority: low` (never spoken) only if the episode began with a `voice` block, so the human who was talking to it hears it is done and nobody else does. Repeat idles in the same conversation post nothing. The roster carries `idle_since`, `owed`, `hold`.
- Pros: the console and roster are the primary view (D58); the human still gets closure on a voice exchange; the fleet-wide chorus of idle cards goes.
- Cons: a human watching only the web console sees one fewer line for crew personas; the console shows state anyway.

**Option B: keep `idle_announce` as today, one low-priority card on every idle.**
- Pros: parity.
- Cons: in a fleet of twelve it is a card per turn per persona; Rick accepted it as a courtesy ping before there was a console.

**Option C: silent idle.**
- Pros: nothing to configure.
- Cons: a human who asked a question and walked away gets no "done" unless the reply itself was spoken; usually it was, so this is close to A, but A keeps the edge case.

### 6. Goal lines, the sweep gate and the memento tick

**Option A (recommended): the poke body is the owed specifics and nothing else; the goal line moves into the role charter; the sweep is a store query; the memento verify is a kernel job.** The role goal ("manage, never build", "finish your assigned tasks") is a standing instruction, so it belongs in layer 2 of D47, rendered once at spawn from `role-goals.md`, where the kit already keeps the canonical text. The board sweep becomes a property of the store: a sweep is a set of row ids frozen at its start with a `reviewed` mark per row; the owed-rows query returns `sweep: { reviewed, total }` and the poke body carries that count. The daily `memento_io.py verify` runs as a kernel scheduled job (`kernel.jobs`, T08) and alerts through the log, never through a persona's prompt.
- Pros: the poke says only what changed since the contract was stated (D52); the sweep count is persona-scoped by construction and cannot go stale in a file; a verification job that depends on some persona ending a turn was never a schedule.
- Cons: the sweep needs one store change (a sweep table or a row flag) on the T19 list; the goal-line INI keys are deleted, so retuning the wording means editing the kit, not a config line.

**Option B: keep the goal line on the poke, as a kernel config string per role.**
- Pros: live retuning, as today.
- Cons: the rider pattern; three sentences per poke per persona per episode, read by a model that already holds them in its system prompt.

**Option C: keep the sweep ledger as a kernel-owned file.**
- Pros: no store change.
- Cons: a second owed-work source beside the store, which is what D21 closed.

### 7. One poker, two triggers

**Option A (recommended): the same rule runs at turn end and on an idle timer; the arbiter's stale pokes retire.** The owed-work rule is one pure function. The kernel runs it when a turn ends with an empty queue, and again every `turn_end.recheck_seconds` (600) while the persona is idle, hold expiry included. A re-check that finds work owed and the cap not reached pokes; at the cap it writes `turn_end.cap_reached` once and leaves the persona idle with `owed: true` on the roster. The arbiter's stuck poke (720 s) is D56's held-turn advisory; its manager-stale poke (2,700 s) is this re-check; both arbiter paths, their tmux wake and their bridge-mtime reads go to the T19 deletion list. Liveness is the registry's `last_event_at` from the engine stream (D56), never a file touch.
- Pros: one author of pokes, one envelope (`kernel` block), one clock; the roster says why a persona is idle; a hold that expires is noticed within one tick.
- Cons: a persona hibernated under D59 is not re-checked (its process is stopped); problem 8 says what happens instead.

**Option B: turn end only, no timer; the manager pokes by DM.**
- Pros: no timer in the kernel.
- Cons: the manager-stale case returns in the manager's own hands; a manager is a persona with the same failure modes.

**Option C: keep the arbiter as the second poker, on the kernel roster.**
- Pros: the arbiter code exists.
- Cons: two authors and two envelopes for one question; the arbiter's section is already on the T19 list under D57.

### 8. Owed work and hibernation

**Option A (recommended): hibernation does not wait for owed work; the row says so and the manager is told once.** An idle persona hibernates after 30 minutes whatever it owes. If it hibernates with `owed: true` or a live hold, the kernel writes `session.hibernated` with the owed count and hold, and sends the manager one `kernel` block (`[kernel HH:MM:SS report idle <id8> owed N]`) through the manager's own inbox, which is itself owed work for the manager under signal 2. The next inbound message, a manager's DM included, wakes it (D59) and the first turn-end re-check runs on that wake. A persona with no manager (chief of staff) reports to the human as one `priority: low` card.
- Pros: D59's "the kernel never retires a persona" and D60's host budget both hold; owed work is not lost, it is surfaced to the one persona whose job is to notice; no process is kept alive to be poked.
- Cons: a worker that stalled hard sleeps until someone acts; that is the manager's role under the role table.

**Option B: owed work defers hibernation.** A persona with owed rows stays running and is re-checked every tick.
- Pros: the persona is there when poked.
- Cons: a stalled persona holds 2 GiB of budget forever at the cap; the first thing D60 was written to prevent.

**Option C: owed work on hibernation triggers a re-spin.**
- Pros: a fresh context sometimes finishes what a tired one could not.
- Cons: a re-spin for a persona nobody is talking to is a token spend with no reader; keep re-spins to pressure, memory, operator and persona triggers (D54, D57, D60).

### 9. Auto-narrate and the liveness clock

**Option A (recommended): both confirmed gone.** Every result frame is parsed into the pyramid and posted (D53), so a turn cannot end unspoken; a model that returns an empty result gets the repair rule's `The reply is on the card.` line. Liveness is `last_event_at` on the registry row, stamped from every engine frame and every gate call (D56, D59). `_try_auto_narrate`, `last_autonarrated_turn_id`, the bridge-mtime touches in four hooks and `bridge_liveness_middleware` go to the T19 list. No alternative is worth an option here; this row exists so the deletion is a ruling, not an omission.

### 10. What the operator tunes

**Option A (recommended): one `[turn_end]` section in kernel config, four manifest overrides, nothing else.** Config: `pokes: on | off`, `poke_cap: 1`, `recheck_seconds: 600`, `verify_after_seconds: 600`, `hold_max_seconds: 14400`, `idle_card: on | off`. Manifest (per persona or role): `poke_cap`, `pokes`, `verify_after_seconds`, `hold_max_seconds`. Runtime: `pokes` per persona through the control API (D61 pattern). Deleted: `settings.json` `heartbeat` and `idle_detection` blocks, the three goal-line INI keys, `stop hook idle behavior`, the arbiter's poke thresholds, `heartbeat-poke-toggle.sh`.
- Pros: every knob has one home and one reader; the roster shows the effective value.
- Cons: the goal-line wording moves from INI to the kit (problem 6).

**Option B: keep the settings file for the heartbeat block, read by the kernel.**
- Pros: no config migration.
- Cons: a `~/.claude` path the kernel was ruled not to depend on (D47).

**Ruled 2026-11-10, one click each.** Decisions 1, 2, 4, 5, 7, 9 as recommended. ## Deleted, kept, left to others
