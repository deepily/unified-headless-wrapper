# The test VM's July global mandates: refreshed from the kit, or left to stand (row 93 of "Outstanding actions")

**As of:** 2026-11-21 · Not a register item; no decision row. Recorded, once ruled, under D45 (Phase 1 code location and write locations) as an amendment to the exit-criteria and switch-over spec, where rows 87 and 94 are recorded.

## In brief

The Phase 1 builder is a Claude Code session that will write the kernel in its own clone on the test VM. Besides its own loader it reads one file that every Claude Code session on that host reads: the global mandates, `~/.claude/CLAUDE.md`. The row 87 session ruled that the builder works under that file as the host has it, and noticed that the host's copy dates from July and differs from the copy in the convention kit (planning-is-prompting) beside it. It left the question to Rick: refresh the file, or say it stands.

This session read both copies by script. Three findings shape the choice:

1. **Nothing the kit's copy adds would change what the builder does.** The four rules the kit has and the host lacks concern worktrees, the shared stash, GPU tests and a manager's ten-minute tick; none meets a builder that works alone in its own clone, on code that touches no GPU.
2. **A refresh is not the builder's alone.** The file is read by six Claude Code projects on this host, five of them not this one, and one Claude Code session was live when the script ran.
3. **The kit's own sync tool refuses the job.** It will not write a single one of the 37 paragraphs that differ, because each carries a line the kit's copy lacks. A refresh therefore means replacing the file whole.

Three decisions are requested: whether the file is refreshed now; if it is, how; and whether the builder's loader names the two things the mandates ask for that it does not yet answer.

## Problems and options

### 1. Whether the host's global mandates are refreshed before the builder's first turn

The builder can start under the July copy or under a newer one. The difference, measured, is compression plus four rules that do not reach a lone builder in its own clone; the cost of a refresh falls on every Claude Code session on the host.

- **A. The July copy stands for the Phase 1 build; the refresh becomes a host chore of Rick's with no kernel gate (recommended).** Row 93 is struck as answered, and a new row records the refresh as owed by Rick at a time of his choosing, tied to no gate. *For:* the builder's behavior is the same under either copy, because every rule that differs in substance is either inapplicable to it (worktrees, GPU, manager tick) or enforced by a hook regardless (stash); nothing changes under five other projects and a live session; ruling 6's words, "as they are", are kept without a second reading; the builder's first turn waits on one thing fewer. *Against:* the builder carries about 7,500 more bytes of mandates in every session than it would under the kit's copy; the host stays four months behind the kit until Rick refreshes it; the builder reads the older, longer brevity section.
- **B. Refresh now, before the first turn.** *For:* the builder and every other session on the host read the current rules in their shorter form; the row closes with nothing left behind it. *Against:* a change to a file that five unrelated projects read, made for a builder it does not affect; the kit's sync refuses, so the file is replaced whole and the host's 332 lines not in the kit's copy go with it (they appear to be older wording rather than local additions, but only a reading of all 37 paragraphs would prove that); the copy installed may itself be behind the development server's.
- **C. Refresh at the convention-kit port.** Step 8 of the Phase 1 spec's order of work, after Kernel-8, is where the builder brings the kit in properly. *For:* the refresh lands with the work that exists to install the kit. *Against:* the port, as specified, concerns the kernel's own rendering of the mandates for its personas, not the host's `~/.claude/CLAUDE.md`; adding the host file to it enlarges a ruled step; and it is still a change under five other projects.

**Recommendation: A.** The measurement removes the reason to refresh for the builder's sake, and what remains is a host-maintenance choice that is Rick's to time.

### 2. If the file is refreshed, how

This decision is put only if decision 1 is ruled B or C, and is recorded as "not put" otherwise.

- **A. A whole-file copy from the kit's copy on this host, after a dated backup beside the file, typed by Rick from a RUNBOOK block (recommended).** *For:* it is the kit's own documented install; the backup makes it reversible in one line; the file is Rick's own configuration, outside this repository, so his hand on it is the right one. *Against:* installs a snapshot that may trail the development server's live file.
- **B. The same copy, run by the planning session on Rick's word.** *For:* one step fewer for Rick. *Against:* a planning session writing host configuration outside its repository, which no ruling has given it.
- **C. Rick copies the development server's live file across.** *For:* the newest text there is. *Against:* that file may carry content specific to that host; nothing here can check it first.

**Recommendation: A.**

### 3. Whether the builder's loader names the session manifest and the task store

Both copies of the mandates ask every session to keep a per-session manifest (`.claude-session.md`, written by a session-start command this repository does not have) and to open an item in the task store for every unit of work. The loader's sentence covers the ritual, the history file and the to-do file only. Left as it is, the builder decides for itself on its first turn.

- **A. The loader's "Conventions" sentence is widened by planning: the build log also stands in for the session manifest and for task-store items; the builder stages its own files by path, never `git add .` (which both copies already forbid) (recommended).** *For:* closes the spec's open question with a rule the builder reads at launch; keeps the build log the one record planning carries into the status page, as ruled; costs one sentence. *Against:* if row 95 shows the task store is reachable from the builder's session, Rick may want the builder visible there, and this sentence would then be changed again.
- **B. Leave the loader as it is until row 95 says what the session can reach.** *For:* no sentence written twice. *Against:* row 92, the first turn, may come before anyone returns to it; the builder would meet two mandates with no instruction.
- **C. The builder uses the task store and the build log both.** *For:* the builder shows on the fleet's board. *Against:* two records of what is owed, against the rule that the build log is the one planning reads; unproven that the store is reachable.

**Recommendation: A.**

### Corrections made during the walk-through (2026-11-21)

Decision 3 as written above, in "Problems and options", rested on a wrong premise: that the task store was optional for the builder. Rick corrected it twice before ruling.
