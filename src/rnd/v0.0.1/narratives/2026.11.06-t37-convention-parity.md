# Convention parity before the AGY handoff (T37): problems, options, recommendations

**As of:** 2026-11-06 · **Author:** Rick Ruiz (drafted with Claude) · **Work item:** T37, amending D40 (dogfooding) · **Audience:** a reader coming to the project cold · **Rulings:** all five adopted as recommended on 2026-11-06, decision D51; spec `specs/2026.11.06-t37-convention-parity-spec.md` · **Live copy:** https://claude.ai/artifact/NVtnUWYxAQRyLbzvvfh8eJ

## Why this matters

The plan hands the building of the kernel to an AI worker running under the kernel once eight acceptance tests pass. Those eight tests prove the plumbing works. None of them proves the worker will follow a single one of the working conventions that make a project manageable from the outside: how a session starts and ends, how work is planned and recorded, how tests gate a commit, how memory survives a restart, how a decision is put to the human. Without those, the operator is not managing a project; they are supervising an unfamiliar contractor by voice.

Some context for a reader coming in cold. The **Lupin kernel** is the host service that runs AI workers (**personas**) on any of three engines: Claude Code, Antigravity and Jetski. Until now every persona has run on Claude Code, and its behavior comes from a large body of conventions kept in a separate repository, **planning-is-prompting**: sixty-four workflow documents, forty-one slash commands, six skills, a global mandates file and thirty-three scripts. The operator manages a Claude Code project through those conventions: a session opens with a known ritual, work is tracked in a task store, plans are serialized to known paths, history and to-do files are kept, a commit needs green tests, and open decisions are walked through one click at a time.

The conventions are written for Claude Code's plumbing: its instruction file paths, its `/clear` command, its hook events, its native to-do tool, its plan mode, its question tool. An Antigravity persona loads none of that. The decision that hands the build to Antigravity was taken on 26 October, before the inventory of what the conventions depend on was weighed against it, and it names no test of convention-following. This document names the gap, sizes it, and proposes where the handoff should sit and what must be true before it.

The short version: keep the handoff, but put a second, short acceptance set in front of it that proves the conventions an implementer needs, port the plumbing those conventions rely on first, and let the Claude Code session that builds the kernel also build that port, since it is the only worker that already follows the conventions.

## The principles this item rests on

**The dogfooding decision.** Once the first-phase acceptance tests pass on the test machine, an Antigravity persona running under the kernel implements the kernel from the second phase on. Planning stays with Claude. The reason is cost and proof: Antigravity tokens are free on the work laptop, and a kernel that can build itself is the strongest demonstration that it works.

**The first-phase acceptance set.** Eight tests, Kernel-1 to Kernel-8: unit tests against fake engines; spawn a persona and see its registry row; send it a line and hear the reply; speak to it from the web client; interrupt it mid-turn; see one forbidden tool call denied; survive a server restart; stop and resume with memory intact. Every one is about the kernel. None is about the persona's habits.

**Skills on every engine.** Every slash command becomes a skill. The kernel installs each persona's skills into its workspace and expands a turn that begins with `/name` from that skill's text before the engine sees it, the same thing Claude Code's command loader does. This decision already provides the route by which conventions reach Antigravity; it does not yet provide the conventions in a form that route can carry.

**Six instruction layers, identical on every engine.** A persona's instructions arrive as the kernel contract, the role charter, the persona's own instructions, the format rules, the project mandates (through an `AGENTS.md` the kernel writes into the worktree), and a first-turn brief with the memento. This is the channel; what goes down it is the open item called persona bootstrap.

**Persona bootstrap is the second phase.** The build plan's second phase is "persona bootstrap and fleet on Jetski": assembling instructions per engine, the memento format, charter briefs, and the installer that deploys planning-is-prompting into a non-Claude workspace. That is the layer an implementer persona would need on day one of the second phase, and the plan has it as the second phase's output.

## What the conventions are

Read from the planning-is-prompting checkout at commit `9d8bf4f` on 6 November 2026, the same commit the October inventory read. Sixty-four workflow documents, forty-one commands, six skills, one global mandates file of 565 lines, thirty-three scripts. Not all of it is needed by a persona working alone on the kernel. The split below is the proposal's first substantive claim.

**Needed by a solo implementer (the convention kit).** The session ritual: `session-start`, `session-checkpoint`, `session-end`, with `history-management`, `todo-management` and `memento-management` behind them. Planning the work: `p-is-p-00`, `-01`, `-02`, `plan-serialization`, `rnd-directory-policy`. Doing the work: the code-style and post-edit-verification sections of the global mandates, `docstring-content`, `testing-baseline`, `testing-remediation`, `testing-harness-update`, `bug-fix-mode`, `branch-pr-and-merge`, `worktree-lifecycle`, `task-store-discipline`. Talking to the human: `cosa-voice-integration`, `cross-session-communication`, `brevity-mandate`, `decision-walkthrough` (the one-click ruling format), `last-call`, `push-to-completion`. About twenty-five workflows and their commands.

**Crew-level, needed from the second phase on.** The cascade review set (nine documents), the adversarial SWE crew set (`swe-team-spin-up`, `swe-team-roles`, `manager-autonomy`, `skeleton-crew`, `role-goals`, `priority-pull-policy`, `post-game`), fleet operations (`fleet-pause-resume`, `fleet-recovery`, `manager-context-monitoring`, `sword-of-damocles`), and the installers and housekeeping (`installation-wizard`, `uninstall-wizard`, `skills-management`, `claude-config-*`, `backup-*`, `loc-delta-global`).

**What the kit depends on that Antigravity does not have.** The October inventory counted the Claude-specific plumbing across the whole layer; the kit inherits most of it.

| Plumbing the workflows assume | Files (whole layer) | What it becomes under the kernel |
| --- | --- | --- |
| The voice tools (`spawn_sessions`, `dm_*`, `task_*`, `ask_*`, `self_respin`) | 53 | Already engine-neutral; no change |
| Slash-command invocation (`/plan-*`, `/p-is-p-*`) | 53 | The kernel expands the skill text before the engine sees the turn (decided) |
| `~/.claude`, `.claude/`, `CLAUDE.md` paths | 52 | Harness-owned paths, written per engine by the installer (not built) |
| `/clear` for a cold start or a rehydration | 18 | Respawn without the stored conversation, or respawn with the memento (decided in principle, not written) |
| Claude hook events (Stop, PreToolUse, SessionStart) | 15 | The kernel's turn-end policy and tool gate (turn-end policy is an open item) |
| Native to-do tools (`TodoWrite`, `TaskCreate`) | 6 | The task store (decided) |
| Plan mode | 5 | Antigravity has a plan mode; mapping unverified |
| `AskUserQuestion` | 4 | The voice `ask_*` tools (decided) |
| Scripts shaped for Claude's hook payload (three guards) and deploy scripts that target `.claude/` | 8 | The common tool shape and a per-engine deploy target (not built) |

The numbers say the port is not a rewrite of the conventions. It is a rewrite of the paths and the six Claude primitives they lean on, plus an installer that knows where an Antigravity workspace keeps skills and mandates.

## The problems, stated one at a time

One problem sits under the rest: **the handoff is scheduled before the thing it depends on is built.** The dogfooding decision triggers on the first-phase tests; the conventions an implementer needs are the second phase's deliverable. The six smaller problems follow from that.

**Problem 1: The gate proves plumbing, not behavior.** Kernel-1 to Kernel-8 would pass for a persona that ignores every convention. Nothing in the acceptance set asks the persona to start a session properly, record its work, run the tests before committing, or put a decision to the human in the agreed form.

**Problem 2: The conventions cannot reach the persona in their current form.** Fifty-two workflow files name Claude's instruction paths; eighteen use `/clear`; fifteen use Claude hook events; six use Claude's native to-do tool; five use plan mode; four use Claude's question tool. Delivered as they stand, the texts would instruct an Antigravity persona to do things it cannot do, and the persona would improvise.

**Problem 3: The installer has no target.** The scripts that deploy mandates and commands write into `.claude/`. The skills-on-every-engine decision says where an Antigravity workspace keeps skills, but nothing writes them there yet, and the hook-shaped guard scripts still expect Claude's payload shape.

**Problem 4: No one is positioned to build the port.** The Antigravity persona cannot build the conventions it lacks, because building them correctly requires following them. The current harness, where conventions already work, is retired by the kernel, so the window in which a Claude Code session can do this work with full conventions closes with the switch-over.

**Problem 5: The operator's management surface disappears.** History and to-do files, session manifests, the memento sweep, the task-store items, the checkpoint ritual: these are how the operator sees a project without reading transcripts. A persona that skips them produces work the operator cannot track by the usual means, which defeats the premise of the wrapper, saving operator attention.

**Problem 6: The handoff has no test of its own.** Even with the port built, there is no acceptance item that says "the persona followed the convention". Without one, convention-following is asserted, exactly the kind of claim the rest of the design refuses to make.

**Problem 7: Scope is undefined.** "All of my conventions" is sixty-four workflows. A solo implementer needs about twenty-five; the rest are crew-level and belong to the second phase anyway. Without a named subset, the port is either too large to finish before the handoff or too small to manage by.

## Proposed solutions

### Solution 1: Where the handoff sits

*Addresses the root problem and Problems 1 and 6.* Four placements were considered.

**A. A conventions gate after the first-phase tests.** A second acceptance set, Convention-1 to Convention-9 below, that an Antigravity persona must pass before it becomes the implementer. The port of the convention kit is the precondition. *Pros:* keeps the dogfooding timing close to the original; makes convention-following a tested claim; the operator's management surface exists from the implementer's first session. *Cons:* delays the handoff by the time it takes to port the kit, roughly two design sessions plus one to two weeks of build.

**B. Hand off on time, degraded.** The Antigravity implementer starts with the six instruction layers and only the skills that do not touch Claude plumbing, and builds the rest of its own conventions as its first job. *Pros:* no delay; the free-token engine starts earning its keep immediately. *Cons:* the persona builds conventions it does not yet follow (Problem 4); the operator manages without history, to-do, checkpoints or the decision format for the duration (Problem 5); this is precisely the outcome the operator said they do not want.

**C. Move the handoff to after the second phase.** Claude Code under the current harness stays the implementer through persona bootstrap; the second phase's own acceptance becomes the conventions gate. *Pros:* no new acceptance set; the conventions are proven as part of a phase that was going to prove them anyway. *Cons:* a whole phase on paid Claude tokens instead of free Antigravity tokens; persona bootstrap also covers the crew-level layer the solo implementer does not need, so the handoff waits on work that is not on its path.

**D. A minimum convention kit, then the gate.** Name the solo-implementer subset (about twenty-five workflows), port only that, test it with Convention-1 to Convention-9, hand off. Cascade review and the crew layer stay in the second phase, built by the Antigravity implementer once it follows the kit. *Pros:* the smallest port that still gives the operator their full management surface; the crew layer is built by a persona already living under the conventions, which is the dogfooding decision's intent. *Cons:* a judgment call on the subset, which may need one or two additions after the first week.

- **Recommendation:** D, with A's gate. It is A with a named scope.

### Solution 2: The convention kit

*Addresses Problem 7.* The subset named in the inventory section: the session ritual (start, checkpoint, end; history, to-do, memento), planning the work (the p-is-p series, plan serialization, the research directory policy), doing the work (code style and post-edit verification, docstrings, the three testing workflows, bug-fix mode, branch and merge, worktree lifecycle, task-store discipline), and talking to the human (voice integration, cross-session communication, brevity, the decision walkthrough, last call, push to completion). Everything else waits for the second phase.

- **Alternative considered:** the whole layer. Roughly two and a half times the port, most of it for roles the implementer does not play.
- **Recommendation:** adopt the subset as the kit, with the explicit rule that a convention missed in the first week is added to the kit, not improvised around.

### Solution 3: The acceptance set Convention-1 to Convention-9

*Addresses Problems 1 and 6.* Each item is one convention observed end to end on an Antigravity persona under the kernel, in the same style as Kernel-1 to Kernel-8.

| # | Do this | Pass when |
| --- | --- | --- |
| Convention-1 | Spawn an implementer persona | It runs the session-start ritual unprompted: start notification, configuration load, workflow discovery, a session manifest entry |
| Convention-2 | Send the turn `/plan-session-checkpoint` | The kernel expands the skill; the persona performs the checkpoint as written |
| Convention-3 | Give it a piece of work by voice | A task-store item exists before any file changes |
| Convention-4 | Ask it to plan a small feature | A plan file appears under the research directory at the path the policy names, in the serialized format |
| Convention-5 | Let it edit a Python file | The edit follows the code-style mandate and the post-edit verification runs and is reported |
| Convention-6 | Ask it to commit | The testing baseline runs first; a red test blocks the commit; a green one lets it through |
| Convention-7 | Force a respin mid-task | The memento is written at the checkpoint and the respawned persona rehydrates from it and continues |
| Convention-8 | Say "wrap up" | The session-end ritual runs: history entry, to-do update, memento sweep, and the push gate arrives as an approval ticket rather than a prompt |
| Convention-9 | Leave it two open design questions | It presents them one at a time through the multiple-choice ask, each with pros, cons and a recommendation |

- **Pros:** nine items, half a day to run; each maps to a convention the operator would otherwise have to police by hand.
- **Cons:** Convention-5 and Convention-9 are judgment calls on the reviewer's part, not binary; they need a short rubric.
- **Recommendation:** adopt as the gate for the handoff, amending the dogfooding decision to read "after Kernel-1 to Kernel-8 and Convention-1 to Convention-9".

### Solution 4: Who builds the port

*Addresses Problem 4.* Three candidates.

- **The Claude Code session that builds the first phase.** It already follows every convention, it is already on the test machine, and the port is text and installer work in the same repository. *Cons:* paid tokens; one more deliverable before the handoff.
- **The Antigravity persona itself.** Free tokens. *Cons:* it would be building the conventions without following them, and the operator cannot manage that work by the usual means while it happens.
- **The operator by hand.** Fastest for the judgment calls (which files, which paths). *Cons:* the operator's attention is the resource the whole design is meant to spare.
- **Recommendation:** the Claude Code session, immediately after Kernel-1 to Kernel-8, as the last thing it does before the handoff. The persona-bootstrap design item supplies the rules it follows.

### Solution 5: One workflow set or two

*Addresses Problem 2.* The port can fork the sixty-four documents into a Claude set and an Antigravity set, or keep one set and move the engine-specific plumbing behind kernel verbs: "start a cold session" instead of `/clear`, "add a task" instead of the native to-do tool, "ask the human" instead of the question tool, harness-owned paths instead of `~/.claude`.

- **Two sets.** *Pros:* nothing in the Claude set changes; lowest risk to current sessions. *Cons:* every future convention edit is made twice, and the two drift within a month.
- **One set behind kernel verbs.** *Pros:* one place to edit; the conventions describe what to do, the kernel supplies how on each engine, which is the instruction-layers decision applied to workflows. *Cons:* the current harness must honor the same verbs until it is retired, so the port touches Claude sessions too.
- **Recommendation:** one set behind kernel verbs. The drift cost of two sets is paid forever; the port cost of one is paid once.
