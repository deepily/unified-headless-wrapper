# The flat-key form of the two configuration tables (row 57 of "Outstanding actions")

**As of:** 2026-11-16 · not a register item; it needs a ruling, and is recorded under the turn-end policy decision (D62), part 10, as row 26 was. This repo at `e86a08d`, lupin at `aabadd221`. Every count below was produced by a zero-token script, `.scratch/row57/probe_table_forms.py`, before this page was written.

## In brief

The kernel's settings live in lupin's `lupin-app.ini`, one setting per line, as lowercase words separated by spaces (`kernel turn end poke cap = 1`). That was ruled on 2026-11-10. Most of the settings that older specs wrote in another style convert mechanically: a section name becomes a prefix. Two do not, because they are tables rather than single values:

- **the context-window table**, seven rows, one per engine and model, each holding two numbers (the model's window and the point where the engine compacts on its own);
- **the memory table**, three rows, one per engine, each holding three numbers (the memory reserved, the hard cap, the heap limit).

Neither can be written in `lupin-app.ini` as the specs wrote it; the script shows the parser rejecting one and mangling the other. Four choices settle the form. The recommendation is the form lupin already uses for its sixty-five voice-persona settings: **one line per number**, the row named in the key.

Nothing here changes a value or a behavior. The windows table is first read at the second kernel milestone (Kernel-2), so the form is owed before then.

## Where the record stands

**The rule.** "Configuration lives in lupin's `lupin-app.ini` through the ConfigurationManager: inheriting blocks, lowercase space-separated keys explained in the splainer … the earlier specs' `[fleet]`/`[inbox]`/`[host]`/`[memory]`/`[context windows]` forms are read as such keys" (framework Section 1, the turn-end policy row, part 10). The rule says the tables become keys; it does not say how a row with several values becomes a key.

**The two tables as written.**

```ini
[context windows]                                   ; context-exhaustion spec, Section 4
; engine:model = window_tokens, ceiling_tokens
agy:fable-5.1-high        = 1000000, 256000
…                                                   ; 7 rows, 14 numbers; engines agy, jetski, claude

[memory]                                            ; host-capacity spec, Section 6
; engine = reserve_bytes, cap_bytes, heap_mib
agy    = 2147483648, 8589934592, 6144
jetski = 2147483648, 8589934592, 6144
claude = 2147483648, 8589934592, none               ; 3 rows, 8 numbers and one "none"
```

**What lupin's parser does with them** (the ConfigurationManager builds Python's `ConfigParser` with no arguments, `cosa/config/configuration_manager.py:246`):

| Fact | Evidence (script section) |
|---|---|
| A colon ends a key, exactly as an equals sign does. The line `agy:fable-5.1-high = 1000000, 256000` is read as key `agy`, value `fable-5.1-high        = 1000000, 256000`; the second `agy:` row then stops the whole file with a duplicate-key error | 2 |
| A comment after a value is kept as part of the value: `host_reserve_floor_bytes` reads as `4294967296      ; 4 GiB`. The specs' blocks carry five such comments; `lupin-app.ini` has none | 3, 8 |
| Keys are lowercased on reading; dots, hyphens, slashes and square brackets inside a key survive; a colon, an equals sign or a space inside a model's name does not | 7 |
| A child block overrides its parent **one key at a time** (`configuration_manager.py:490`): a host's block can change one key and inherit the rest | 8 |
| The manager can list every key in force (`get_keys`, line 728), so a reader can find all keys under a prefix | 8 |
| A value can be read as a comma list, split on a comma **followed by a space** only (line 911): `1000000,256000` comes back as one item | 5 |
| A value can be read as JSON or a Python dictionary; fourteen keys in `lupin-app.ini` do this today, all on one line; no value in the file continues over several lines | 6, 8 |

**Precedents in `lupin-app.ini` for a table.** One key per cell: the sixty-five `cc session voice persona …` keys (one list of names, then `… maria voice id`, `… maria icon`, `… maria color`, `… maria profile`), and the forty-two `external repo <name> <kind>` keys. One key per table: the fourteen model-parameter keys whose value is a dictionary.

**How the tables are used.** The context table is looked up by one engine and one model when a persona starts (`context_windows.get( ( engine, model ) )`, context-exhaustion spec, Section 5); a model that is not in it reads as "unknown" and triggers nothing (acceptance test Pressure-4). The memory table is looked up by engine at each admission, and re-read from disk each time (host-capacity spec, Section 2). Neither use walks the table; each wants one row.

**The heap column.** The host inventories of 2026-11-11 found that neither engine honors the heap setting on a `--version` call, and the host-capacity spec's Section 15 says the setting "is not relied on". The column was not withdrawn. This page carries it as written; withdrawing it is a matter for the host-capacity decision, not for the form.

**The rest of row 57** is mechanical and counted: the fleet spec's nine `[fleet]` keys and one `[host]` key; the log spec's seven `log …` and `watch …` keys; the context-exhaustion spec's six `[context pressure]` keys; the host-capacity spec's eight `[host]` keys and three single-valued `[memory]` keys. Thirty-four keys, listed under "What follows without a decision".

**One correction to row 57 itself.** The row lists `[kernel memento]` among the context-exhaustion spec's forms to rewrite. It is not a setting: it is the heading of a message block the kernel sends a persona (Sections 3 and 8 of that spec). Nothing is rewritten there.

## Problems and options

### 1. How a row with several values is written

**A. One key per number, the row named in the key (recommended).**

```ini
kernel context windows agy fable-5.1-high window tokens   = 1000000
kernel context windows agy fable-5.1-high ceiling tokens  = 256000
kernel memory agy reserve bytes                           = 2147483648
kernel memory agy cap bytes                               = 8589934592
kernel memory agy heap mebibytes                          = 6144
```

- For: it is the rule as ruled (lowercase words, one value, each explainable in the splainer) and the form the file already uses for personas and repositories. Every number carries its name, so no reader depends on position. A host's block can change one number (the test VM's cap, one model's ceiling when the context capture corrects it) and inherit the rest. "None" needs no spelling: Claude simply has no heap key. Each lookup is one plain `get`.
- Against: twenty-two lines for the two tables where the specs had ten. A row can be half written (a window with no ceiling), which the older form could not express; problem 4 answers that. Adding a model is two lines.

**B. One key per row, the values a comma list.**

```ini
kernel context windows agy fable-5.1-high = 1000000, 256000
kernel memory agy                         = 2147483648, 8589934592, none
```

- For: closest to the specs; ten lines; a row is whole or absent.
- Against: the numbers are positional, and two of the memory numbers are both byte counts of the same magnitude, so a swap reads as valid. The manager's list reader splits only on comma-space, so a missing space yields one item. "None" becomes a magic word. A host cannot override one number without restating the row. The meaning of each position lives only in the splainer.

**C. One key per table, the value a JSON dictionary.**

```ini
kernel context windows = { "agy": { "fable-5.1-high": { "window tokens": 1000000, "ceiling tokens": 256000 }, … }, … }
```

- For: one read gives the whole table; names are labelled; a model's name may hold any character, capitals and colons included; fourteen keys already work this way.
- Against: seven rows on one line (the file has no multi-line values today, though the parser accepts them). A host's block that changes one number must restate the entire table, and then silently stops inheriting later additions to the parent's. One stray comma loses every row at once. It is the least like "lowercase space-separated keys".

**Recommendation: A.**

### 2. The order of words inside the key

This arises only under A.

**A. The row first, then the quantity (recommended):** `kernel context windows agy fable-5.1-high ceiling tokens`, `kernel memory agy cap bytes`.

- For: the order of both precedents (`cc session voice persona maria voice id`, `external repo <name> <kind>`); a row's keys sit together in the file and in a sorted listing; the prefixes `kernel context windows` and `kernel memory` are the ones the record already names.
- Against: under `kernel memory`, the per-engine keys share a prefix with the three single-valued keys (`kernel memory notice ratio`, `kernel memory respin ratio`, `kernel memory respin window hours`), so no engine may ever be named `notice` or `respin`. The check in problem 4 knows the three names.

**B. The quantity first, then the row:** `kernel context windows ceiling tokens agy fable-5.1-high`, `kernel memory cap bytes agy`.

- For: all ceilings line up as a column; the key's tail is exactly the engine and model; no shared-prefix question.
- Against: unlike both precedents; a row's numbers are scattered through the list; a model name at the end of a key invites trailing-space mistakes.

**Recommendation: A.**

### 3. A model name that a key cannot hold

Under A or B the model's name is part of a key. The parser lowercases keys and ends a key at a colon or an equals sign; a space would split the name into two words. Every model name in the record today is already safe (`fable-5.1-high`, `opus-5.5-high`, `gemini-3.8-flash-high`, `claude-fable-5-1`, `claude-opus-5-5`); a name of the form `vendor:model` would not be.

**A. Normalize the name before the lookup (recommended):** lowercase it, and write a hyphen for each colon, equals sign or run of spaces. The file is written with the normalized name; the persona's own model name is untouched everywhere else.

- For: every name an engine can report has a row it can find; one small pure function, tested; the same idea as the persona-name rule ruled on 2026-11-15.
- Against: two names that differ only in those characters would share a row (none do today); the name in the file is not always character for character the name the engine prints.

**B. Lowercase only; any other name has no row.** Such a model reads as "unknown", as any unlisted model does.

- For: nothing to explain; the file's name is the engine's name apart from case.
- Against: a model with a colon in its name can never be given a window, so context-pressure protection is silently off for it; the only sign is the one `pressure.window_unknown` record at its start.

**Recommendation: A.**

### 4. A row that is incomplete or unreadable

One key per number makes new mistakes possible: a window without its ceiling, a misspelled quantity (`cieling tokens`), a value that is not a number, a ceiling above its window, a cap below its reserve. Today's rule for an out-of-bounds kernel key is a refusal to start (the interrupt-exit key, ruled 2026-11-16).

**A. Refuse (recommended).** At start, the kernel lists every key under the two prefixes; any key that does not parse as a known row and quantity, any incomplete row, any non-number, and any row that breaks an ordering (ceiling ≤ window; reserve ≤ cap) stops the start with the key named. On the memory table's re-read at an admission, the same check runs; a failure refuses that admission with the key named and leaves running personas as they are. An **absent** row stays what it is today: for a model, "unknown" (Pressure-4); for an engine, a refusal, since nothing can be reserved for it.

- For: a typing mistake cannot quietly switch off a protection; the same rule as the other kernel keys; the mistake is reported where and when it was made.
- Against: one bad line stops the kernel from starting; the check must be kept in step with the list of quantities.

**B. Tolerate.** A row that is incomplete or unreadable is treated as absent, and one alert record is written.

- For: the kernel always starts.
- Against: a misspelled ceiling turns a listed model into an unknown one, and context-pressure protection for it is off until someone reads the log; for memory, "absent" has no safe meaning.

**Recommendation: A.**

## What follows without a decision

- **Values do not change.** Every number moves as written. The heap number is written `heap mebibytes` (no abbreviation in a new name, as `characters` was ruled for row 26); Claude has no such key.
- **Comments move off the value lines,** onto lines of their own or into the splainer, since the parser keeps a trailing comment as part of the value.
- **The mechanical keys** (section name becomes prefix; underscores become spaces; a word the prefix already says is not said twice):
  - fleet spec: `kernel fleet size cap`, `kernel fleet size cap maximum`, `kernel fleet batch cap`, `kernel fleet skeleton crew`, `kernel fleet worktree root`, `kernel fleet gate claim seconds`, `kernel fleet idle hibernate minutes`, `kernel fleet idle advise hours`, `kernel fleet kept tree sweep hours`; `kernel host class`.
  - log spec: `kernel log segment max megabytes`, `kernel log retain minutes`, `kernel log persona max megabytes`, `kernel log frame max kilobytes`, `kernel log stderr lines per minute`, `kernel log sweep interval minutes`; `kernel watch held turn seconds`.
  - context-exhaustion spec: `kernel context pressure notice ratio 1m class`, `… respin ratio 1m class`, `… notice ratio 200k class`, `… respin ratio 200k class`, `kernel context pressure class boundary tokens`, `kernel context pressure compaction drop fraction`.
  - host-capacity spec: `kernel host class`, `kernel host reserve ratio`, `kernel host reserve floor bytes`, `kernel host pressure ratio`, `kernel host pressure rearm`, `kernel host memory sample seconds`, `kernel host memory log minutes`, `kernel host idle hibernate minutes under pressure`; `kernel memory notice ratio`, `kernel memory respin ratio`, `kernel memory respin window hours`.
- **The four specs are rewritten in place by script,** each with an amendment listing what was and what is, as the Phase 1 and broadcast specs were for row 26. The code inside those specs reads the tables as objects and does not change.
- **A small loader is written and tested** (`.scratch/row57/`): it builds both tables from the keys, with the normalizing function and the check, and is inlined in an amendment to the turn-end policy spec, which owns the configuration rule.
- **No decision number.** As with row 26, the ruling is recorded as an amendment under the turn-end policy decision, part 10; the framework's sentence on kernel configuration gains the form.
- **Not examined here:** how the kernel re-reads `lupin-app.ini` at each admission through a ConfigurationManager that is built once. The fleet and host-capacity specs both require the re-read; neither says how. If it has no row, it gets one in "Outstanding actions".
