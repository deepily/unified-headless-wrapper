# Two entries the switch-over list is missing, and what the check for them found (row 28 of "Outstanding actions")

**As of:** 2026-11-16 · not a register item. It adds rows to the switch-over list of record, which belongs to the decision on exit criteria and the switch-over (D63), and it asks four rulings. This repo at `5462087`, lupin at `27e646d0ed` (the test VM's checkout). Every count below was produced by a zero-token script, `src/captures/t19_hook_import_survivors.sh` (self-test, fifteen cases), before this page was written; its output is `src/captures/out/t19-hook-import-survivors-lupin-host-test-20261116.txt`.

## In brief

When the kernel replaces today's harness, a list says what happens to every piece of the old one: deleted, kept, renamed, and on which of three dates (the **Move**, when the kernel's code lands in lupin; the **Switch**, when the fleet changes over; the **Delete**, when the old harness is removed after a soak). That list is Section 5 of the switch-over spec, and a script carries the same rows in a form a machine can check against a lupin checkout.

On 2026-11-11 the ruling on the task store's manager checks named two entries the list lacked and did not add them. Row 28 is the duty to add them:

1. **A temporary fallback in the manager check.** While old and new harness run side by side, lupin asks the kernel whether a persona is a manager and, failing that, reads the old harness's session file. The fallback must be removed at the Delete.
2. **The podcast door reads the same session files** to say who is asking, and nobody has said what becomes of that.

Both entries are written below, with a choice in each. But checking the second one ("is the podcast door the only such case?") turned up a larger fact, which is the main reason this page asks for rulings rather than making a clerical edit:

> **Forty-four files that survive the Delete import code that the Delete removes.** The list deletes the old harness's code tree whole. Sixty files outside that tree import from it. The list deletes fourteen of them. Of the forty-six that remain, forty-four import at least one module that will no longer exist, and would fail to load the day the tree is removed. The two entries of row 28 account for four of the forty-four.

The recommendation is to add the two entries now, add a machine check so the Delete cannot pass while any such import remains, and carry the other forty files as one owed piece of work due before the Move, not to dispose of them here.

## Problems and options

### 1. How a machine checks that the manager check's fallback is gone

The entry is: "the session-file fallback of the role check (`resolve_role`'s `bridge` parameter in `cosa/rest/persona_role.py`), bound at three sites (`routers/tasks.py`, `task_promotion_gate.py`, `task_priority_firewall.py`); a lupin change, added at the Move, removed at the Delete; replaced by the grant and the kernel roster alone." The question is what the script greps for, since "bridge" as a word occurs all over lupin.

- **A. Name the one function that reads the file, and grep for that name (recommended).** The ruling's module gains one helper, `session_file_role( persona_id )`, the only place the old manager test is imported; the three sites pass it as `bridge=session_file_role`. Script row: `symbol|delete|Delete|session_file_role`. *For:* the three sites become countable (the name is present in four files from the Move, in none after the Delete); a parameter left behind as dead code is caught; the old import shrinks from three files to one at the Move. *Against:* one new name set here that the ruling did not set; lupin's implementer must use it.
- **B. No new name; grep for the old manager test's import path.** Script row: `symbol|delete|Delete|hooks.lib.manager_figure`. *For:* checkable today (three files outside the tree), nothing invented. *Against:* it proves the import is gone, not the fallback; a `bridge` parameter that is never passed again would survive unnoticed; and if decision 3 is taken as recommended this row checks nothing the general check does not.

Recommendation: A.

### 2. What becomes of the podcast door's session-file read

- **A. Re-point it at the Move, in the same order as the task doors (recommended).** The door takes the asker's name, binding identifier and sender identifier from the proven grant when the request carries one, then from the kernel roster, then from the session file while both harnesses run; the session-file branch and the import leave at the Delete. List row: Keep, re-pointed; Move (re-pointed), Delete (file branch removed). *For:* a kernel persona's consent card names who is asking from the first day of the shadow run; the router is already being edited at the Move for the grant check; one order of sources for every door. *Against:* one more lupin change at the Move; the door's three small helpers change their inputs.
- **B. Leave it alone until the Delete.** List row: Keep; the session-file read removed at the Delete, the grant's claims in its place. *For:* nothing to build at the Move; the door works without a file. *Against:* through the shadow run and the soak every kernel persona's card reads "an unrecognized session", on the one card whose purpose is the operator's informed yes; the card is filed under a generic sender; the rewrite still has to be done, later and under the Delete's deadline.

Recommendation: A.

### 3. What to do about the other forty surviving imports

- **A. Add the check now; carry the forty as one owed row, due before the Move (recommended).** The Delete clock gains a machine condition: the survivors script reports no surviving file that imports a deleted module. A new row in "Outstanding actions" owes the mapping: each of the forty to a ruled replacement where one exists, the rest brought back as decisions, grouped by the fourteen modules. *For:* the Delete cannot pass with a broken import, from today; the two entries of row 28 are closed without waiting; the mapping is mostly reading rulings that exist, and a row suits that. *Against:* an owed item of unknown size sits before the Move.
- **B. The same check, but the forty become a register item (T40) with its own narrative.** *For:* if the mapping turns up many real decisions (where `fleet_data_root` lives; what the direct-message and notification routers read instead of session files), a register item gives them a ruling and a spec. *Against:* it reopens a design register that closed on 2026-11-15, before anyone knows whether the forty need design at all.
- **C. Dispose of all forty in this session.** *For:* nothing left owed. *Against:* eighteen files read the session-file module in different ways; doing them justice is several sessions' reading, and row 28's two entries would wait on it.
- **D. Record the count and add no check.** *For:* least work. *Against:* the list of record stays unable to see the fault it has just been shown.

Recommendation: A, with B available if the mapping shows the decisions are many.

### 4. When the mapping of the forty is due

Applies under 3A or 3B.

- **A. Before the Move (recommended).** *For:* the Move is when lupin gains the roster client, the grant check and the role module, which are what most of these imports will be re-pointed to; the list must be complete before the code that implements it is written. *Against:* it adds to what stands before the Move.
- **B. Before the Delete.** *For:* nothing breaks until the tree is removed. *Against:* a shared helper such as `fleet_data_root` needs a new home, and finding that out during the soak leaves the Delete waiting on a refactor of fifteen files.

Recommendation: A.
