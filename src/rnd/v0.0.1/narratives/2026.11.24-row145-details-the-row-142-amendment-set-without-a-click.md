## Problems and options

### 1. How the list of notification kinds is separated

`kernel inbox admitted payload kinds` is the only list among the fifty. Today it holds one kind, `dm_grade`, so the separator has never been exercised. The code splits on commas, as lupin's own lists are written. It keeps a kind that is written twice.

- **A (recommended): commas; a kind written twice is refused, naming the kind.** Pros: lupin's practice; the same answer you gave this morning for two settings naming one pool (refused, the second named); a duplicate is nearly always a slip in editing. Cons: one more sentence.
- **B: commas; a kind written twice is read once.** Pros: forgiving; nothing downstream sees a duplicate. Cons: a slip passes unseen; differs from this morning's ruling on pools.
- **C: confirm as written** (kept twice). Pros: no change. Cons: whatever reads the list sees two entries for one kind.

### 2. The working trees' folder

The rule as written accepts anything that begins with `/` or `~` and hands it on untouched. No code in the record expands `~`, and the code that uses the folder would create a folder named `~`.

- **A (recommended): the settings module expands `~`, and the path must be absolute once expanded,** the rule you ruled this morning for the key file. `~/.lupin/kernel/worktrees` becomes the account's own folder; `~trees` and `~nobody_here/trees` are refused (they do not expand to a full path); the value the rest of the kernel holds is always a full path. Pros: one rule for both paths; the gap closes where the value is read, once. Cons: the module's returned value is no longer the text as typed (the starting value's test changes).
- **B: confirm as written, and the fleet's code expands `~` where it uses the folder.** Pros: the settings module stays a pure check. Cons: every later reader of the value must remember to expand; two rules for two paths; `~trees` is still accepted at the start and fails later.
- **C: `~` refused; the setting must be a full path.** Pros: nothing to expand. Cons: the starting value you ruled today (`~/.lupin/kernel/worktrees`) could no longer live in the baseline block, since the home folder differs by host and account.

Under any option `/` alone is still a full path and is accepted; I recommend no rule against it (a host that sets it has said what it wants, and the persona account cannot write there).

### 4. The function `is_permissive_host`

You ruled that a development host does what a test host does in all four places where `test` and `production` differ. The code puts that one question in one function, so no caller compares words itself.

- **A (recommended): confirm the function and its name.** Pros: the name carries a verb and reads as a question, as six other `is_…` functions in the record do; when a later ruling makes a development host differ, one function changes. Cons: "permissive" is a new word in the record; it appears in no spec's prose before today.
- **B: rename it** (for instance `is_test_like_host`, or `should_tolerate_host_gaps`). Pros: avoids the new word. Cons: I found no name that says the four things more plainly.
- **C: no function; each of the four places compares the class itself.** Pros: none I can state beyond fewer names. Cons: four places to change, and to forget.

### 5. The order of checking

The kernel names the first bad setting in the table's order and stops; the three relations between two settings are checked only after every single setting has passed.

- **A (recommended): confirm.** Pros: every other settings module in the record stops at the first failure; one error is what the two printed lines and the refused start were ruled around; a relation is only meaningful between two values that are each legal. Cons: a settings file with several mistakes costs one start for each (each start is zero tokens and under a second, and row 146 writes the fifty values once).
- **B: every bad setting is reported in one start.** Pros: one pass fixes a file with several mistakes. Cons: a new shape of error for this module alone, or a change to every settings module; the printed refusal grows from two lines to two for each failure.

### 6. "Checked at the kernel's start" on five lines

Every line of the fifty ends by saying when the setting is read. Five say "Checked" instead of "Read". For three of them that is the honest word: the gate's hook, not the kernel, uses `kernel gate retry seconds`; a persona's tool server uses `kernel client retry seconds`; and when `kernel inbox grade dms` is read is the open question of row 143. For the other two (`kernel inbox admitted payload kinds`, `kernel inbox broadcast result priority`) the session wrote "Checked" because their own spec does not say when they are read. But the amendment itself says, under "What follows", that each of the fifty is read once at the kernel's start and held until a restart.

- **A (recommended): the three keep "Checked"; the two say "Read at the kernel's start".** Pros: each line says what the record says; the two no longer hedge against the amendment's own statement. Cons: two lines change.
- **B: confirm all five.** Pros: no change. Cons: two lines suggest a doubt the record does not hold.
- **C: all fifty say "Read".** Pros: one sentence everywhere. Cons: says the kernel reads what another process uses, and settles row 143 by a side door.

One thing I checked and leave alone: `kernel host class` is also used by the gate's hook, and its line says "Read". The kernel itself uses it in three of the four places, so "Read" is true of it.

### 7. The renamed switch's starting value

Until this afternoon the switch was `kernel inbox dm grades = on`. You ruled that it takes `true` or `false` like every other switch and renamed it `kernel inbox grade dms`. The session wrote its starting value as `True`.

- **A (recommended): confirm `True`.** Pros: it means what `on` meant (a persona is shown the grade of a direct message it sent); the other five switches among the fifty are written `True` as well. Cons: none found.
- **B: `true`, lowercase, for all six.** Pros: matches the words in the bound ("`true` or `false`"). Cons: six values and their lines change for a spelling the kernel reads identically; lupin's own file uses both.

### 8. The exit code of a refused start

The amendment says a bad setting stops the start with exit 78. No ruling of this afternoon said so; the session took it from the kernel lifecycle decision, where reading the settings is the first step of the start and a failure of that step is exit 78, which systemd is told never to retry.

- **A (recommended): confirm 78.** Pros: it is what the lifecycle decision already rules for this step; a second code would need a reason. Cons: none found.
- **B: a code of its own for a refused setting.** Pros: a script could tell a bad setting from another refusal by the code. Cons: the unit file lists one code not to retry; the refusal's two lines already say which setting.
