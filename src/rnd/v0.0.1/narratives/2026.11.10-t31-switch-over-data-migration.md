# The switch-over data migration: what moves when AH4L stops (T31)

2026-11-10 · Rick Ruiz · Claude doc (link added after publication) · ruled as D64 (2026-11-10)

## In one paragraph

When the kernel fleet takes over from the current harness (AH4L), a handful of things that live today in files on each fleet host have to end up in the kernel's registry or in Lupin's database, or the personas that come back under the kernel will not be the personas that went to sleep: they would have new identifiers, fresh voices, no memory of which messages they had already read, and no link to their managers. This item names each of those things, says where it goes, and settles the order of the switch-over week's first steps, which the previous item left with a defect (the migration step runs while the old harness is still writing the files it migrates). The reading of lupin at `82fdc0182` shrank the item: the task store and the memento records need no migration at all, because both are keyed on the persona's *name* and stored where the switch does not reach. What remains is five concrete transfers (the roster, the voice allocations, the message cursors, the session topics, the memento mirror), one archive, and one new kernel command that does them from a snapshot, dry-run by default. The recommendation makes the voice-persona name the thread of continuity, which in turn makes the voice pool the one piece of new Lupin storage this item asks for.

## What the record says today

- **The register (framework Section 15, Section 20).** `TODO(T31)` is one line: bridge files to the registry; live tasks and their `accountable_manager`; DMs and asks in flight; mementos under `~/.claude`. Since 11-03 it has also owned the voice-persona pool store (the pool's state turned out to be the bridge files), since 11-10 the broadcast door's roster read and the topic write (D61), the sweep ledgers to the store (D62), and the archive step of the switch-over (D63).
- **The field map (T10 spec Section 5).** Written on 11-03 and amended by D59 and D62: `persona_id := stable_session_id[:8]`; `session_id` becomes `conversation_id` for a persona staying on Claude; role, model, project, workspace, voice persona, topic and owner copy across; the process plumbing and every turn-end field are dropped. It names "`manager_session_id[:8]`" as the source of `manager_id` and separately lists `spawned_by` among the dropped fields.
- **The checklist (T19 spec Section 4.2, D63).** Day 0 tags `ah4l-final` and cuts the branch; then 1 freeze, 2 archive, 3 migrate, 4 stop AH4L, 5 flip, 6 rename the wire, 7 spawn the kernel fleet from the role templates, 8 inventory. The archive is "bridge files, the pool store, the sweep ledgers and `~/.claude` mementos to `~/.lupin/archive/ah4l-<date>.tar.gz`, kept 30 days"; the migration is "bridge rows to the registry, the pool store, the door's roster read and the topic write, the sweep ledgers to the store". Rollback restores the archive over the home directories.
- **The inbox (T12 spec Section 4, D52; T27 spec Section 3, D55).** Each kernel persona keeps `inbox.json` with `acknowledged` ids and three cursors, `answers_cursor`, `dm_cursor`, `voice_cursor`. On every connect the kernel pulls owed answers (surface everything), the DM list (seed the cursor, surface nothing) and, after D55, `GET /api/notifications/undelivered?job_id=&since=`, acknowledging each voice row after the stdin write. The D55 migration adds `listener_delivered_at` to `notifications` and sets it nowhere but the ack route.
- **The registry row (Phase 1 spec Section 7, D59).** `PersonaRow` has identity, engine, model, project, sender id, workspace, conversation id, state, process id, `manager_id`, host, billing and the lifecycle timestamps. It has no field for the voice persona or the topic yet, although Section 4.1 of the framework says the registry holds one name field, `voice_persona`, and D61 sends the topic there.

## What was found in lupin

Read from the laptop clone at `82fdc0182`, read-only.

**The bridge file.** `cc-{pid}.json` under `~/.claude/sessions/` (`LUPIN_HOOK_SESSIONS_DIR` overrides). Written by `register_session.py` at every SessionStart and patched by nineteen other sites. Its lineage fields are `spawned_by` (the spawning manager's session id, forwarded as `COSA_VOICE_SPAWNED_BY`) and `spawned_by_persona` (the manager's name frozen at spawn so a dead worker still resolves to its true manager). There is no `manager_session_id` field. The liveness rule every server-side reader applies is `find_active_sessions`: pid alive, bridge touched within 12 hours, a voice persona allocated.

**The twenty writers, sorted.** The item asked which are readers the kernel roster replaces and which are writers that simply stop.

**The readers the roster replaces.** `GET /api/commons/active-sessions` and the broadcast fan-out (`find_active_voice_persona_sessions`), the voice-persona pool snapshot and the manager badge (`_resolve_manager_persona` walks `spawned_by`), the speakerphone gate in `_notify_impl`, the two arbiter projections and the tasks router's manager-only guard (T21). Under the mixed fleet (D63) the first four read the union; after the Delete clock, the kernel roster alone.

**The voice-persona pool.** `cc session voice persona pool` in `lupin-app.ini` is the configured pool; occupancy is computed on every request from the live bridges' `voice_persona` field; allocate writes the bridge, release clears it. With no bridges there is no occupancy. The domain of uniqueness today is one host's sessions directory, read through the container's bind mount.

**The task store is engine-blind and session-blind.** `task_items.owner_persona` and `accountable_manager` are canonical persona names (`maria`, `mr radio`), canonicalized at every write seam and swept by `persona_key_backfill.py`; `created_by` is free text carrying the old session id, historical only. The hook-side mirror (`task_store_mirror.py`) is a deprecated no-op since the store-canonical cut-over, so `.task-store-map-*.json` and `.task-store-spool-*.jsonl` carry nothing the store lacks. A persona that returns under the kernel with the same name owns the same rows.

**The sweep ledger is name-keyed too.** `board-sweep-<persona-slug>.json` in the sessions directory: `started_at`, `total_at_start`, the frozen `board_ids`, the `reviewed` list, read with an expiry.

**The in-flight ledgers.** Per session, in the sessions directory: `.dm-inbox-hwm-{id}.json` and `.ask-answer-hwm-{id}.json`, both `{ cursor_ts, surfaced_ids }` with a 500-id tail, plus the append-only `.ask-surfaced-{id}.log`. They are the shape of `inbox.json` already. The voice buffer `cc-buffer-{id}.jsonl` holds inbound frames that arrived mid-turn and were not yet drained; every one of them is also a row in `notifications`. Voice has no high-water mark: nothing on the host records which human messages a seat has read, and after the D55 migration every pre-existing `human_to_ai` row has `listener_delivered_at = NULL`.

**Mementos.** The records are in the repository's `io/mementos/` (gitignored, so not in any fresh worktree) at the **main checkout**: `memento_repo_root.py` resolves a linked worktree to the parent of its `--git-common-dir`, and the kernel's persona worktrees are linked worktrees of the same checkout (D59). The mirror is `~/.claude/mementos/<repo>/`; D54 moves it to `~/.lupin/mementos/<repo>/` and says "no on-disk migration" of the records, which is right, but the new mirror directory starts empty. Readers accept both stamp keys.

**What else is under `~/.claude` on a fleet host.** `sessions/` (the bridges, buffers, ledgers, holds, sweep ledgers, task-store map and spool, `spawned-<manager>.json`, `cc-stable-*.id`, `cc-listeners.log`), `mementos/`, `heartbeat-events/`, the deployed `CLAUDE.md`, and `projects/` (Claude's own transcripts, which the kernel never writes and the rollback needs intact).

**The checklist defect.** Step 4.2.3 migrates the bridges while the listeners, the arbiter and the seats are still running (4.2.4 stops them). The T10 spec's premise for the field map was "AH4L is stopped first, so the bridges are at rest". Both cannot hold.

## The problems

1. **Order.** The data is migrated before its writers stop, and the liveness test that selects the rows (pid alive) is false the moment they do stop.
2. **What comes back.** A kernel persona is minted at `POST /personas`; the switch-over needs rows that carry an existing id, name, topic and lineage, and the checklist's step 7 spawns fresh personas from templates, which would mint new ids and orphan the suffix every client and store already uses.
3. **Resume or restart.** The field map says a persona staying on Claude resumes its conversation. The kernel launches with its own six instruction layers; a resumed AH4L conversation carries the hooks' injected reminders and the tmux-era contract.
4. **The pool has no store.** Allocate and release need somewhere to live that is not a bridge file, and the uniqueness domain has to be stated.
5. **The roster readers.** Which server-side reads become roster reads, and when the topic write moves.
6. **Messages in flight.** Three cursors per persona have to be seeded or the first connect replays history (voice) or loses the freeze window (DMs).
7. **Tasks.** The register says "live tasks and their `accountable_manager`"; the store says the key is the name.
8. **Sweeps.** D62 moved the sweep into the store but left "a table or a per-row flag" open, and D63 lists the ledgers as a migration row.
9. **The mirror.** The memento mirror directory moves; the readers must find what was there.
10. **The archive and the tool.** What the archive holds, how it expires, and what runs the whole thing, by whom, with what proof.

## Options and recommendations

### 1. The order of the Switch clock's first steps

**A (recommended): snapshot, then stop, then archive, then import.** Day 0 as D63 wrote it. Then: 1 freeze (no spawn; managers finish or hand off; every open sweep completed; the board swept); 2 **every live seat writes its memento** (`memento_io.py write --slot io`, by broadcast to all, acknowledged on the acks topic); 3 **snapshot**: `lupin kernel migrate snapshot` writes `ah4l-roster-<host>-<date>.json`, one entry per bridge that passes today's liveness rule, with the fields of the map below and the three ledgers inlined; 4 stop AH4L (the D63 step 4, unchanged); 5 archive; 6 import from the snapshot, never from the directory; then the flips, the renames, the wake (step 7 becomes a wake, see 2), the inventory. Pros: the rows are read while the pids that qualify them are alive; nothing migrates under a writer; the snapshot is a file the rollback rehearsal can replay. Cons: one more artefact; the D63 numbering changes.

**B: keep D63's order and migrate from live bridges under a lock.** Pros: no change to the checklist. Cons: the listener re-registers on its next SessionStart and the arbiter touches mtimes every tick; a lock on a directory of files written by eleven processes is not a lock.

### 2. What a migrated persona is

**A (recommended): an imported, hibernated registry row.** `lupin kernel migrate import` writes one `PersonaRow` per snapshot entry with the snapshot's `persona_id`, `state: hibernated`, `engine: claude`, no process, `conversation_id: None` (see 3), the fields of the map below, and `imported_from: ah4l-<date>` on the row. Import is a kernel verb, not an API route: `POST /personas` keeps minting. D63 step 7 becomes `lupin fleet wake --all` (D59's wake: admission, a worktree if the imported one is gone, the D54 first turn with the memento), and only after the fleet is up does Rick move roles onto their template engines persona by persona through the re-spin handshake. Pros: `job_id`, suffix, socket name, mute state, DM routing, memento stamps and task ownership all continue; the wake is machinery that already exists. Cons: the registry gains an import path that must refuse an id already present; the fleet runs on Claude for its first hours after the switch.

**B: fresh spawns from the role templates, names carried over.** Only the voice names survive; everything else is minted. Pros: the simplest import (none). Cons: every DM thread, the client's mute state and the owed-answer routing by `job_id` break at once; the memento resolver falls back from the id to the slug.

**C: import, then re-spin each row onto its template engine in the same step.** Pros: the fleet is on its target engines from day one. Cons: a cold start of every persona at once, on new engines, at the start of the soak; a failure is indistinguishable from an engine fault.

### 3. Resume or restart on Claude

**A (recommended): cold start from the memento; `conversation_id` is not imported.** The memento written in step 1.2 is the continuity mechanism everywhere else (re-spin, dismiss and spawn, engine change). The T10 map row "a persona staying on Claude resumes it" is struck. Pros: one bootstrap path; the kernel's instruction layers meet no stale context. Cons: a seat that failed to write a memento starts from its last record, possibly a day old; the snapshot reports those seats by name so Rick can nudge them before step 4.

**B: resume the AH4L conversation (`--resume <session_id>`).** Pros: nothing lost. Cons: the context carries every `<system-reminder>` the hooks injected and the old contract; `--append-system-prompt` adds the kernel's layers on top; two contracts in one window.

### 4. The voice-persona pool store

**A (recommended): a Lupin table, the endpoint keeps its contract, the kernel is a client.** `voice_persona_allocations( persona_id text primary key, persona_key text not null, host text, allocated_at, released_at )` with a partial unique index on `persona_key where released_at is null`. `POST …/voice-persona/{persona_id}/allocate` (preference chain, 409 with the holder, 422 off-pool) and `…/release` write the table; the pool snapshot reads it; the kernel calls allocate after the mint and before the launch, release at dismissal, never at hibernation (T16 spec Section 15 row 6). The registry row caches `voice_persona` for the roster and the sender badge. The configured pool stays in `lupin-app.ini` under its T38-renamed key. Import: one allocation row per snapshot entry, `allocated_at` from the bridge. Pros: fleet-wide uniqueness regardless of hosts (D59: one fleet per Lupin instance, one kernel per host); the endpoint's three callers change one parameter (the full UUID becomes the eight-hex id); the rollback is a `truncate`. Cons: a second place that knows the name (registry cache and table); the kernel depends on Lupin being up to spawn, which D45 already accepts.

**B: the registry is the store; the endpoint proxies to the kernel socket.** Pros: one writer. Cons: uniqueness per host, not per fleet; the endpoint is down when the kernel is; the pool snapshot has to fan out over kernels.

**C: no pool; each role template pins a name.** Pros: nothing to allocate. Cons: two personas of one role on one project collide; the ad hoc seat (a persona spawned from the console with no template) has no voice.

### 5. The roster readers and the topic write

**A (recommended): four readers to the union read at Move, the kernel roster at Delete, as D63 wrote; the manager badge and the speakerphone gate change meaning.** `_resolve_manager_persona` follows `manager_id` through `GET /personas` instead of walking `spawned_by`. The speakerphone gate in `_notify_impl` stops reading a bridge: under D11 and D28 mute is the client's, so the gate is removed with the bridge and the toggle tools become no-ops that say so (one line in the T27 spec). `set_session_topic` calls `PUT /personas/{persona_id}/topic` on the kernel socket from the Move clock; the listener's `_update_session_topic` is already a Delete row. Pros: one roster. Cons: the badge needs the lineage field to be populated by the import (map below).

**B: keep a bridge-shaped shim that the kernel writes for the readers.** Cons: a second writer of a file format the inventory script is meant to prove gone.

### 6. Seeding the three cursors

**A (recommended): from the ledgers and the bridge's last-interaction time, in one server-side statement for voice.** Per imported persona, `inbox.json` is written by the import with: `dm_cursor := .dm-inbox-hwm.cursor_ts`, `answers_cursor := .ask-answer-hwm.cursor_ts`, `acknowledged := the union of the two surfaced-id lists and the surfaced log`; `voice_cursor := bridge.last_interaction_at`; and the import runs one `UPDATE notifications SET listener_delivered_at = :t WHERE job_id = :id AND direction = 'human_to_ai' AND created_at < :t AND listener_delivered_at IS NULL` per persona, through a new fleet-key route `POST /api/notifications/undelivered/ack-before { job_id, before }` (the only second setter of the column, import-only, logged). The first pull then returns exactly the human messages that arrived after the seat's last turn; duplicates against the ledger are impossible because nothing older is unacked. The voice buffer is archived, not replayed (its frames are rows). Pros: lossless for the freeze window; the replay set is the real in-flight set; the server state is left consistent for the Delete clock. Cons: one new route with a narrow contract.

**B: every cursor at the snapshot time.** Pros: no ledger reading. Cons: a DM or human line that landed between a seat's last turn and the snapshot is never surfaced, and the freeze window is exactly when managers are handing off.

**C: no seeding; rely on the age cap.** Cons: the first pull replays every human line to that seat within the cap; the DM pull seeds and surfaces nothing, so in-flight DMs are lost anyway.

### 7. Tasks

**A (recommended): no migration; the name is the key; the freeze does the work.** The freeze step already sweeps the board; the recommendation adds that each manager hands off or closes its live reports in the store before step 1.2, and that the snapshot prints, per persona, the count of owed rows by name so the first turn-end tick under the kernel can be checked against it (TurnEnd acceptance already covers the query). `created_by` is left as written. The manager-only guard moves to `persona_id` under T21 as planned. Pros: nothing to write. Cons: a persona renamed at the switch loses its rows, so the import refuses a snapshot entry whose name is not in the configured pool.

**B: rewrite `created_by` and any session id in `blocked_by` to persona ids.** Cons: a historical column rewritten for no reader.

### 8. Sweeps

**A (recommended): a `task_sweeps` table, and no ledger migrates.** `task_sweeps( id, persona_key, project, started_at, board_ids jsonb, reviewed jsonb, total_at_start int, closed_at )`, one open sweep per persona and project (partial unique index). The owed-rows query returns `sweep: { reviewed, total }` from the open row (D62). The Move-clock Lupin row is this table rather than a per-row flag, because a flag cannot freeze the set or carry `started_at` for the expiry rule the ledger has today. Because the freeze completes every open sweep, no ledger is imported; the ledgers are archived; the D63 migration row loses its last clause. Pros: D62's open choice closed with the shape the ledger already has. Cons: a sweep a manager cannot finish in the freeze restarts from the store under the kernel.

**B: import unexpired, incomplete ledgers as open sweeps.** Pros: nothing restarts. Cons: a row set frozen under AH4L against a board the freeze is changing.

### 9. The memento mirror

**A (recommended): copy, then the readers see one path.** `rsync -a ~/.claude/mementos/ ~/.lupin/mementos/` at the archive step, idempotent; `memento_io.py verify` (the daily kernel job, D62) runs once against the new mirror before the wake. The records in `io/mementos/` are not touched. Pros: the kernel depends on nothing under `~/.claude` (D54's rule). Cons: a few hundred small files duplicated for 30 days.

**B: point `LUPIN_MEMENTO_MIRROR` at the old directory.** Cons: kernel state under `~/.claude` for as long as anyone forgets to move it.

### 10. The archive, its expiry, and the tool

**A (recommended): one tarball per host, written by the same command, expired by a kernel job.** `lupin kernel migrate archive` writes `~/.lupin/archive/ah4l-<host>-<date>.tar.gz` holding `~/.claude/sessions/` whole, `~/.claude/mementos/`, `~/.claude/heartbeat-events/`, `~/.claude/CLAUDE.md`, the deployed `settings.json`, the arbiter's local snapshot store, a copy of `lupin-app.ini` as of the tag, the roster snapshot and the import report; beside it `ah4l-<host>-<date>.manifest.json` with every path, size and sha256. Claude's `~/.claude/projects/` is left in place, never archived (the rollback needs it where it is). Expiry: the daily `kernel.jobs` run deletes an archive older than `kernel archive retention days` (30) and logs `archive.expired`. The tool is one kernel CLI family, `lupin kernel migrate snapshot | archive | import | report`, dry-run by default, `--apply` to write, idempotent on `persona_id` (an id already in the registry is skipped and reported), reading only the snapshot file; `report` prints the row counts the Delete review attaches. Rick runs it on each fleet host as the persona account from the laptop (SSH; the console's `:` grammar is for the kernel socket, not for host commands). Rehearsal: Switch-4 (the rollback rehearsal on the test VM) gains the forward half, an import from a snapshot captured on the development server, so the first real import is the second one ever run. Pros: one artefact per host, one command, one rehearsal. Cons: the kernel grows a verb used once; the archive of a busy host is a few hundred megabytes.

**B: a central archive on the development server, pulled over SSH.** Cons: the rollback restores per host anyway.

**C: a shell script in `src/captures/` rather than a kernel verb.** Pros: nothing in the kernel for a one-off. Cons: the import writes the registry and `inbox.json`, which only the kernel may write (one writer, D14, D52); a script that writes them is a second writer.
