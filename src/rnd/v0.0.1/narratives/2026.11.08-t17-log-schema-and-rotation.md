# Log schema, rotation and the observers that read it (T17): problems, options, recommendations

2026-11-08 · Rick Ruiz · Claude doc: https://claude.ai/artifact/Hwx8ePwqojtBnGTMDZMpDB

## Why this matters

Every other ruling in this design ends the same way: "it is logged". The inbox ruling rebuilds its ledger from the log. The voice-out ruling measures and cuts nothing, and leaves the measure in the log. The credential ruling redacts at the log writer. The bootstrap ruling writes the memento's age there. The arbiter, folded into the kernel, reads the logs and the registry instead of Claude transcripts. The web console and the terminal console are both readers of the same file. So the log is the one artifact the whole system agrees to trust, and it has never been specified: not its line format, not its names, not how big it may grow, not what happens to it when a persona lives for a month.

This item is the last design the first-phase bootstrap candidate waits on. The first kernel acceptance test writes the log; the third reads it back; the seventh rebuilds a ledger from it. A kernel session that starts building without this item will invent a format, and every later reader will be written against the accident.

Four questions were parked here by earlier sessions: the record schema and rotation; what replaces the turn-age watchdog's terminal-pane check once there is no terminal; how the web console's tailer turns kernel records into the display blocks it already knows; and whether two Lupin routers are deleted or repointed. Reading the code answered one of them outright and reshaped two others.

## The principles this item rests on

1. **One append-only file per persona, from one writer, is the source of truth for all observation** (the session-log decision). Everything below preserves that: rotation is done by the writer, never by an outside tool; nothing else writes beside it.
2. **Redaction happens at exactly two choke points, and the log writer is one of them** (the credential ruling). Any byte that reaches disk under the kernel's name goes through the writer, or it is a hole.
3. **The log is a record, not a report.** It holds what happened in the order it happened. Summaries, pressure estimates and advisories are derived by readers and, when they matter, written back as their own records, never by editing earlier lines.
4. **Readers already exist; keep their contracts.** Lupin's tailer, its wire protocol, and the multiplexer's console were built and tested against Claude transcript files. The kernel log is a different file with a different grammar, but the wire between Lupin and the browser does not need to change.
5. **Bound everything.** Lupin's own history (748,063 hook-log files, 6.1 GB, the leading hypothesis for a fleet outage) is the reason every file the kernel writes has a size, an age and a count that stops it.
6. **No name crosses an interface; the eight-hex persona id does.** The id names the directory, the socket, the job and the log. The console's seat id is the same eight hex.

## The problems, stated one at a time

**Problem 1 — Twenty-five names and no envelope.** Each ruling named the records it needed, in its own style. A reader that wants "everything about turn 41" has nothing to join on; a reader that wants "the order things happened in" has a wall-clock timestamp that two writers on one host can tie. The kernel's own events (start, stop, upgrade, sweep) have nowhere to go at all.

**Problem 2 — Engine stderr is a third writer, and it is not redacted.** The credential ruling applies `redact()` at exactly two choke points. A raw `engine.stderr` file is a third: an engine that prints its environment, or a traceback carrying a header, lands a secret on disk unredacted. It also grows without bound and is the one file in the persona directory no reader knows how to rotate, because the engine process holds it open.

**Problem 3 — Nothing says how big a log may get or how it is cut.** A chief of staff is meant to live for weeks. One file per persona lifetime is unbounded. Cutting it with an outside tool breaks the single-writer rule and the tailer's byte offsets at once. Cutting it too finely (one file per turn) recreates the 748,063-file directory. And the ledger rebuild needs to find recent `inbox.written` records somewhere.

**Problem 4 — A 16 MiB frame is a 16 MiB log line.** A tool result that dumps a file fills a segment in a few turns and makes every tailer poll copy megabytes to render a truncated block. "Every frame verbatim" is the session-log decision's letter; it has never been weighed against what the frames actually carry.

**Problem 5 — The receipt can be posted before the record is on disk.** The inbox ruling's order (write to stdin, append the ledger, post the receipt) exists so that a crash between steps replays at most once. The rebuild reads `inbox.written` from the log. If the log line is still in a buffer when the receipt goes out and the host loses power, the ledger and the log disagree about a message the human has been told was received.

**Problem 6 — The held-turn detector has no pane to look at.** The arbiter's watchdog needs two signals: a dangling tool call in the transcript, and an idle terminal pane. The kernel owns the process and reads its frames directly, so both signals exist in a better form, but nothing says where the detection runs, what threshold it uses, or whether the kernel, which unlike the arbiter *can* interrupt the turn, should.

**Problem 7 — The tailer resolves seats through bridge files and maps Claude transcripts.** Under the kernel there are no bridge files and no Claude transcripts. The tailer's path resolver, its mapper, and the roster's source (`/api/arbiter/fleet-state`) are the three places that know about the old world. Everything downstream of them, the offsets, the epoch, the coalescing, the client store and the renderer, is already right.

**Problem 8 — Two routers were filed under "delete or repoint" and one of them is already a gravestone.** `claude_code_queue` holds two 410 tombstones and nothing else; there is nothing to repoint and nothing to design, only a deletion-list row. `cc_transcript` is the real question, and its answer is Problem 7's.

## Proposed solutions

### Solution 1: One envelope, dotted kinds, payload under `data` (Problem 1)

**Option A — A seven-field envelope with a naming rule (recommended).** Every line is one JSON object:

```json
{ "timestamp": "2026-11-08T18:04:55.123456Z", "monotonic": 10482.771, "sequence": 12345,
  "persona_id": "a1b2c3d4", "turn_id": 41, "kind": "gate.deny", "data": { ... } }
```

- `timestamp` is wall-clock UTC with microseconds, for humans and for joining against Lupin's rows. `monotonic` is the kernel's monotonic clock, for ordering and durations within one kernel run. `sequence` is a per-persona integer that never repeats or decreases, across segment rolls and kernel restarts (recovered from the newest segment's last line at start). `turn_id` is the per-persona turn counter the inbox ruling already uses, null for records outside any turn. `kind` is `owner.event`, lowercase, two or three segments, where the owner is the kernel module that wrote it. Everything the kind needs is under `data`, so the envelope never collides with a payload field and `jq 'select(.kind=="voice.result") | .data'` is the whole query language.
- The kinds, grouped by owner. **`log.`**: `segment` (the first line of every file: schema version, kernel version, engine, engine version, model, previous segment, first sequence), `truncated`, `swept`. **`session.`**: `spawned` (argv, environment keys, `kit_commit`, `mandates_sha256`, conversation id requested), `state` (from, to, reason), `interrupt`, `respawn`, `resume_mismatch`, `exited` (code, signal), `stopped`. **`engine.`**: `stdin` (every frame written to the engine, verbatim), `frame` (every frame read, verbatim, with `event_kind` ∈ `init | text | tool | tool_done | usage | result`), `stderr` (one line each). **`inbox.`**: the five from the inbox ruling, unchanged. **`voice.`**: `result` (the fifteen fields), `posted` (notification id, status, bytes, `spoken_chars`). **`gate.`**: `allow`, `deny`, `would_deny`, `ask`, `unreachable` (the bare `gate_unreachable` renamed), each with `call_id` and `args_sha256`. **`ask.`**: `opened`, `answered`, `expired`, `escalated`. **`memento.`**, **`respin.`**, **`mandates.duplicate_global`**: as the bootstrap ruling named them. **`watch.`**: `held_turn`, `pressure` (the fleet-health module's own records; the threshold is T23's). **`kernel.`**: `started`, `stopped`, `upgraded`, written to the kernel's own log (Solution 9) with `persona_id: null`.
- Pros: one grammar for every reader; a join key per turn; a total order per persona; the existing names survive (dotted ones as they are, the three bare ones folded into `session.spawned` or renamed); the rule tells the next ruling where its records go without a conversation.
- Cons: the three bare names in the bootstrap and Phase 1 specs change; `monotonic` is meaningless across kernel restarts and must be read beside `sequence`.

**Option B — Flat records: envelope fields and payload fields side by side.**
- Pros: one level less to type.
- Cons: a payload field named `kind` or `timestamp` shadows the envelope; every reader must know every kind's fields to parse the envelope; the inbox ruling's `inbox.received` already carries a raw notification dict whose keys would collide.

**Option C — Keep the names as the rulings wrote them, add a timestamp, no envelope.**
- Cons: Problem 1 as stated; the bootstrap candidate's first test would be written against it.

### Solution 2: Stderr goes through the writer (Problem 2)

**Option A — The kernel pumps stderr line by line into the log as `engine.stderr` records (recommended).** The raw file is deleted from the Phase 1 spec. The pump reads the pipe with the same line limit as stdout, redacts at the writer like every other record, and rotates with the segments. A cap of `log stderr lines per minute` (default 600) drops the excess and writes one `log.truncated { stream: stderr, dropped }` record per minute, so a looping engine cannot flood the log.
- Pros: two writers again, as the credential ruling requires; stderr is in the same order as the frames it explains; rotation and retention are one problem, not two; the console can show it.
- Cons: a pathological engine's stderr now competes for the segment; the per-minute cap is a dial that must exist.

**Option B — Keep the raw file, redact it at read time.**
- Cons: the secret is on disk the whole time; every reader must redact; the file is still unrotatable while the process holds it.

**Option C — Keep the raw file, rotate it by reopening at each segment roll.**
- Cons: the engine holds the file descriptor, so the kernel can rotate only by passing a pipe anyway, at which point Option A is the same work with redaction included.

### Solution 3: Writer-owned segments, age retention in exact minutes, a floor and a cap (Problem 3)

**Option A — Segments (recommended).** The writer appends to `~/.lupin/kernel/personas/{persona_id}/log/{yyyy.mm.dd-HHMMSS}.jsonl` and rolls to a new file on any of three triggers: the file reaches `log segment max megabytes` (default 64, Lupin's number); the kernel starts (so every segment's first line names the kernel version that wrote it); the first record of a new UTC day. Every segment's first line is `log.segment`, naming the previous segment and the first sequence, so the chain can be walked backwards. Retention is a sweep inside the kernel, hourly, dry-run by default in the command-line verb and applied by the timer: a segment is deleted when it is older than `log retain minutes` (default 20,160, fourteen days, measured in minutes as the `io/tmp` ruling insisted) **and** it is not one of the two newest; and whenever a persona's `log/` exceeds `log persona max megabytes` (default 1,024) the oldest beyond the floor goes regardless of age. A persona directory whose row is `closed` is deleted whole once its newest segment passes the retention age; its registry row stays, so a later spawn from the same manifest resumes the stored conversation cold. The sweep writes `log.swept { persona_id, deleted: [names], bytes }` to the kernel log.
- The ledger-rebuild constraint relaxes once stated precisely: the rebuild reads retained segments newest-first for the answers and DM cursors (the newest `inbox.received` of each kind) and for `inbox.written` ids, stops at 500 or at the oldest retained line, and logs `inbox.rebuilt { from_log_lines, ids_found }`. A message older than the recovered cursor is never pulled again, so fewer than 500 ids is a complete rebuild, not a partial one. The inbox spec's Section 9 is amended to say so.
- Pros: the writer is the only process that creates or ends a file, so the single-writer rule holds; the tailer's `file_epoch` becomes the segment name and a roll is the `rotated` state it already handles; three bounds (size, age, count) and no flat directory of thousands of files; Lupin's own defaults and its minutes lesson reused.
- Cons: a reader that wants a whole month walks several files; the daily roll makes short-lived personas leave one small file per day of life.

**Option B — One file per persona lifetime, deleted when the persona is reaped.**
- Cons: unbounded for the chief of staff; the tailer's REST backlog window becomes the only way to read a 2 GB file; no retention at all for a persona that never stops.

**Option C — `logrotate` with `copytruncate`.**
- Cons: copies then truncates a file the writer has open, so a record written between the copy and the truncate is lost; invalidates every tailer offset without an epoch change; a second process writing to the directory. Lupin's own script documents why not.

**Option D — One file per turn.**
- Cons: the 748,063-inode directory, again.

### Solution 4: Verbatim to one megabyte, then head and tail with a hash (Problem 4)

**Option A — Cap a single record's `data` at `log frame max kilobytes` (default 1,024); beyond it keep the first and last quarter and write `truncated: true, original_bytes, sha256` (recommended).** Applies to `engine.frame`, `engine.stdin` and `engine.stderr` only; kernel records are small by construction. The hash lets two sightings of one oversized blob be matched without storing it twice.
- Pros: a tool result that dumps a file no longer costs the log a megabyte per line and the tailer a megabyte per poll; what the model saw is still legible at both ends; the session-log decision's "every frame" survives as "every frame, bounded".
- Cons: an analysis that needs the middle of a two-megabyte tool result has lost it; the decision amends the letter of the session-log decision.

**Option B — Verbatim always, up to the 16 MiB line limit.**
- Pros: nothing is ever lost.
- Cons: Problem 4 as stated; the daily segment can roll ten times in an afternoon.

**Option C — Cap at 256 KiB.**
- Cons: a long ordinary file read is cut; the gain over one megabyte is small once segments exist.

### Solution 5: Flush every record; sync the ones a crash would contradict (Problem 5)

**Option A — `flush()` after every record; `fsync()` after `inbox.written`, every `session.*`, `gate.deny` and `gate.ask`; the inbox's receipt post waits for that sync (recommended).** The writer is one asyncio task per log consuming a queue; `append( kind, data, turn_id=None, durable=False )` returns a future that resolves when the line is flushed, or synced when `durable` is set. The session awaits the durable future for `inbox.written` before posting the receipt, which is the order the inbox ruling already prescribes, now with the disk in it.
- Pros: the rebuild and the ledger cannot disagree after a crash about any message the human was told was received; a dozen syncs per turn, not thousands; frames stream unsynced.
- Cons: the receipt is delayed by one sync (milliseconds on the test VM's disk); the durable set is a list someone must keep.

**Option B — `fsync()` every record.**
- Cons: a sync per text delta on a streaming engine; the Jetski family emits dozens per second.

**Option C — `flush()` only.**
- Cons: Problem 5 as stated.

### Solution 6: The session detects the held turn; the fleet-health module only reads (Problem 6)

**Option A — Detection in the session task, advisory through the escalation chain, interruption behind a manifest flag that defaults off (recommended).** The session owns the process, so it has the arbiter's two signals exactly: the open tool call (an `engine.frame` of event kind `tool` with no `tool_done`) and the pane (no frame of any kind since it). The signature: state `busy`, open tool call older than `watch held turn seconds` (default 600, the arbiter's), no frame since; never in `awaiting_human` (an open ticket is a wait, not a hang; `ask_wait` holds at most 150 s by the ticketed-asks ruling). On match the session writes `watch.held_turn { call_id, tool, age_seconds, action }` once per call id and posts one advisory up the escalation chain (`priority: high`, `type: alert`, the same rail as a process exit). Manifest `watch: { held_turn_action: advise | interrupt }`, default `advise`; `interrupt` sends the interrupt the kernel already owns (the urgent-message path) and the next envelope opens with the kernel block naming the cut call, as the inbox ruling specified. The fleet-health module (the former arbiter) reads `watch.*` and `engine.frame[usage]` records and the registry; it polls nothing and holds no detector. The arbiter's `turn_age_watchdog.py` and `context_pressure_writer.py` are retired at switch-over.
- Pros: no second process re-deriving state the kernel already has; the flood guard is one set of call ids per session, cleared when the call completes; the kernel can act where the arbiter could only advise, and the operator chooses per persona; the Jetski family's 180 s MCP cut means a held turn past 600 s there is an engine hang, not a slow tool.
- Cons: an `interrupt` default would be wrong for a persona running a legitimately long shell command, which is why it is off; the threshold is one number for every tool until usage says otherwise.

**Option B — The fleet-health module polls the logs for dangling `tool` records.**
- Cons: re-reads what the session knows; a second clock; the arbiter's design reproduced inside the kernel.

**Option C — Interrupt by default after a second threshold.**
- Cons: cuts long builds and test runs; the inbox ruling's interrupt path was designed for a human's urgent message, not a timer.

### Solution 7: Keep the tailer and the wire; swap the resolver, the roster's source and the mapper (Problem 7)

**Option A — Three swaps inside Lupin, zero client changes (recommended).**
- *Resolver:* `resolve_transcript_path( persona_id )` asks the kernel over its Unix socket (`GET /personas/{persona_id}`), gets `log_dir`, and takes the newest `*.jsonl` in it by name. The kernel directory `~/.lupin/kernel/` is bound into Lupin's container at the same absolute path, as the sessions directory is today; the socket comes with it. A segment roll is a changed path, which the tailer already reports as `rotated`, and the client already refetches the backlog from offset zero. `file_epoch` is the segment name.
- *Roster:* `/api/cc-transcript-roster` projects `GET /personas` from the kernel instead of `/api/arbiter/fleet-state`; `transcript_watchable` is "the newest segment exists here"; an unreachable kernel is reported as `unreachable`, never as an empty fleet, exactly as today.
- *Mapper:* a kernel-record mapper beside the Claude one, same block shape, same three rules. `engine.stdin` → role `user`, kind `text` (the envelope as written). `engine.frame[tool]` → `tool_call` with the tool name and its input one-lined; `[tool_done]` → `tool_result`, named through the same bounded call-id index; `[result]` → role `assistant`, kind `text` (the final text; the spoken line is in `voice.result`); `[text]` deltas skipped by default behind the dial `persona log show deltas` (off); `[init]` → role `kernel`, kind `kernel`, "started agy 1.4.7 gemini-2.5-pro conversation …"; `[usage]` skipped (the fleet-health module's business); a `thinking` block only if an engine is measured to emit one (none is today). `session.*`, `gate.deny`, `gate.ask`, `inbox.duplicate`, `inbox.rebuilt`, `watch.*`, `engine.stderr`, and `voice.result` with `needs_repair` → role `kernel`, kind `kernel`, one line each. Everything else skipped by rule (a). The renderer shows kind `kernel` as plain text today; a style for it is console work (T20).
- *Paths:* `/api/cc-transcript/{cc_session_id}` and `/api/cc-transcript-roster` keep their paths and their admin gate through Phase 1, because the seat id is the persona id byte for byte. A rename to `persona-log` is a switch-over row (T19), when the old transcripts are gone.
- Pros: the smallest change that works; every tested piece of the console (gap repair, epoch change, coalescing, grace, admin gating) is reused as is; the kernel gets no second tail protocol.
- Cons: Lupin's container must mount the kernel directory; a host that does not share the kernel's filesystem cannot watch its personas (the fleet item, T16, owns multi-host).

**Option B — The kernel serves the tail over its API and Lupin proxies it.**
- Pros: works across hosts.
- Cons: a second offset-and-epoch protocol in the kernel, mirroring 495 lines that already exist; the proxy adds a hop to every poll; premature before the fleet item rules on multi-host at all.

**Option C — A new log view in the multiplexer.**
- Cons: a client rewrite for a console that already renders every block kind the kernel will send.

### Solution 8: `cc_transcript` is repointed; `claude_code_queue` leaves this item (Problem 8)

**Option A — Repoint `cc_transcript` per Solution 7; strike `claude_code_queue` from T17 and put its two tombstones on the deletion list (recommended).** The arbiter's watchdog daemon and context-pressure writer join them there, since Solution 6 replaces both. Framework Section 18's row changes from "delete or repoint" to "repointed (T17); tombstones to T19".
- Pros: the item's scope matches the code; the deletion list gets three rows with a reason each.
- Cons: none found.

**Option B — Rename the routes now.**
- Cons: a client change during Phase 1 for no behavior; the old transcripts are still watched under the current harness.

**Option C — Delete `cc_transcript` and build a kernel-side console later.**
- Cons: the console disappears at switch-over and comes back at an unspecified date.

### Solution 9: The kernel keeps a log of its own, by the same writer (a corollary of Problem 1)

**Option A — `~/.lupin/kernel/log/{yyyy.mm.dd-HHMMSS}.jsonl`, same envelope with `persona_id: null`, same segments, same sweep (recommended).** Kinds: `kernel.started` (version, config digest, owner user id present, invariants checked), `kernel.stopped`, `kernel.upgraded`, `log.swept`, `vetting.*` from the self-update ruling, `registry.written`.
- Pros: the only process events that otherwise go to a terminal or journald are in the same grammar as everything else; the sweep's own work is on record.
- Cons: one more directory under the sweep's eye.

**Option B — Kernel events to stderr and the service manager's journal only.**
- Cons: two formats; `jq` cannot join them; the sweep's deletions are unrecorded.
