### The data directory

- The October line: "Test a separate `--app_data_dir` per persona with the OAuth token symlinked, then resume in it. Settings, conversations and token currently share one directory."
- It was written for three kinds of isolation. The design has since settled each of them another way:
  - *Sign-in.* One Google-account sign-in per host, shared by every persona, kept in one file; several sign-ins were considered and rejected because "the tool keeps one sign-in per operating-system account, so several accounts would race" (sign-in and quota spec, lines 11, 25, 500). A directory per persona would need a copy or a link of that file in each, which is the arrangement the ruling avoids.
  - *Settings.* Each persona's hooks, agent definition and instruction files are written into its own worktree (framework Section 5.1, the `tool_veto` and `system_prompt_flag` rows; Section 10.3).
  - *Conversations.* Each persona resumes by a conversation identifier the kernel holds and verifies at every start (Phase 1 spec, the resume rule).
- Identity, the "C3 partial case" the framework's table cites, passed on 2026-10-18 by another route: each engine process inherits its own environment.
- On this host: `--app_data_dir` is **not among the 26 flags `agy --help` lists**, yet the name occurs 12 times in the 1.5.9 binary, once in the form of a launch flag. During this session's exploration the flag was tried once by hand with an absolute path: the engine refused it ("must not be absolute") but had already created a directory tree under `~/.gemini/`. So the flag is real, undocumented, and takes a name relative to `~/.gemini/`. The script does not launch with it, for that reason.
- What the record does not show: any fault from several engines sharing the one directory. Two engines ran side by side in October's identity capture without one. If a fault appears it will appear in the first acceptance test that runs two personas together.

### Stopping in the middle of a tool call

- The October line: an interrupt while the model was writing text ended the process "in about 0 s"; an earlier one, during a shell command, "suggests about 6 s". One observation, never repeated.
- How the kernel interrupts the Jetski family: a signal to the engine's process group; the engine writes its last frame and exits; the kernel starts it again on the same conversation (framework Section 5.1; Phase 1 spec, line 130 and the state table at lines 149 to 158).
- **A gap found while reading.** The state table has a row for "the process exits while being interrupted" and none for "the process does not exit". A persona whose engine hangs after the signal stays in the interrupting state for good, and the urgent message that caused the interrupt is never delivered. Nothing else catches it: the held-turn watch runs only while a persona is busy (log spec, Section 7), and the kernel's ordered stop has its own limits (10 seconds of grace, 180 to drain) that do not apply here.
- The acceptance test for interrupts, Kernel-5, runs on the real engine but interrupts a model that is counting aloud, which is the fast case.
- The vendor's release notes add two facts: since 1.4.11 an interrupted turn's last frame says so (`finished_reason: interrupted`); since 1.5.5 a headless run "finishes shutting down within 30 seconds" after its result. Neither states the time from the signal to the result during a tool call.
- Measuring it costs a model turn or two, on each engine.

### Denying a tool-server tool by rule

- The October line belonged to a fallback: if no hook could veto a tool call, deny the engine's own shell tool by a static rule and route commands through a Lupin tool. It asked whether such rules exist and how one names a tool-server tool.
- The fallback was never needed: the hook veto passed on AGY and on Jetski (the first gate, C1), and on Claude.
- The tool-approval ruling considered static engine rules mirroring the gate and set them aside: "a second rule table to keep in step; deny rules do still work under bypass, so this stays available as defense in depth if a case appears" (tool-approvals spec, line 239).
- The syntax is now public. AGY: `mcp(server/tool)` as a deny or ask rule (release notes, 1.5.8), honored when permissions are skipped ("your explicit deny rules still apply", 1.5.2), listed at zero tokens by `agy -p "/permissions"`, which on this host shows three scopes and only `command(…)` rules. Claude: `mcp__<server>__<tool>`, and deny rules still block under bypass (framework Section 2, the permissions paragraph; Section 8's name table).

### An interrupt sent as a message, on the Jetski family

- The October line: the Jetski family answers a `control_request` with "not supported yet"; "check `agy changelog`. When it lands, flip `interrupt_mode` to `control` and the respawn disappears." Claude has this and it was verified (C6): the process survives an interrupt.
- Today, AGY 1.5.9, at zero tokens: a `control_request` on standard input is answered `stream input message event "control_request" is not supported yet`, where an unknown message (`interrupt`) is merely ignored with a warning. The vendor still reserves the name and still refuses it. The release notes do not mention it in any version.
- The design does not need it. The signal route is measured, is in the Phase 1 state table, and gives each persona crash containment as a side effect (framework Section 2, the process-boundary table).
- The kernel already runs a check on every engine version it has not seen before, and refuses to start a persona on a version that fails it (the engine-vetting ruling).
- Not read: Jetski itself, which runs only on the cloud workstation. The script takes `jetski` as its argument.
- A detail for whoever next uses the capture driver: `drive.py` sends this message with a `type` field; AGY 1.5.9 reads `event`, so the driver's form is refused one step earlier, for the missing field.

### Claude's `auto` mode against the gate

- This line is not from October; it was added by the tool-approval ruling on 2026-11-05. That ruling keeps `auto` mode out: it is "a second, opaque authorizer" (framework Section 8, the Claude paragraph), and in a headless run its classifier "pauses after 3 consecutive blocks, which … is a silent denial" (tool-approvals spec, line 32).
- The capture it left is a comparison: the same set of tasks run under skipped permissions and under `auto`, counting what the classifier blocks against what the gate would deny. The framework's own entry says when: "after Kernel-1 to Kernel-8; needs a task set and a Claude host."
- Neither exists today: no kernel code is written, and no task set is defined. Nothing in any phase waits on the result; it would only inform a later proposal to reverse the ruling.

## Problems and options

### 1. The data directory for each persona

The line asks for a capture of an arrangement the design no longer wants.

- **A. Close as not needed (recommended).** Record why (sign-in shared by ruling, settings in the worktree, conversations by identifier), and record what was learned about the flag so nobody rediscovers it. *For:* consistent with three rulings; no cost. *Against:* if shared state between engines ever proves a problem, the flag's behavior on resume is still unmeasured.
- **B. Capture it anyway.** One zero-token launch with a relative name, then a resume, which costs a turn. *For:* a known escape route. *Against:* tests a hidden flag the vendor may remove; writes into the directory that holds the host's sign-in; answers a question nobody is asking.
- **C. Leave the line open until two personas have run together.** *For:* closes on evidence. *Against:* keeps a register item open for a test that will report the fault by itself if there is one.

### 2. Where the stop time during a tool call gets measured

- **A. Inside Kernel-5, as a second leg (recommended).** Kernel-5 already interrupts the real engine; add a leg that interrupts during a long shell command and writes the seconds from signal to exit into the interrupt's log record. *For:* no separate capture; measured on the kernel's own launch line, per engine, and again whenever the test reruns. *Against:* the number arrives only when Kernel-5 does.
- **B. A capture now.** A small script, one or two turns on the cheapest model, run by Rick on each engine. *For:* the number in hand before the build. *Against:* tokens and a runbook entry for a figure that changes nothing before Kernel-5, since decision 3 can be set without it.
- **C. Drop the line.** *For:* least work. *Against:* leaves the one observation of 6 seconds as the whole record.

### 3. What the kernel does when an interrupted engine does not exit

The gap described above. Independent of decision 2.

- **A. Wait 30 seconds, then kill the engine's process group and start it again on the same conversation (recommended).** One configuration key, `kernel interrupt exit seconds = 30`. The figure is the vendor's own stated limit for a headless run to finish shutting down; the only observation (6 seconds) is well inside it. The kill is logged, and the ordinary resume check then says whether the conversation survived. *For:* an urgent message is always delivered; the engine is given the time its vendor says it may take, so a kill should not cut a conversation being saved. *Against:* in the worst case a spoken urgent message waits 30 seconds.
- **B. The same with 10 seconds,** the kernel's existing grace figure. *For:* faster worst case; one figure fewer. *Against:* shorter than the vendor's stated limit, so it risks killing an engine that is still writing its conversation, which the resume check would then report as a mismatch.
- **C. No limit; leave it to the operator.** *For:* nothing to build. *Against:* a hung persona that looks busy, and an urgent message silently undelivered.

### 4. The rule syntax for tool-server tools

- **A. Close on the record (recommended).** The fallback was never needed; the syntax is published for both families and written down here. *For:* complete; no cost. *Against:* the AGY rule has not been exercised on this host (the 1.5.8 note is itself a fix for such rules being ignored).
- **B. Exercise one rule.** Write an `mcp(…)` deny rule into a throwaway project, run one turn that calls the tool. *For:* seen working. *Against:* a turn spent on a mechanism the tool-approval ruling set aside.

### 5. The message interrupt on the Jetski family

It is refused today and the design does not wait for it, but the day it lands it removes a restart from every interrupt.

- **A. Close the capture; add the zero-token probe to the check the kernel runs on each new engine version (recommended).** The check sends the one message with no turn in flight and records the answer; when the answer stops being "not supported yet", the kernel posts one notice. The adapter is not changed by the notice: switching the interrupt route is then a small item of its own, with a capture of what the engine does. Jetski's reading today is one run of the new script on the cloud workstation. *For:* nobody has to remember to look; costs no tokens; no behavior changes unasked. *Against:* one more line in the version check.
- **B. Close and drop.** *For:* simplest. *Against:* the improvement arrives unnoticed.
- **C. Keep the line open and reread the release notes by hand.** *For:* no kernel change. *Against:* the notes have never mentioned it, so the reading would be of the wrong source.

### 6. Claude's `auto` mode

- **A. Carry it as one row in the list of owed actions, to run after the Claude adapter exists, with no gate waiting on it (recommended).** *For:* the register item can close; the question is not lost; it sits where it can be done (it needs the gate's would-deny log and a Claude persona). *Against:* a row that may stay open a long time.
- **B. Drop it.** The ruling already keeps `auto` out. *For:* one row fewer. *Against:* the ruling itself asked for the comparison.
- **C. Keep the register item open for it.** *For:* visible in the register. *Against:* an item that cannot close before Phase 3 for a study no phase needs.
