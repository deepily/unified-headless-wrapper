## Problems and options

### 1. The word that marks a refusal as caused by the settings file

A spawn refused because a key is bad has to reach its caller as something. The amendment made it the existing refusal, `admission_refused` (HTTP 409), with a new value of its `check` field: `configuration`. Not retryable.

**A. Confirm: `admission_refused`, `detail.check: configuration`, not retryable (recommended).**
- For: every caller already handles this refusal and already reads `check`; nothing new to learn. It is true to what happened: the admission ran and said no. "Not retryable" is right, because retrying changes nothing until a person repairs the file. The word matches `ConfigurationError`, `ConfigurationManager` and the amendment's titles.
- Against: the other six values name a limit the request ran into; this one names a fault in the kernel's own settings, which the caller did not cause and cannot cure.

**B. A new error code of its own, `configuration_invalid`, as a server fault (HTTP 500 or 503).**
- For: says plainly that the fault is the kernel's side, not the request's.
- Against: a new code in the catalogue, a new branch in every caller and in the command line's exit codes, for a case that behaves exactly like a refusal: nothing changed, nothing was admitted. A 503 would be marked retryable by the contract's own rule, and it is not.

**C. The same refusal with another word, `settings`.**
- For: the plainer word.
- Against: the code says "configuration" everywhere; a second word for the same thing.

### 2. What the refusal says

The control API's rule is that a refusal's message is one plain sentence, because a model reads it as the result of its tool call and a person reads it on the command line. The amendment set the message to the error's raw text, which reads `kernel fleet size cap: above its maximum of 18: 20`. A manager persona that asked for two workers and got that back has not been told that nothing is wrong with its request, nor that no later request will succeed either.

**A. A sentence built from the key and the reason, and both carried as fields (recommended).** The message: `The settings file cannot be used, so nothing is admitted: kernel fleet size cap is above its maximum of 18: 20.` The fields: `detail: { check: configuration, key, reason }`. The sentence is built by one function from the error's two fields; the twelve texts the probe printed all read correctly after "is".
- For: keeps the contract's rule, which the other six refusals keep. A model is told what to do with it (stop asking; tell someone). A program that wants the key reads a field rather than cutting a string, which the contract forbids anyway ("nothing parses it").
- Against: one more function and one more test. The wording becomes something to keep steady.

**B. As written: `<key>: <reason>`, and `detail` carrying only the check.**
- For: nothing to build; the text is exact.
- Against: the one refusal that breaks the contract's sentence rule; the key reachable only by parsing.

**C. The raw text as the message, with `key` and `reason` added as fields.**
- For: programs are served.
- Against: the model and the person at the command line are not.

### 3. A wake while a key is bad

A hibernated persona is woken by a message arriving for it, and a wake is an admission. If the file changed since the last good read and now has a bad key, something must happen to that wake. The amendment chose: deferred exactly as a wake refused for memory is. The message stays queued, one record is written, and the wake is retried until the file is repaired. Nothing is lost. What it costs: until someone repairs the file, **every hibernated persona that receives a message stays asleep.**

**A. Confirm the deferral, and name the key in the record: `session.resume_deferred { reason: configuration, key }` (recommended).**
- For: one rule for spawns and wakes, which is what ruling 4 says of spawns and what you ruled for a bad table row on the same day (refused, with running personas left as they were). Nothing is dropped. A bad edit is noticed within one message rather than at the next spawn, which may be hours away. The memory reason carries `fit`, the number that explains it; this one should carry the key for the same purpose.
- Against: one mistyped number silences every sleeping persona until it is corrected.

**B. Confirm as written: `{ reason: configuration }` and nothing else.**
- For: nothing to change.
- Against: whoever reads the log must find the key somewhere else.

**C. A wake uses the last good record; only spawns are refused.** The reader keeps the last configuration that passed, so the means exist.
- For: a typing mistake cannot silence the fleet. Sleeping personas keep answering.
- Against: wakes are then admitted against numbers the operator has replaced, including a memory reservation changed to relieve a full host; the mistake stays unnoticed until someone spawns; and spawns and wakes follow different rules.

### 4. Which bad key defers a wake

Nobody chose this; the code implies it. The reader builds one record from every admission key (the six dials, the memory table, the three memory ratios) or raises one error. A wake reads only the memory part. So today a mistake in `kernel fleet batch cap`, which no wake ever consults, defers every wake (the probe, finding 2).

**A. Any bad key defers a wake: the file is whole or it is refused (recommended).**
- For: one record, one check, one sentence to explain. It is how the start already behaves: the kernel will not start on any bad key, whichever part of it would have read that key. The repair is the same edit either way, and the file is in a state its operator did not intend.
- Against: the reach of a typing mistake is wider than strictly necessary.

**B. A wake is deferred only for a key it reads: the reserve keys and the memory table.**
- For: the narrowest effect.
- Against: two loaders, or one loader that reports errors by part; the reader must keep a half-good record; and a file known to be wrong keeps being used in part, which is the kind of quiet fallback the row 57 and row 60 rulings turned down.

### 5. Who is told

The person who can repair the file is you. As written, a refused spawn tells its caller and nobody else; if the caller is a manager persona, you learn of it only if the manager thinks to say so. A deferred wake is announced "as for memory": one line to the persona's manager and one spoken line to you, per persona, and the only spoken wording on record is `<name> is waiting for room on the host`, which would be false here. With eight personas asleep and a bad file, the memory pattern would speak eight lines about one mistake.

**A. One spoken line to you per bad file, whichever admission meets it first, spawn or wake; each deferred wake still writes its record and advises its manager (recommended).** The line: `The kernel's settings file has a bad key, <key>. Nothing is admitted until it is corrected.` "Per bad file" means once for each new state of the file that is refused; correct it wrongly and you hear the new key once.
- For: you hear about it once, at once, with the key, however it was met. Managers still learn why their worker has not answered. No chorus.
- Against: a small piece of new state (the file already announced). It departs from the memory pattern, where each persona's wait is its own news.

**B. As for memory: one line per deferred persona, with its own wording (`<name> is waiting for the settings file to be corrected`); a refused spawn tells only its caller.**
- For: no new machinery; the same shape as the other three reasons.
- Against: many lines for one cause; none of them names the key; and a refused spawn with no wake pending tells you nothing.

**C. Nobody beyond the caller and the log.**
- For: the least to build.
- Against: a fleet that cannot grow or wake, and the one person able to cure it is not told.

### 6. A file already refused, not yet repaired

Ruling 2 was "only when the file has changed". The amendment stores the file's three identifying values only after a read that passed, and says what follows: "a read refused for a bad key is therefore made again at the next admission though the file has not changed". Measured: twenty reads in five minutes for one waiting persona (the probe, finding 1). Each read is about 23 ms of the kernel's one thread and, with a launch override in force, about six printed lines. Eight waiting personas make eight reads every 15 seconds, for as long as the file stays wrong: the one case in which the file is read without having changed.

**A. Remember the refused file as well: read once, refuse again from memory, read again when the file changes (recommended).** The reader stores the identifying values and the error of the last refused read; while the file still has those values, the admission is refused with the same error and `init()` is not called.
- For: it is ruling 2 kept in the bad case as well as the good one: the file is read when it has changed, and at no other time. No repeated reads, no repeated printing. About four lines of code. A repair is still seen at the very next admission, because any repair changes the file.
- Against: a second remembered state. A key whose value comes from an environment variable could not be cured without touching the file; the amendment already notes that the kernel's environment does not change while it runs, so the case does not arise.

**B. As written: a refused file is read again at every admission and every retry.**
- For: nothing to change; the cost is small in absolute terms (eight waiting personas take about 1.2 percent of the thread).
- Against: reads of a file known not to have changed, against the sense of ruling 2; log noise that grows with the number of sleepers, precisely while someone is trying to read the log to find the fault.

### 7. The names

Row 71 lists five. The module holds nine that the builder will copy, so all nine are put to you:

| Name | What it is |
|---|---|
| `configuration_reread.py` | the module |
| `AdmissionSettings` | the six dials, as one frozen record |
| `AdmissionConfiguration` | what one admission decides on: those six, the memory table and the three memory ratios |
| `AdmissionConfigurationReader` | the object that holds the kept manager and answers each admission |
| `load_admission_settings` | checks the six keys and builds the first record |
| `load_admission_configuration` | builds the second record (not on row 71's list) |
| `file_identity` | returns the file's inode, size and modification time |
| `current()` | the reader's one method: the configuration for this admission |
| `launch_overrides` | the overrides the manager was first built with |

They break no house rule: no abbreviation, no engine's name. One thing to weigh: "identity" in this project otherwise means who a persona is proven to be (the proven-persona-identity ruling), and here it means which file this is.

**A. Confirm all nine (recommended).**
- For: each says what the thing is; the fleet spec already uses one; `file_identity` cannot be mistaken in context, since its argument is a path and it lives in the configuration module.
- Against: the word "identity" doing two jobs in one code base.

**B. Confirm eight and rename `file_identity` to `file_stamp`.**
- For: "identity" keeps one meaning.
- Against: "stamp" suggests a time alone, and the inode is the half that catches an atomic replacement.

**C. Name them yourself.** As you did with `ConfigurationError`.

### 8. The acceptance tests and their gate

Five tests, all with Kernel-1: the file untouched means no read (Reread-1); a limit lowered on disk takes effect without a restart, by replacement and by edit in place (Reread-2); a launch override survives the re-read (Reread-3); a memory ratio changed on disk does not move the running sampler (Reread-4); each admission key, missing and out of range, stops the start or refuses the spawn (Reread-5). Kernel-1 is the right gate: it is where admission is built, on fake engines, and the memory tests that the fourth leans on (Capacity-1 to Capacity-5) run there too.

The gap: **no test wakes a persona while a key is bad.** Reread-5 refuses a spawn. The deferral of problem 3 is behavior with no test, and it is the behavior with the widest effect.

**A. Confirm the five with Kernel-1 and add Reread-6 with Kernel-1 (recommended).** Reread-6: a hibernated fake persona, a key made bad on disk, a message sent to the persona. Proves: the wake is deferred with its record, the message is still queued, the file is read once however many passes go by (if problem 6 is ruled that way), you are told once (if problem 5 is), and on the first pass after the file is corrected the persona wakes and receives the message.
- For: the deferral is proved where it is built; one test covers what problems 3 to 6 settle.
- Against: one more test at the first gate, which already carries the most.

**B. Confirm the five as written; no sixth.**
- For: nothing added to Kernel-1.
- Against: the builder may leave the wake path out and every test still passes.

**C. Confirm the five, and put the sixth at Kernel-2.**
- For: lightens the first gate.
- Against: Kernel-2 is the first gate with a real engine; this test needs none, and the memory wake test it mirrors (Capacity-5) is at Kernel-1.
