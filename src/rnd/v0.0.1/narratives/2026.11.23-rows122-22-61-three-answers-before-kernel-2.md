# Three small answers before the second kernel gate: the two quota settings, the shared Google account, the heap setting (rows 122, 22 and 61 of "Outstanding actions")

**As of:** 2026-11-23 (second session) · written on the test VM under Antigravity, before any ruling; the rulings were entered the same evening · this repository at `05fa442`, lupin at `e8f253162d` (read for one fact: its settings file holds no kernel key yet) · no register item and no new decision row; what is ruled here is recorded under the decisions on engine sign-in and quota and on host capacity (D68 and D60 in the glossary).

## In brief

Three questions have stood open on the list of owed work, each needed before the second kernel gate (Kernel-2), which is the first gate where the kernel reads a real host's settings file and starts a real engine.

1. **The two quota settings.** The kernel refuses to start a new persona when an allowance is under a floor (0.15), and keeps a reserve (0.25) for managers. Both numbers are settings. No ruling has ever said whether the settings must be present, what values are legal, or what the kernel does when one is missing or absurd. Every comparable setting has had that ruling; these two were missed.
2. **The shared account.** Whether the development server and the test VM are signed in to the same Google account. Only Rick knows: the design never reads an account's identity. The answer changes no code, but it says whose usage the test fleet's allowance is shared with.
3. **The heap setting.** The design launches the Antigravity engine with a setting that limits its JavaScript memory heap to 6,144 MiB, on the belief that the engine is a Node program. A script run for this page shows that it is not: **the engine on this host is a Go program with no such heap, so the setting cannot do anything.** The same reading shows that the companion setting, which stops the engine from relaunching itself, is a name the engine's binary does not contain.

Eight decisions are asked: four on the first question, two on the second (the second of them only if the answer is "the same account"), two on the third. Nothing is built yet, so each is a change to text and reference code only.

## Where the record stands

### The two quota settings (row 122)

- The two keys are `kernel engine quota spawn floor = 0.15` and `kernel engine quota reserve = 0.25`, as ruled on 2026-11-23 (sign-in and quota spec, the amendment for row 21, "Records and configuration"). That amendment says in so many words that whether they are required and bounded "is not ruled here or anywhere".
- In the reference code they are defaults of a class (`QuotaPolicy`, the same amendment): a file that omits them, or misspells one, runs on 0.15 and 0.25 without a word.
- The floor is an admission check: it refuses a spawn (`engine_quota`, `reason: low`). A wake is never refused by the floor ("a wake's message deserves an answer while any allowance remains"; the spec's Section 6). The reserve is not an admission check: it runs before every new turn, and under it only the chief of staff and managers start turns. It has two companion keys, `kernel engine quota reserve mode` (`observe`, `enforce` or `off`; `observe` today, to be switched to `enforce` after a week of records) and `kernel engine quota reserve roles`. Neither companion has a ruling on presence or legal values either.
- What the comparable settings were ruled to do (turn-end policy spec, the amendments for rows 59, 60 and 71):
  - **Nine single-valued keys** (memory and context pressure): required; each ratio above 0 and at most 1; a missing one refused by its name, "so a misspelled key shows as its right name missing".
  - **Six admission keys** (fleet size, batch size, host reserve): required and bounded. At the kernel's start a bad one stops the start, naming the key. The file is read again at an admission only when it has changed; a bad key then refuses a spawn (`admission_refused`, `detail.check: configuration`, the key named) and defers a wake (`session.resume_deferred { reason: configuration, key }`), with one spoken line. The kernel keeps running on the last configuration that passed, and running personas are untouched. "Every other consumer keeps its start values."
- Lupin's settings file on this host holds no kernel key of any kind yet (0, by this page's script), so no existing file is affected by any answer.

### The shared account (row 22)

- The sign-in and quota spec asks it as open item 4 of its Section 20: "If the development server and the test VM are signed in to the same Google account, their fleets and Rick's own sessions share both pools; the inventory shows the account's store but never its identity, so Rick answers this one."
- The decision as ruled is one sign-in per host, shared by every persona on that host. Nothing in it requires the two hosts to differ.
- The meter the kernel reads is the account's meter, not the host's. So if the account is shared, each kernel already sees what the other host and Rick's own sessions have drawn: the floor and the reserve act on the true remainder. What neither kernel can see is the other's intentions: two kernels may each admit a spawn against the same remainder.
- This session's own meter, read at its opening: the group that holds the Claude models stood at 93% of its twenty-hour allowance. Whatever else draws on that account draws on that figure.

### The heap setting (row 61)

- Ruled on 2026-11-10 (host capacity, parts 5 and 6): the "Node engines" (Antigravity's `agy`, and Jetski) are launched with `NODE_OPTIONS=--max-old-space-size=6144` and `GEMINI_CLI_NO_RELAUNCH=true`, so that a runaway heap dies with a legible error below the 8 GiB memory cap, and so that the process the kernel holds is the engine itself and not a parent of it. Claude Code gets the cap alone.
- The host inventories of 2026-11-11, on both hosts: both engines ran `--version` with a bogus flag in `NODE_OPTIONS` and did not refuse it, as a Node runtime would. The spec's Section 15 concluded: "Ruling 5's heap setting is not relied on; the scope's `memory.max` is the cap", with the caution that the test "does not prove the flag is ignored in a session".
- The key was carried through the rewriting of 2026-11-16 as `kernel memory <engine> heap mebibytes`, optional for every engine, "although Section 15 found it is not relied on; withdrawing it is this decision's matter and was not ruled".
- **Read for this page** (`src/captures/t25_engine_runtime.sh`, zero tokens; output `src/captures/out/t25-engine-runtime-lupin-host-test-20261123.txt`), on the test VM, 2026-11-23, 15:06 US Eastern:

  - **`agy` is a Go program.** It has no V8 heap for `--max-old-space-size` to limit, and its binary does not contain the flag's name. The one occurrence of the string `NODE_OPTIONS` in it sits in a packed list of other tools' command-line words (looked at by hand, not by the script). The heap setting cannot act on it, in a session or out of one. This closes the caution the inventory left.
  - **The relaunch variable's name is absent from the binary,** and the one running session is a single process with no engine-like child. The variable and the relaunch it guards against belong to the Node program the design was first written against.
  - `claude` is a compiled Bun program; it has no heap key in the design and none is proposed.

The development server's `agy`: the inventory of 11-11 found a compiled binary that ignored the bogus flag, and the script has not been run there. The running `agy` process is a copy the engine replaced on disk when it updated itself, so the live reading is of a slightly older build than the binary reading. A kernel launch (headless, with a prompt) is a different launch line from this interactive session; the capture that would watch one (C20, row 10 of the same list, two one-line prompts) has never run.

## Problems and options

### 1. Whether the two quota settings must be present (row 122)

- **A. Required (recommended).** A file without `kernel engine quota spawn floor` or `kernel engine quota reserve` is refused, naming the missing key; the values live in the baseline block of lupin's settings file, as the fifteen comparable keys do. *For:* one rule for every number the kernel acts on; a misspelled key is caught instead of running silently on a default; the code holds no second copy of the numbers. *Against:* two more lines every settings file must carry; the reference code's defaults go, and its tests pass the values in.
- **B. Optional, defaults in code.** As the reference code stands. *For:* nothing to write; a kernel starts on a bare file. *Against:* the silent failure this list of work has been removing since 2026-11-16: a typing error in the key leaves the default in force and nobody is told.
- **C. The floor required, the reserve optional.** *For:* the reserve only observes today. *Against:* it is the number that will be switched to `enforce`; two rules for two neighbouring keys.

### 2. What values are legal (row 122)

- **A. Each above 0 and below 1; no order required between them (recommended).** *For:* 0 would turn a rule off without saying so, and 1 would refuse every spawn (or defer every worker's turn) as soon as an allowance is touched; the reserve already has its own off switch, its mode. Either order of the two numbers is coherent (a floor above the reserve stops spawns before it idles workers; a floor below it, as today, does the reverse), so none is imposed. *Against:* the floor then has no off switch at all; turning it off means a very small number, such as 0.01.
- **B. From 0 to below 1, with 0 meaning "off".** *For:* an explicit way to disable the floor. *Against:* a second, unlabelled off switch for the reserve beside its mode; a 0 typed by mistake disables a guard silently.
- **C. Above 0 and at most 1,** the bounds the nine memory and context ratios have. *For:* identical wording. *Against:* 1 is useless here, where there it is a legitimate "never".

### 3. When the two settings are read, and what a bad one does (row 122)

The floor acts at a spawn; the reserve acts at every turn. The comparable six admission keys are read at the start and again at an admission when the file has changed.

- **A. Both join that same reading; a turn is never stopped by a bad key (recommended).** At the start, a missing or out-of-range key stops the kernel, naming it. When the file changes, both are read again with the admission keys: a bad one refuses a spawn (`admission_refused`, `detail.check: configuration`) and defers a wake (`reason: configuration`, the key named), exactly as the six do, and the kernel keeps the last values that passed. The reserve's check before a turn uses those last good values and reads no file itself. *For:* no new behaviour and no new record, only two more keys in an existing list; the numbers can be re-set after the first week of records without restarting the kernel, which is what the spec promises; a typing error can never idle a running fleet. *Against:* a bad quota key defers a wake although a wake is never subject to the floor; that is already true of every admission key (a wake is deferred by a bad key "no wake reads"), and the manager is told which key.
- **B. The floor joins the re-read; the reserve keeps its start value.** *For:* the reserve is not an admission matter, and "every other consumer keeps its start values" was the rule. *Against:* switching the reserve's number means a restart of the kernel; two lifetimes for two neighbouring keys.
- **C. Both keep their start values.** *For:* least to build. *Against:* every change of either number is a kernel restart.

### 4. The reserve's two companion keys (row 122; raised while reading for this page)

The reserve cannot be used without its mode and its list of roles, and neither has a ruling on presence or legal values.

- **A. They travel with the reserve (recommended).** `kernel engine quota reserve mode` is required and is one of `observe`, `enforce`, `off`; `kernel engine quota reserve roles` is required and is a list of at least one role, each a role the kernel knows; both are read when the reserve is, and a bad one is treated as in decision 3. *For:* the switch to `enforce`, the one change the spec schedules, then needs no restart and cannot be mistyped silently (`enforced` would otherwise mean whatever the code makes of an unknown word). *Against:* two more required lines; the row named two keys, and this makes four.
- **B. Left as they are, with a new row on the list.** *For:* keeps this session to what the row asked. *Against:* the same gap, left open one row along; it would come back before the mode is switched.

The spec's other settings of this family (the meter's interval, the reminder hours, the overage switch and the rest, nine keys) are not touched by either option and get a row on the list.

### 5. Whether the two hosts are signed in to the same Google account (row 22)

This is a fact, not a choice, so there is no recommendation: **the same account on both; a different account on each; or the development server has no Antigravity sign-in of its own.** The answer is written into the sign-in and quota spec's host results. It changes no code and no test.

### 6. If the account is the same: what is done about it (row 22; asked only then)

- **A. Nothing now; it is recorded and accepted (recommended).** *For:* the meter is the account's, so each kernel refuses and reserves against the true remainder whoever drew it down; the test fleet is small; until the switch-over only one host runs a kernel. *Against:* a test run can spend allowance that production work and Rick's own sessions wanted, and the floor will then refuse spawns for a reason that lies on another host; when both hosts run kernels, each may admit a spawn against the same remainder.
- **B. A separate account for the test VM before Kernel-2.** *For:* the test fleet can exhaust its allowance without touching anything else. *Against:* a second subscription and a second sign-in to keep alive; the vendor does not support extra accounts as a way to extra limits (the spec's alternatives table), so it must be a genuinely separate seat.
- **C. A higher floor on the test VM.** *For:* one line in that host's settings; it leaves more of the shared allowance alone. *Against:* it guards spawns only; a running test fleet still draws to nothing.

### 7. Whether the heap setting is withdrawn (row 61)

- **A. Withdrawn for every engine (recommended).** `kernel memory <engine> heap mebibytes` leaves the design: the key, the field in the memory record, and `NODE_OPTIONS` in the launch environment. The 8 GiB cap on the persona's control group is the one memory bound, for every engine as it already is for Claude Code. A file that still carries the key is refused as an unknown key, by the rule already ruled for the memory table. *For:* the setting cannot act on the engine it was written for; a key that does nothing reads as protection that is not there; one fewer field to rename and test at the build. *Against:* if Jetski proves to be a Node program, a heap limit there would have to be ruled again; an engine that runs away is then ended by the cap, with a less legible last line than a heap error.
- **B. Withdrawn for `agy`; kept, optional, for Jetski until it is read.** *For:* loses nothing that might yet work. *Against:* keeps the whole mechanism (key, field, launch variable) alive for an engine not on any host the kernel runs on, on a guess.
- **C. Kept as carried.** *For:* no edit; it is harmless. *Against:* the record goes on saying a heap limit exists.

### 8. The relaunch variable, and the capture that was to test it (row 61's finding; touches row 10)

- **A. Withdrawn with the heap setting; the capture's Antigravity leg closed by this page's reading (recommended).** `GEMINI_CLI_NO_RELAUNCH` leaves the launch environment; the host-capacity decision's part 6 becomes "no engine is given a runtime setting; the cap alone". Row 10 (C20 on the test VM) is struck as answered at zero tokens: the binary does not contain the variable's name and a running session is one process. Jetski is read by the same script when someone is next on the cloud workstation (a new row). The kernel's own check at Kernel-2, that the process it holds is the engine, stands. *For:* removes a setting that cannot be read; takes one host run off the list before Kernel-2. *Against:* the live reading is of an interactive session, not a kernel launch; if a headless launch did fork a child, Kernel-2's own test would be the first to show it.
- **B. Kept until C20 has run** (two one-line prompts on the test VM). *For:* the question is answered on the launch line the kernel will use. *Against:* spends a host run to test a variable whose name the binary does not hold; C20's heap line reads the host's `node`, which the spec already calls void for a compiled engine.
- **C. Withdraw the variable, keep row 10 open** for the process-tree reading alone. *For:* the tree under a headless launch is still worth one look. *Against:* the capture's script would need rewriting first, since both its legs are built on the two variables.

### 8, put again after the ruling on decision 7

Decision 7 was ruled as its option B: the heap setting is withdrawn for `agy` and kept, optional, for Jetski until Jetski is read. Decision 8's recommendation assumed the heap setting gone for every engine ("no engine is given a runtime setting"), so it is re-presented to match:

- **A. The same treatment as the heap setting (recommended).** `GEMINI_CLI_NO_RELAUNCH` is no longer sent to `agy` and is kept for Jetski until Jetski is read; the host-capacity decision's part 6 then names Jetski alone. Row 10 (C20 on the test VM) is struck as answered at zero tokens. One new row: run `t25_engine_runtime.sh` on the cloud workstation, which settles the heap setting and the relaunch variable for Jetski together. *For:* one rule for the two variables, which travel as a pair; one host run off the list before Kernel-2. *Against:* the live reading is of an interactive session, not a kernel launch; Kernel-2's own test would be the first to show a child under a headless launch.
- **B. As A for the variable, but row 10 stays open** until the process tree under a headless launch has been seen once. *For:* the tree is read on the launch line the kernel will use. *Against:* the capture's script is built on the two variables and would be rewritten first; a host run stays on the list.
- **C. Kept for both engines until C20 has run as written.** *For:* nothing changes on a reading of the binary alone. *Against:* sends `agy` a variable whose name its binary does not hold.

## A finding while recording, ruled with one click (2026-11-23)

Decision 7 did not say what the kernel does with a settings file that still carries the heap key for an engine that cannot use it; by the ruling of 2026-11-16 the key was optional for every engine, Claude Code included, where it was read and ignored. Three options were put: refused by name for every engine but Jetski (recommended); refused for `agy` only; accepted and ignored everywhere. **Ruled: refused by name for every engine but Jetski,** as recommended.
