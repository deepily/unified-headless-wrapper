# The inbox envelope and ledger (T12): problems, options, recommendations

**As of:** 2026-11-06 · **Author:** Rick Ruiz (drafted with Claude) · **Work item:** T12, the inbox details left open in framework Section 6 (voice in) · **Audience:** a reader coming to the project cold · **Rulings:** all seven adopted as recommended on 2026-11-06, decision D52 (inbox envelope and ledger), with a rider provision on ruling 2; spec `specs/2026.11.06-t12-inbox-envelope-spec.md` · **Live copy:** https://claude.ai/artifact/4epUVtgprT2im9CDNFeUW8

## Why this matters

Every message a persona receives arrives through one door, the inbox. The human speaks or types, a peer persona sends a direct message, a late answer comes back on a question the persona asked, and later the kernel itself will poke a persona about owed work. The inbox decides three things the operator feels directly: how a message is worded when the model finally reads it, whether a message can be lost or read twice, and whether a message waits for the current turn to finish.

The routing rule was decided in October: an idle persona starts a turn; an urgent human message interrupts a busy persona; everything else queues and is merged into the next turn. What was left open is the detail underneath that rule. The merged turn has a shape, the **envelope**, and nobody has written it down. The kernel keeps a record of which messages it has delivered, the **ledger**, and nobody has said where it lives or what survives a restart. And Claude Code, alone among the three engines, accepts a message in the middle of a turn, which the design has noted but not ruled on.

These details are small to write and expensive to get wrong. A badly shaped envelope makes the model misread who said what, or treat four queued messages as one conversation. A ledger with the wrong acknowledgement order loses a voice message in a crash or replays it. And the current harness carries a habit worth not inheriting: it repeats its standing instructions on every single turn, inside the message itself, which costs tokens on every exchange and is the exact verbosity the project is built to remove.

## The principles this item rests on

**The inbound routing rule.** Idle: start a turn now. Busy and the message is human and urgent: interrupt, then start. Everything else: queue, and merge the queue into the next turn. Peers and late answers never interrupt. This narrative does not reopen the rule; it writes what sits under it.

**One socket per persona, held by the kernel.** The kernel keeps one WebSocket per persona, named `cc-listener-` plus the persona's eight-character id, in one process. Lupin already routes persona-targeted notifications to a session of exactly that name, so the server needs no change for delivery. Whether it replays anything on reconnect is a separate question, and this narrative answers it below from the source.

**Acknowledge on write, never on receipt.** A message counts as delivered when the kernel has written it to the engine's standard input, not when it came off the socket. Anything unacknowledged must come back. This is the at-least-once promise, and it is what the ledger exists to keep.

**Ticketed asks.** Every question a persona asks opens a ticket and holds at most 150 seconds. An answer that arrives while no wait is open is kept on the ticket, and the kernel may also deliver it as the persona's next inbound message. So "answer" is a third kind of inbound message, beside human and peer.

**Six instruction layers, identical on every engine.** Standing instructions reach the model through the kernel contract, the role charter, the persona's own instructions, the format rules, the project mandates and a first-turn brief. This is where anything the model must always know belongs. Nothing standing should ride inside a message.

**The kernel speaks at the result.** The kernel reads each turn's reply, splits it into spoken lines, abstract and document, and posts one notification. The persona does not call a tool to speak. So the current harness's per-turn reminder to "call notify to reply aloud" has no counterpart here.

**Capability flags, not engine names.** Where engines differ, an adapter flag says so and the kernel reads the flag. The flag that matters here is `accepts_input_mid_turn`: yes on Claude Code (measured in October: a message written 1.8 seconds into a turn was absorbed and answered in the same result), no on the Jetski family.

**One append-only log per persona is the source of truth for observation.** Every frame, every inbound message, every routing decision goes there from a single writer. Any index the kernel keeps beside it must be rebuildable from it.

**Skills on every engine.** A turn that begins with a slash and a skill name is expanded from the skill's text before the engine sees it. The envelope has to say what that means when a turn holds several messages.

## What exists today

Read from the lupin clone on the laptop (commit `53e86d2`, 2026-11-04). The current harness does the inbox job with a listener process per session, a buffer file, tmux keystrokes and three hook-side catch-up modules. The kernel replaces all of that, but the framing and the catch-up behavior are the parity baseline.

**How a message is framed before the model reads it.** Four framings exist, and they do not agree with each other.

| Source | Framing today | Where it is built |
| --- | --- | --- |
| Human voice, pane idle | A `<voice-message>` envelope around the text, then a `<system-reminder>` rider telling the agent to reply through `notify` and to keep spoken lines short. Both on every turn | `speakerphone_wrap` in `hook_common.py` |
| Human voice, pane busy | Buffered to a file, drained at the next tool boundary as `[Voice]: ` lines. A header line is added only when more than five messages drain at once | `format_voice_context`, `format_backlog_header` |
| Peer direct message | A `<system-reminder>` block headed `PEER DM from <persona> <icon>:`, the body, then a reply line spelling out the `dm_send` call with message id and thread id, then a style tag. Delivered by tmux if the pane is idle, else buffered | `build_peer_dm_reminder` |
| Late answer | `[Late answer to a question you asked earlier — context only, no action required]`, then `Question:`, `Answer:`, `Answered at:`. The question is always included: the code's own comment says a bare answer with no question is worse than nothing | `_format_answer_block` in `answer_catchup.py` |

The `<system-reminder>` wrapper is a Claude Code convention. The rider and the reply line are standing instructions repeated per message. The text inside is cut at the first `</voice-message` or `<system-reminder` it contains, so a message cannot forge its own wrapper.

**How duplicates and gaps are handled.** There is no one ledger; there are three partial ones, all hook-side files keyed on the first eight characters of the session id.

| Path | Record | Catch-up source | First-run rule |
| --- | --- | --- | --- |
| Late answers | A high-water mark file (`.ask-answer-hwm-<id>.json`) plus a side-log of surfaced answer ids (`.ask-surfaced-<id>.log`, append-only, capped at 500) | `GET /api/notifications/answers-owed`, per persona, on every connect and every prompt | Surface everything owed; never suppress the first pull |
| Peer direct messages | A high-water mark file (`.dm-inbox-hwm-<id>.json`) | `GET /api/dm/list`, the owner's inbox, at the start of a turn | Seed the mark and surface nothing, so a live backlog is not replayed |
| Human voice | Nothing | Nothing. A voice message that arrives while the listener is down is gone | n/a |

**What the server replays on reconnect: nothing, for a listener.** The Phase 1 spec assumed the server replays missed notifications when a socket reconnects. The source says otherwise. The sequence-numbered replay (`last_seq` in the auth message, `replay_and_resume`, a `resume_complete` frame with a `gap` flag) runs only for a session that holds a device slot, and `resolve_device_slot` grants a slot only to a mobile session that sent a device id. A `cc-listener-` session gets no slot and no replay. The pull endpoint `GET /api/notifications/undelivered` returns a user's notifications in state created or queued; a message that reached any client, the sender's own browser included, is delivered and will not appear there. So today there is no way to recover a human message the listener missed while a browser was open, and the harness accepts that.

**What the listener sends back.** For a human message it posts a low-priority "gist", three to five words, to the sender's card as a receipt. That is a product behavior, not an acknowledgement the server acts on.

**How an engine takes a turn.** The kernel writes one JSON line to the engine's standard input: `{"type": "user", "message": {"role": "user", "content": <text>}}`. The envelope is that `content` string. There is no second channel; whatever the model is to know about a message must be in the text or in the standing instructions.

**Two documents disagree about the inbound type.** The framework's type table says an inbound message has `source: human / peer / answer`. The Phase 1 spec's type says `source: voice | console | web | cli`. One is who sent it; the other is which client carried it. Both are useful and they need separate fields.

## The problems, stated one at a time

**Problem 1: The envelope has no written form.** The routing rule says queued messages are "merged into one turn" and the framework sketches `[voice] / [dm from X] / [answer]`. Nothing says what a merged turn looks like as text: how messages are separated, what each one is headed with, in what order they appear, and how the model is told that four messages are four messages and not one.

**Problem 2: The current framings are Claude-shaped and inconsistent.** Voice is wrapped in `<voice-message>` and `<system-reminder>`, peer messages in `<system-reminder>`, late answers in a bracketed line, buffered voice in a different bracketed line. The `<system-reminder>` tag is a Claude Code convention the Jetski family has no reason to honor. The kernel's rule is identical text on every engine, so one grammar has to replace four.

**Problem 3: Standing instructions ride in every message.** The voice rider (how to reply aloud, how long to keep it), the per-message `dm_send` reply line with two ids, and the style tag are sent on every turn. Under the kernel the first is obsolete, because the kernel speaks at the result, and the rest belong in the contract layer, once. Left as they are, they cost tokens on every exchange, which is the waste the wrapper exists to cut.

**Problem 4: A message can forge its envelope.** Today's defence cuts a message at the first wrapper tag it contains. A plain-text header grammar needs its own version of that rule, or a message body that happens to start with the header pattern becomes a fake second message.

**Problem 5: There is no ledger, only three partial ones, and none for voice.** Late answers and peer messages each have their own high-water mark file and their own pull endpoint, with opposite first-run rules. Human voice has none: a message that arrives while the delivery process is down is lost. The kernel holds every socket in one process, so a kernel restart is exactly the moment all three paths are needed at once. What the kernel records per message, and where, is undecided.

**Problem 6: The reconnect assumption in the Phase 1 spec is wrong.** It says the server replays missed notifications on reconnect. For a `cc-listener-` session the server replays nothing; the replay is for mobile devices. Catch-up is a pull, and for human messages there is no pull that works while a browser is open. Either the kernel inherits the gap, or a small server change closes it.

**Problem 7: The acknowledgement order is unspecified.** "Acknowledge on write" is a principle; the order of the three steps (write to the engine, record in the ledger, post the receipt) decides what happens in a crash between any two of them. Written in one order the message is lost; in the other it is delivered twice. Only one of those is acceptable, and the duplicate must be caught by id.

**Problem 8: Claude's mid-turn ability is noted but not ruled on.** Claude Code absorbs a message written during a turn; the Jetski family does not. The framework records the capability and says the router reads the flag, but not what the router does with it: whether a busy Claude persona gets its non-urgent messages now, or waits for the result like the others. The current harness, for comparison, drains buffered messages at the next tool boundary, which is mid-turn delivery.

**Problem 9: The inbound type is defined twice, differently.** Who sent it (human, peer, answer) and which client carried it (voice, web, console, command line) are both called `source` in two documents. The envelope needs the first; the log needs both.

**Problem 10: An interrupted turn leaves the model without a marker.** After an urgent interrupt the next turn starts with the urgent message, but nothing tells the model its previous turn was cut short, at which tool, or that the message it is reading is the reason. Claude Code keeps the process, so the model may notice; a respawned Jetski persona has only its stored conversation.

## Proposed solutions

### Solution 1: The envelope grammar (Problems 1, 2, 9)

One plain-text grammar for every engine. Each message is a block: a header line in square brackets at the start of a line, then the body verbatim, then a blank line. The header names the kind of message, the time, and the attributes a reply needs. Four kinds: `voice` (the human, whichever client carried it), `dm` (a peer persona), `answer` (a late answer on a ticket), `kernel` (the kernel itself: an interrupt marker now; owed-work pokes and broadcasts later, under their own items). Which client carried a human message (voice, web, console, command line) is a `channel` field in the log, not in the header: the model treats the human's words the same way whichever way they came, and the one thing that used to depend on channel, how to speak the reply, is now the kernel's job.

```
[inbox: 3 messages, oldest first. They are separate messages, not one conversation.]

[kernel 13:02:10] Your previous turn was interrupted during the tool call `bash` by the urgent message below.

[voice 13:02:11 urgent]
Stop the migration and check the disk first.

[dm 13:02:40 from María a1b2c3d4 message 7f3e2c90 thread 9c1d4b77]
The schema diff is in io/commons/schema-diff.md. Reply when you have read it.

[answer 13:03:05 ticket ask-3f2a9c1e by human]
Question: Delete the stale worktrees under seats/?
Answer: yes
```

A single message is sent with its header alone and no count line. Times are the host's local clock to the second; a message older than the current day carries its date too. An answer always carries the question it answers, as today. A peer message carries the sender's name, the sender's persona id, the message id and the thread id, because a reply needs all four.

**A. Prefixed lines, as the buffered path does today.** `[Voice]: text` per message, one line each. *Pros:* smallest; exists. *Cons:* a multi-line body has no end marker; peer messages and answers need ids a one-line prefix cannot carry cleanly; today's own code abandons it for peer messages.

**B. Headed blocks, as above.** *Pros:* one grammar carries all four kinds; multi-line bodies are natural; attributes are named, not positional; readable by a human in the log and by the model alike; no engine-specific tag. *Cons:* needs a forgery rule (Solution 3); slightly longer than A.

**C. XML-style tags, as the voice wrapper does today.** `<message kind="voice" ...>body</message>`. *Pros:* familiar to Claude; attributes are explicit. *Cons:* it is the Claude convention the Jetski family has no reason to honor; closing tags double the framing cost; the forgery rule is the same problem with more surface.

**D. JSON.** One object per message in a code block. *Pros:* unambiguous. *Cons:* the model reads JSON worse than prose, escapes make quoted speech ugly, and it is the most tokens of the four.

**Recommendation: B.** The `InboundMessage` type gains `kind` (voice, dm, answer, kernel) and `channel` (voice, web, console, cli), and `source` disappears from both documents.

**Direction, and what the log records per message.** The envelope implies direction from `kind` and one attribute: `voice` is human to AI; `dm` is AI to AI; `answer` carries `by human`, `by <persona id>` or `by learner`; `kernel` is the kernel. The model needs nothing more. Analysis does not read the envelope; it reads the per-persona log, which sees both ends of every message:

| Direction | Where it is recorded | Event | What it carries |
| --- | --- | --- | --- |
| Human to AI, AI to AI inbound, answers, kernel | Recipient's log | `inbox.received`, then `inbox.written` | The raw notification dict verbatim (Lupin's `direction`, `sender_id`, `sender_persona`, `thread_id`, `reply_to`, `priority`, notification id, timestamps) plus the kernel's `kind`, `channel`, `received_at`; `inbox.written` adds the turn id |
| AI to human | Sender's log | the result notification the kernel posts | Spoken characters, abstract length, `needs_repair`, the notification id Lupin returned |
| AI to AI outbound | Sender's log | the gate's record of the `dm_send` call | The tool arguments as the model wrote them, before any rewriting |

A treatment study joins on the message id: the sender's gate record holds the text as written, the recipient's `inbox.received` holds the text as delivered after Lupin's rewriter, and both carry the same id. What is not deducible today is which treatment Lupin applied, because the rewriter runs on the Lupin side. The notification record needs a treatment stamp (`rewrite: {applied, rule_version, chars_before, chars_after}`), a row for the Lupin application changes item; the kernel copies it through untouched because it keeps the raw dict.

### Solution 2: What rides in the header and what lives in the contract (Problem 3)

**A. Per-message instructions, as today.** Every peer message carries the full `dm_send(...)` reply line; every voice message carries the speaking rider. *Pros:* the model never has to remember how to reply. *Cons:* the same forty to eighty tokens on every message, forever; the rider is already obsolete under the kernel.

**B. Identifiers in the header, instructions in the contract, once.** The header carries the facts a reply needs (sender id, message id, thread id, ticket id). The kernel contract layer says, once per persona: a `dm` block is answered with `dm_send` using the ids in its header; an `answer` block is context and needs no reply; a `voice` block is the human and the end-of-turn reply is spoken for you; a `kernel` block is the kernel, not a person. *Pros:* the envelope carries data only; standing text is paid for once per spawn; the same words on every engine. *Cons:* a long session that compacts its context could lose the contract text; that is a general property of the six-layer design, not of this item, and the contract is re-sent on every spawn.

**Recommendation: B.** No per-turn rider of any kind. The style tag that rides peer messages today becomes one line in the format rules layer.

**Ruled with a provision (2026-11-06).** B is adopted. The operator is skeptical that current models, which were not trained for a voice-in, voice-out environment, will follow a contract faithfully over a long run of turns, and suspects per-turn reinforcement, or ultimately a fine-tuned adapter, may be needed. So the envelope keeps an optional per-persona **rider**: text the kernel prepends or appends to every envelope, off by default, set in the manifest, and logged on every envelope it touches so its effect can be measured like any other treatment. It is turned on only if the contract alone proves insufficient.

### Solution 3: How the merge is composed (Problems 1, 4, 10)

These are the mechanical rules; they come as a set.

1. **Order is arrival order, oldest first.** After an urgent interrupt the urgent message is already at the front of the queue by the routing rule; no other reordering.
2. **The count line opens every envelope that holds more than one message.** Today's buffered path adds a header only above five messages. Under the kernel a merged turn is the exception, and a model that reads two messages as one conversation answers the wrong thing, so the line is cheap insurance at two. *Alternative:* keep today's threshold of five. *Recommendation:* at two.
3. **An interrupt leaves a marker.** When a turn was interrupted, the next envelope opens with a `kernel` block naming the tool call that was cut and pointing at the message that caused it. On the Jetski family, whose process exits on interrupt and is respawned with its stored conversation, this is the only way the model learns what happened.
4. **Skill expansion is per block.** A body whose first line begins with a slash and a known skill name is expanded in place; the header is untouched. Two slash commands in one envelope expand independently.
5. **The forgery rule indents instead of cutting.** Today's defence truncates a message at the first wrapper tag inside it, which throws away the human's words. Under the kernel, any body line that would parse as a header (a line starting with `[voice`, `[dm`, `[answer`, `[kernel` or `[inbox`) is indented by one space. The model reads it unchanged; the parser, and any later tool that reads the log, cannot mistake it for a header. Nothing is dropped.
6. **One result, one notification.** A merged turn produces one reply and one spoken notification, as the streaming decision already says. The model is expected to answer every block; the format rules layer says so.

### Solution 4: Where the ledger lives and what it holds (Problem 5)

The ledger answers one question per message: has this notification id been written to the engine? It also keeps the cursors the pull catch-ups need.

**A. The session log is the ledger.** Every inbound message and its acknowledgement are already log events. On restart the kernel scans the log for acknowledged ids. *Pros:* one file, one writer, nothing to keep consistent. *Cons:* the log is the big file and it rotates (log rotation is an open item); a restart scan grows with the log; the cursors for the two pull endpoints have nowhere natural to live.

**B. A small index file per persona, beside the log, rebuildable from it.** `~/.lupin/kernel/personas/{persona_id}/inbox.json`: the last 500 acknowledged notification ids (oldest dropped), the answers cursor (latest `responded_at` seen), the direct-message cursor (latest `created_at` seen), and the time of the last write. Written atomically through a temporary file and rename after each acknowledgement; messages arrive at human speed, so the write rate is trivial. The log stays the record: `inbox.received`, `inbox.written`, `inbox.duplicate` events with the id, kind, channel and turn. If the index is missing or unreadable the kernel rebuilds it from the log tail and says so in the log. *Pros:* restart is one small read; the cursors have a home; the three hook-side files of today collapse into one; the log remains the truth. *Cons:* two files per persona instead of one; a rebuild path to test.

**C. Ledger columns in the registry.** *Pros:* one file for the whole kernel. *Cons:* the registry is rewritten on every state change for every persona; putting 500 ids per persona in it makes every write large, and a corrupt registry would take the ledgers down with it.

**D. Server-side acknowledgement.** The kernel tells Lupin which ids it has delivered and keeps nothing. *Pros:* the server already stores notifications. *Cons:* a new endpoint and a new state per notification per listener; a kernel that cannot reach the server cannot acknowledge, so the local record is needed anyway. Worth doing later for the voice gap (Solution 5), not as the ledger.

**Recommendation: B.** The queue itself is not persisted: a message received but not yet written is in memory, and if the kernel dies it is unacknowledged by construction and comes back through whatever catch-up its kind has.

### Solution 5: Acknowledgement order and catch-up (Problems 6, 7)

**The order.** Write to the engine's standard input, then append the id to the ledger, then post the receipt. A crash between the write and the append leaves the id unacknowledged, so catch-up delivers it a second time and the model sees a duplicate; a crash in the other order would lose it. Duplicates are the accepted cost of at-least-once, and most of them are caught: a replayed id that is already in the ledger is dropped and logged. *Alternative:* append first, then write, which can lose a message but never repeats one. *Recommendation:* write first. A lost voice message is the one failure the operator cannot detect; a repeated one they can.

**The receipt.** The three-to-five-word gist posted to the sender's card today is a product behavior the web client relies on. The kernel keeps posting it, at low priority, after the write. It is not an acknowledgement the server acts on.

**Catch-up on every connect of a persona's socket**, first connect included, since the server replays nothing for a listener:

| Kind | Pull | Cursor | First-run rule |
| --- | --- | --- | --- |
| Late answers | `GET /api/notifications/answers-owed` for the persona | answers cursor | Surface everything owed (as today) |
| Peer direct messages | `GET /api/dm/list`, filtered to the persona | direct-message cursor | Seed the cursor and surface nothing (as today), so a live backlog is not replayed |
| Human voice | none today | none | n/a |

Every pulled id is checked against the ledger before it is queued, so a message delivered live and then pulled is not delivered twice.

**The voice gap.** A human message that arrives while the kernel is down and a browser is open is marked delivered by the browser's receipt and cannot be pulled back. Two choices:

**A. Inherit the gap.** The current harness has it; nobody has reported it; a kernel restart is rarer than a listener restart. *Pros:* no server change on the critical path. *Cons:* the one message class the operator cares most about is the one with no recovery.

**B. Close it with a small Lupin change, scheduled under the Lupin application changes item.** The dual emit already computes `listener_delivered` per notification; record it, and let `GET /api/notifications/undelivered` take a `job_id` and return the messages that listener never received. The kernel then pulls it like the other two, with a third cursor. *Pros:* at-least-once holds for every kind; the change is small and local to code already read. *Cons:* a server change, so a lupin-side task on the dev server, with its own tests.

**Recommendation: B, but not in Phase 1.** Phase 1 inherits the gap; the server change is the first row of the Lupin application changes item, and the kernel's catch-up table gains its third row when it lands.

### Solution 6: The Claude mid-turn write policy (Problem 8)

The question is what a busy persona does with a non-urgent message when its engine can take one mid-turn.

**A. Queue everywhere.** Ignore the capability; every engine merges at the result. *Pros:* one code path, one behavior to test, the envelope always forms the same way. *Cons:* on Claude a human's follow-up waits out the whole turn, which can be minutes on a document turn; a step backwards from the current harness, which drains buffered messages at the next tool boundary.

**B. Write now where the flag says yes, for every non-urgent kind.** `if adapter.accepts_input_mid_turn: write now, else queue`. The message goes down as a one-block envelope; Claude absorbs it at its next boundary and the turn's single result answers both. Peer messages and answers go the same way; they still never interrupt. *Pros:* parity with today's tool-boundary drain; the operator's follow-up lands as soon as the model can see it; the rule is one line and reads the flag, as the framework already says. *Cons:* two delivery shapes to test; a message written while the model is inside a 150-second ticket wait lands only when that tool returns, which is still sooner than the result; the October measurement was one run, so this needs its own acceptance test when the Claude adapter is built.

**C. Human messages now, peers and answers at the result.** *Pros:* the human never waits; the quieter kinds stay quiet. *Cons:* a second rule for no measured benefit; a late answer is often what the running turn is waiting for.

**Recommendation: B.** Phase 1 exercises only the queue path, since the Jetski family cannot take mid-turn input; the write-now path is proven when the Claude adapter is built, and the capture that measured absorption becomes its acceptance test.

### Acceptance

Six tests, word-prefixed `Inbox-`, added to the Phase 1 set where the fake engine can carry them and to the Claude phase otherwise.

| # | Do this | Pass when |
| --- | --- | --- |
| Inbox-1 | Queue a voice message, a peer message and an answer against a busy fake engine | One envelope, arrival order, the count line, each block headed per the grammar, the answer carrying its question |
| Inbox-2 | Deliver the same notification id twice, once live and once by pull | Written once; the second is logged as a duplicate |
| Inbox-3 | Send a voice message whose body contains a line that reads `[dm 10:00:00 from x]` | The line arrives indented by one space; the turn has one block |
| Inbox-4 | Kill the kernel after a write and before the ledger append; restart | The message is delivered again from catch-up; nothing already acknowledged is replayed; the index rebuilds from the log when deleted |
| Inbox-5 | Interrupt a turn with an urgent message | The next envelope opens with a kernel block naming the interrupted tool call |
| Inbox-6 | (Claude phase) Send a non-urgent message during a `sleep 15` turn | Written at once; one result answers both; the log shows `inbox.written` before the result frame |
