## Problems and options

### 1. Which account the kernel is on port 8000 (row 129)

The kernel sends a key, and the key is an account. The key the host already holds is admitted on port 8000 as `claude.code@lupin.deepily.ai`. The same key is admitted on port 7999, the instance the builder is voiced through and that speaks to Rick.

- **A. The existing key and its account** (`claude.code@lupin.deepily.ai`, role `service_account`). *For:* nothing to create; proved tonight; it is what D50 already calls the fleet key, "shared by every seat", and rules "stays for Phase 1". *Against:* a kernel under test that is pointed at port 7999 by mistake is admitted there too, and speaks aloud on the live instance; in port 8000's records the kernel cannot be told from any other holder of that key (today there is none).
- **B. An account of the kernel's own on port 8000 only,** with its own key in its own file, made with lupin's `create_service_account_postgres.py` against `lupin_db_test`. *For:* that key is refused on port 7999, so a wrong address fails closed; the kernel's requests are its own in the records. *Against:* one more account and key file to make and keep (and to make again whenever the test database is rebuilt); a second design of "the fleet's account" ahead of T39 (the fleet's own account on the development server), which is where that question was put; a third key for Lupin's check to try on every request (about 345 ms per active key, D70).
- **C. The builder checkout's service login** (`claude.code@unified-headless-wrapper-builder.deepily.ai`), created as a user row on port 8000. *For:* names the checkout that runs the tests. *Against:* it is a password login, the credential D50 keeps apart from the fleet key; the kernel would hold a password it has no ruled use for.

**Recommendation: A.** It is the account the earlier rulings already give the kernel, and it works today. The wrong-address risk is real but small in Phase 1 (one persona, on a test host) and is better met by problem 2, where the address is a required setting with no default.

### 2. How the kernel is told the server's address and the key file

- **A. Two required settings in lupin's configuration file,** read through the configuration manager like every other kernel setting: `kernel lupin url` and `kernel lupin key file` (a path; the key itself is never in configuration). No default for either: the kernel refuses to start without them, so no build can reach port 7999 by omission. On the test VM: `http://localhost:8000` and `~/.lupin/notification-api.key`. *For:* the house rule (kernel configuration lives in lupin's configuration file); one place; the copied-in configuration manager already reads it in Phase 1. *Against:* two more required settings.
- **B. Read `~/.lupin/config` as Lupin's voice tools do** (the `[environments]` default, its `api_url` and `api_key_file`), with a new environment section for port 8000. *For:* no new settings; one file already names both. *Against:* that file's default on this host is port 7999, so the kernel would follow the default to the live instance unless every run names the other section; a second configuration source beside the one the rule names.
- **C. The address on the command line, the key file in an environment variable.** *For:* matches Kernel-2's line as written. *Against:* nothing records what a running kernel was pointed at except its start line; the systemd unit would carry both.

**Recommendation: A.**
