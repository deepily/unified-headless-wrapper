# Engine sign-in and quota for a headless fleet (T22)

2026-11-11 · narrative for Rick's rulings; Claude doc `https://claude.ai/artifact/3XSJLiXTEfaP4VwqMa2Rdf`. **Ruled the same day as D68, eleven for eleven as recommended, one click each** (table at the end). Specification: `specs/2026.11.11-t22-engine-sign-in-and-quota-spec.md`.

## In brief

Every AGY persona on a host runs on one thing the Lupin kernel does not own: Rick's Google account, signed in once at a terminal and cached on the host. That sign-in lapses and has to be renewed by hand. The account's usage allowance is shared by every persona on every host that uses it, Google publishes no numbers for it, and when it runs out the engine retries quietly for minutes before it says so. Today nothing in the design notices any of this. A fleet whose sign-in lapsed at 03:00 would look, to the kernel, like fourteen personas that all crashed.

This item gives the kernel a small, honest picture of the account: is it signed in, how much is left, and what just went wrong. It uses that picture in four places: at start, at admission (the fifth check, left as an empty slot by the fleet ruling), when a turn fails, and in a daily cost table. Eleven decisions are requested, each with a recommendation.

No model call was spent on this item. Everything below is from the public record and from the two repositories; the one thing only the hosts can answer is collected by a zero-token script (last section).

What is already settled and not reopened here:

- **The engines are separate processes the kernel starts and watches.** The kernel does not sit between an engine and Google; it can only read what the engine prints and start or stop it.
- **Default models per role are Claude models reached through AGY** (Fable for the chief of staff, managers, steward and author; Opus for implementers, reviewers and testers).
- **AGY subagents are denied on every role**, so the engine's own subagent quota defects do not apply.
- **Admission is one ordered list of checks in the kernel**; four are ruled (skeleton crew, batch size, fleet size, host memory) and the fifth was reserved for this item.
- **A refusal has one body and a closed catalogue**; the control API ruling reserved `engine_quota` as a refusal reason and allowed it to be retryable.
- **Any persona with a shell can read the engine's sign-in.** The credential ruling accepted that: on one operating-system account the account is the boundary.
- **Billing through Vertex is a Claude-engine option only**, built later; on AGY it is refused by name "until this item rules otherwise".

## Where the record stands

Rick's answer on 11-11: AGY on both hosts uses a cached Google-account sign-in that has to be renewed periodically with the AGY command-line tool.

**How AGY can be signed in without a person present.** Google documents three routes.

| Route | How | Reaches the Claude models? | Paid by |
| --- | --- | --- | --- |
| Cached account sign-in | sign in once interactively; over SSH the tool prints a link and takes a pasted code; headless runs reuse the cached sign-in | yes, on a paid plan (Ultra includes third-party models) | the plan's flat price; shared allowance |
| Gemini API key | `modelProvider: gemini` in the tool's settings plus `GEMINI_API_KEY` in the environment | no: requests go straight to the Gemini API | per token |
| Cloud credentials | `gcloud auth application-default login`, then `AGY_ADC_AUTH=true`; Gemini Enterprise in a Cloud project | Opus and Sonnet, if an administrator enables partner models; Fable is not in the published table | per token |

Without a cached sign-in and without a terminal, a headless run exits with `authentication required` instead of hanging.

**Where the cached sign-in lives.** By default in the desktop keyring. On a headless Linux server the keyring is often absent or locked, and separate AGY processes then cannot see a sign-in another process saved; users report that `GEMINI_FORCE_FILE_STORAGE=true` makes the tool keep it in a file (`~/.gemini/antigravity-cli/antigravity-oauth-token`) that every process can read. The kernel will start engines from a background service with no desktop session, which is exactly the case those reports describe. Which store the two hosts use today is not known; the script reads it.

**Several engines on one sign-in.** A third-party check on AGY 1.4.7 (our version) found that the tool refreshes its short-lived token in memory and did not rewrite the file in weeks of daily use, and that two headless runs at once both finished. One open report describes a fresh headless process occasionally failing to read a valid file sign-in and falling into the interactive flow.

**What the allowance is.** It belongs to the account, not the process or the host.

- Two clocks per pool: a five-hour allowance that refills, under a weekly ceiling. Ultra is described as five or twenty times Pro. No numbers are published, and Google says limits vary with capacity and with how much work each prompt causes.
- Separate pools per model family: one for Gemini models, one for Claude and GPT models (the meter also shows a third group for one Gemini model). Our default roles all draw on the Claude pool.
- Paid overage exists: purchased credits, spent only if a setting says so (`useG1Credits` in the tool's settings; a second spelling, `useAiCredits`, appears in the shared settings file and has been reported to turn itself back on).
- Google's plans page says bringing your own key or endpoint for extra limits is not supported.

**The meter can be read for free.** `agy -p "/usage" --output-format json` is answered by the tool itself: no model turn, no tokens, about two seconds. It returns, per pool and per clock, the fraction remaining and the reset time. Signed out with no terminal, the same command exits 1 in under a second. So one cheap command answers both "are we signed in?" and "how much is left?". One caveat from the record: a monitoring project saw the meter report a pool as full while an earlier exhaustion had not yet reset.

**What exhaustion looks like.** The engine's error text is `RESOURCE_EXHAUSTED (code 429): Individual quota reached. … Resets in 148h49m28s.` The reset is stated in the message.

- The engine retries inside the turn. Reports describe retries every second or so for minutes, about ten minutes in one, and for the whole of the run's time limit in another, although the message itself says the reset is hours away.
- A headless run that ends this way reports `status: ERROR` with the text in `error`, and can still exit 0.
- A resumed conversation can repeat an old quota error on a turn that succeeded.
- A bare `429 … Resource has been exhausted (e.g. check quota)` with no reset is also what Google's backend returns when it turns a system prompt away (reported for prompts that name other vendors' coding agents). It is not exhaustion, and tools that treated it as exhaustion put healthy accounts into cool-down.

**What Lupin does today.** Nothing at the fleet level. Lupin's one-shot AGY runner (`cosa/orchestration/agy/runtime.py`) tells a 503 from every other failure and leaves retry to its caller. The credential watcher restarts Lupin's containers when Claude Code's token file changes; it does not concern AGY. `vertex_spend_ceiling.py` records a lesson that applies here: a dollar budget is an alert, never a brake, because the bill arrives hours late; only a rate limit stops spend.

**Found in our own record.** The credential rule's path list protects `~/.gemini/*/oauth*`. AGY's file is named `antigravity-oauth-token`, which that pattern does not match, so the rule that forbids a persona from reading the engine's sign-in does not cover the file the sign-in is in.

## Problems and options

### 1. Which sign-in the fleet runs on

The fleet needs a sign-in that works with nobody present and reaches the models the roles are set to.

- **A (recommended): the cached account sign-in, one per host, shared by every persona.** Pros: it is what works today; it reaches Fable and Opus; flat price. Cons: it lapses and needs a person; one shared allowance; no per-persona accounting by Google.
- **B: Cloud credentials through Gemini Enterprise.** Pros: built for headless use; no weekly ceiling; a service identity instead of a person's. Cons: billed per token (a fleet of Opus personas is a real bill); partner models need an administrator's opt-in; Fable is not in the published table; unmeasured on our hosts.
- **C: a Gemini API key.** Pros: per process, truly headless. Cons: Gemini models only, so it cannot run the default roles; per token.
- **D: several accounts, switched per persona.** Pros: more allowance. Cons: the tool keeps one sign-in per operating-system account; the third-party switchers swap a global entry and race; the plans page says extra limits by other means are not supported.

Recommendation: A now. The manifest's `billing` field gains the value `cloud` as a reserved word for route B on AGY, refused until a capture shows it working with the role models; C and D are not built.

### 2. Where the sign-in is kept, so a kernel-started engine can find it

A sign-in saved to a desktop keyring may be invisible to a process started by a background service.

- **A (recommended): a file, always.** The kernel sets `GEMINI_FORCE_FILE_STORAGE=true` in every engine's environment and in the sign-in command the runbook gives Rick; at start it proves, from inside its own service, that an engine can read the meter. The file is mode 600 and the credential rule's pattern is corrected to cover it. Pros: one store that every process reads; no desktop session needed; testable at start. Cons: rests on an environment variable known from issue reports rather than Google's documentation, so the script checks it on both hosts first; if a host's sign-in is in the keyring today, one fresh sign-in is needed.
- **B: the keyring, with a session bus kept alive for the service.** Pros: Google's documented default. Cons: more moving parts on a server; the reported failures are in exactly this arrangement.
- **C: leave it as found on each host.** Pros: nothing to do. Cons: two hosts may differ; the first kernel start finds out.

### 3. When the sign-in lapses

Rick renews the sign-in by hand. Between the lapse and the renewal every turn fails.

- **A (recommended): the kernel notices, holds the fleet, and tells Rick once.** A zero-token read of the meter every ten minutes, at kernel start, and again whenever a turn fails with `authentication required` (retried once, because of the reported one-off read failure). On a lapse: the account is marked lapsed; spawns and wakes are refused with the reason `engine_login`; running personas are held, not counted as crashed, not poked, their messages kept; one high-priority card and one spoken line carry the exact command to run; the next good read lifts the hold and each held persona is told in one kernel line. No persona may sign in or out: a gate rule denies the interactive sign-in and `/logout`. Pros: one clear signal instead of fourteen crashes; nothing lost; nothing spent. Cons: the fleet stops until Rick acts.
- **B: A, plus the kernel relays the sign-in link to Rick's console and takes the code back.** Pros: Rick renews from the laptop without opening a shell on the host. Cons: the kernel would carry a sign-in code, which the console ruling kept out of it; more to build. Worth revisiting once the laptop console exists.
- **C: do nothing special.** Cons: crash-loop marks on every persona, pokes into a dead engine, and a confusing night.

If the script shows the sign-in's age follows a regular interval, A also warns a day ahead.

### 4. How the kernel knows how much is left

- **A (recommended): the engine's own meter, read every five minutes, with one override.** The read is free. An exhaustion the kernel actually saw outranks the meter for that pool until the reset the error stated, because the meter has been seen to lag. Each read is a record; the newest is on the roster and in `lupin kernel status`. Pros: Google's own number; no arithmetic on unpublished limits; covers use by the other host and by Rick's own sessions on the same account. Cons: field names are observed, not documented, so an unreadable answer is "unknown", which never refuses anything.
- **B: the kernel counts its own tokens against a configured budget.** Pros: no dependence on the meter. Cons: the limits are unpublished and vary; it cannot see the other host or Rick's own use.
- **C: no meter; react to errors only.** Pros: least to build. Cons: the first sign is a failed turn after minutes of retries.

### 5. The fifth admission check

- **A (recommended): refuse a spawn when the model's pool is exhausted or nearly so; defer a wake only when it is exhausted.** A spawn is refused when the pool is blocked, or when its five-hour remainder is under 15% or its weekly remainder under 5%. The refusal names the pool, the remainder and, when known, the reset, as a retry time. A hibernated persona's wake is never refused for a low meter (its message deserves an answer while any allowance remains), only deferred while the pool is blocked, exactly as the memory ruling defers a wake with no room. Unknown admits. Pros: no new persona is started into an allowance that cannot carry it; the numbers are configuration. Cons: the two floors are guesses until a week of records exists.
- **B: refuse only when exhausted.** Pros: simplest. Cons: a batch of eight spawned at 3% remaining fails together minutes later.
- **C: no check.** Cons: leaves the slot empty.

### 6. A turn that runs into the limit

Left alone, the engine retries for minutes inside the turn, and the kernel's held-turn and turn-end rules would then advise, poke and eventually mark the persona as failing.

- **A (recommended): recognize it, stop the retries, wait for the reset, lose nothing.** On the first error that states a reset: the pool is marked blocked until then; the kernel interrupts the turn (the measured interrupt) so the engine stops retrying; the persona's state is `quota_blocked`: not a crash, not a held turn, not poked, free to hibernate. The message it was working on is kept and, after the reset, opens its next turn inside one kernel line, as the lifecycle ruling does after a crash. Rick gets one card per pool per block, with the reset time in his own time zone; each manager is told once. Pros: minutes of pointless retries saved per persona; one notice instead of one per persona; no lost message. Cons: relies on recognizing the error text, which is why decision 9 exists.
- **B: let the engine retry until its own time limit.** Pros: nothing to build. Cons: every persona in the pool burns its time limit, then fails; pokes repeat it.
- **C: treat it as a crash.** Cons: three in ten minutes marks the persona crash-looping, which needs a re-spin to clear, for a condition that clears by itself.

### 7. What a persona does while its pool is blocked

- **A: wait.** Pros: every turn runs on the model the role was given, which keeps the measurements this project exists for clean. Cons: a blocked Claude pool silences the chief of staff and the managers for up to five hours, or days at the weekly ceiling.
- **B (recommended): wait by default; a persona may name one fallback model, used only while its own pool is blocked.** A manifest field, empty by default; the fallback must be in a different pool; every turn's record already carries the model, and the persona is told in one kernel line when it changes and when it changes back. Suggested use: the chief of staff and managers, so Rick can still reach the fleet. Pros: reachability where it matters; opt-in and visible. Cons: the engine fixes the model at launch, so each switch is a re-spin through the memento handshake; a Gemini manager behaves differently from a Fable one.
- **C: every persona falls over automatically.** Pros: the fleet keeps working. Cons: silently changes what is being measured and drains the second pool too.

### 8. Paid overage

The account can spend purchased credits when the allowance runs out, if a setting allows it. A fleet can spend much faster than a person.

- **A (recommended): never, enforced.** One kernel key, default never. At start the kernel writes the engine's own setting to match (both spellings, since one has been reported to re-enable itself) and records what it found. Pros: a fleet cannot run up a bill overnight; the lesson already written into Lupin's Vertex module. Cons: a blocked pool stays blocked until its reset.
- **B: always.** Pros: no stoppage. Cons: unbounded spend at per-token prices with no brake the kernel controls.
- **C: leave the setting as found.** Cons: nobody knows which it is on which host.

Rick can still flip the key for a deadline; it is one line and takes effect at the next engine start.

### 9. Telling real exhaustion from its look-alikes

- **A (recommended): a closed table of seven kinds, and only one of them blocks a pool.**

  | Kind | Recognized by | The kernel |
  | --- | --- | --- |
  | Sign-in lapsed | `authentication required` | decision 3 |
  | Exhausted | a 429 that states a reset | decision 6; blocks the pool until that reset |
  | Rate limited | a per-minute 429 | nothing: the engine's own retry handles it |
  | Unavailable | 502, 503, 504 | nothing for the first; the held-turn rule covers a long one |
  | Bare 429 | a 429 with no reset | never blocks; the second in a row for one persona while the meter shows allowance raises one alert that the prompt may have been turned away |
  | Stale error | an error on a turn that produced a reply and no new error step | ignored, recorded |
  | Other | anything else | recorded at alert level, text kept |

  The table is tested against texts from the public record and from whatever the two hosts' own engine logs already hold (the script collects those at zero cost). Pros: a look-alike can never stop the fleet; new shapes land in "other" and are seen. Cons: text matching against a tool that updates itself; the engine-update vetting already reruns fixtures on a new version, and these join them.
- **B: any 429 blocks the pool.** Pros: simple. Cons: one turned-away prompt silences every persona in the pool: the exact failure other tools have reported.
- **C: learn the shapes by exhausting the allowance on purpose.** Cons: spends a week's allowance to learn what a search gave for free.

### 10. Sharing one allowance across a fleet

Fourteen personas draw on one five-hour allowance. Without a rule, workers can spend it and leave the personas Rick talks to with nothing.

- **A (recommended): keep a reserve for the personas Rick talks to; run it in observe mode first.** When a pool's five-hour remainder falls under 25%, only the chief of staff and managers start new turns in that pool; other personas' turns wait for the refill, their messages kept. It ships logging what it would have deferred, like every new gate rule in this project, and is switched to enforce from the first week's records. Pros: the fleet stays steerable at the end of a window; one number. Cons: workers idle at the end of a window; the right number is unknown today.
- **B: first come, first served.** Pros: nothing to build. Cons: the manager is the persona most likely to be silenced, because it speaks least often.
- **C: a token budget per persona.** Pros: fair. Cons: needs the pool's size, which is unpublished; much more to tune.

### 11. The cost baseline

The register asks for a cost figure comparable to the Claude Max plan, and carries a deferred capture on prompt caching.

- **A (recommended): no capture; a daily table from records the kernel already writes.** Each turn's record carries the engine's token counts, including tokens read from cache. A daily kernel job rolls them up by persona, role and model; `lupin kernel usage` prints the table with three derived columns: what the day would have cost at list prices (prices are configuration, never guessed: an unpriced model shows a blank), the share of each pool the day consumed (from the meter), and tokens per percentage point of pool (which, over a week, is the unpublished size of the allowance). The baseline is one working week of the shadow run, set beside the same week's Claude Code usage from the sessions it shadows. The cached-token column answers the caching question from ordinary use, so that line leaves the deferred captures. Pros: free; comparable; keeps improving. Cons: no number until the shadow run.
- **B: a dedicated measuring run now.** Pros: a number this month. Cons: spends allowance on a synthetic workload that will not match real use.
- **C: skip it.** Cons: the engine comparison this project is for has no cost side.

## What follows without a decision

- **Other engines.** The three reads (signed in, meter, error kind) are an adapter surface. The Jetski adapter answers "unknown" until someone reads Jetski's own record on the work laptop; the Claude adapter fills them in when it is built (Claude Code prints its own limit messages and has a Vertex route already ruled). Unknown never refuses.
- **Two hosts, one account.** If the development server and the test VM use the same Google account, their fleets and Rick's own sessions draw on the same pools. Reading the meter covers this; counting tokens would not.
- **The credential rule's pattern** is corrected whatever is ruled above.
