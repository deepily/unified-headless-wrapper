## In brief

The kernel's log has six acceptance tests, Log-1 to Log-6. Two documents say when they run, and they disagree about three of them.

- The log's own specification (ruled 2026-11-08) runs all six during Phase 1, each with one of the eight kernel gates: the redaction test (Log-4) with the first gate, the held-turn test (Log-5) with the fifth, the console test (Log-6) with the third, "Lupin side after the move".
- The framework's table of exit criteria (ruled 2026-11-10, two days later) keeps Log-1 to Log-3 in Phase 1 and places Log-4 to Log-6 in Phase 2, after the kernel has moved into lupin.

The builder of the first gate needs to know whether the redaction test is theirs. The record gives no reason for the later placement, and three other documents side with the log's specification. The recommendation is that the specification is right and the framework's table is corrected.

The check written to confirm this compared every acceptance test in the repository, not the log's alone, and the same table disagrees with three more tests' own specifications. It also omits seven whole families of tests that later rulings added. Those are put as separate decisions, so the session can stop at the log if Rick prefers.

## Problems and options

### 1. Where the redaction test and the held-turn test run

Log-4 and Log-5: Phase 1, as the log's specification says, or Phase 2, as the framework's table says.

**Option A (recommended): the log's specification is right.** Log-4 runs with Kernel-1 and Log-5 with Kernel-5; the framework's Section 15 table and D63's row are corrected, and the exit-criteria specification gains an amendment.
- Pros: the code under test is built in Phase 1 and both tests run on the fake engine; redaction is proved before a real key is ever logged; four documents already say this, so three passages change in two files, plus one amendment.
- Cons: Kernel-1 and Kernel-5 stay as heavy as the Phase 1 specification already makes them.

**Option B: the framework's table is right.** Both move to Phase 2; the log's specification and the Phase 1 specification gain amendments, and D56's row is corrected.
- Pros: lighter Phase 1 gates.
- Cons: Phase 1's working day of real use would write logs through a writer whose redaction no test has proved; a hang in a tool call would go undetected by any tested path through Phase 1; more documents change (three rows of the Phase 1 specification, the log's specification, D56).

**Option C: divide them.** Log-4 with Kernel-1; Log-5 in Phase 2, once the ticket store is real.
- Pros: the ticket clause is tested against the real store.
- Cons: the clause needs only the session state, which Phase 1 has; the watch itself would be untested for a phase.

### 2. How the console test, which has two halves, is written

Log-6 is one test number proving two things in two phases.

**Option A (recommended): one number, both gates stated in both places.** The table's Phase 1 row gains "the kernel side of Log-6 with Kernel-3" and its Phase 2 row keeps "Log-6 (the Lupin side)", matching the log's specification and the Phase 1 specification word for word.
- Pros: nothing is renumbered; every document already written stays true.
- Cons: a test that passes twice has to be read carefully.

**Option B: the whole test in Phase 2.** The Phase 1 specification's Kernel-3 row loses its Log-6 clause by amendment.
- Pros: one test, one gate.
- Cons: a record the console needs and the kernel fails to write would be found only after the move, when the fix is in a different repository.

**Option C: two numbers.** Log-6 becomes the kernel side; a new Log-7 is the Lupin side.
- Pros: one test, one gate, and nothing found late.
- Cons: a new number in a ruled specification, and every "Log-1 to Log-6" in the record becomes stale.

### 3. The three other tests the same table misplaces

Inbox-6, TurnEnd-4 and TurnEnd-6 conflict in the same way, for the same apparent cause.

**Option A (recommended): correct them now, by the same rule.** Each takes the phase its own specification's stated dependency lands in: Inbox-6 to Phase 3, TurnEnd-4 and TurnEnd-6 to Phase 2. Same edit, same amendment.
- Pros: in each case the table's phase is one in which the test cannot run at all, so there is no judgment to make; the table is corrected once, not twice.
- Cons: widens a row that named the log only.

**Option B: a new row in "Outstanding actions".** This session corrects the log alone.
- Pros: the row stays the size it was written.
- Cons: the table is known wrong in three places and left so; TurnEnd-4 and TurnEnd-6 sit in the Phase 1 exit until someone returns.

**Option C: rule each of the three separately now.** Three more questions.
- Pros: each gets its own look.
- Cons: three clicks for corrections with one possible answer each.

The four unplaced tests are not conflicts and are not proposed for correction here. "After Kernel-8" (Console-4, Console-5) is compatible with Phase 2 but does not say it; "Switch" (Naming-4, Naming-5) may mean the test Switch-1, which is Phase 2, or the Switch clock, which is the switch-over week, and the naming specification's own text (the old route answering 404) fits the clock better. Under any option they become one new row, to be settled when those specifications are next touched.

### 4. The seven families the table never gained

Fifty-three tests state a gate in their own specification and appear nowhere in Section 15, whose Gate G2 row requires "the full table green".

**Option A (recommended): name them in the table now,** each family at the gate its own specification states, taken from the script's output.
- Pros: Section 15 becomes what D63 says it is, the owner phase of every family; the Phase 1 exit gains the 31 tests it is silently missing; mechanical.
- Cons: the table's cells, already long, grow by seven phrases.

**Option B: make the script's output the list of record,** as the exit-criteria ruling did for the deletion list; Section 15 keeps a summary and a pointer.
- Pros: the list can no longer drift from the specifications, because it is read from them.
- Cons: a change to what D63 ruled the table is; larger than this row.

**Option C: a new row in "Outstanding actions",** nothing changed now.
- Pros: smallest session.
- Cons: the gap stays open through Kernel-1, which is where it first bites.

### 5. Whether the check is kept as a standing step

The script exits non-zero under `--check` while any test reads `conflict`.

**Option A (recommended): yes, one line in the ruling protocol.** Recording (Section 6, the framework step) runs it after the framework is edited.
- Pros: a new acceptance table cannot again be entered in Section 15 at a different phase without the session seeing it; under a second, zero tokens.
- Cons: one more step at every recording; the script's mapping of words to stages needs a line when a specification invents a new phrase.

**Option B: keep the script, add no step.** It is run when someone thinks to.
- Pros: nothing added to the protocol.
- Cons: this conflict stood for seven days and was found by accident.
