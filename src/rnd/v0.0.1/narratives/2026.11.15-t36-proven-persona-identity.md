# Proven persona identity on Lupin's endpoints (T36)

**As of:** 2026-11-15 · Read at this repo `b25e684` and lupin `aabadd221` (test VM, `/mnt/lupin-data/lupin`). Every count below is from `src/captures/t36_identity_seam_inventory.sh`, run on the test VM before the first question (`src/captures/out/t36-identity-seams-lupin-host-test-20261115.txt`).

## In brief

When an agent (a persona) calls Lupin, Lupin learns two things. It learns *which account* is calling, from a key that every persona on the host shares. It learns *which persona* is calling from a name the caller writes into the request. The first is checked. The second is taken on trust: anyone holding the shared key can post, file tasks or answer questions as any persona.

The kernel is the one process that knows who each persona is, because it started them. This item decides how the kernel vouches for a persona to Lupin, call by call, so the persona's name on a request is proven rather than asserted.

Eight decisions are requested; a ninth was raised after the walk-through and is recorded in the table. None blocks the first eight kernel gates: the work lands when the kernel moves into lupin, and the switch that makes proof mandatory is thrown at the switch-over.

## Where the record stands

**How Lupin checks a caller today.** One function, `require_api_key_or_jwt` (`cosa/rest/middleware/api_key_auth.py`, from line 205), accepts either the shared key or a browser login and returns the account's user id, nothing else. Eighteen routers sit behind it, holding 123 routes; eight of those routers read a persona's name from the request (commons, decision proxy, direct messages, notifications, podcast proxy, speakerphone, tasks, voice persona). The notification route takes the sender as a plain query parameter (`routers/notifications.py`, line 894).

**The shared key is slow to check.** The key table has no column that identifies a key, only its hash (`postgres_models.py`, table `api_keys`: `id`, `user_id`, `key_hash`, `description`, `is_active`, `created_at`, `last_used_at`). So `_validate_api_key_sync` (from line 35; the loop at line 80) tries the incoming key against every active key in turn. One try costs about 345 ms inside the Lupin container on the test VM (bcrypt, cost 12, measured). The test database has two active keys; the production count is on the development server and not yet read.

**Who sends the shared key.** Twenty-two places in lupin's code: seven in the persona's tool server (`lupin_mcp/`: four in `cosa_voice_mcp.py` at lines 3781, 3941, 3984 and 4035, and one each in `task_store_tools.py`, `reuse_candidates.py` and `session_spawner.py`), five in the old harness's hooks, and ten in services that are not personas at all (the arbiter's notifier, the prediction engine, the embedding and speech-to-text providers, the heartbeat poker, the software-engineering team orchestrator). The record so far said "four outbound sites"; that is one file of the tool server, not the whole of it.

**A correction to the framework.** Its list of routers a persona reaches names `v2_ask` and `docs_files`. Neither accepts the shared key: both take a browser login only (`get_current_user`). They need nothing from this item.

**What earlier rulings already fixed.**

- The account is the security boundary on a host; personas sharing one account can read each other's files (credential exposure ruling, 2026-11-06). On the test VM the account can also become administrator, so there the boundary is the host itself; accepted.
- Every decision the gate makes is recorded with a call id and a hash of the call's arguments, so a later proof can be tied to the exact call the gate approved (Phase 1 specification, 2026-11-08).
- For the four staffing tools, which call the kernel itself, the kernel already accepts a persona only against an approval its own gate recorded within thirty seconds (fleet ruling, 2026-11-09). This item is the same idea carried to Lupin.
- The kernel identifies a caller on its own socket by the control group the calling process runs in; the record says plainly this guards against confusion and is "not a boundary" (control API ruling, 2026-11-11).
- The task store reads a persona's role from the kernel, and once proof exists a request whose written name disagrees with the proven one is refused (`signature_mismatch`); the proof is to carry the role (task store ruling, 2026-11-11).
- The configuration key `kernel grant required` is added when the kernel moves into lupin and switched on at the switch-over, once no old-harness session remains (exit criteria ruling, 2026-11-10).

**Two mechanisms were on the table.** (a) A key per persona, minted at spawn and revoked at dismissal. (b) A *grant*: after the gate approves a tool call, the persona's tool server asks the kernel for a short signed note saying "persona X may make this one request", and Lupin checks the note.

**What the host allows.** Lupin runs a single server worker (`lupin_app/main.py`, line 1204), so a list of already-used grants can live in memory. The signature library for public-key signing (Ed25519, in the `cryptography` package) is present in both Lupin containers (47.0.0) and in the host's Python (3.4.8); in lupin it arrives through another package rather than being declared. The test VM does not let one process read another's memory unless it is its parent (`ptrace_scope` 1), but the account there has passwordless `sudo`, which overrides that.

## Problems and options

### 1. What proves a persona to Lupin

- **A. The kernel's signed grant, alone (recommended).** The shared key keeps proving the account; the grant proves the persona and the request. *For:* one check in one place; nothing secret is handed to the persona, so nothing can be copied by a sibling; a leaked shared key can no longer speak as a persona; no growth in the key table. *Against:* every persona call needs the kernel reachable; about 150 lines each in the kernel and Lupin.
- **B. A key per persona.** *For:* uses the door Lupin already has. *Against:* a sibling on the same account can read the key file, so it proves nothing the shared key does not; with the key check as it is, eighteen personas add up to six seconds to every request; a key proves who, never which approved call.
- **C. Both.** *For:* two layers. *Against:* all of B's cost for no added proof.

### 2. How the grant is signed

- **A. A public-key signature whose private half never leaves the kernel's memory (recommended).** The kernel makes a fresh key pair at every start; Lupin reads the public half over the kernel socket and reads it again when it meets a key it does not know. The kernel marks itself non-dumpable and, on a production host, refuses to start where any same-account process may read its memory. *For:* there is no secret file for a persona to read and nothing secret in Lupin's configuration; a kernel restart retires the old key by itself. *Against:* lupin must declare the `cryptography` package it already ships; on a host where the account is an administrator (the test VM) memory is not protected either, as already accepted.
- **B. One shared secret in both configurations** (what the register sketched). *For:* standard library only. *Against:* the secret sits in a file on the persona's own account and in Lupin's container; whoever reads either can sign as anyone.
- **C. A public-key signature with the private half in a file.** *For:* survives a kernel restart. *Against:* the file is as readable as B's secret; grants live thirty seconds, so surviving a restart buys nothing.

### 3. What one grant covers

One tool call can make several requests (send, then poll for an answer).

- **A. One request (recommended).** The grant names the method, the path with its query, a hash of the body, the persona, its role, the gate's call id and an expiry thirty seconds out, and is good once. A tool call that makes several requests asks for one grant each, against the same gate approval, for as long as the call is open (a configured ceiling). *For:* a captured grant is useless for anything else; the kernel's log shows every request a tool call made. *Against:* one local socket round trip per request.
- **B. One tool call, reusable until it expires.** *For:* fewer round trips. *Against:* not single-use, so a captured grant can be replayed against other bodies and paths.
- **C. A session token per persona.** *For:* cheapest. *Against:* a bearer token in the persona's reach: mechanism B of problem 1 under another name.

### 4. Which requests must carry a grant

Ten of the twenty-two senders of the shared key are services, with no kernel behind them.

- **A. Any shared-key request that names a persona (recommended).** A sender, creator or actor ending in `#` and eight hex characters is a persona; with the switch on, such a request needs a grant for that same persona. A shared-key request with no grant may speak only under a service name. Browser logins are untouched. *For:* services keep working unchanged; the rule is one check of the name's shape, in one dependency on the eight routers. *Against:* a leaked key can still post as a service name (as today); separating service keys is a later item.
- **B. Every shared-key request.** *For:* the key alone does nothing. *Against:* ten service call sites would need a kernel that they do not run under.
- **C. Writes only.** *For:* less traffic to grant. *Against:* reads of another persona's messages and tasks stay unproven.

### 5. How Lupin remembers a grant was used

- **A. In memory, plus "nothing older than this server" (recommended).** A table of used grant ids, each dropped at its expiry; a grant issued before the server started is refused. *For:* no storage; the restart rule closes the one gap an in-memory table has. *Against:* correct only while Lupin runs one worker, which it requires today for another reason; the check asserts it.
- **B. A database table.** *For:* survives restarts and several workers. *Against:* a write per request, to guard a thirty-second window.

### 6. How the requirement is switched on

- **A. Three positions: off, observe, required (recommended).** In observe, a grant that is present is checked and a missing or bad one is logged, not refused. *For:* the shadow run shows every caller that would be refused before any is; the same pattern as the gate's rules. *Against:* a third state to test.
- **B. Two positions.** *For:* simplest. *Against:* the first evidence of a missed caller is a refusal on switch-over day.

### 7. When the kernel cannot be reached

- **A. The call fails, with a named reason (recommended).** The tool returns `grant_unavailable` to the agent; Lupin, when required, answers 401 `grant_required`. *For:* identity is never silently unproven; the agent sees a retryable cause. *Against:* a kernel restart pauses persona calls for its duration (seconds).
- **B. Fall back to the shared key alone.** *For:* availability. *Against:* stopping the kernel would switch the proof off.

### 8. The slow key check that remains

Mechanism (a) would have forced a fix to the check-every-key loop. Without it the loop still costs about a third of a second per active key on every shared-key request.

The cause: keys are stored only as bcrypt hashes, which are slow by design and salted, so a key cannot be looked up; with no identifying column, every active key is tried. Nothing is remembered between requests. A matching key costs about half a second on average with two active keys, about a second with five, about two with ten; a wrong key always costs the whole sweep. Every request of every persona tool call pays it; the grant adds well under a millisecond beside it. (This explanation was asked for during the walk-through, and the options below are the ones then put.)

- **A. Raise a lupin ticket proposing a fast hash (recommended).** Store a SHA-256 of each key in an indexed column, filled the first time an old key passes the slow check; bcrypt retired for keys once all are filled. *For:* the check falls to microseconds for every caller; no key is reissued. Bcrypt's slowness protects short passwords; a key of 64 random characters cannot be guessed from a fast hash. *Against:* a table migration and a change to the door every caller uses, so lupin reviews it; a change of posture to state.
- **B. A ticket proposing a key identifier.** An indexed column with the key's first characters, filled the same way, bcrypt kept. *For:* the smallest change of posture; the cost becomes flat. *Against:* every request still pays about 345 ms.
- **C. A ticket proposing only a one-minute memory of verified keys.** *For:* no table change. *Against:* the first request each minute and every wrong key pay the full sweep; a revoked key works for up to a minute.
- **D. Leave it.** *For:* no work. *Against:* the cost grows with every key added for any reason.

## What follows without a decision

- The persona's identity and role are read from the grant; a written name that disagrees is refused (`signature_mismatch`, already ruled for the task store, now for all eight routers).
- The kernel's own posts on a persona's behalf (speech out, broadcasts) carry a grant the kernel signs for itself, with no gate call behind it and a kind that says so.
- The four staffing tools keep their in-kernel approval claim; no signature, because both ends are the kernel.
- The identifying `User-Agent` header from the credential ruling becomes checkable: its gate call id is in the grant.
- The tool server needs no call id handed to it: the kernel finds the open approval by persona, tool and argument hash, as it does for the staffing tools.
- What this does not close: a process on the persona account can still move itself into another persona's control group and ask for a grant against that persona's pending approval. The gate observes the move. The boundary remains the account, as ruled; this item removes every cheaper forgery.
- The old harness's five hook sites retire with the harness; the framework's router list is corrected (problem "A correction" above); "four outbound sites" becomes seven.
