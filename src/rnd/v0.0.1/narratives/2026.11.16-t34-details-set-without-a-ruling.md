## Where the record stands

**The two rulings these details serve.**

- *An interrupted engine that does not exit* (ruling 3). The Jetski family is interrupted by a signal: the engine exits and the kernel starts it again on the same conversation. The Phase 1 design had no rule for an engine that ignores the signal, so its persona would have stayed "interrupting" for good and the urgent message never delivered. You ruled 30 seconds, then the kernel kills the engine and restarts it. You also ruled (ruling 2) that the time from signal to exit is written to the log, so the first real kernel run measures it.
- *The interrupt as a message* (ruling 5). Claude accepts an interrupt as a message and keeps running. The Jetski family refuses that message today with the words "not supported yet", which suggests the vendor means to support it. You ruled that the kernel asks again each time it meets a new engine version, tells you once if the answer changes, and changes nothing else on its own.

**What the existing design already fixes** (read today, not recalled):

- The log already has `session.interrupt` (written when the signal is sent, with the cause) and `session.respawn` (written when the engine is started again). Log lines are appended and never rewritten. Source: the log specification, Section 4, lines 78 to 79.
- The kernel calls a persona "crash-looping" after 3 crashes in 10 minutes, and then stops starting it automatically until someone intervenes. Source: the lifecycle specification, lines 15 and 98.
- When the kernel is stopped in an orderly way, a busy engine gets up to 180 seconds to finish, chosen because 180 seconds is the longest any tool call may run. Source: the lifecycle specification, lines 13 and 69.
- The kernel's existing notices to you use two grades that matter here: a held turn is `priority: high`, `type: alert`; "the kernel restarted" is `priority: low` with the sound suppressed. Source: the log specification, line 199; the lifecycle specification, line 149.
- The check on a new engine version runs once per version, under a lock, in a throwaway workspace, and keeps its result in `vetted-engines.json`. Source: framework Section 1, the engine-vetting row.

**What the hosts showed today.** On AGY 1.5.9 and on Jetski 2026.11.13, the interrupt message is refused at zero turns and zero tokens. A message with an unknown name is ignored with a warning; a malformed one is refused for a missing field. Those three behaviors are where the answer words of detail 5 come from.

**Not verified.** No kernel code exists, so none of these details has been exercised except in the reference module (eighteen tests, which cover details 1 to 3 only). The 40 seconds of detail 4 is a figure I chose, not one I measured.

## Problems and options

### 1. Where the log records how long the exit took

Two rulings say the time is logged and a kill is logged. Neither says in which record.

- **A. A new record, written when the engine is gone** (as written; recommended). It holds the seconds, whether the kernel forced the exit, and which tool call was open. *For:* one line answers "how long did the stop take, and was it forced" with no cross-referencing; existing records keep their meaning. *Against:* one more kind of record in the catalogue, and one more row for the console to know how to display.
- **B. Add the fields to the restart record.** *For:* no new kind. *Against:* a restart after a crash has no interrupt, so the fields would be empty there; and if the restart itself fails, the measurement is never written.
- **C. Add the fields to the interrupt record.** *For:* it is the most literal reading of "the interrupt's log record". *Against:* that record is written when the signal is sent, before the exit time exists, and log lines are never rewritten. It would mean delaying the record, and then an engine that hangs leaves no trace that an interrupt was sent.

### 2. What values the limit accepts

The ruling gave 30 seconds as a setting. A setting needs a rule for a nonsensical value.

- **A. 5 to 180, and the kernel refuses to start outside it** (as written; recommended). The floor is below the one observation on record (about 6 seconds with a shell command open), so a test can set a short limit, and a healthy exit is not normally killed above it. The ceiling is the orderly stop's 180 seconds. *For:* a typing mistake is caught at startup, not on the first urgent message. *Against:* the floor of 5 sits under the 6-second observation, so someone who sets 5 in production would kill healthy engines; and the bounds are one more thing to maintain.
- **B. Any positive number.** *For:* simplest. *Against:* 0.5 kills every interrupted engine before it can save its conversation; 86,400 quietly restores the bug the ruling fixed.
- **C. A floor of 10, ceiling 180.** *For:* production cannot be set under the observed exit time. *Against:* the acceptance test that proves the kill would take at least 10 seconds per run, or need a separate test-only override.

### 3. Whether a kill by the kernel counts as a crash

Three crashes in 10 minutes stop a persona from being restarted automatically. A forced exit looks like a crash to anything counting exits.

- **A. It does not count** (as written; recommended). *For:* the crash count exists to catch an engine that fails by itself; a kill is the kernel's own act, and three urgent messages to a slow engine within 10 minutes should not park the persona. Each forced exit is still in the log, with `forced: true`. *Against:* an engine that hangs on every interrupt is never parked automatically; someone has to notice the pattern in the log.
- **B. It counts.** *For:* an engine that repeatedly ignores the signal is unhealthy, and parking it draws attention. *Against:* the persona that most needs to receive urgent messages is the one taken out of service by receiving them.
- **C. It does not count, but three forced exits in 10 minutes send you one alert.** *For:* closes the gap in A without parking anyone. *Against:* a new counter and a new notice for a case that has never been observed; it can be added when the first forced exit is seen in a real log.

### 4. How the version check asks the question

The ruling said the version check "gains a zero-token probe". The spec had to say how it runs.

- **A. One separate launch, the interrupt message as its only input, cut at 40 seconds** (as written; recommended). The 40 is the vendor's stated 30 seconds for a headless run to shut down, plus 10. *For:* the probe cannot disturb the existing check, and if it hangs it costs 40 seconds once per engine version. Today's Jetski hang is the argument for a hard cut on every launch. *Against:* one more engine start per new version; the 40 is a chosen figure.
- **B. Send the message inside the existing check's launch.** *For:* no extra start. *Against:* that launch spends a model turn, and an interrupt arriving in it could spoil the tool-table reading that decides whether the version is admitted.
- **C. A shorter cut, 10 seconds.** *For:* faster. *Against:* a cut shorter than the vendor's stated shutdown time would record a slow healthy answer as unreadable.

### 5. How the answer is named and where it is kept

- **A. Four words (`refused`, `ignored`, `accepted`, `unreadable`), kept on the version's entry in the vetted-versions file and written once to the kernel's log** (as written; recommended). `refused` is today's answer. `ignored` is what an unknown message gets. `accepted` is a reply with no error. `unreadable` is everything else, including a hang. *For:* each word maps to a behavior seen today or to the one being waited for; the file answers "what did this version say" and the log answers "when did it change". *Against:* `accepted` has never been observed, so its definition is a guess at what the vendor will ship.
- **B. Two words, supported or not.** *For:* simpler. *Against:* a hang, a vendor rewording and a real refusal all read as "not", so a change in the vendor's wording would pass unnoticed.
- **C. Keep the engine's raw reply and no classification.** *For:* nothing is lost or guessed. *Against:* "did it change" becomes a text comparison that fires on any rewording, and the notice of detail 6 has nothing stable to key on. (The raw reply is kept anyway, in the check's run directory.)

### 6. How you are told

The ruling said "one notice on a change". The spec set its grade and what happens the first time.

- **A. An information card at low priority; the first reading is announced only when it is not `refused`** (as written; recommended). *For:* nothing is broken when the answer changes, so it should not sound like an alert; and on the first kernel start, every engine reporting the known answer would be noise. *Against:* a low card can be missed, and the change is the one event that opens new design work.
- **B. The same card at medium priority.** *For:* harder to miss. *Against:* it puts an optional design opportunity on the same footing as things that need action.
- **C. Always announce the first reading.** *For:* you see proof the probe ran. *Against:* one card per engine on first start saying what is already known; the log line is the proof.

### 7. The acceptance tests and when they run

The spec names five tests. The names follow the house rule (a word saying what is proven). The open part is the gate each runs with.

- **A. As written** (recommended): the two fake-engine tests of the limit and the fake-engine test of the probe with the first kernel gate; the probe on the real engine with the second gate, where the version check is first exercised for real; the measurement of a real interrupt during a shell command with the fifth gate, which is the existing interrupt test. *For:* each test runs at the first gate where what it needs exists. *Against:* three more tests on the first gate, which is the bootstrap candidate and should stay small.
- **B. Move the three fake-engine tests to the fifth gate, with the other interrupt tests.** *For:* a smaller first gate. *Against:* the state machine would be built and passed at the first gate with a known hole (the engine that never exits), and patched four gates later.
