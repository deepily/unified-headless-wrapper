## In brief

The Phase 1 builder is a Claude Code session that will write the kernel on the test VM. On 2026-11-22 Rick ruled that its list of work is Lupin's task store, and that the list which defines Phase 1 is put there before its first turn, by the process of planning-is-prompting (PiP), the repository of workflows, global mandates and scripts that Lupin's sessions work under: a machine-readable file, the plan stub manifest, which PiP's importer turns into rows that Rick approves in one batch. This narrative says what that file should contain. The file itself is written after the rulings.

The manifest has a fixed grammar: a plan is phases, a phase is steps, and a step is a task, a decision or a gate. Phase 1 of the kernel is described in other words: an order of work in eight steps, eight acceptance gates (Kernel-1 to Kernel-8) that turn green out of number order, the families of tests that run with those gates, and eight stops at which the builder waits for Rick's word. The work of this item is the mapping from the one to the other.

Reading the record and PiP by script turned up four things that shape the choices:

1. **The order of work leaves ten modules without a step.** The Phase 1 spec's layout lists 26 modules, two of them marked for Phase 2. The order of work names 12 by file, and the shim and the command line in other words. Ten modules that Phase 1 needs (lifecycle, jobs, admission, worktree, capacity, launch, the log sweep, the log mapper, the watch command, the entry point) have no step. They arrived with later rulings, each with tests that run with a Kernel gate, and the order of work was never brought up to date.
2. **PiP's validator will not accept the Phase 1 spec as the plan.** It compares the manifest's phases with the headings of the plan file that begin "Phase N". The spec has one such heading, its own title ("Phase 1 spec"), which the validator reads as a plan of one phase.
3. **The task store on this host has never held a row for this project.** It holds 69 rows across four other projects; one persona, `cheech`, is the accountable manager on every row that names one. The record names no manager for the builder.
4. **A planning session cannot write the rows, and should not.** The importer writes only for an actor that is a persona with a session, and the ruling already gives the write to Rick or to the builder's manager. Planning's part ends at a validated manifest and a recorded dry run.

Thirteen decisions follow. Most are small. The first four set the shape of the list; the rest say where it lives and who holds it.

**PiP's process** (a deployed copy with no HEAD to cite: `workflow/plan-stub-manifest.md`, 145 lines; `workflow/scripts/plan_stub_import.py`, 1,018 lines; a sample manifest):

- A manifest is a JSON file: a header (the plan file it describes, project, prefix, plan name, a correlation key of the form `epic:<slug>`, the owning persona) and a list of phases. A phase has a number, a name and steps; a step has a stable key, a name, a class (`task`, `decision` or `gate`), a priority, one line of acceptance, and the keys it depends on. A step may carry a gate class (`none`, `manager` or `operator`).
- A phase not yet broken down goes in with no steps and a trigger for its expansion; it becomes one row marked `STUB`. Growing the plan later is an edit to the manifest and a second run, which creates only what is new.
- The importer writes every title: `[UHW] <plan name> · Phase 3 of 9 · Step 2 of 6 · <step name>`. The store cuts a title at 120 characters. With a plan name of twelve characters that leaves 70 for a step's name.
- `validate` writes nothing and checks the schema, the keys, the dependencies, and that the phases of the manifest are the "Phase N" headings of the plan file, no more and no fewer. In the Phase 1 spec it finds one such heading, the title.
- `import` without `--write` prints the rows it would create, after reading the store for rows already there. With `--write` it creates them in the holding area, unapproved, each owned by the header's persona, who is also set as its accountable manager. It needs an actor of the form `<persona> <session id>`. PiP records that a seat which is not a manager may file only at the lowest priority, and that the store's ratio of rows created to rows closed can refuse a create.
- PiP keeps manifests under `src/docs/plan-stubs/`, because its write guard refuses anything but markdown under `src/rnd/`. This repository has no `src/docs/`, no PiP installed and no such guard; five JSON files already sit under `src/rnd/`, all captures.

## Problems and options

### 1. What a phase of the manifest stands for

The manifest's unit of progress is the phase: every title reads "Phase P of N". The build has three candidate units.

- **A. One phase for each step of the order of work (recommended).** Eight phases, in the order the builder works and stops. *For:* the order of work is the ruled sequence; each phase ends at exactly one of Rick's stops; the board's "Phase 4 of N" answers "where are we?" in the terms the loader uses. *Against:* a title reads "Phase 4" inside what the project calls Phase 1; the plan's name has to carry that (decision 13).
- **B. One phase for each Kernel gate.** *For:* the gates are what the exit criteria count. *Against:* they turn green out of number order, two steps share Kernel-1, one step turns three gates green, and steps 7 and 8 have no gate; the phases would not be the order of work.
- **C. One phase, "Phase 1", with the eight steps as its steps.** *For:* the validator accepts the spec as it stands, by the accident of its title. *Against:* nothing below a step can be a row, so the modules, the test runs and the stops have nowhere to go; the board would show eight rows for the whole build.

### 2. What the rows inside a phase are

- **A. One task for each module or named piece of work, one task for running and recording the gates' tests, and one `gate` row for Rick's stop (recommended).** Phase 3 would read: registry, manifest, API, command line, "run Kernel-2 and record it", "Rick's word". *For:* a row is a unit the builder can claim, finish and close with a commit as its receipt; follow-on rows it files (the four to six each ticket raises) have an obvious parent. *Against:* about forty rows at the first import, near the room PiP once measured.
- **B. One task for each step of the order of work, plus the stop.** Sixteen rows. *For:* small, and nothing is invented beyond Section 13's own sentences. *Against:* a row such as "events, the adapter, the pyramid and the session log" closes only when all four are done, so the board says nothing for days; the builder would split it by hand, which PiP forbids for plan rows.
- **C. One task for each acceptance test.** *For:* done is unambiguous. *Against:* well over a hundred rows; the store's ratio would refuse them, and the tests are already listed, by gate, in framework Section 15.

### 3. The ten modules the order of work does not place

- **A. Planning places each in the phase whose gate first needs it, in the manifest, and a script checks that every Phase 1 module of the layout stands in exactly one row (recommended).** The placement is read from the owning spec of each module and from the Section 15 table (admission and capacity with the first two phases, since their fixtures run with Kernel-1; lifecycle and jobs where Kernel-7's tests need them; and so on), and is shown to Rick as a table before the manifest is written. The Phase 1 spec gets an amendment that says so. *For:* the list that defines Phase 1 is complete on the first day, as ruling 3 asks; the gap is closed where it was made. *Against:* planning decides ten placements the order of work never ruled; one may prove wrong in the build, and is then moved by an edit to the manifest.
- **B. The manifest holds only what Section 13 names; the builder files the rest as follow-on rows when a gate's tests demand them.** *For:* nothing is placed without a ruling. *Against:* the builder discovers, at each gate, modules nobody listed; the first count of the work is short by more than a third.
- **C. A register item first: rewrite the order of work, then write the manifest.** *For:* the spec itself becomes right. *Against:* the body of a ruled spec is not rewritten; an amendment (option A) does the same with one session less.

### 4. Where the acceptance families appear

- **A. In the acceptance line of each "run and record" row, by gate name, with the families read from framework Section 15 (recommended).** The row for Kernel-2 reads: "Kernel-2 green with every family that runs with it (framework Section 15, the Phase 1 row); counts in the build log". *For:* one list of tests stays one list; a family moved by a later ruling needs no change to the manifest. *Against:* the row does not itself name the families; the builder reads a second document, which its loader already tells it to read.
- **B. Named in full in each row's acceptance line.** *For:* the row stands alone. *Against:* a second copy of the Section 15 table, which nothing keeps in step.

### 5. How Rick's eight stops appear

- **A. The last step of every phase is a `gate` row, gate class `operator`, depending on that phase's "run and record" row; the next phase's first rows depend on it (recommended).** *For:* PiP's own rule, that an operator decision is a step and not prose; the stop is visible on the board and closes with Rick's word as its receipt. *Against:* eight rows only Rick can close.
- **B. No row; the phase row's closing is the stop.** *For:* fewer rows. *Against:* the importer gives a phase row no gate class and no acceptance; nothing on the board says the builder is waiting for Rick.

### 6. Planning's two reviews, between steps 2 and 3 and between steps 5 and 6

- **A. No row (recommended).** The reviews are planning's reading of the build log, ruled not to be a stop of the builder's; planning's own list is the status page, and they are entered there. *For:* the store stays the builder's list; no ruling is changed. *Against:* the board does not show them.
- **B. A `gate` row at the end of phases 2 and 5, after Rick's stop.** *For:* visible. *Against:* it makes the review a second stop of the builder's, which row 94 ruled it is not; planning is not a persona and cannot close a row.

### 7. Which phases go in broken down, and which as a single unexpanded row

- **A. Steps 1 to 7 broken down; step 8, the convention-kit port, unexpanded until Kernel-8 is green (recommended).** *For:* steps 1 to 7 are specified to the module; the port is specified across three other specs, is the builder's own job after Kernel-8, and its rows are best written with the kernel in hand. PiP's rule, that everything the plan details goes in at once, is met. *Against:* about forty rows on the first day.
- **B. Steps 1 and 2 broken down; each later step expanded at the stop before it.** *For:* a small first import; each expansion can use what the build has learned. *Against:* six more manifest edits and imports, each a planning session's work and a batch for Rick to approve; the board undercounts the work until late.
- **C. All eight broken down now.** *For:* one import. *Against:* the port's rows would be guesses.

### 8. Whether the relocation is in the manifest

The order of work has eight steps; the relocation follows the eighth and closes Phase 1, with an exit of its own.

- **A. A ninth phase, unexpanded, to be expanded when the stop after step 8 is given and its five status-page rows are answered (recommended).** *For:* the board's "of N" is true to what closes Phase 1; the relocation's test, the eight gates green again from lupin, has a place to stand. *Against:* the builder's loader ends at the relocation, so the ninth phase is worked under lupin's own instructions; the row would outlive the document that seeded it.
- **B. Left out; the plan ends at the stop after step 8.** *For:* the manifest covers exactly the order of work and the loader's span. *Against:* the board would read "Phase 8 of 8" done while Phase 1 is still open.

### 9. What the builder is waiting on from others, and what the status page already assigns to it

- **A. The builder's own status-page rows (27, 34, 35 and 55) become steps, each naming its row; what Rick or a host owes before a gate becomes one `decision` row for each stage of the countdown, owned by Rick, which the first rows of the waiting phase depend on (recommended).** Its acceptance is that the countdown script shows the stage at zero. Row 109, the standing rename rule, gets no row. *For:* the builder's list is whole, and a phase that cannot start says so on the board, without copying the thirteen rows the status page holds. *Against:* two more rows of Rick's; the status page's rule that nothing owed is recorded anywhere else is bent by a pointer.
- **B. Neither; the status page stays the only place.** *For:* one list of what is owed, strictly. *Against:* the builder's list omits four pieces of its own work, and the builder can reach Kernel-2's phase with nothing to tell it that eight answers are missing.
- **C. Every owed row copied into the manifest.** *For:* everything on the board. *Against:* two lists to keep in step; the status page loses.

### 10. The plan file the validator reads

- **A. An amendment to the Phase 1 spec, written by this item, with one "Phase N" sub-heading for each phase of the manifest; the manifest's `plan_ref` is the spec (recommended).** Each sub-heading names its step of the order of work, the modules decision 3 places in it, and its gates. *For:* the plan the rows point at is the document the builder already reads first; the amendment is how the protocol records a change to a ruled spec in any case. *Against:* the spec's title already reads as "Phase 1" to the validator, which is harmless only while the manifest has a phase 1; headings in a spec written to satisfy a tool.
- **B. A plan page of its own, beside the status page, holding only the phase headings and pointers into the spec.** *For:* the spec is left alone. *Against:* a third document between the spec and the board, with nothing to keep it true.
- **C. This narrative as the plan file.** *For:* no new document. *Against:* a narrative records how a ruling was reached; it is not kept current.

### 11. Where the manifest file lives

- **A. `src/docs/plan-stubs/kernel-build.stubs.json`, PiP's convention (recommended).** *For:* the path PiP, its reviewers and the port in step 8 expect; the builder's clone receives it, since that clone leaves out only the two root loaders. *Against:* a new top-level folder for one file.
- **B. Under `src/rnd/v0.0.1/`, beside the spec.** *For:* with the design. *Against:* PiP's write guard refuses it once PiP is installed, at step 8.
- **C. Under `src/uhw_kernel/`.** *For:* with the code. *Against:* that path is the builder's, and everything in it but the build log goes to lupin at the relocation.

### 12. Who owns the rows, and who runs the import

The importer sets one persona as owner and accountable manager of every row, and writes only for an actor who is a persona in a session. The record names no manager for the builder.

- **A. Rick names the builder's manager; that persona is the manifest's owner and runs `import --write`; Rick approves the batch (recommended).** The builder takes rows from its manager, as the baseline has every worker do. *For:* the store's own roles, used as built; a manager's seat may file above the lowest priority. *Against:* a second session in the build that no ruling has yet described; if none exists, this option waits on row 95.

- **C. The owner is `rick`.** *For:* known today. *Against:* Rick becomes the manager of some forty rows.
