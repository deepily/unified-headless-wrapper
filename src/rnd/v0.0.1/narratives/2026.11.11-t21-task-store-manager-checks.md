# The task store's manager checks (T21)

2026-11-11 · narrative for Rick's rulings. Claude doc: `https://claude.ai/artifact/Pq46zmxzkgpDMdrrdPKxct`. Specification: `specs/2026.11.11-t21-task-store-manager-checks-spec.md`. **All eight decisions were ruled as recommended on 2026-11-11.**

## In brief

Lupin's task store lets only a manager do certain things, and it decides who is a manager by opening a Claude Code session file on disk. A manager running on any other engine has no such file, so the store would refuse it. This item moves that decision onto the persona's identity in the Lupin kernel. Eight decisions are requested, each with a recommendation.

The register describes the work as one check: "the tasks router's manager-only guard on minting blocked tasks". The reading found nine places, not one. That changes the size of the item, and it is the first decision.

What is already settled and not reopened here:

- **A persona is one eight-character identifier**, minted by the kernel, and it is byte-for-byte what the store already parses out of the caller's signature.
- **Roles are a fixed list of seven**, set in the persona's manifest at spawn: chief of staff, manager, steward, author, implementer, reviewer, tester.
- **The fleet key proves the account, not the persona.** Every persona on a host shares it. Proven persona identity is a separate open item, scheduled with the kernel's move into Lupin.
- **Names carry over at the switch-over; identifiers do not.** The task store stays keyed on the persona's name.
- **The shapes of the two new tables** (the voice pool and the board sweep) and of the owed-work query were ruled with the switch-over. Only their doors are left.

## Where the record stands

Read in Lupin at commit `82fdc0182` and in the design repository at `3330a7b`.

**Seven doors ask "is the caller a manager?", and all seven call one function.** `is_manager_figure` lives in the Claude Code hooks tree and is imported by the server.

| Door | Where | What a non-manager is refused |
| --- | --- | --- |
| Blocked mint | `create_task` | creating a task that is born blocked |
| Priority at create | `task_priority_firewall` | creating above the worker priority |
| Priority raise | `task_priority_firewall` | raising a row into P1 to P4 (P0 stays the operator's alone) |
| Manager close | `transition_task` | closing a row on a manager's attestation |
| Promotion | `promotion_precheck` | admitting a row out of the holding area |
| Un-park ask | `ask_to_unpark` | asking the operator to un-park a row |
| Request filing | `file_request` | filing a promote or demote request |

**Two more places read the same session file for identity, not role.** `_requester_persona` and `_resolved_manager_attestation` look up the caller's voice-persona name so that a typed name cannot stand in for it.

What else the reading found:

1. **"Manager" has two sources today.** Explicit: the session was spawned into the role `manager`. Implicit: the session's voice persona is one of the project's named standing personas. The second is computed from an environment variable the server does not have, so it is stamped into the session file at start and read back.
2. **The caller's identifier is typed, not proven.** The tool server signs every write as `<persona name> <eight hex>` and the store reads the eight hex off the end. Anything holding the fleet key can type another seat's.
3. **The check fails closed, with three distinct messages**: no identifier, a session file that could not be read, and "resolved, not a manager". Lupin's own notes record why: a locked-out manager who is told the wrong cause goes hunting the wrong problem.
4. **A browser has no session file.** The operator's own approval was once refused for that reason, so a logged-in approver account is checked first and passes without the role check.
5. **The framework says role logic belongs in the kernel**, in what a persona is shown and what the gate allows. These seven rules need the row's own state (its present priority, whether it is held), which the gate never sees.
6. **Lupin's server can already ask the kernel.** The control API contract lists it as a caller of the roster, with the kernel's socket mounted into its container. The manager badge was moved onto that read yesterday.
7. **For the shadow run and the soak, both harnesses run side by side.** Claude Code sessions with session files and kernel personas without them will both write to one task store.
8. **Outside this item:** eight other server modules read session files (direct messages, commons, notifications, voice persona, speakerphone, the arbiter, the transcript tailer, the podcast proxy). Most have owners in earlier rulings. The podcast proxy is not in the switch-over inventory script; it is raised there.

## Problems and options

### 1. How much this item covers

The register names one door. The code has seven doors on one function, plus two identity reads of the same file.

- **A (recommended): all nine reads in the task store, through the one function.** Pros: the seven doors already share a predicate, so one change moves them all; leaving six behind would refuse a kernel manager at six doors instead of seven. Cons: a larger item than the register row says.
- **B: the blocked mint only, as written.** Pros: smallest change. Cons: a kernel manager still cannot raise a priority, promote, close on attestation or file a request; the register would need six new rows the same day.
- **C: every server-side read of a session file, in all nine modules.** Pros: one sweep. Cons: reopens what the application-changes, broadcasts, log and data-migration rulings already assigned.

### 2. Where the rule lives

The framework says role logic belongs in the kernel. These rules depend on the row.

- **A (recommended): the rules stay in Lupin's task store; only the fact "what role is this persona" comes from the kernel.** Pros: the rule sits beside the row state it needs; the browser path and the fleet path stay one rule; nothing is decided twice. Cons: amends the framework's sentence to "role logic belongs in the kernel, except a rule that needs the row".
- **B: move the seven checks into the kernel's gate and delete them from the store.** Pros: matches the framework as written. Cons: the gate would have to fetch each row before every task call; the operator's browser never passes the gate, so the rules would still be needed in the store; a direct call with the fleet key would meet no rule at all.
- **C: both, the gate first and the store as backstop.** Pros: defence in depth. Cons: two pieces of code deciding one rule, which Lupin's own notes warn against in three places.

### 3. Where the role fact comes from

- **A (recommended): Lupin asks the kernel for the persona's row, over the socket already mounted in its container, and keeps the answer for thirty seconds.** Pros: one source of truth; role and liveness in one read; the same read the manager badge already uses; when proven identity arrives, the lookup is replaced by a signed claim with no change to the rules. Cons: a manager's write made in the seconds a kernel is restarting is refused and must be retried; the test instance's container needs the socket mounted too.
- **B: the kernel writes each persona's role into a Lupin table at spawn, and the store reads its own database.** Pros: no dependency on the kernel at request time. Cons: a second copy of the registry to keep true; every kernel start would have to reconcile it.
- **C: the persona's tool server states its role in a request header.** Pros: no lookup at all. Cons: the role becomes as typeable as the identifier is today, and it is the one fact these doors exist to check.
- **D: bring proven identity forward and carry the role in it.** Pros: the proper answer. Cons: it is scheduled with the kernel's move into Lupin; pulling it forward holds this item behind that one.

### 4. Who counts as a manager

- **A (recommended): role only. A persona whose role is `manager` or `chief_of_staff` passes.** The named-standing-persona rule retires with the session files. Pros: one fact, set once in the manifest, the same on every engine; the chief of staff staffs managers and may run a team, so it cannot rank below them. Cons: a standing persona spawned into a crew role loses what its name bought it; that is a change in behaviour, if any such seat exists.
- **B: role `manager` only.** Pros: narrowest reading. Cons: the chief of staff could not raise a priority on work it assigned.
- **C: role, or a name on the standing list.** Pros: exact parity with today. Cons: the name is display continuity, its folding rule is an open item, and an author who happens to carry a standing name would pass as a manager.

### 5. How the caller is identified

- **A (recommended): keep reading the eight hex off the signature for now; when proven identity turns on, take it from the signed grant and refuse a signature that disagrees.** Pros: no change to the tool server or the wire today, because the kernel's identifier was designed to be that same string; the weakness is the one already accepted. Cons: until then, a typed identifier is still believed.
- **B: a required `Lupin-Persona-Id` header now.** Pros: stops parsing a name-and-identifier string. Cons: every caller changes for a value that is exactly as typeable.
- **C: change nothing until proven identity lands.** Pros: no interim work. Cons: kernel managers are refused at seven doors for the whole of Phase 2.

### 6. The weeks when both harnesses run

- **A (recommended): ask the kernel first, then the session file; record which answered. The session-file branch is a row on the switch-over list and is removed at the Delete clock.** Pros: both fleets write to one store through the shadow run and the soak; the audit trail shows which source said yes. Cons: two sources for a bounded time.
- **B: the kernel only, from the Move clock.** Pros: one source at once. Cons: every Claude Code manager still under the old harness loses seven doors during the soak.
- **C: a configuration key choosing the source.** Pros: an operator can force one side. Cons: one more switch to set wrong on one of two hosts; option A needs none.

### 7. What a refused caller is told

The "stale session file" cause disappears. A new one appears: the kernel cannot be reached.

- **A (recommended): four causes, four wordings. No identifier, 403. Not on the roster (dismissed or never spawned), 403. On the roster with another role, 403, naming the role seen. Kernel unreachable, 503 with a retry interval and the words "not a permissions problem".** Pros: keeps Lupin's hard-won rule that causes must not read alike; a retry is the right act for one cause only, and the status says so. Cons: one more status for the tool server to pass through.
- **B: 403 for all four.** Pros: simplest. Cons: a manager refused during a kernel restart is told it is not a manager.
- **C: allow the write when the kernel cannot be reached, and flag it.** Pros: no write is lost to a restart. Cons: the door opens widest when least is known.

### 8. The doors of the three new store surfaces

The board sweep's start, mark and close, the voice pool table, and the owed-work query all sit behind the fleet key.

- **A (recommended): no role check on any of them. A persona opens and marks only its own sweep, and the store takes the persona's name from the kernel's row for the identifier, never from a typed field. The owed-work query stays readable by any fleet-key caller. The voice pool is written by the kernel alone.** Pros: today's sweeps are run by seats that are not managers, so a role check would break them; the name cannot be typed. Cons: one kernel read per sweep call.
- **B: sweeps are manager-only.** Pros: one more consistent door. Cons: refuses the seats that sweep today.
- **C: no checks; the typed persona name is believed.** Pros: nothing to build. Cons: one persona could mark another's sweep reviewed.
