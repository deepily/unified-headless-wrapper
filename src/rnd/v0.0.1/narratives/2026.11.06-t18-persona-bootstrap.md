# Persona bootstrap (T18): problems, options, recommendations

**As of:** 2026-11-06 · **Author:** Rick Ruiz (drafted with Claude) · **Work item:** T18, persona bootstrap, framework Section 13 · **Audience:** a reader coming to the project cold · **Rulings:** all six adopted as recommended on 2026-11-06, decision D54 (persona bootstrap); spec `specs/2026.11.06-t18-persona-bootstrap-spec.md`; the convention kit and the verb table were already ruled with convention parity (D51) the same day, so this item supplies the rules that port follows · **Live copy:** https://claude.ai/artifact/AhAMxEqGfx6bsLRjFLAgEJ

## Why this matters

A persona is a model running inside an engine, inside a git worktree, under the Lupin kernel. Everything it knows about how to behave arrives through six layers of text the kernel renders at spawn: who it is, what its role is, its own instructions, the response format, the project's standing rules, and a first turn. Launch per persona settled layers one to four and the channel each takes on each engine. Two things were left open and both are this item: the standing rules and the first turn, which together are the whole of what makes a persona follow Rick's working conventions rather than merely answer.

The conventions themselves exist and are mature. They live in the planning-is-prompting repository: sixty-one workflow documents, forty-one slash commands, six skills, one global mandates file and thirty-three scripts, written over six months of running Claude Code sessions by voice. The trouble is that every one of them was written for Claude Code on a developer's own machine. The commands are installed by an interactive wizard into `.claude/commands/`; the mandates are deployed to `~/.claude/CLAUDE.md`; the memento that lets a session survive a context reset is mirrored under `~/.claude/mementos/`; and the writer that produces it learns the session's identity from lupin's bridge files, which only exist under the current harness. None of that is reachable from a Jetski-family persona, and the kernel is designed to depend on none of it even on Claude.

Convention parity made this the handoff's precondition. The first implementer of the kernel after Phase 1 is an AGY persona, and it may only take the work once it has been observed following each of nine kit conventions end to end (Convention-1 to Convention-9). That gate cannot be passed without answering four questions this document puts to Rick: where the kit lives for a persona, how the standing rules reach every engine without a global file, what a memento is under the kernel and how a persona is rehydrated from one, and what installs all of it. A fifth question, the charter briefs for crew and cascade seats, is deferred to Phase 2 by the same ruling; this document reserves its place in the first turn and no more.

## The principles this item rests on

**Six instruction layers, identical text on every engine.** Ruled with launch per persona. Layers one to four (kernel contract, role charter, persona instructions, format rules) go through `--append-system-prompt` on Claude and the agent-definition body in the worktree on the Jetski family. Layer five, the project mandates, is the worktree's `CLAUDE.md` on Claude and a kernel-written `AGENTS.md` copy on the Jetski family. Layer six is the first user turn. The kernel depends on no global instruction file: a fleet host also runs Rick's own ad hoc sessions, and global state is neither per persona nor recorded per spawn.

**Instruction files live in the worktree.** The kernel writes each persona's `AGENTS.md` and `.agents/` into its worktree at provisioning and excludes both from git. No global agent definitions.

**Commands are skills, on every engine.** Every slash command becomes a `SKILL.md`; the kernel installs each persona's skills into `.agents/skills/` (Jetski family) or `.claude/skills/` (Claude), and expands a turn that starts with `/name` from that skill before the engine sees it. Skills load natively on both Jetski-family binaries (measured in October); there are no custom commands there.

**One workflow set, behind kernel verbs.** Convention parity ruled that the kit's documents name the verb, not the engine primitive: *start cold*, *rehydrate*, *add a task*, *ask the human*, *plan first*, *mandates file*, *skills directory*. The current harness honors the same verbs until switch-over.

**One identifier, eight hex, minted by the kernel.** The persona id is the job id, the sender suffix, the socket name and the directory name. The current harness's eight-hex `stable_session_id[:8]` migrates to it byte for byte.

**A rule adds a step; a mechanism removes a decision.** Rick's standing doctrine, and the reason the memento writer exists: on 13 July a careful session following a written rule destroyed two irreplaceable records, because writing and destroying were spelled the same. Every proposal below prefers a kernel act over an instruction the model must remember.

**The memento is testimony, not measurement.** A rehydrated session verifies what the record claims before carrying it, and its first obligation is to reconcile owed work against the task store, which is canonical. The record is immutable; the pointer is derived and safe to overwrite; the mirror is what survives `git clean`.

**Mandates are copied, never authored twice.** On the Jetski family `AGENTS.md` carries exactly what Claude would load from the worktree, so there is no second source. Drift between a canonical paragraph and a deployed copy is the defect planning-is-prompting's parity checker exists to catch: a single stale sentence survived five sightings across two weeks because each fix landed on one copy.

## What exists today

Read on 2026-11-06 from the laptop checkouts, read-only: `planning-is-prompting` at `9d8bf4f` (the same commit the capability inventory and convention parity read) and `lupin`.

**A command is a thin wrapper around a workflow it reads at an absolute path.** `.claude/commands/plan-session-start.md` is thirty lines: the project's prefix (`[PLAN]`), the history file's absolute path on the dev server, and the instruction to read `planning-is-prompting/workflow/session-start.md` in full before doing anything. The workflow itself is 1,747 lines. `plan-memento.md` has the same shape over a 569-line workflow. The installation wizard writes these wrappers per project, filling in the prefix and paths; it is 4,367 lines of interactive Claude workflow and is already outside the kit. So a persona running a kit command needs two things: the wrapper, and a way to read a document that lives outside its worktree. Whether a Jetski-family `read_file` reaches outside the workspace has never been measured; the Phase 0 captures measured reads of paths inside it.

**The global mandates file is 565 lines and is deployed, not loaded from the repo.** `global/CLAUDE.md` holds the brevity mandate, the task-store mandate, parallel-session safety, Code Style, PATH MANAGEMENT, POST-EDIT VERIFICATION, TEST OWNERSHIP and the notification protocol, among others. It is deployed to `~/.claude/CLAUDE.md` on each machine; `doc_deploy_parity.py` detects drift between the canonical and deployed copies (and deliberately never repairs it); `sync_deployed_claude_md.py` repairs the one safe kind of drift on request; `nightly_deploy.py` ships a repo's merged head to a remote host. The launch-per-persona spec left a branch open here: if capture C15b finds that `~/.claude/CLAUDE.md` still loads under the kernel's Claude flags, the mandates "stay in `~/.claude/CLAUDE.md` on Claude". That branch contradicts the same spec's rule that the kernel depends on no global file, and this document closes it.

**The memento is already a mechanism, and its only engine coupling is identity and paths.** `memento_io.py` (3,763 lines) is the sole writer. It stamps line 1 of every record `<!-- memento-record: persona=… session_id=<eight hex> written_at=… slot=… -->`, writes an immutable record (`io/mementos/<slug>-<eight hex>.md` or `.claude-memento-<slug>-<eight hex>.md`), re-points a per-persona pointer that carries a full copy of the record, and mirrors the record under `~/.claude/mementos/<repo>/`; it refuses to overwrite a record (exit 3) and offers `amend`, `adopt`, `resolve`, `regenerate-pointer`, `migrate` and `verify`. A third slot, `tmp`, writes outside the repo to `$LUPIN_MEMENTO_DIR` or `/tmp/mementos/<repo>/`, boot-wiped, with no mirror. Three couplings to the current harness: the session id it stamps is resolved from lupin's bridge files when not passed; the mirror root is `~/.claude/mementos/`; and the eight hex it stamps are the current harness's `stable_session_id[:8]`, which is exactly the kernel's persona id after migration.

**The contract is nine elements and is content, not code.** Current state, cast roster, open findings, active DM threads, standing guidance, heartbeat state, rehydration instructions, the verbatim pending list (demoted to a store-unavailable fallback once the task store became canonical), and the retro deposit. Two of the nine apply only in cascade mode. The refresh trigger is being given work, not elapsed time: a record that says "nothing owed" and is then handed a task lies to its successor.

**Rehydration today is a path appended after the task, and the reader is the model.** lupin's `spawn_sessions( seed_memento=… )` appends the value verbatim under the heading "Prior context (memento, your earlier work on this, for reference)", after the task so the task drives. The value may be the record's content or its path; a census of 1,660 transcripts found 130 children given an absolute path, every one of which opened the file. The session-start hook `register_session.py` resolves a seat's memento by exact eight-hex match first, then the live pointer, then the newest record for the persona's slug, and refuses the retired shared pointer because it would hand one persona another's state. The session-end ritual sweeps mementos older than two days into the trash after digesting them into history, keeping the newest per live persona.

**Convention parity already ruled the shape of the port.** Twenty-five workflows in four groups; paths become `$LUPIN_WORKSPACE`, `$LUPIN_SKILLS_DIR`, `$LUPIN_MANDATES_FILE`; eighteen `/clear` uses become *start cold* or *rehydrate*; fifteen hook-event uses map to the kernel's first turn, turn-end policy and the tool gate; six `TodoWrite` uses go to the task store; five plan-mode uses become an explicit plan step; four `AskUserQuestion` uses become ticketed asks; the memento scripts' paths become harness-owned; the installers gain a per-engine target. What it did not rule, and left to this item, is each of those as a concrete mechanism.

## The problems, stated one at a time

**Problem 1: the kit's documents are outside the worktree.** A command tells the model to read a workflow at an absolute path in the planning-is-prompting checkout. A kernel persona's workspace is a lupin worktree; its native read tool may refuse a path outside it (the Jetski family) or may not (Claude), and nothing has measured which. Even where the read succeeds, the persona reads whatever commit the checkout happens to be at, so two personas spawned a day apart can follow different conventions and no record says which.

**Problem 2: every command carries project values the wizard filled in by hand.** The prefix, the history file's path, the installed workflow list. Under the kernel a persona may be provisioned into any lupin worktree at any time; nothing interactive can run first. The values must come from somewhere the kernel can read.

**Problem 3: the global mandates have no kernel channel.** They are the mandates the acceptance gate checks (Code Style, POST-EDIT VERIFICATION, TEST OWNERSHIP, PATH MANAGEMENT are four of the nine conventions), and today they reach a session only through `~/.claude/CLAUDE.md`, a host-level file the kernel does not own. The launch spec's own conditional would keep them there on Claude if C15b finds the file loads. If it does, a Claude persona gets Rick's live copy, unversioned, while a Jetski persona gets whatever the kernel copied, and the two engines no longer read identical text. If it does not, nothing delivers them on Claude at all.

**Problem 4: the memento writer learns its identity from a harness that will not exist.** `memento_io.py` resolves an omitted session id from lupin's bridge files; the kernel has no bridge files (its registry replaces them, per the switch-over data migration item). Its mirror root is `~/.claude/mementos/`. Its stamp calls the eight hex a `session_id`, which under the kernel is the persona id. And the current harness's session-start hook, which is the one reader that resolves a record by that id, is on the deletion list.

**Problem 5: rehydration is a path handed to the model, under a heading that promises content.** The spawner appends whatever it is given; the child must notice it was given a filename, open it, and verify it. The transcript census shows the children do open it, and shows nothing about whether they use what they read. Two measured failures (a "33 files" figure that summed to nothing; three commits reported as held that were already pushed) came from carrying a record's claim without re-running it. The design relies on a rule at the read end, which is the failure class the writer was built to remove at the write end.

**Problem 6: the first turn has no defined composition.** The launch spec says layer six is "memento rehydration, charter brief" and leaves the rest here. Three things compete for it: the session-start ritual the gate expects to run unprompted (Convention-1), an engagement brief when the persona is a crew or cascade seat (Phase 2), and the memento. The order matters: lupin's standing directive is that the task leads and the memento follows, because the last thing read tends to drive.

**Problem 7: the verb *prepare for re-spin* has no kernel act behind it.** Today a manager says the phrase, the worker reaches a safe checkpoint, writes its memento and acknowledges by direct message; the manager then reaps and respawns it with the memento path. Under the kernel `lupin persona respin <id>` is one command (Convention-7 tests it mid-task), so the kernel must run that three-beat handshake itself: tell the persona, wait for the record, respawn with it, and decide what to do when no record appears.

**Problem 8: there is no installer for a persona.** The wizard is interactive and Claude-only and is not in the kit. The deploy scripts ship a repo head to a host, check mandate parity, and repair one kind of drift; none of them writes a skill into a worktree. Provisioning a worktree is already a kernel act (it writes `AGENTS.md` and `.agents/` and excludes them from git), so the installer is either the provisioner or a second thing the provisioner calls, and the choice decides whether a persona can ever be spawned into a repo nobody has "installed".

## Proposed solutions

### Solution 1: The kit is rendered into the worktree from a pinned commit (Problems 1, 2)

The kernel keeps one checkout of planning-is-prompting per fleet host at `~/.lupin/kit/`, at the commit named in `~/.lupin/kernel/kit.lock`. At provisioning it renders the twenty-five kit skills into the persona's `$LUPIN_SKILLS_DIR` (`.agents/skills/` or `.claude/skills/`): one folder per skill holding `SKILL.md`, the rendered wrapper (name, description, the project's values, and the instruction to read the workflow beside it), and `WORKFLOW.md`, the canonical workflow copied verbatim. The project's values come from one committed file, `<repo>/.lupin/project.yaml` (`prefix`, `history_file`, `todo_file`, `kit_groups`); provisioning refuses a repo without it and names the missing field. The registry row and the spawn log record `kit_commit`. Rendering is idempotent on every spawn, as the launch files already are, so a new lock takes effect at the next respawn.

| Option | Pros | Cons |
|---|---|---|
| **A. Render into the worktree from a pinned commit (recommended)** | Every read is inside the workspace, so the outside-workspace question never needs measuring; the exact text a persona followed is recorded per spawn; a new kit version is one lock change and a respawn | A copy per worktree (about 1.5 MB); the kernel owns a git checkout; `doc_deploy_parity` must learn the new deployed location |
| B. Reference the checkout by absolute path, with `--include-directories` on the Jetski family | No copies; the kit updates in place | Needs a capture to prove the read works; unversioned, so two personas a day apart follow different text and nothing records which; `--include-directories` is one more flag per engine to verify on every engine update |
| C. Inline the whole workflow into each `SKILL.md` | One file per skill; the kernel's `/name` expansion delivers the text and logs it | A 1,747-line skill body is loaded natively by the engine on every trigger, not only on the command; the skill and the workflow drift into one undiffable file |

*Recommendation: A.* The wizard is not ported: it serves human installs into repositories no persona runs in. The `.claude/commands/` wrappers lupin and planning-is-prompting carry for the current harness are regenerated from the same templates and the same project file by one script at the port, which is the cost convention parity already accepted for a single workflow set.

### Solution 2: Layer five is a kernel-rendered mandates file; the host's global file is nobody's dependency (Problem 3)

The kernel writes `<worktree>/.lupin/mandates.md` at provisioning: the kit's `global/CLAUDE.md` at the pinned commit, then the project's `CLAUDE.md`, then `CLAUDE.local.md` when present, in that order. That file is `$LUPIN_MANDATES_FILE` on every engine and the file of record for any workflow or script that reads the mandates. Delivery: on the Jetski family the file is copied to `AGENTS.md`, as already ruled; on Claude the project files load natively from the worktree and the global part is appended as a fifth block of `--append-system-prompt`, so the model reads the same text split across two channels. The spawn log records `mandates_sha256`. A `~/.claude/CLAUDE.md` on a fleet host is Rick's own file; capture C15b now answers only whether a Claude persona sees the global mandates twice, which is tolerated and logged, and the launch spec's conditional is withdrawn.

| Option | Pros | Cons |
|---|---|---|
| **A. Kernel-rendered file, global part through the system prompt on Claude (recommended)** | Identical text on both engines from one pinned source; no host file is load-bearing; a hash per spawn | On Claude the global and project parts travel by different channels; a host that also deploys `~/.claude/CLAUDE.md` shows Claude personas the global part twice until the deploy stops on fleet hosts |
| B. Write the global part to `<worktree>/CLAUDE.local.md` on Claude | One channel on both engines (a context file) | Clobbers a developer's own `CLAUDE.local.md` in a shared checkout; `CLAUDE.local.md` is a gitignored convention the kernel would be silently repurposing |
| C. Keep deploying to `~/.claude/CLAUDE.md` and let C15b decide (the launch spec's conditional) | No new rendering | Unversioned on Claude, invisible to the spawn log, absent on Claude if C15b says no; contradicts the no-global-file rule |

*Recommendation: A.* The file is the whole of `global/CLAUDE.md` after the port, never a subset: a subset is a second source that drifts.

### Solution 3: The memento writer becomes harness-owned by three small changes (Problem 4)

`memento_io.py` stays the one writer and keeps its three slots, its record, pointer and mirror, and its nine-element contract. Three changes: it reads `LUPIN_PERSONA_ID` from the environment before it consults any bridge file, and refuses to run with neither; the mirror root becomes `$LUPIN_MEMENTO_MIRROR`, default `~/.lupin/mementos/<repo>/`; and the line-1 stamp writes `persona_id=<eight hex>` where it wrote `session_id=`. Every reader (the writer's own `resolve`, the kernel, the current harness's hook until it is deleted) accepts either key, because the value is the same eight hex either way. Records written before the port need no migration.

| Option | Pros | Cons |
|---|---|---|
| **A. Identity from the environment, mirror re-rooted, stamp renamed, readers accept both (recommended)** | A few dozen lines; records and pointers stay where every workflow, the session-end harvest step and the sweep expect them; nothing on disk migrates | Two spellings of one key coexist until the current harness is deleted |
| B. A kernel-owned store under `~/.lupin/kernel/personas/<id>/mementos/`, no files in the repo | The kernel resolves everything; no pointer, no mirror | Breaks the harvest step, the sweep, the post-game arming that reads sibling records in the repo, and every naive reader; a port the size of the writer itself |
| C. Set `LUPIN_MEMENTO_DIR` only and change nothing else | Zero port | The writer still needs a bridge file to learn who it is; the mirror stays under `~/.claude/` |

*Recommendation: A.* The kernel never writes a memento: its content is the persona's testimony. The kernel reads them.

### Solution 4: The kernel composes the first turn; the memento arrives as content, last (Problems 5, 6)

Layer six is one kernel message in the inbox envelope's vocabulary, a `[kernel first-turn …]` block, composed in this order:

1. **The spawn line.** `cold` or `rehydrate`, the persona id and role, `kit_commit`, `mandates_sha256`. One line, so the model can say what it was given.
2. **The session-start ritual, expanded.** The kernel expands the kit's `session-start` skill into the turn exactly as it would expand `/plan-session-start` typed by a human. Convention-1 ("the ritual runs unprompted") becomes a mechanism: the ritual is the first instruction, not a habit the model must have.
3. **The brief, when the spawn carried one.** From the manifest's `brief:` or the spawn call. In Phase 1 this is a task statement or nothing; in Phase 2 it is a crew or cascade seat's charter section. The slot exists now so the order is fixed before the content does.
4. **Prior context.** The record's full content, inlined by the kernel under the heading "Prior context (memento written <when>, <age>; verify before you carry it)", with its line-1 stamp intact. The kernel resolves the record itself: exact persona-id match first, then the newest record for the persona's slug across `io`, `root`, `tmp` and the mirror. A record older than a day is inlined with a staleness line, never silently dropped. No record means a cold spawn and no heading. The log gets `memento.rehydrated` with the record's path, hash, `written_at`, age and which match found it.

The task leads and the memento follows, per lupin's standing directive. The persona's obligation to verify the record and reconcile owed work against the task store stays in the kit (session-start's reconciliation step), where it is already written; the kernel does not grade testimony.

| Option | Pros | Cons |
|---|---|---|
| **A. Kernel composes all four parts; memento inlined as content (recommended)** | The ritual is guaranteed; the heading says content and carries content; the kernel logs exactly what was rehydrated; the model never derives a path | A long first turn (a few thousand tokens) on every spawn; the kernel must know the kit's skill name for the ritual |
| B. Kernel sends the spawn line and brief; the model runs the ritual and opens the memento by path | Short first turn | Convention-1 depends on model compliance; the heading-versus-content mismatch survives; nothing logs what the model actually read |
| C. Memento first, then the ritual and brief | The successor reads its own state before anything else | Reverses the directive that the task drives; a large record buries the instruction, which is the measured failure the directive was written against |

*Recommendation: A.*

### Solution 5: Re-spin is a kernel handshake with a bounded wait and a cold fallback (Problem 7)

`lupin persona respin <id>` runs the kit's three beats itself. The kernel writes a `[kernel respin …]` block: reach a safe checkpoint, write your memento (`memento_io.py write --slot io`), end your turn. It waits for the turn to end, bounded by `respin.timeout` (default ten minutes). It then looks for a record stamped with this persona id and newer than the request. Found: respawn with it (Solution 4). Not found: send the request once more with the kit's three-beat text; still none at the next turn end: respawn cold, narrate `respin_without_memento`, log it. The acknowledgment is the turn end plus the record's existence, which the kernel verifies; no direct message is required. A persona asking for its own re-spin (today's `self_respin`, in the first person) opens a ticket to its approver under the tool-approval rules; an answered ticket runs the same handshake. The default slot is `io`: a kernel persona is resumed across reboots (Kernel-8), so a boot-wiped `tmp` record would strand a resume, and clutter is the session-end sweep's job.

| Option | Pros | Cons |
|---|---|---|
| **A. Kernel-run handshake, bounded, cold fallback, slot `io` (recommended)** | One command does what three beats and a manager did; the only acknowledgment is one the kernel can check; a persona that cannot write a memento is still respawned | A persona mid-edit at the timeout is respawned without a record of that edit; the timeout is a guess until measured |
| B. Respawn immediately with the newest existing record | Instant | The record predates the request and lies about owed work, the exact staleness the refresh rule warns against |
| C. Require a direct-message acknowledgment before respawn | Matches today's text | A message is a rule the model must remember; a persona that forgets is never respawned |

*Recommendation: A.*

### Solution 6: The provisioner is the installer, and kernel-owned files are gate-protected (Problem 8)

There is no separate install step. `lupin persona spawn` provisions: it reads `.lupin/project.yaml`, checks out the kit lock's commit under `~/.lupin/kit/` if the checkout is behind, renders the skills (Solution 1) and the mandates (Solution 2), writes `.git/info/exclude`, and records `kit_commit` and `mandates_sha256` in the registry row and the spawn log. Pinning the kit is an operator act: `lupin kit pin <commit>` rewrites the lock; the next spawn or respawn of each persona picks it up. One new gate rule, `kernel_owned_file`, mode `enforce`: a persona's write under `$LUPIN_SKILLS_DIR`, `.lupin/`, `.agents/`, `AGENTS.md` or `.claude/settings*.json` in its own worktree is denied with the reason that these are rendered by the kernel; a convention that needs changing is changed in the kit, never in a worktree. `doc_deploy_parity` gains the rendered worktree copy as a deployed location, so a drifted mandate paragraph is reported the same way it is on a host today.

| Option | Pros | Cons |
|---|---|---|
| **A. Provisioning renders everything; no install step; kernel-owned files denied to the persona (recommended)** | A persona can be spawned into any repo that has a project file; what it was given is recorded; it cannot quietly rewrite its own conventions | The wizard's interactive choices (which workflow groups) collapse to `kit_groups` in the project file; a manager that wants to add a provisional mandate in Phase 2 needs a kernel verb for it |
| B. Port the installation wizard | Keeps the interactive flow | 4,367 lines of Claude-only interaction for a decision the project file makes once; cannot run at spawn time |
| C. Keep `nightly_deploy` and `sync_deployed_claude_md` as the installer | Already exists | They deploy a repo head to a host and repair one kind of drift; neither writes a skill into a worktree or knows a persona exists |

*Recommendation: A.*

Half a day. A failure names the mechanism (renderer, resolver, handshake, gate rule); the fix is to the kernel, never to the test.
