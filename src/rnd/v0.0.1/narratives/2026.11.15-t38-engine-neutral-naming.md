# Names that say "Claude Code" where a persona is meant (T38)

**As of:** 2026-11-15 · drafted on the test VM under Antigravity, against this repo at `5e04b90` and lupin at `aabadd221` · counts from `src/captures/t38_naming_inventory.sh`, output `src/captures/out/t38-naming-lupin-host-test-20261115.txt` · no ruling taken yet.

## In brief

Lupin grew up with one engine, so the word for "a persona's seat" became `cc` (Claude Code): `cc-listener-…`, `cc_session_id`, `cc session voice persona pool`. The kernel runs three engines. A name that says `cc` on something an Antigravity persona touches is wrong on its face, and each one left in place is a place where a reader, or a model, infers the wrong engine.

The register sized this job at 2,669 occurrences of `claude_code` alone. **The inventory, run for the first time, finds 203 of those in code that will survive**; the old count was mostly tests and documentation. For every engine name taken together:

- In lupin's code proper there are 2,134 engine-named occurrences in 264 files.
- 636 of them, in 80 files, sit in files the switch-over list already deletes. They need no rename; they vanish.
- **1,498 occurrences in 184 files survive**, as 380 distinct names. Those are the subject of this item.

The survivors are not a smear. They fall into nine families, and most of the wire-visible ones are small: the listener socket name is 23 occurrences in 8 files; the broadcast route is 12 in 7.

Ten decisions are requested. The first two set the rule (what is exempt, what word replaces `cc`); six settle one family each; the last two say how the rule is kept and what is left as history.

## Where the record stands

**The rule already in force** (framework Section 4.1, written 2026-11-08): no identifier that reaches a kernel persona says `cc`, `claude_code` or `claude.code` unless it names the Claude engine itself. It covers kernel code, new Lupin code, new configuration keys, routes, style classes and log kinds. Existing names were to be inventoried, then renamed on three clocks: wire contracts and configuration keys at the switch-over, internals when convenient, and the kernel never carrying one.

**What earlier rulings handed to this item:**

- The listener socket name `cc-listener-{id}` becomes `persona-listener-{id}` (sketched in the register; the socket ruling made the old name a wire contract with Lupin).
- The broadcast route `/api/commons/broadcast-to-cc-sessions` gets a name without `cc` (Rick, 2026-11-10); the new name was never chosen.
- The transcript route `/api/cc-transcript/*` becomes `/api/persona-log/*` (the log ruling).
- The `cc session voice persona …` configuration key names (the persona-name ruling of 2026-11-15, which rewrites those same lines into key form and left the prefix to this item).
- The switch-over list has three rename rows for these and four "move key" rows that turn fourteen `cc session …` fleet keys into `kernel fleet …` keys.

## Problems and options

### 1. What "the engine itself" exempts

The rule excuses a name that means the Claude engine. Without a list, every rename invites the argument again.

- **A. Three exemptions, listed (recommended).** (i) The Claude adapter and the `claude.code@` sender address; (ii) the Claude job family, which launches Claude Code by name and whose job type is stored in rows; (iii) the vendor's own names (`CLAUDE_CODE_…` variables, `~/.claude`). Everything else that means "a persona", "a seat" or "the fleet" is renamed. *For:* matches what the names mean; no stored job rows to migrate; removes 118 + 131 occurrences from the job. *Against:* `cc-` stays as a job-identifier prefix, the one place the two letters survive on purpose.
- **B. Exempt only the adapter and the vendor's names; rename the Claude job to an engine-neutral job.** *For:* no `cc` left anywhere. *Against:* the job is not engine-neutral today; renaming it claims a generality that does not exist, and the stored job type needs a data migration.
- **C. Exempt anything not on the wire.** *For:* least work. *Against:* leaves `cc_session_id` in every signature a persona's implementer reads; the rule exists because models read code.

### 2. The word that replaces `cc`

The register sketches `persona` everywhere. Lupin also says `session`, `seat`, `agent` and `worker` for the same thing.

- **A. `persona` for what belongs to one persona, `kernel fleet` for what belongs to the fleet, `engine` where the vendor's program is meant in general; where dropping `cc session` leaves a clear name, just drop it (recommended).** So `persona-listener-{persona_id}`, `persona_id`, `persona log`, `voice persona pool`, `kernel fleet size cap`. *For:* three words that the kernel's design already uses with fixed meanings; "voice persona" is already Lupin's term and the name of its allocation table. *Against:* `persona` must then never be used loosely for a role or a voice.
- **B. `agent`.** *For:* common industry word. *Against:* Lupin already uses "agent" for its own in-process agents (`cosa/agents/`); collision.
- **C. `session`.** *For:* closest to today's names. *Against:* in the kernel a session is one engine process, many per persona over its life; the word would mean two things.

### 3. The voice-persona key names, and when they change

Sixty-five keys begin `cc session voice persona`, plus `cc session worker default voice mode`. Lupin reads them, not the kernel (six surviving files, the two configuration files among them). The persona-name ruling already rewrites every one of these lines into key form.

- **A. Drop the prefix (`voice persona pool`, `voice persona <key> voice id`, `voice persona <key> display name`, `worker default voice mode`), in the same lupin change as the persona-name rewrite, with no alias (recommended).** *For:* the 65 lines are edited once, not twice; the file and its readers ship in one commit, so no reader can see a half-renamed file; row 32 of the outstanding actions (the test VM's modified file) has to be settled once. *Against:* makes that one lupin change larger; a host with a locally edited file must merge by hand.
- **B. Same names, at the switch-over, with the rest of the wire.** *For:* keeps the persona-name change small. *Against:* two passes over the same lines; the old hooks, alive until then, would have to be taught nothing either way.
- **C. `persona voice …` or `kernel persona …`.** *For:* follows the register's sketch literally. *Against:* `kernel …` keys are the kernel's, and these are Lupin's; `persona voice` reverses a term Lupin already uses.

### 4. The listener socket name: how the cut-over happens

Lupin routes a persona's notifications to a socket named exactly `cc-listener-{id}`, and decides "persona or browser" by that prefix in six places. The Phase 1 kernel talks to an unmodified Lupin, so it must use the old name at first.

- **A. Lupin accepts both prefixes from the move into lupin, through one helper that replaces the six prefix tests; the kernel connects as `persona-listener-` from that day; the old prefix is removed with the old harness (recommended).** Until the move, the Phase 1 kernel holds `cc-listener-` as one constant in its Lupin boundary module, the only occurrence permitted. *For:* no coordinated two-sided change on switch-over day; the six scattered tests become one function; the mixed fleet of the shadow run works with both. *Against:* two prefixes live for the length of the shadow and the soak.
- **B. One flag day at the switch-over, both sides at once (the register's sketch).** *For:* never two names. *Against:* adds a wire change to the busiest day; the kernel soaks under a name it will not ship with.
- **C. Keep `cc-listener-` forever as an opaque wire constant.** *For:* zero work. *Against:* it is the first string a kernel implementer meets.

### 5. The transcript stream: how much of it is renamed, and on which clock

The record renames only the route, and names two clocks for it: the framework's Lupin section says the switch-over, the switch-over list says after the last Claude transcript seat is gone.

- **A. The whole family in one change (routes to `/api/persona-log/…`, message kinds to `persona_log_watch` and its three siblings, the field to `persona_id`, the five keys to `persona log …`, the file names), on the list's clock: at Delete, after the last Claude seat (recommended).** *For:* server and client ship together, so no alias is needed; a route called `persona-log` carrying `cc_session_id` and answering `cc_transcript_state` would be a half-rename; until the last Claude seat goes, the name is still true. *Against:* the name stays wrong for Antigravity personas through the soak; about 210 occurrences in one change (16, 73, 106 and 18 by the inventory).
- **B. The whole family at the switch-over.** *For:* right as soon as Antigravity personas are the fleet. *Against:* one more change on switch-over day.
- **C. The route only (the record as written).** *For:* smallest. *Against:* the half-rename described above.

### 6. The broadcast route's new name

- **A. `/api/commons/broadcast` (recommended).** *For:* shortest; sits beside `/api/commons/broadcast-history`; who receives is in the message's addressing, not the path. *Against:* says nothing about the recipients.
- **B. `/api/commons/broadcast-to-personas`.** *For:* explicit. *Against:* under the broadcast ruling a message can address one persona or all; "to personas" restates the default.
- **C. `/api/commons/broadcast-to-fleet`.** *For:* names the default. *Against:* wrong for a message addressed to one.

Either way the rename lands at the switch-over as the list says; the route has seven reader files, all in the lupin checkout.

### 7. Names the hosts hold

The shared key's file name and the hooks' virtual-environment variable are in compose files, environment files and on disk on every host.

- **A. Rename each only when its host step is being done anyway: the key file when the shared key is next rotated or replaced, the variable when the hooks tree is deleted; both become "operate" rows on the switch-over list (recommended).** *For:* no host is touched for a name alone; a persona never reads either name. *Against:* both outlive the switch-over by an unknown time.
- **B. At the switch-over, with the wire.** *For:* done once. *Against:* a credential file renamed on the day the fleet changes hands, for no change in behavior.
- **C. Never.** *For:* nothing to do. *Against:* an open-ended exception with no reason recorded.

### 8. Browser names and internal identifiers: the clock, and how it is tracked

Roughly half of the 1,498 surviving occurrences belong to none of the families above: they are internal names and browser names (409 of them in browser files). The record says "opportunistic, no gate".

- **A. Opportunistic with a ratchet: the inventory's survivor count is recorded at the switch-over and a lupin check fails if it rises; a file touched for another reason is renamed then (recommended).** *For:* the count can only fall, and it is tracked rather than guessed; no rename-only change competes with real work. *Against:* no date by which it reaches the exempt floor.
- **B. A deadline: zero outside the exemptions at Delete.** *For:* an end. *Against:* a change of several hundred occurrences with no behavior behind it, at the moment the old harness is being removed.
- **C. Opportunistic, untracked (the record as written).** *For:* least machinery. *Against:* new `cc` names can arrive unnoticed; that is how the count got here.

### 9. How the rule is kept in new code

- **A. A test (recommended).** In the kernel, an acceptance test, `Naming-1`, run with the first kernel gate: the engine-name pattern has zero matches in the kernel package outside a two-entry allow-list (the listener constant of decision 4, the Claude adapter). In lupin, the ratchet of decision 8. *For:* the rule holds without anyone remembering it; a model writing kernel code is corrected by a failing test. *Against:* an allow-list to maintain.
- **B. Review only.** *For:* nothing to build. *Against:* the two names introduced and corrected on 2026-11-08 were caught by luck.

### 10. Tests, documentation and the record

Tests hold 6,512 occurrences and documentation 4,187.

- **A. Tests follow the code they test, in the same change; documentation and this repo's record are history and are not rewritten; anything newly written obeys the rule (recommended).** *For:* a transcript or a ruled spec that says `cc-listener-` is describing the Lupin of its day, correctly. *Against:* a search for `cc` keeps finding documents.
- **B. Sweep the documentation too.** *For:* a clean search. *Against:* 4,187 edits to history; a ruled spec's body is never rewritten by this protocol.

## What follows without a decision

- **The register row is corrected.** Its counts stood for tests and documentation; the framework will carry the inventory's figures and point at the script.
- **636 occurrences need nothing.** They go with the files the switch-over list deletes, 73 of the 87 engine-named file paths among them. `cc_pid`, the `cc-{pid}.json` bridge files and the `cc-buffer-…` files go the same way.
- **Crew names of the form `cc-{role}-{name}`** (and the worktree and direct-message names built from them) are composed in one place, `lupin_mcp/session_spawner.py:1036`, which the list deletes. The rule in force keeps the kernel from composing them again.
- **Fourteen fleet keys** already move to `kernel fleet …` under the switch-over list; this item adds nothing to them.
- **The inventory script reads the switch-over list's delete rows directly**, so the two scripts cannot disagree about what survives.
- **New rows on the switch-over list** follow from decisions 3 to 7; they are added when this item is recorded.
- **The development server's reading** is owed after the rulings, as a new top block in the runbook; lupin there may be at a later commit.
