# The unprivileged account for the kernel and the engines (row 39 of "Outstanding actions")

**As of:** 2026-11-16 · not a register item; it needs rulings, and is recorded under the fleet decision, part 9, as row 20 was. This repo at `183fcb8`, lupin on the test VM at `67456220d`. Every count below comes from the account inventory Rick ran on the development server on 2026-11-16 (`src/captures/out/t16-account-inventory-dual-rtx-4090s-20261116.txt`), and each sum was rechecked against that file for this page. **Four statements about the development server are readings or inferences, not host facts, and are marked "to be confirmed"; a second zero-token script, `src/captures/t16_account_reach.sh`, confirms them and is owed before the first question is put** (RUNBOOK, top block).

## In brief

The fleet decision already says that on a host holding a person's credentials, the kernel and the engines run under an account of their own, with no `sudo` and no Docker membership, and that the kernel refuses to start otherwise. It left the details to an inventory of the development server. The inventory is in, and it changes the question in three ways.

1. **The fleet runs as Rick's own login.** There is no second account today. `rruiz` is the fleet, and `rruiz` is also the person, with `sudo`, Docker and LXD.
2. **The fleet uses Docker all day, by hand.** About 700 typed Docker commands and 230 script runs in thirty days. The plan was a short list of approved scripts; three quarters of the use is not scripts.
3. **Taking away the Docker group does not close the door by itself.** The commonest Docker command is "run something inside the development container", and that container is given Rick's Google sign-in, his Lupin service credentials and the whole projects folder. Whoever may enter the container holds what it holds. (To be confirmed on the host.)

So the item is no longer "create an account and write a short list". It is seven choices: which account is the fleet's; how it reaches Docker; what happens to the Docker commands that cannot safely be allowed; what the containers may hold; how two accounts share three repositories; and two repairs to the kernel's startup check. The recommendation in one sentence: **the fleet keeps the account it already has, stripped of its powers, and Rick takes a new login for himself; Docker is reached through one root-owned program that allows reading, entering and restarting named containers and refuses the rest; no container the fleet may enter is given a person's credential.**

Nothing here is applied before the switch-over, which is already ruled. Nothing here touches the test VM, where the host itself is accepted as the boundary.

## Where the record stands

**What is ruled.** "A dedicated unprivileged account on any host that holds a human's credentials; `[host] class: production | test`; on `production` the kernel refuses to start when its account is privileged; applied at switch-over, details after an inventory on the development server" (framework Section 1, the fleet row, part 9). "Privileged" is defined in the fleet spec, Section 12: passwordless `sudo`, or membership of `docker`. The credential-exposure decision, as amended on 11-09, gives the reason: where the account is privileged, the boundary between a persona and everything else on the machine is the machine, not the account. The switch-over list carries the work as two rows: create the account, then set the host's class to `production` (switch-over spec, Section 5).

**What the fleet spec assumed, before the inventory.** Two costs: each repository made group-writable for the new account, and "a short `sudoers` list of named scripts" for "test tiers that drive Docker" (fleet spec, Section 12). It said plainly that everything past the startup check was conditional on the inventory.

**What the public record says.**

- Docker's own documentation: "the `docker` group grants root-level privileges to the user". Anyone who can write to the socket can start a container with the machine's whole disk mounted. LXD's group is the same in effect.
- Rootless Docker gives an account its own private Docker. It cannot see or control the containers of the system's Docker, and graphics cards need extra configuration under it (NVIDIA's container toolkit documentation). The development stack is on the system's Docker and uses the graphics cards (`docker-compose.yml`, lines 127, 444, 799).
- A filtering proxy in front of the socket (the commonly used one is Tecnativa's `docker-socket-proxy`) allows or blocks whole classes of request: all `exec`, all container creation. It does not tell one container from another. Docker's authorization plugins can inspect each request in full, but apply to every user of the daemon, since a local socket does not say who is calling.
- A `sudoers` rule is safe only when the program it names cannot be changed by the account it serves. A rule naming a script inside a repository the fleet writes gives the fleet root, because the fleet can edit the script. The one rule on the host today follows the safe pattern.
- Git refuses, by default, to work in a repository owned by another user, because a repository's own configuration and hooks can run programs. A `.git` folder that two accounts can both write lets each run code as the other the next time that other types a git command there.

**One observation from the test VM** (`src/captures/out/t16-account-reach-lupin-host-test-20261116.txt`, the new script's shakedown): there the containers also run as user 1001, a number that belongs to no account on that machine, while the person's login is a different number. The lupin checkout there is owned by 1001. The VM already has, by accident, the separation the development server lacks: the stack's files belong to one identity and the person's to another.

## Problems and options

### 1. Which account is the fleet's on the development server

The ruling says "a dedicated account". It does not say which of the two identities moves. Everything on disk that the fleet touches already belongs to `rruiz`: three repositories and 64 worktrees, the containers' user number, `~/.lupin`, the Claude session records, the systemd user units, the lingering session. What belongs to the person is smaller: a Google sign-in, a GitHub credential, any SSH keys, and the three group memberships.

- **A. The fleet keeps `rruiz`; Rick takes a new login.** `rruiz` leaves `sudo`, `docker` and `lxd`; Rick's credentials are removed from its home and reissued in the new login's, since they have been within the fleet's reach until now.
  - *For:* nothing the fleet uses changes owner; no image is rebuilt; the containers' user number already matches; the repositories need no shared group for the fleet's sake. The work is one account created and a handful of credentials moved.
  - *Against:* it changes Rick's daily habits, not the fleet's: a new home, shell, editor settings, and his own Claude sessions under the new login. An account named after a person becomes a service account (it can be renamed; the number is what matters). Credentials must be reissued, not just moved, to mean anything.
- **B. A new account for the fleet; `rruiz` stays Rick's.** As the fleet spec assumed.
  - *For:* Rick's working environment is untouched; the account's name says what it is.
  - *Against:* everything the fleet touches changes owner or gains a shared group; the containers still run as user 1001, which would then be Rick, so entering a container is acting as Rick on every writable mount until the images and the compose file are changed to the new number; `~/.lupin`, the session records and the units move.
- **C. No separate account on this host.** Class the development server `test`, accept the machine as the boundary as on the test VM, and amend the ruling's application.
  - *For:* no work, no disruption.
  - *Against:* a persona that errs, or is steered by something it read, holds Rick's Google sign-in, his GitHub credential and, through Docker, the machine. This is the exposure the ruling was made to close, on the one host where it matters.

**Recommendation: A,** if the host check confirms that `rruiz` is user 1001 and shows nothing in its home that cannot move. It puts the change on the lighter user. Rick is the judge of the cost to his own working day, which this page cannot measure.

### 2. How the fleet's account reaches Docker

The fleet cannot do its work without Docker: 231 entries into containers and 382 reads a month, and the merge tests run inside the test container. It cannot be in the `docker` group, by the ruling.

- **A. One root-owned program behind one `sudoers` rule, and a small `docker` stand-in on the fleet's path.** The stand-in passes every `docker …` command to the program; the program allows a fixed set of verbs against a fixed set of container names, both listed in a root-owned file, and refuses everything else with a message. Reading verbs are allowed on anything. `exec`, `stop` and `restart` are allowed on named containers, and `exec` never as root and never privileged.
  - *For:* the 700 typed commands and the scripts work as typed; it tells one container from another; it is the pattern the host already uses for its one passwordless rule; it is perhaps two hundred lines with tests, no new service.
  - *Against:* it is code that runs as root and must be written carefully (argument parsing is where such programs fail); every new Docker flag the fleet wants is a change to it; `compose` commands read a file the fleet can write, so they cannot be allowed as they stand (problem 3).
- **B. A filtering proxy on the socket, or an authorization plugin.**
  - *For:* no program of ours runs as root; the proxy is widely used.
  - *Against:* the proxy cannot allow entering one container and forbid another, nor forbid entering as root; the plugin applies to Rick's own Docker use as well and adds a policy engine to the host. Either is a new standing service.
- **C. Rootless Docker for the fleet's account.**
  - *For:* a real boundary; the fleet's Docker cannot touch the machine.
  - *Against:* the fleet could no longer see the development stack at all, which is what it uses Docker for; moving the stack under a rootless daemon means reworking the graphics-card setup. A migration, not a setting.
- **D. Leave the fleet in the `docker` group and drop that test from the startup check.**
  - *For:* nothing to build.
  - *Against:* it is option C of problem 1 by another name; the account boundary would be decoration.

**Recommendation: A.**

### 3. What happens to the Docker commands the program must refuse

Seventy-six calls in the month create a container, build an image, copy files in or out, or publish: `compose up`, `cp`, `run`, `build`, `rm`, `push`, `tag`. Each can hand its caller the machine (a container created with the disk mounted; a compose file edited before `compose up`). The restart script takes the `compose up` path by itself when it detects that a container's definition has drifted.

- **A. Refused, with a message that says so; a persona that needs one asks Rick, who runs it from his own login.** The ask goes through the tool gate's existing question route.
  - *For:* no new mechanism; the dangerous eleven percent gets a person's eyes; the count includes Rick's own sessions, so the fleet's real number is at most 76 a month and probably well under.
  - *Against:* a person is in the loop for every container rebuild, up to two or three a day; a drift at night waits until morning.
- **B. Named operations inside the program:** "recreate service X", "rebuild image Y", each reading its compose file and build context from a copy the fleet cannot write, which Rick refreshes when he accepts a change to them.
  - *For:* rebuilds need no person; still no arbitrary container.
  - *Against:* a second, promoted copy of the deployment files to keep current, and the development container mounts the live checkout by design; more root-run code; it should be built against measured need, and the fleet's own share of the 76 is not yet known.
- **C. Allowed.**
  - *Against:* this is the `docker` group again.

**Recommendation: A now, B when a month under the kernel shows how many asks the fleet really makes.** The program logs every refusal, so the number will exist.

### 4. What a container the fleet may enter is allowed to hold

Entering the development container is a third of all Docker use, and that container holds Rick's Google sign-in and every repository on the host. With problems 1 to 3 settled exactly as recommended, a persona could still read that sign-in with one allowed command. (To be confirmed on the host.)

- **A. A rule, checked: no container on the program's list is given a person's credential, and the program refuses to enter one that is.** The check reads the container's mounts against a short list of credential paths, at each `exec`. Lupin replaces the Google sign-in mount with a service account's key (a lupin ticket; the mount exists for phone wake-up messages).
  - *For:* closes the door the first three choices leave open; the check is a few lines in a program that already inspects the container; it fails loudly when someone adds such a mount later.
  - *Against:* a lupin change is owed before the switch-over, or the fleet cannot enter the development container at all; the list of credential paths has to be kept.
- **B. Accept it and write it down:** the development container is inside the fleet's boundary, and so is whatever it mounts.
  - *For:* no lupin change.
  - *Against:* the Google sign-in stays within reach, which is most of what the account boundary was for.
- **C. No entering containers.**
  - *Against:* the fleet could not run its tests.

**Recommendation: A.** The writable projects folder in the container is not a person's credential and stays; under problem 1's option A those files are the fleet's own.

### 5. How two accounts share the three repositories

Whichever account is second (Rick's new login under 1A, the fleet's under 1B) needs the three repositories.

- **A. Separate clones.** The second account has its own clone of each and exchanges work by fetch and push, as with any collaborator. It may read the first account's working tree; it does not write there and does not run git there.
  - *For:* neither account can run code as the other through a repository's configuration or hooks; git's ownership guard stays on; no modes or groups to maintain across 64 worktrees.
  - *Against:* disk for a second clone of each; Rick, if he is the second account, edits in his clone and pushes, and sees the fleet's uncommitted work only by reading its files.
- **B. One copy, a shared group.** A group both accounts belong to, `core.sharedRepository=group`, the set-group-ID bit on 394 folders in lupin's `.git` and their like in the other two, and each account telling git the repositories are safe.
  - *For:* one copy; either account edits anywhere; what the fleet spec assumed.
  - *Against:* telling git a shared repository is safe is the step that lets the other account's hooks and configuration run as you; the boundary of problem 1 then has a standing hole in both directions; one file created with the wrong mode breaks the other account's next commit.

**Recommendation: A.**

### 6. Which powers the startup check tests for

The check today names passwordless `sudo` and the `docker` group. `rruiz` is also in `lxd`, which gives the same reach and is not tested (row 64).

- **A. Test the capability, not the name: refuse when the account can write the Docker, LXD, Incus or libvirt socket, or belongs to the `disk` group.**
  - *For:* catches a socket opened by an unexpected group or mode; one test per daemon; the list is short and each entry is a known route to root.
  - *Against:* the list beyond Docker and LXD is this session's, not read from a host; it will need an entry when another such daemon appears.
- **B. Add `lxd` to the two named tests and stop.**
  - *For:* exactly what was seen.
  - *Against:* a group name is a proxy; the socket's mode is the fact.
- **C. Leave it as written.**
  - *Against:* the development server would pass the check after leaving `docker` while still in `lxd`.

**Recommendation: A.**

### 7. How the startup check treats the one `sudoers` rule the fleet now needs

Under problem 2's option A the fleet's account has a passwordless rule, and the check as written refuses any.

- **A. The check allows exactly the programs named in one kernel setting, and only when each is owned by root and not writable by anyone else; any other passwordless rule refuses the start.** The setting's name is ruled with this choice: `kernel host passwordless programs`, a list of paths, empty by default.
  - *For:* the allowance is visible in configuration; a program that became writable is caught at start.
  - *Against:* the kernel must read `sudo -n -l`, whose output it parses; a second place (the setting) to keep in step with `sudoers`.
- **B. The check ignores `sudoers` rules that name a single program and refuses only "all commands".**
  - *For:* no setting.
  - *Against:* a rule naming a fleet-writable script passes.
- **C. No rule: the program is reached another way** (a small root service on a socket).
  - *For:* the check stays as written.
  - *Against:* a standing root service where a `sudoers` line does.

**Recommendation: A.**
