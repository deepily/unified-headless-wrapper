# AH4L capability inventory: everything Lupin AF does through Claude Code

**As of:** 2026-10-18 · lupin `78982e4fc` · **Author:** Rick Ruiz

**Purpose:** a complete list of the functions Lupin AF provides to Claude Code sessions, so that UHW moves Claude, Jetski and AGY onto equal footing without rediscovering a missing function late. This document only inventories. It does not decide whether the current split across MCP, hooks, REST and bridge files is right; that decision comes next (§18).

**Method:** built from the code. Every `@mcp.tool` in `lupin_mcp/cosa_voice_mcp.py`, every hook entrypoint and its 42 library modules, all 37 routers in `cosa/rest/routers/`, `lupin_arbiter_app/`, `cosa/agents/heartbeat_arbiter/` and `cosa/agents/shared/`, the scripts and systemd units in `src/scripts/`, the on-disk state patterns, the environment variables, and `.claude/commands` and `.claude/skills`. Not covered: the planning-is-prompting repo's own workflow files (not mounted), and the Lupin web/mobile clients beyond what the harness feeds them.

## 0. The interfaces at a glance

| Interface | Inventory | Who calls it | Engine coupling |
|---|---|---|---|
| **MCP** (`cosa-voice`, stdio, user scope) | 33 tools + liveness middleware + outbox | the model, in-turn | **none in the protocol**: any MCP-capable engine can call it. Coupled only through identity resolution (bridge-file lookup) |
| **Claude hooks** (8 events, user scope) | 8 entrypoints, 42 library modules | the Claude Code process | **total**: event names, payload schema, response schema, timing semantics |
| **REST** (`:7999`, FastAPI in Docker) | 37 routers; 9 of them serve sessions directly | MCP server, hooks, listener, clients, arbiter | **none**: HTTP plus `X-API-Key` |
| **WebSocket** (`:7999`) | notification queue events | per-session listener, clients | none, though the per-session listener is a harness artifact |
| **Bridge and state files** (host) | `cc-{pid}.json` plus about 20 other file families | hooks, MCP server, listener, arbiter, scripts | **high**: keyed by Claude's process id, carry `transcript_path` and the tmux session |
| **tmux** | `send-keys` injection from 6+ components | listener, broadcasts, self-respin, arbiter, heartbeat, DM tutor | **high**: assumes an interactive TUI pane |
| **Arbiter** (`:8001`, systemd) | fleet loop, health, context pressure, watchdogs | standing service | **medium**: reads Claude transcripts and tmux panes |
| **Slash commands and skills** | lupin: 51 commands, 10 skills; planning-is-prompting: 41 commands, 6 skills, 61 workflows (§19) | the model | **total**: only Claude Code loads `.claude/commands` and `.claude/skills` |

## 18. Patterns that matter for the interface decision

1. **MCP is already the engine-neutral agent API.** 33 tools cover voice, asks, personas, DMs, commons, tasks, fleet and respin. C3 proved both Jetski-family binaries reach it with identity through the inherited env. The only coupling is identity resolution (bridge-file lookup), and it disappears with `LUPIN_PERSONA_ID`.
2. **Hooks carry three different jobs.**
    - *Guards* (PreToolUse) need an in-engine veto, and all three engines have one.
    - *Event observation* (Post, Notification, Stop) is replaced by the harness event stream.
    - *Context injection* (SessionStart, UserPromptSubmit, Stop-block) is replaced by the harness writing turns.
3. **Seven components assume a TUI pane:**
    - the listener
    - broadcasts
    - self-respin
    - the arbiter's live notify
    - the heartbeat UserPromptSubmit re-entry
    - the DM tutor
    - the turn-age watchdog's pane check

    All of them become inbox writes or kernel operations.
4. **Six components read the Claude transcript:**
    - auto-narrate
    - `heartbeat_task_state`
    - context pressure
    - the turn-age watchdog
    - the console tailer
    - `transcript_reader`

    The harness log replaces all of them for every engine.
5. **The bridge file is four things at once:** an identity registry, a liveness clock, a voice-state store (speakerphone, persona, idle), and a lineage record. A single-writer registry owned by the kernel separates them.
6. **Claude-only names are embedded in policy:** `Task` (subagent governance), `Write|Edit` (memento guard), `Read/Grep/Glob` (permission auto-allow), `TaskCreate/TaskUpdate` (mirror). Each becomes a common-shape rule.
7. **The workflow layer is the largest unported surface.** It has 51 commands, 10 skills and the planning-is-prompting workflows, and only Claude loads them.

### Rulings (2026-10-18)

- **D21.** The global task store is the **only** source of owed work. Retire the native `Task*` transcript replay (`heartbeat_task_state`) and the deprecated mirror.
- **D22.** Native task tools in any engine (Claude `TodoWrite`/`TaskCreate`, any Jetski-family equivalent) are irrelevant to the design. Workflows that reference `TodoWrite` are rewritten to use the store.

### 19.5 What Jetski needs to run this layer, and the captures that decide it

- **C11: Jetski's instruction and extension surfaces.** Is there a global instruction file and a project instruction file (the analogue of `~/.claude/CLAUDE.md` and `CLAUDE.md`)? Custom commands? Skills (Jetski exposes an internal `skill_search` tool)? What do `jetski agents` / `--agent` definitions look like? This decides whether planning-is-prompting installs **into Jetski's native surfaces** or **through the harness**.
- **C12: Jetski's subagent tool and `--mode plan`.** The tool name is needed to enforce the crew rule. Plan mode maps the workflows' plan-mode steps.
- **C13: C9/C10 rerun with a pinned `--model`.**
- **C14: how long an MCP call may block.** A cosa-voice ask blocks until the human answers. If Jetski times MCP calls out, sync asks need another shape (a ticket plus the answer delivered as the next turn).

All four are scripted in `src/captures/capabilities_followup.sh` (runbook §9). C11 plants one codeword per candidate surface and denies every tool, so a codeword in the reply means the engine loaded that surface itself.

**Engine-neutral option, for the interface decision.** The harness itself could load commands and skills for every engine:
- A spoken or typed `/plan-review-cascaded …` is expanded by the kernel from the command file and sent as the turn's text.
- Skills are exposed as a skill index in the system prompt, plus a cosa-voice `load_skill` MCP tool.

That puts Claude, Jetski and AGY on identical footing and keeps one installation of planning-is-prompting. It is a candidate, not a decision.
