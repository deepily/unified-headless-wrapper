The Lupin kernel

October 2026 · how the kernel, its four interfaces and the three agent harnesses fit together

The Lupin kernel is one service per host that runs every AI agent and decides what each agent may do. Every tool an agent calls passes the kernel's check first. The kernel serves its own resources directly. For Lupin's resources, such as tasks, asks and DMs, it lets the agent's call through to the Lupin application, whose endpoints stay as they are.

It replaces the Claude-only harness we use today (AH4L). Claude Code, AGY and Jetski agents plug into it on equal terms, so a manager or worker behaves the same whichever model or harness runs it.

The four interfaces

Each interface serves one kind of caller. Together they are the only ways in or out of the kernel.

1MCP tools

for the models

The Lupin tool set (cosa-voice): speak, ask, message a colleague, post to the commons, read tasks. The model calls these like any other tool.

2Hook shim

for the harness

A small script each harness runs before every tool call. It asks the kernel “may this agent run this tool?” and blocks the call on a no.

3Notifications

between AI and you

The kernel holds one WebSocket per agent to Lupin, carrying your replies and colleagues' messages in. Narration goes out through the REST endpoint /api/notify.

4lupin CLI

for operators and scripts

Start, stop and inspect agents; check fleet health. It talks to the kernel's local socket.

Owned and brokered resources

The kernel makes every allocation and permission decision. What differs is where the data lives. Owned resources exist only inside the kernel: the agent processes, their identities and roles, their conversations and workspaces, the tool gate, message routing, fleet health and the session logs. Brokered resources already have a home in the Lupin application, which stays the system of record. For those the kernel authorizes but does not relay. The agent's own cosa-voice tools call Lupin directly, and only after the kernel has allowed the call.

How the three harnesses plug in

A harness is the program that runs a model as an agent. Claude Code, AGY and Jetski each start, configure and interrupt agents differently. A small adapter per harness family hides those differences. AGY and Jetski share one adapter because they share tool names, configuration files and hook format. Claude Code gets its own adapter, built last.

The differences that matter: Claude Code can absorb a message mid-turn, while AGY and Jetski take it on the next turn. AGY and Jetski cut any tool call off at 180 seconds, so a question to you returns a ticket and the answer arrives later. AGY does not run the tool check inside its subagents, so the kernel cannot see what they do.

The FastAPI services and the data

Today there are two FastAPI services. The Lupin application runs on port 7999 with 37 routers, nine of which agents call. A separate arbiter service on port 8001 tracks fleet capacity and health. The current Claude harness calls both directly.

With the kernel, the Lupin application stays as it is. The arbiter folds into the kernel. The kernel runs its own small FastAPI app, but only on a local socket, for the tool check, the CLI and health. Agents reach Lupin's routers only through their cosa-voice tools, and every such call is allowed or denied by the kernel first. So there is one place to see and control every agent request, without a proxy in the path.

In one sentence: the kernel owns the agents and approves every call they make, while Lupin's data and endpoints stay where they are today.

How an agent's call to Lupin is authorized

LayerWhereWhat it decides
Exposurecosa-voice MCP server, configured by the kernelWhich tools tools/list shows this role. Exposure only (D25): a call to an unlisted tool still reaches the server, and the gate logs it as a would-deny (observe). Switching that rule to enforce is a config change.
Gatekernel /gate, via the hook shimWhether this call, with these arguments, is allowed. Per-call rules live here, for example that a worker's ask must go to its manager. It runs before the MCP server sees the call.
AuthenticationLupin endpointWhich account is calling: X-API-Key or JWT, resolved to a user id. The persona is the sender_id the MCP server asserts.

Role logic belongs in the first two layers, not in the endpoints. One exception exists today: the tasks router's manager-only guard reads Claude Code session bridge files. It must move to persona identity before AGY or Jetski managers can use it. An agent with shell access could still call the REST API directly with the key. Under D25 that is accepted (no adversarial agents), and the gate can flag such calls in observe mode.
