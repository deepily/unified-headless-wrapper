# T32 · Credential exposure: the four credentials on a fleet host, three gate rules, the approval witness, redaction

**As of:** 2026-11-06 · **Resolves:** T32 (framework Section 8.1) · **Ruling:** D50 · **Source read:** lupin `53e86d277` (2026-11-04), laptop clone, read-only · **Narrative for cold readers:** `narratives/2026.11.06-t32-credential-exposure.md` · **Opens:** T36

## 1. Problem

The register row said: an agent with shell access can read the outbound `X-API-Key` and call REST directly; add an observe rule. Reading lupin found four credentials on a fleet host, not one, and the one that matters most is not the key. Under D25 every persona runs as one operating-system user, so **there is no credential boundary between personas; the user account is the boundary.** The design cannot stop a key read. It can see the bypass, keep secrets out of what the kernel writes and speaks, keep approvals (D49) unforgeable, and keep the one credential that would forge them off the host.

## 2. Ruling (D50), six parts, all taken as recommended on 2026-11-06

1. **Owner password off the fleet host.** Kernel config carries `owner_user_id`; the `[owner]` section of `~/.lupin/config` is never written on a host that runs personas; the kernel refuses to start if it finds one, or finds a per-project service login on Lupin's effective approver map (Section 4.4).
2. **Approvals count only through a door a persona cannot fake.** `approver: human`: a yes counts only when `authenticated_account_email` resolves through `approver_persona_for_account`; a fleet-key answer is stored with `answered_by.method = api_key` and does not satisfy the gate. `approver: manager | chief_of_staff`: the kernel is the authority on who answered, from the gated `ask_answer` call it witnessed; Lupin's `answered_by` is not consulted for persona approvers (Section 4.3).
3. **The secrets row splits into three rules:** `credential_read` enforce, `credential_print` observe, `direct_call` observe per instance and role (Section 4.2). Replaces the T26 spec's single "Secrets and credentials" row.
4. **Direct calls are detected two ways:** pattern rules in the gate now; one identifying header on every cosa-voice outbound call now (Section 4.6); reconciliation of Lupin's access log against gated calls later, under this item (Section 6).
5. **Redaction at the kernel's two writers:** the session log writer and the narration path (Section 4.5).
6. **T36 opened:** per-persona API keys and authenticated persona identity; first task the O(N) bcrypt sweep (Section 7). The fleet key stays for Phase 1.

## 4. Contract

### 4.1 Credential inventory on a fleet host

| Credential | Lives | Proves | Buys a persona that bypasses the gate |
|---|---|---|---|
| Fleet key | `src/conf/keys/<KEY_NAME>` | the account | any endpoint as any `sender_id`: DMs as a peer, task writes, dismissals, ticket writes |
| Service login (per project) | `~/.lupin/config [<project>]` | a Bearer token naming the service email | the JWT door as a non-approver, while that email is off the approver map (invariant, 4.4) |
| Owner login | `~/.lupin/config [owner]`, optional | a Bearer token naming the human | the approver door: approve its own ticket. **Must not exist on a fleet host** (invariant, 4.4) |
| Engine vendor credentials | engine home and env | the vendor account | spend and exfiltration; nothing inside Lupin |

### 4.2 The three rules, on the common shape (Section 8 tool map)

```python
# kernel config
credential_paths = [ "src/conf/keys/", "~/.lupin/config", "~/.ssh/", "~/.claude/.credentials.json",
                     "~/.gemini/*/oauth*", "~/.config/gcloud/", "*.pem", "*.key" ]
lupin_instances  = { "voice": "127.0.0.1:7999", "destructive_test": "127.0.0.1:<port>" }
kernel_socket    = "~/.lupin/kernel/kernel.sock"

TOKEN_SHAPES = r"ck_live_[A-Za-z0-9_-]{64,}|X-API-Key|Authorization: *Bearer"
ENV_DUMP     = r"\b(env|printenv|set)\b(?!\s*=)|\$\{?[A-Z_]*(KEY|TOKEN|SECRET|PASSWORD)"

def credential_read( call ):
    target = call.read.path if call.read else call.shell.command if call.shell else ""
    return any( fnmatch_path( target, p ) for p in credential_paths )

def credential_print( call ):
    return bool( call.shell ) and re.search( ENV_DUMP, call.shell.command ) is not None

def direct_call( call ):
    text = call.shell.command if call.shell else call.fetch.url if call.fetch else ""
    hit  = next( ( name for name, host in lupin_instances.items() if host in text ), None )
    if kernel_socket in text or "--unix-socket" in text: hit = "kernel"
    if hit is None and re.search( TOKEN_SHAPES, text ): hit = "unknown"
    return hit    # None, or the instance name the would-deny log line carries
```

| Rule | Mode (Phase 1) | Reason | Log line carries |
|---|---|---|---|
| `credential_read` | **enforce** | a persona never legitimately reads a key; cosa-voice does. Same class as database and liveness. `install-cosa-voice.sh`'s preflight is an install, already an `ask` row | path matched |
| `credential_print` | observe | ordinary debugging; the leak path is the log and narration, handled by 4.5 | command |
| `direct_call` | observe, **per instance and per role** | the D45 builder persona and the tester hit `destructive_test` all day; `voice` and `kernel` on non-tester roles are the likely `enforce` end state, decided from the first weeks of would-deny lines like the rest of the taxonomy | instance, role, command |

Mode is a config field per (rule, instance, role) for `direct_call`; per rule for the other two.

### 4.3 The approval witness (amends T26 spec 4.3)

```python
# gate: every MCP call passes here with arguments (D35). Record answers the kernel saw.
if call.mcp and call.mcp.tool == "ask_answer":
    witnessed[ ( call.mcp.arguments[ "ticket" ], persona_id ) ] = gate_call_id

# approval check, after the ticket reads answered:yes
def answer_counts( ticket ):
    if ticket.approver == "human":
        return ticket.answered_by == "human" and ticket.answer_auth == "jwt"     # second door, stamped by Lupin
    approver_id = ticket.answered_by.split( ":" )[ 1 ]                            # "manager:<persona_id>"
    return ( ticket.id, approver_id ) in witnessed                                  # the kernel saw the ask_answer
```

A yes in the store that fails `answer_counts` is ignored, the ticket stays open, and the gate logs `direct_call` with instance `voice` and the ticket id. `answer_auth` is the `_answered_by` method Lupin already stamps on notification answers (`api_key | jwt`), carried onto the ticket record (Section 5).

### 4.4 Startup invariants

```python
def check_credential_invariants( config, lupin ):
    parser = configparser.ConfigParser(); parser.read( os.path.expanduser( "~/.lupin/config" ) )
    if "owner" in parser:
        raise KernelRefused( "[owner] section in ~/.lupin/config: remove it; set owner_user_id in the kernel config" )
    if not config.owner_user_id:
        raise KernelRefused( "owner_user_id missing from the kernel config" )
    approvers = lupin.get( "/api/tasks/approval-settings" )[ "approver_accounts" ]   # effective map, fleet key suffices
    service   = { parser[ s ].get( "email", "" ).lower() for s in parser.sections() if parser[ s ].get( "email" ) }
    if clash := service & { e.lower() for e in approvers }:
        raise KernelRefused( f"service login on the approver map: {sorted( clash )}" )
    for path in config.credential_paths:              # amended 2026-11-09: nothing readable by other accounts
        if os.path.exists( path ) and os.stat( path ).st_mode & 0o007:
            raise KernelRefused( f"{path} is readable by other accounts: files 640, directories 750" )
```

**Amended 2026-11-09, after the test VM check** (T20 spec Sections 2.2 and 14). Two changes. (1) *File modes:* `~/.lupin/config` and `notification-api.key` were found at mode 664 on the test VM, in a 775 directory. Credential files are 640 and their directory 750; group access stays because the Lupin container reads through the group. The loop above enforces it, and `src/captures/t32_credential_inventory.py` reports modes. (2) *The boundary:* "the user account is the boundary" holds only where the persona account is unprivileged. On the test VM that account has passwordless `sudo` and is in the `docker` group, so the boundary there is the host. This is accepted for the test VM. The kernel records `persona_account_privileged` in `kernel.started`; nothing that speaks as a human is kept on a persona host (D58); unprivileged persona accounts for production hosts are a T16 question.

Runs before the first spawn; failure is narrated through `POST /api/notify` with the fleet key and the kernel exits non-zero. `owner_user_id` is resolved once by the human from their own machine (`/auth/login` → `user.id`) or from the database, and replaces `_stamp_owner_user_id_on_bridge` for every kernel-managed persona.

### 4.5 Redaction at the two writers

```python
SECRET_SHAPES = {
    "fleet_key"   : r"ck_live_[A-Za-z0-9_-]{64,}",
    "google_oauth": r"ya29\.[A-Za-z0-9_-]{20,}",
    "google_key"  : r"AIza[0-9A-Za-z_-]{35}",
    "anthropic"   : r"sk-ant-[A-Za-z0-9_-]{20,}",
    "jwt"         : r"eyJ[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}",
    "private_key" : r"-----BEGIN [A-Z ]*PRIVATE KEY-----[\s\S]*?-----END [A-Z ]*PRIVATE KEY-----",
    "ini_password": r"(?im)^(\s*password\s*=\s*)(\S+)",
}

def redact( text ):
    for kind, shape in SECRET_SHAPES.items():
        def mark( m ):
            secret = m.group( 2 ) if m.lastindex == 2 else m.group( 0 )
            tag    = f"<redacted:{kind}:{hashlib.sha256( secret.encode() ).hexdigest()[ :8 ]}>"
            return m.group( 1 ) + tag if m.lastindex == 2 else tag
        text = re.sub( shape, mark, text )
    return text
```

Applied at exactly two choke points: the per-persona JSONL writer (Section 11) and the narration path (`POST /api/notify` and the end-of-turn reply, Section 7). Not applied to the gate's own would-deny lines beyond those two writers, because they go through the same JSONL writer. The console and web view read the log, so they inherit it. The fingerprint keeps two sightings of one token linkable without the token.

### 4.6 The identifying header

cosa-voice adds `User-Agent: cosa-voice/<version> persona=<persona_id> gate=<gate_call_id>` at its four outbound sites. `gate_call_id` is the id the shim returned for the allowing `/gate` call, passed to the server through the same environment the identity uses (`LUPIN_PERSONA_ID`, D46) or a per-call file; the exact handoff is decided when the shim is written (Phase 1 spec Section 8). Lupin's access log keeps `User-Agent`. Nothing reads it yet; Section 6 does.

## 6. Deferred under T32: reconciliation

The kernel keeps every gate call id it allowed per persona. A job tails Lupin's access log (or a `GET /api/admin/access-log?since=`) and flags any request authenticated by the fleet key whose `User-Agent` carries no `gate=` the kernel issued: a direct call, whatever command produced it. Output: the same `direct_call` would-deny line, source `reconciliation`. Needs the header (shipped now), an access-log reader on the Lupin side, and a kernel job; not Phase 1.

## 7. T36 · per-persona API keys and authenticated persona identity (opened)

One `ck_live_*` per persona, minted at `POST /personas` through `ApiKeyRepository.create_key`, revoked at reap. Then `require_api_key_or_jwt` returns key metadata and `sender_id` is authenticated, which closes T21 properly and lets the fleet-state rows (`task_reassign`, `dismiss`) be checked server-side. **First task:** a key-identifier prefix (`ck_live_<id>_<secret>`) for an O(1) lookup, because `_validate_api_key_sync` bcrypt-checks every active key per request. **Not isolation:** a persona can still read a sibling's key off the same user; the record becomes truthful, the boundary does not move.

**Added 2026-11-08, the second mechanism:** a kernel-signed single-use grant per gated call. After `/gate` allows, the cosa-voice process asks `POST /gate/grant { persona_id, tool, args_sha256 }` on the kernel socket; the kernel matches it to the gate record (same persona and hash, within seconds) and returns a token `{ iss: lupin-kernel, sub: persona_id, aud: lupin, jti: call_id, ep: "POST /api/dm/send", args: args_sha256, exp: +30 s }`; Lupin's `require_kernel_grant` checks signature, `ep`, body hash and single use. Compared with (a): a grant cannot be usefully stolen (bound to one call, spent once, dead in 30 s), it proves the MCP server sent what the gate approved, and the fleet key stops carrying persona authority; it adds a second trust root (the signing key, provisioned beside `owner_user_id`, rotated with the fleet key) and one local round trip per call. Both mechanisms are ruled under T36, scheduled with the kernel's move into lupin; INI `kernel grant required` stays off until switch-over because AH4L sessions have no kernel.

## 9. Alternatives considered

| Alternative | Why not |
|---|---|
| Keep one `enforce` secrets row | tripped daily by the D45 builder and the tester against the destructive-test server; a daily-tripped rule gets switched off |
| File permissions on `~/.lupin/config` and the key | same user; meaningless |
| A separate operating-system user for the kernel | the real fix for the class; reopens D25 and the ownership of worktrees, sockets and logs. Revisit when D25 is revisited |
| Trust Lupin's `answered_by` for persona approvers | caller-declared (Problem 7 in the narrative); a persona can answer as its own manager |
| Block `env` and friends | buys little; a persona quoting a secret it read, or an engine error echoing a header, is not a command the gate sees. Redaction at the writers is the matching control |
| Reconciliation only, now | the stronger detector, but a Lupin change plus a kernel log-reading job the first build does not need |
| Per-persona keys in Phase 1 | seconds per request under the bcrypt sweep until the key-id prefix lands; schema change before the kernel exists |
