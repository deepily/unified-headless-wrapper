# Tool approvals: what replaces AH4L's voice-approved permission flow

**As of:** 2026-11-05 · resolves T26 as **D49** · follows D25 (threat model, rule modes), D27 (escalation), D37 (ticketed asks), D47 (launch per persona) · Claude Code behavior checked against code.claude.com on 2026-11-05

## 1. Problem

AH4L's `permission_request.py` existed because interactive Claude Code prompts. It auto-allowed `Read`/`Grep`/`Glob`, forwarded every other prompt as a 25 s spoken yes/no (under the 30 s hook timeout), and denied the prompt outright when voice was buffered so the voice got through. Five guards had a second escape hatch: a human exported `LUPIN_ALLOW_GIT_STASH`, `LUPIN_ALLOW_BRANCH_LOCK_BYPASS`, `LUPIN_ALLOW_UNSCOPED_KILL`, `LUPIN_ALLOW_MERGE_COMMIT` or `LUPIN_COMMIT_SCOPE_ACK` in the tmux pane and the guard stood down for the session.

Under UHW nothing prompts. Every engine launches with `--dangerously-skip-permissions`, and the gate is the only check. So the question is not where the prompt goes; it is whether human approval of a single tool call exists at all, and which layer owns it.

## 2. Ruling (D49)

| Question | Ruling |
|---|---|
| Which layer owns approval | **The gate.** A fourth rule mode, `ask`, built on ticketed asks (D37) and the escalation chain (D27). No engine prompt machinery on any engine |
| Claude's permission mode | `--dangerously-skip-permissions` (`bypassPermissions`), the family's flag. Because that mode ignores allow rules, the role allow-list is `--tools "<list>"`, not `--allowedTools` (D47 corrected) |
| Who answers | A per-rule `approver` (`human` \| `manager` \| `learner`), Phase 1 default `human`; the D27 chain is the fallback when the approver misses the deadline; the preference learner shadow-predicts every approval ticket from the first one |
| Rule table | The destructive-act taxonomy of Section 6 (reversibility × blast radius): about nine `ask` rows, `enforce` rows with no AH4L ancestor, two of AH4L's five overrides demoted to `observe`; the `LUPIN_ALLOW_*` env vars are deleted |
| Not used | `--permission-prompt-tool`, `PermissionRequest` hook, PreToolUse `defer`, `auto` mode (deferred capture), `--permission-prompts none` (pending C18) |

Nothing of `permission_request.py` survives. The human-facing end of the flow (a spoken yes/no on the phone) survives as the `human` approver of a ticket.

## 3. Engine facts the ruling rests on

| Fact | Claude `-p` | Jetski / AGY |
|---|---|---|
| Headless default | Manual mode since v2.1.302: a call that needs approval is denied unless an allow rule, a `PermissionRequest` hook or `--permission-prompt-tool` resolves it | a missing `permissions.allow` rule auto-denies, empty stdout, rc 0 (prototype, 2026-10-12) |
| Under `bypassPermissions` | everything runs; deny rules still block; **allow rules have no effect**; PreToolUse `deny` still blocks (C5, C15b); a call that would still prompt is denied, not asked | same flag; project hook `deny_reason` blocks (C1) |
| Restricting built-ins | `--tools "<names>"` removes unlisted built-ins (MCP untouched; omitting `AskUserQuestion` removes it); `--allowedTools` only pre-approves | `tools:` in the `--agent` definition (C11c) |
| Prompt forwarding | `--permission-prompt-tool <mcp tool>` (the SDK's `canUseTool` over stdio; holds the engine open; must return allow or deny); `PermissionRequest` hook (`decision.behavior`); PreToolUse `ask` \| `defer` | **none measured.** "Hook `allow_tool`" appeared in the framework twice and in no capture; withdrawn |
| `defer` | exits the `-p` run with `tool_deferred` for a later `--resume`; one tool call per turn or it is dropped; wedges under `bypassPermissions` (issue 82198, open) | — |
| `auto` mode | a classifier reviews each action; drops a bare `Bash` allow rule; pauses after 3 consecutive blocks, which in `-p` with no prompt tool is a silent denial | — |
| `--permission-prompts none` (≥ 2.1.259) | denies would-prompts, removes `AskUserQuestion`, **tells the model not to retry denied requests**; denials appear as `permission_denied` system frames and `permission_denials` on `result` | — |
| Regression to know | since 2026-03 a PreToolUse `allow` no longer overrides an `ask` rule; `PermissionRequest` is the approving hook | — |

The one primitive the design uses is the deny-with-reason that G1 verified on AGY and Jetski and C5 on Claude.

## 4. Contract

### 4.1 Rule modes

| Mode | On match |
|---|---|
| `enforce` | deny with the rule's reason |
| `ask` | find a `tool_approval` ticket for (`persona_id`, `rule`, `approval_key( call )`). Answered yes and unconsumed: allow once. Otherwise open one if none is open and deny with the instruction in 4.3 |
| `observe` | allow; log would-deny (D25) |
| `off` | allow |

### 4.2 Rule fields

```yaml
rule: merge_head
mode: ask
approver: human                      # human | manager | learner      Phase 1 default: human
fallback: [ manager, chief_of_staff, learner ]    # D27 chain, walked when the approver misses the deadline
approval_timeout_seconds: 600        # expiry answers "no"
scope: call                          # Phase 1: one act. "session" is a later extension (Section 10)
```

`approval_key( call )` and `question( persona, call )` are code on the rule, not configuration (4.5).

### 4.3 Gate

```python
def decide( persona, call ):
    """
    Requires:
        - call is in the common shape (framework Section 8); persona carries id, role and manager
    Ensures:
        - never blocks on a human; returns allow() or deny( text ) at once
        - an ask-mode allow consumes the ticket, so one answer approves one act
    """
    rule = first_match( RULES, call )
    if rule is None or rule.mode in ( "off", "observe" ):
        return allow()
    if rule.mode == "enforce":
        return deny( f"{rule.name}: {rule.reason}" )
    key    = rule.approval_key( call )
    ticket = tickets.find( persona.id, kind="tool_approval", rule=rule.name, key=key )
    if ticket is None:
        ticket = tickets.open( persona_id=persona.id, kind="tool_approval", rule=rule.name, key=key,
                               question=rule.question( persona, call ), approver=rule.approver,
                               fallback=rule.fallback, deadline_seconds=rule.approval_timeout_seconds )
        return deny( f"needs approval · ticket {ticket.id} · call ask_wait( \"{ticket.id}\" ); "
                     f"when it returns answered:yes, repeat this exact call" )
    if ticket.status == "pending":
        return deny( f"approval pending · ticket {ticket.id} · call ask_wait( \"{ticket.id}\" )" )
    if ticket.status == "expired" or ticket.answer == "no":
        return deny( f"refused by {ticket.answered_by}: {ticket.message or 'no reason given'}" )
    if ticket.consumed_at:
        return deny( f"approval {ticket.id} already used; ask again" )
    tickets.consume( ticket.id )
    return allow( approved_by=ticket.answered_by, ticket=ticket.id )
```

The model sees the deny text behind the engine's own prefix (`tool call denied by pre-tool hook: …`; Jetski adds `Encountered error in tool execution:`), the turn continues, and the only thing the model has to do is what the text says: call `ask_wait`, then repeat the call. `ask_wait` already exists and is listed for every role (D37, role table Section 2).

### 4.4 Ticket record

Kind `tool_approval` in the D37 store (`/api/asks/{ticket}`), opened by the kernel on the persona's behalf:

```json
{ "ticket": "ask-3f2a9c1e", "kind": "tool_approval", "persona_id": "9b1e4c7a", "role": "implementer",
  "rule": "merge_head", "approval_key": [ "merge_head", "lupin", "wip-v0.0.1" ],
  "call": { "shell": { "command": "git merge --no-ff feature/x", "cwd": "/home/x/lupin-wt/9b1e4c7a" } },
  "question": "implementer 9b1e4c7a wants to make a merge commit on lupin wip-v0.0.1. Allow?",
  "approver": "human", "fallback": [ "manager", "chief_of_staff", "learner" ],
  "opened_at": "…", "deadline_at": "…",
  "status": "answered", "answer": "yes", "answered_by": "human", "message": null,
  "learner_prediction": { "answer": "yes", "confidence": 0.71 },
  "consumed_at": "…" }
```

`learner_prediction` is written at open time by the shadow learner and never read by the gate. `answered_by` is `human`, `manager:<persona_id>`, `chief_of_staff:<persona_id>` or `learner`.

The kernel keeps the tickets it opened in memory (it holds the persona's socket and sees `notification_responded`), so the gate path does one REST call per *new* approval, not per tool call. A cache miss falls back to the store.

### 4.5 `approval_key`: approve the act, not the text

A model told "repeat this exact call" still rewrites `--force` as `-f`, or adds `--no-edit`. If the key were a hash of the command, the second call would open a second ticket and the human would be asked twice. Each rule therefore defines what was approved in normalized terms, and a different spelling of the same act matches:

| Rule | `approval_key( call )` | `question` |
|---|---|---|
| `stash` | `( "stash", repo )` | "`<role> <id>` wants to stash in `<repo>`. Allow?" |
| `branch_lock` | `( "branch_lock", repo, target_branch )` | "… wants to write to locked branch `<branch>` in `<repo>`. Allow?" |
| `kill` | `( "kill", target_kind, target )` with target normalized to a pid or a process name | "… wants to kill `<target>`. Allow?" |
| `merge_head` | `( "merge_head", repo, current_branch )` | "… wants to make a merge commit on `<repo> <branch>`. Allow?" |
| `commit_scope` | `( "commit_scope", repo, sorted( paths_outside_scope ) )` | "… wants to commit `<n>` files outside its scope in `<repo>`: `<paths>`. Allow?" |

`repo` is resolved from the common shape's `cwd` (framework Section 8, port rule 1), never from the hook process.

## 5. Routing: approver, fallback, learner

- **`approver`** names who is asked first. `human` posts the question through the notifications API exactly as a `converse` does. `manager` DMs the persona's manager (`dm-<manager>`), who answers with `dm_respond`; the chief of staff has no manager, so for it `manager` means `human`. `learner` lets the preference learner answer outright.
- **`fallback`** is walked when the approver misses the deadline: by default manager, then chief of staff, then the learner as a marked surrogate (D26). The chain is the D27 chain; approvals add nothing to it.
- **The learner shadows every approval ticket from the first one** (it already shadows asks, D27). Approval tickets are a closed-vocabulary decision (rule, key, role, repo, branch, time of day, recent history) with a binary label and an observable consequence, which makes them the cleanest dataset the learner will get. Promotion from shadow to `approver: learner` is per rule, on measured agreement with the human over N tickets; the floor and N are T29's.
- **`approver: manager` is a setting to measure, not a default.** A manager approving is itself a model judgment, with task context and without calibration. Whether a manager approves what Rick would is a question for the same dataset.

## 6. Rule table of record: the destructive-act taxonomy (2026-11-05)

The first draft of this section listed the five guards AH4L let a human override by env var. That was a parity artifact (D25: ported guards keep `enforce`), not a derivation: it answered "what did the tmux pane ask you?" rather than "what should a persona never do without a yes?". Rick asked for the second question on 11-05; this table is the answer and is the rule table of record. The modes are a starting point, taken as written without row-by-row ruling; they are revisited from C18 and the first weeks of tickets.

Sorting criterion, two axes. **Reversibility:** can the kernel or a human undo it from what is left on disk or in Lupin? **Blast radius:** the persona's own worktree, the shared repo or server, the fleet, or the outside world. `ask` is for acts that are irreversible or cross the persona's boundary *and* are sometimes legitimate; `enforce` for acts a persona never legitimately does; `observe` for acts worth a log line under D25 but not a gate yet.

| Class | Acts (common shape, normalized) | Reversible | Radius | Mode | `approver` | `approval_key( call )` |
|---|---|---|---|---|---|---|
| History rewrite on shared refs | `push --force` / `--force-with-lease`; `reset --hard` or `checkout -- .` discarding uncommitted work; `rebase` of a branch present on `origin`; `branch -D`; `tag -d`; `stash drop` / `stash clear` | no | repo | **ask** | human | `( "history", repo, ref )` |
| Branch lock | any write to a locked branch (gate part of `branch_lock_guard`); the git reference-transaction hook stays as the second layer and consumes the allowance file below | partly | repo | **ask** | human | `( "branch_lock", repo, branch )` |
| Merge head | `merge --no-ff` / a merge commit onto a protected branch | yes (revert) | repo | **ask** | human | `( "merge_head", repo, branch )` |
| Commit scope | commits touching paths outside the persona's declared scope | yes | repo | observe | — | — (`LUPIN_COMMIT_SCOPE_ACK` was an acknowledgment, not a gate) |
| Stash | `git stash` (push) | yes | own worktree | observe | — | — (the AH4L guard protected a shared pane; one persona per worktree makes it noise) |
| Filesystem destruction | `rm -r`/`rm -rf` outside the persona's worktree and `/tmp`; deletes under `io/` (documents, commons topics, audio); `git clean -fdx`; `git worktree remove` of a seat not its own | no | server | **ask** | human | `( "delete", sorted( top_level_targets ) )`; deletes inside its own worktree are allowed |
| Process and service | `kill`/`pkill` outside its own process tree; `systemctl` on lupin units; `docker rm` / `compose down`; stopping the test server | partly | server | **ask** | human | `( "kill", target_kind, target )` |
| Kernel and Lupin liveness | killing the kernel, the :7999 instance or its database container | no | server | **enforce** | — | — |
| Database | `psql` / `alembic downgrade` / `DROP` / `DELETE` against lupin's PostgreSQL | no | server | **enforce** (Phase 1; revisit for the dogfooding persona, D40) | — | — |
| Outbound effects | first `git push` of a branch in a persona session; opening a PR; `curl -X POST`/`gh` writes to external services; publishing packages; sending mail | no | world | **ask** (first push), observe (later pushes to the same branch) | human | `( "push", repo, remote, branch )`; `( "external", host, verb )` |
| Fleet and peers | `dismiss_sessions` of a persona it did not spawn | partly | fleet | **ask** | **manager** (the first real case for that setting; the chief of staff asks the human) | `( "dismiss", target_persona_id )` |
| Fleet cap | `spawn_sessions` beyond `fleet_size_cap`; `self_respin` while owing work | partly | fleet | **enforce** | — | — |
| Lupin state | `task_reassign` off another's task; deleting commons topics; answering a DM addressed to the human | yes | fleet | observe | — | — |
| Secrets and credentials | reading `src/conf/keys/`; `~/.ssh/*`; printing environment variables that look like tokens | n/a | world | **enforce** (T32 narrows to observe for direct REST calls only) | — | — |
| Host and engine | `pip install` / `npm -g` outside a venv; `apt`; `agy update` / `claude install` (conflicts with D48 vetting) | partly | server | **ask** | human | `( "install", manager, package )`; `( "engine_update", binary )` |
| Cost | spawning N personas on `fable-5.1-high`; a fan-out above a budget | n/a | wallet | observe (until T22 gives numbers) | — | — |

Where the five AH4L overrides landed: `LUPIN_ALLOW_BRANCH_LOCK_BYPASS` → branch lock (`ask`); `LUPIN_ALLOW_MERGE_COMMIT` → merge head (`ask`); `LUPIN_ALLOW_UNSCOPED_KILL` → process and service (`ask`); `LUPIN_ALLOW_GIT_STASH` → stash (`observe`); `LUPIN_COMMIT_SCOPE_ACK` → commit scope (`observe`). All five env vars are deleted at the port either way. An env var covered a session; a ticket covers one act (`scope: session` is Section 10's first extension). Three rows (kernel liveness, database, secrets) have no AH4L ancestor, which is the clearest sign the parity list was the wrong starting point.

**Branch protection has a second layer outside the gate:** the git reference-transaction hook (`branch_guard`, engine-neutral, role table Section 3). It does not see tickets. An approved branch-lock ticket therefore has to reach it too, or the approval is moot: the gate's allow for a branch-lock act also writes a one-shot allowance the git hook consumes (`<repo>/.git/lupin/branch-lock-allow-<persona_id>-<ticket>`, expiring with the ticket). **To verify at the port:** how lupin's `branch_guard` honors `LUPIN_ALLOW_BRANCH_LOCK_BYPASS` today, on the laptop clone, read-only. Until then the allowance file is the design and the env read is the fallback.

`question( persona, call )` follows one template per row: "`<role> <persona_id>` wants to `<act in plain words>` on `<target>`. Allow?".

## 7. Claude launch under D49

```
claude -p --input-format stream-json --output-format stream-json --verbose --include-partial-messages \
       --session-id <id> --setting-sources project,local --settings <persona>/settings.json --strict-mcp-config --mcp-config <persona>/mcp.json \
       --dangerously-skip-permissions --tools "<role native list>" --model <D44> --append-system-prompt "<layers 1–4>"
```

- `--dangerously-skip-permissions`: the family's flag; the engine's permission layer is transparent, the gate is the check, and every Claude capture so far (C5–C7, C9, C15b) was taken under it.
- `--tools "Bash,Read,Grep,Glob,Write,Edit"` (per role, from the role table): under `bypassPermissions` allow rules have no effect, so `--allowedTools` is a no-op there; `--tools` removes what is not listed, which is the role table's intent, and leaves cosa-voice alone. `AskUserQuestion` is gone by omission, matching the never-listed row. `Grep` and `Glob` must be named: the `default` set leaves them out on macOS and Linux.
- Not passed: `--permission-mode` (bypass is set by the flag), `--permission-prompt-tool`, `--permission-prompts`.
- The `--settings` file carries the PreToolUse shim only; no `permissions.ask` rules (they would re-create prompts), no `PermissionRequest` hook.

**Why not `dontAsk` + `--allowedTools`.** It keeps Claude-only heuristics alive as engine-side denials the gate never sees (protected paths `.git`, `.claude`, `.mcp.json`; critical-path `rm`; network-path reads). An AGY persona would not get those denials; parity is measured on Claude (D19).

**Why not `--permission-prompt-tool` / `canUseTool`.** Claude-only; holds the engine open on a human; and the tool must return allow or deny, so a pending answer has to become a deny anyway, which is this design with extra parts.

**Why not `defer`.** Claude-only, one call per turn, open bug under `bypassPermissions`, and the approval flow does not need the process to pause.

**Why not `auto`.** A second, opaque, Claude-only authorizer with its own tool surface. Its targets overlap D25's threat model, so it is worth measuring, not adopting: a deferred capture in framework Section 14.5.

**`--permission-prompts none`.** Two of its three effects are already achieved (would-prompts are denied under bypass; `AskUserQuestion` is gone via `--tools`). The third, "do not retry denied requests", is the one instruction the approval flow cannot tolerate if it is a blanket one. The docs do not say which. C18 question 3 decides whether it ever ships.

## 8. Session state and timing

- `awaiting_human` from ticket open to resolution, as for any ask (D37, framework Section 5.2). A persona that ends its turn with the ticket open goes `idle`; the answer is delivered as its next inbound message (framework Section 6) as well as kept on the ticket.
- The gate never waits. Hook timeouts (Claude PreToolUse default 600 s; the shim sets its own) and the family's 180 s MCP cut are irrelevant to approvals: the only held call is `ask_wait`, which holds ≤ 150 s by D37.
- Cost per approved act: one deny, one `ask_wait` (possibly repeated), one repeat of the call. Approvals are rare by construction; the five rules cover destructive acts only.
- Interrupts: an urgent human message interrupts a persona in `awaiting_human` as usual (D8). AH4L's "deny the prompt when voice is buffered" has no counterpart because nothing blocks.

## 10. Extensions, deliberately later

1. `scope: session` on an answer ("yes, for this session"): the kernel stores a per-persona allowance keyed on (`rule`, `approval_key`) until respin or dismiss.
2. `approver: manager` and `approver: learner` as defaults for specific rules, once the agreement data says so (T29).
3. Claude `auto` mode against the gate: the same task set under `bypassPermissions` and `auto`, classifier blocks against gate would-denies (framework Section 14.5).
4. `--permission-prompts none`, if C18 shows it does not suppress the repeat.
5. Row-by-row ruling on Section 6's modes, from C18 and the first weeks of tickets.

## 12. Alternatives considered

| Alternative | Why not |
|---|---|
| Engine-native prompts routed to voice (`--permission-prompt-tool`, `PermissionRequest`, `defer`) | Claude-only; a second authorizer beside the gate; breaks parity |
| Approval as a cosa-voice tool the model calls before a risky act (`request_approval( act )`) | relies on the model to know what needs approval; the gate already knows, and the rule's deny is the prompt |
| Static engine `permissions.deny` rules mirroring enforce guards | a second rule table to keep in step; deny rules do still work under bypass, so this stays available as defense in depth if a case appears |
| Keep the five guards `enforce` and add `ask` rules only on demand | leaves five sanctioned acts with no path once tmux is gone |
